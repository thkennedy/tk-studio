## Intent

Today a supervisor that dies mid-run leaves a `running` queue run that the next `recover` ends `partial` (`orphaned: supervisor restart`), and it releases the checkout lock while the detached worker may still be running (DW-3, DW-7). A worker that exits with no status block ends `blocked` (AD-11 `MISSING_STATUS_BLOCK`). Nothing is ever resumed. This story makes both cases resumable. The supervisor records the worker's session id and process group on the queue run before spawning it. On restart, or after a silent exit, it resumes a skill run with `claude -p --resume <session-id>` on the same tier, once by default, when the transcript exists (restored from the nightly backup if it was garbage-collected) and the 21-5 guards leave budget. Otherwise the run ends `partial` with the reason named. Acceptance (c): no run is silently lost.

## Acceptance Criteria

1. **AC1:** Given the supervisor is killed mid-run, when it restarts, then every run it owned is found in the queue; each resumes with `--resume <session-id>` on the same tier and branch when its session transcript exists and its guards leave budget, and otherwise finishes `partial` naming the guard or `supervisor restart` (superseding Story 21.3's orphan rule for runs that can resume).
2. **AC2:** Given a worker that exits without a status block (runbook §8: silent REPL exit), when the exit is detected, then the same resume-or-partial rule applies, capped at one resume per run by default, and a second failure ends `partial`.
3. **AC3:** Given a resume whose transcript the CLI has garbage-collected, when the nightly backup holds a copy, then the transcript is restored from the backup before resuming; with no copy, the run ends `partial` naming the missing transcript.
4. **AC4:** Given the repo's test suite, when it kills the supervisor at three points (after `wake`, mid-invoke, before `finish`), then each case ends resumed or `partial` with its events recorded, and the suite is green.

Replan notes in `stories.yaml` (they bind):
- (21-1/21-3) Adopt a studio run only if it is absent from the pre-verb snapshot stored at `verb_started` and was minted at or after it. The earliest wins, and an ambiguous lookup fails (`studioRunFinder`, unchanged).
- (21-3) Resume extends `Queue.recover({end, find})` and its owner identity (hostname + pid + nonce + start time). The queue run id and `studio_run_id` stay separate. DW-3 is this story's.
- (21-4) "The same tier" means the queue run's stored `tier`/`sandbox`/`model`/`effort`. Rebuild `Started` through `validate()` so `registryRoot` (the sbx VM root) never falls back to the caller root. An sbx run's transcript is inside the microVM.
- (21-5) A resume drives through 21-5's guards: the remaining wall clock through `wallClockGuard` (and the in-VM `timeout` on sbx), `account` after the resumed iteration, and a trip ends `partial` naming the guard. Every end `recover` writes goes through `Queue.end`'s `stop` option with `studio_outcome` (this closes DW-8). The kill of the recorded worker group must cover DW-7. `Queue.pacing()` must still see a resumed run as live.

## Risks and open decisions

- **Block If** a resume needs the session id and it cannot be known before the worker ends. The plan pre-mints it (`--session-id <uuid>`), recorded on the queue run before the spawn. If the installed CLI refuses `--session-id` with `-p`, or `--resume` with `-p` starts a new id, HALT and consult. Do not parse ids out of transcripts by mtime.
- **Block If** resuming needs `finish` or `account` on a studio run that is no longer resumable, or any change to `jobrun.py` or the plugin (AD-2).
- **Block If** AC2's "a second failure ends `partial`" would make a worker's missing status block anything but a named failure (AD-11). The reason must still name `MISSING_STATUS_BLOCK` and why no resume happened (cap reached, no transcript, budget spent). An auth failure (Max login) and a preflight `ran: false` stay `blocked` and are never resumed. Changing the existing 21-1/21-5 `blocked` pins for a silent exit is expected: record it as a DRIFT.
- The recorded worker group: SIGKILL of the supervisor leaves a detached POSIX worker alive in its own group (21-5). `recover` must kill that group, or wait for it, before it resumes or releases the lock, and only when pid plus start time still match (a reused pid is not the worker). On win32 use `taskkill /F /T /PID` on the recorded pid with the same start-time check. This closes DW-3/DW-7 only if the record is written before the worker starts work. Say which window remains, if any.
- Resume cap: "one resume per run by default". Store the count as `resumed` events (or a column). A configurable cap (for example a `max_resumes` key in `TK_SUPERVISOR_CONFIG`) is optional. Do not add it if it pushes the Files list past 10.
- Double counting: with `--resume` (no `--fork-session`) the resumed session appends to the same `<sid>.jsonl`. Account only message ids not already accounted by the interrupted iteration (record the accounted ids or counts on the `resumed` event). On sbx the result's `num_turns`/`usage` covers only the resumed iteration.
- Where resumes run: `recover` runs on `run`, at tick start, and in `recover` and `drain`. A resume drives a worker for up to its remaining guard. Keep `recover` itself short (take over ownership, then drive) so that `run` for another job is not held behind someone else's resume. Record the choice as a DRIFT if it moves driving out of `Queue.recover`.
- Core runs execute inside `wake` and have no claude session. They are never resumed, and keep `cancel` plus `partial` `supervisor restart`.
- Backup: runbook §6 is the existing host job (robocopy `/E` of `~/.claude/projects`). The supervisor only reads it, from an environment-named root. The SPEC's CAP-9 open question ("where does it live, what mechanism makes it, and does the supervisor own it or an existing host job?") is answered by that runbook section; note it in the README. The backup never covers the sbx microVM.
- The pacer: a resumed run is `running` under the new owner, so `Queue.pacing().live` holds the job. A run ended by the restart carries `studio_outcome`, and `stopped` when `stop.on_status` lists its state (DW-8).
