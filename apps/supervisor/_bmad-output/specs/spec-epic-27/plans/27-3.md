## Intent

After 27.1, a launch run whose engine paused rests `paused`. It keeps its worktree, its checkout lock, its pin (27.2) and a draft PR. Today nothing moves it on: an operator follows the attended recipe of 2026-10-14 (tk-studio `kb/agent-pc-setup-runbook.md` "When a run pauses"; `tools/sbx-engine/resume-run.sh` header). That recipe is: read the verdict, commit the engine's staged harvest, meter the story, `bmad-loop archive` the run, and launch the epic again (hole 9).

This story makes it a tick pass with three outcomes:

- **Landed story with a verdict that is not `escalate`:** close it out and relaunch under the same queue run with a `close-out` event.
- **Landed story with no verdict, or `escalate`:** wait for a human. The tick sends one notification, and the page row says "awaiting a ruling".
- **Story with no landed work:** leave it for `POST /runs/{id}/resume` (`bmad-loop resolve`).

## Acceptance Criteria

1. **AC1:** **Given** a run that paused at the commit gate or on an escalation with the story's spec at `status: done` and a `reconcile_verdict` other than `escalate` recorded **When** the supervisor's tick sees it **Then** it commits the engine's staged harvest on the run branch with a named message, harvests the story's meter observation to the host ledger (Story 26.4's `meter.py harvest`), archives the run (`bmad-loop archive`, through `sbx exec`), relaunches the epic through `tk-studio-launch` (which skips done stories) under the same queue run with a `close-out` event, and never re-implements the story
2. **AC2:** **Given** the same run with no verdict, or `escalate` **When** the tick sees it **Then** it stays paused, one notification names the story and the reason, and the run's page row says "awaiting a ruling"
3. **AC3:** **Given** a story that halted before any commit **When** the tick sees it **Then** nothing is closed out; the run stays paused for the resume path (`bmad-loop resolve`), which the supervisor exposes as `POST /runs/{id}/resume` with an optional restore patch
4. **AC4:** **Given** the supervisor's test suite **When** it runs **Then** all three cases are pinned with a fake engine, on both hosts

## Settled shape

These are the planner's rulings on the shapes the story leaves open. They come from the bmad-loop and tk-studio CLIs cited above. The gate's write surface excludes `SPEC.md`, so they live here only, and no `SPEC.md` bullet was appended.

- **Harvest commit message** (a named message): `supervisor: close-out harvest for <story key> (run <queue run id>, engine <engine run id>)`.
- **Closable verdict:** any non-empty `reconcile_verdict` other than `escalate` (`not-required`, `no-impact`, `adjust-stories`). The verdict is missing when the key is absent or empty.
- **Close-out order:** commit, then meter, then archive, then relaunch. If any step fails, the run stays `paused` with a `close-out-failed` event naming the step and its error. Write it once per step and error, not on every tick. The steps already done are not undone. Each step is idempotent: a clean tree, the `harvested.json` markers, and an archived run dir counted done. The next tick retries.
- **Event kinds:** `close-out` (written with the `paused` → `running` move; its detail is `{story_key, verdict, commit, meter, archive}`), `close-out-failed`, `awaiting-ruling` and `engine-resume`. None of these reuses 27.1's `closing-out` or `closed_out`, and the PR close-out lease is not touched (27-1 replan).
- **No story key** (`paused_story_key` absent) or **no spec found:** nothing is closed out. It is treated as AC3, so the run stays paused for the resume.
- **`POST /runs/{id}/resume`:**
  - Body `{restore_patch?: string}`, a path relative to the run's worktree that must resolve inside it (`isWithin`). It is passed as the VM path. Any other field or type is `400 SchemaError`.
  - The command is `bmad-loop resolve --project <vm worktree> --no-interactive --resume [--restore-patch <vm path>] <engine id>`. On sbx it runs through `sbx exec`. It is spawned as the supervisor's own child, and that child is the engine's hold for the resume's life. The run moves `paused` → `running` with `engine-resume`. The engine pid is re-read from `engine.pid` (bmad-loop rewrites it at resume start) through 27.2's `recordEnginePid`.
  - Answers:
    - `200 {ok, run_id, state:"running", engine_run_id}`.
    - `404 RunNotFound`.
    - `409 RunNotPaused` (any other state).
    - `409 ExternalRun`.
    - `409 StoryLanded` when the paused story's spec is `status: done`. That run is the close-out's, so a resume never re-drives a landed story.

## Risks and open decisions

- **Oversize, band L.** The story touches 11 files, two of them new. That is four mechanisms (close-out, awaiting a ruling, the resume route, the relaunch's queue moves), each touching queue, cli and tests. If the Files list grows past these 11, HALT and record it for `bmad-correct-course`.
- **The relaunch must go through the pinning recorder** (27.2 consult 1 rule). Never call `releasePin` between the commit, the archive and the relaunch: the pin is released only at the final `ended`.
- **The restart caution above** is a correctness requirement. Pin it with a test: the relaunch driver dies before its new `launched`, and `recover` ends or resumes the run instead of skipping it.
- **The real `sbx run -d` on a sandbox that is already pinned.** The relaunch re-pins it. The fake answers 0, and the real behaviour is `unverifiable-here`. If the real `sbx` refuses, that is a DRIFT for the attended session, not a code guess.
- **Block If:** the relaunch needs `tk-studio-launch` to be told which stories to skip. The story says the launch skips done stories itself, and the supervisor must not re-derive that.
- **Block If:** a paused stage other than the commit gate or an escalation turns out to have a `status: done` spec. Record it, and do not widen AC1 to it.
