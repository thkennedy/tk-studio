## Intent

Today an sbx run's `claude -p` worker runs `launch.py start`, which starts `bmad-loop run` detached inside the microVM. Once the worker's `sbx exec` returns, nothing holds the VM, so the engine dies when the sandbox stops (hole 7). Studio runs started outside the queue (`jobrun.py` by hand, MCP `tk_job`) are invisible to the pacer (DW-6). This story makes the supervisor pin the sandbox (`sbx run -d --name`), hold its own `sbx exec` for the engine's life, record the in-VM engine pid and the sandbox, kill by that pid through `sbx exec` on cancel or a guard trip, and release the pin when the run ends. It also writes a lock file that names the queue as the only starter, and records hand-started runs as `external` so the pacer counts them live.

## Acceptance Criteria

1. **AC1:** **Given** an sbx-tier run **When** the worker starts **Then** the supervisor runs `sbx run -d --name <sandbox>` to pin the sandbox, holds its own `sbx exec` for the engine's lifetime from the console session (never a Claude desktop-app session), records the in-VM engine pid and the sandbox name on the run, and releases the pin (`sbx stop`) when the run ends and no other run holds the sandbox
2. **AC2:** **Given** a cancel or a tripped guard on an sbx run **When** it fires **Then** the engine's process group inside the microVM is killed by name of the recorded pid through `sbx exec` (argv only, no shell), the kill is recorded, and a kill that leaves the pid alive after its wait holds the run as DW-3 specifies
3. **AC3:** **Given** `jobrun.py submit|wake` run by hand or through the MCP `tk_job` surface on a project the supervisor serves **When** it would start a run **Then** the supervisor's lock file for the checkout names the queue as the only starter, the hand-started run is recorded as `external` on the next tick with its studio run id, and the pacer counts it as live until it ends (DW-6 closed)
4. **AC4:** **Given** the supervisor's test suite **When** it runs **Then** the pin, hold, release, kill-by-pid and external-run detection are pinned with a fake `sbx`, on both hosts

## Settled shape

- **The starter lock file:** a deferred entry. It lives at `<studioHome>/projects/<project key>/starter.lock`, where `studioHome(env)` is `TK_STUDIO_HOME` or `~/.tk-studio`, and the key is the one `projectKey` reads. It is JSON: `{"starter": "tk-studio-supervisor queue", "checkout": "<checkoutKey(root)>", "since": "<ISO time>", "supervisor_pid": <pid>}`. The supervisor rewrites it atomically whenever it ticks or claims for a served project, and never writes it in the checkout's tree, where it would dirty `git status` and block the launch. A tk-studio-side change makes `jobrun.py submit|wake` read it, proposed in `tk-studio-side-epic-27.md`. The basis is AD-3 (working data goes in the per-user store, never in a VCS) and AD-20 (one run-workspace tree per project). This bullet is appended to SPEC.md's design notes.

## Risks and open decisions

- **Oversize, band L.** There are 11 files, two of them new. That is past 27.1's nine, for a stated reason: four mechanisms (pin/hold/release, kill, lock file, external) each touch queue, cli and tests. Do not split it here. If the Files list grows past these 11, HALT and record it for `bmad-correct-course`.
- **The engine pid source is a bmad-loop file, not a contract.** `engine.pid` (`"<pid> <start>"`) is read-only from the worktree. If it is absent or unparsable, fall back to `sbx exec <sb> pgrep -f "bmad-loop run"` matched to the engine run id. If neither names exactly one pid, record `engine pid: unknown`, hold nothing new, and leave the 27.1 probe path unchanged. Never guess a pid to kill.
- **Which guard covers a launched engine.** The existing guards (`wallClockGuard`, the in-VM `timeout`, the host timer) bound the worker, not the detached engine. Wire kill-by-pid into the existing trip branches and the cancel. If the dev finds that a guard must bound the engine's own life past the worker (a new guard), that is not in the story: record a DRIFT and do not invent the guard.
- **A supervisor restart drops the hold.** The hold is the supervisor's child. `recoverQueue` must respawn it for every launched or paused sbx run whose recorded engine pid is still live (start time matched), before the sandbox can stop. Pin this.
- **Release.** Run `sbx stop` only at the deferred `ended` (27.1 replan), and only when no other `queued`/`running`/`paused` or external run records the same sandbox. Never release it on `paused` or at launch return.
- **The lock file is advisory until tk-studio honours it.** AC3 is met by the file plus external detection. The `jobrun.py` side goes in the hand-over and is `unverifiable-here`.
- `unverifiable-here`:
  - the real `sbx run -d`/`exec`/`stop` against Docker Sandboxes on the agent PC;
  - the hold from the console session on win32 (operator-decisions §5, §6);
  - the win32 `bun test` run;
  - the tk-studio-side `jobrun.py` change.
