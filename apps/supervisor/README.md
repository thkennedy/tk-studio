# tk-studio-supervisor
Durable driver for tk-studio on the agent PC: queue, guards, worker tiers, tailnet API. A driver-contract consumer outside the plugin (AD-2).

Today it queues studio jobs durably, wakes one, runs it headless, and finishes it from the command line. It drives the studio only through the published contract: `registry.py show`, the `jobrun.py` verbs, `claude -p "/tk-studio:<skill> <payload>"`, and the launch core's `status` (§1 pure-data allowance).

## Operator commands

```bash
bun install
bun src/cli.ts run studio-health --directory <this repo>          # skill job: submit → claude -p → finish
bun src/cli.ts run maintenance-conformance --directory <this repo> # core job: wake runs it, status reports it
bun src/cli.ts submit studio-health --directory <this repo>       # validate + queue only (idempotent)
bun src/cli.ts submit <job> --directory <godot root> --editor-in-the-loop   # snapshot the project before it starts
bun src/cli.ts run studio-health --directory <root> --tier sbx --sandbox claude-<project>   # the worker inside the sbx microVM
bun src/cli.ts recover                                            # the restart rule over the queue
bun src/cli.ts drain                                              # recover, then drive every unowned queued run
bun src/cli.ts serve                                              # the HTTP API on the tailnet (see HTTP API)
bun src/cli.ts verify <run id>                                    # re-run an ended run's host leg (Story 33.8)
bun test
bunx tsc --noEmit
```

**Tests (Story 33.4).** A suite makes every temp folder through `test/tmp.ts`: `tempDir("tk-sup-<what>-")`, never `mkdtempSync` (`grep -rn mkdtempSync test` lists only `tmp.ts`), and wraps each queue it opens in such a folder in `track(new Queue(…))`. `test/preload.ts` closes the tracked queues first (an open SQLite file cannot be removed on Windows, hole 63) and then removes the folders at the end of the `bun test` process (a preload's `afterAll` runs once, after its last file; under the host gate every file is its own process, so there it is per file), and at process exit and on SIGINT/SIGTERM (holes 64, 70). On the Windows host the run's host leg (`tools/verify_host.py`, its `supervisor` gate) runs each `test/*.test.ts` but the e2e `test/command-line.test.ts` in its own `bun test` (420 s each, every `TK_SUPERVISOR_*` unset, `TMPDIR`/`TEMP`/`TMP` at a per-run `tk-verify-supervisor-*` folder under the host's own temp folder, never inside a git checkout, which the queue refuses), then `bunx tsc --noEmit -p apps/supervisor`, whenever `apps/supervisor` changed; the e2e suite is run by hand.

Conformance through the supervisor (driver contract §8). The manifest is read from the installed plugin. Drives the §2 payload can express go through `server.ts` over stdio as `tk_invoke` calls (identical payloads share one run). Fixture CLIs and non-payload verbs (research `seed|spine`, launch `pipeline.py resolve|apply`) run direct via uv under the §1 pure-data allowance:

```bash
bun src/conformance.ts --json                                           # every manifest surface through the supervisor
bun src/conformance.ts --json --compare-direct                          # also runs runner.py run --no-emit direct and compares
bun src/conformance.ts --json --harness --surface tk-studio-detect      # spend-bearing harness drive, judged per §8
```

- Each surface gets the runner's checks: `registered`, `status-block`, `unrunnable-core`, `auth-preflight`, then one check per manifest drive.
- The report's `driver` is `tk-studio-supervisor`. `harness_pass` is `{declared, state}`, the same as the runner's.
- Without `--harness`, an `expect: harness-blocked` drive is one ok check naming the skip. With `--harness`, it runs through the worker path in `auto` mode under the drive's deny-only settings profile (`--settings`), bounded by the drive's `timeout` or 180 s. A profile carrying anything but `permissions.deny` is refused with `DenyProfileRefused` before any process starts.
- `--compare-direct` forwards `--harness` only when it is given, and cannot be combined with `--surface`. The report gains `comparison: {ok, divergences[]}`.
- Exit 0 when every check passes and the comparison (if run) is equal. Exit 1 on a failure or a divergence. Exit 2 when the suite or the direct runner cannot run.

`run` prints one JSON summary. It exits 0 when the run completes. It exits 1 on any other run outcome, including the outcomes that end before a studio run exists: a missing Max login (`state: blocked`, nothing queued), a wake/submit answered without waking (`not-woken`), a lock wait (`queued`), and a run already `running` under another live owner. Once a run exists, a later failure (a refused `finish` or `status`) is reported with its run id; a refused `finish` reports the run's actual state from `status`. If a wake/submit times out, the CLI looks for a run of the job that was not in the `status` snapshot it took just before; it never adopts a run it did not start. A run it finds still `queued` or `running` is ended through a contract verb: a skill run with `finish --state blocked`, a core run with `cancel`. The CLI then reports that run with its id and exits 1. It exits 2 when the invocation or setup is refused before a studio run exists: a bad flag or a flag missing its value (a host bypass request, an unknown `--permission-mode`), a missing `TK_STUDIO_ROOT`, an incompatible contract, `QueueDbMissing` or `QueueDbPlacementRefused`, an unregistered project or a `--directory` that is not the registered root, an unreadable config, a job that `resolve` refuses, or a wake/submit the verb refuses outright, answers without a `run_id`, or times out with no new run found.

`run` prints `run_id` (the queue run id, `q-<job>-<UTC compact>-<rand>`) and `studio_run_id` (the studio's run id, once minted).

## HTTP API

`bun src/cli.ts serve` starts the API (`Bun.serve`). It binds only `TK_SUPERVISOR_BIND` on `TK_SUPERVISOR_PORT` (default `8787`) and prints `{ok, listening}`. It refuses to start, exit 2 with a named error and nothing bound, when the bind is unset (`ApiBindMissing`), `0.0.0.0`, not an IPv4 literal, or outside `100.64.0.0/10` (`ApiBindRefused`); when `TK_SUPERVISOR_TOKEN` is unset or empty (`ApiTokenMissing`); when `TK_SUPERVISOR_PORT` is set but is not a port number (`ApiPortInvalid`); when `TK_SUPERVISOR_SESSION_SECRET` is unset or empty (`SessionSecretMissing`) or shorter than 32 bytes (`SessionSecretWeak`); when only some of the TLS variables are set (`TlsConfigIncomplete`), or the cert or key file is missing or unreadable (`TlsCertUnreadable`). Every message names variables, never a value. With `TK_SUPERVISOR_TLS_CERT`, `TK_SUPERVISOR_TLS_KEY` and `TK_SUPERVISOR_TLS_NAME` set, `Bun.serve` answers `https` with that certificate on the same bind and `listening` is `https://<TLS_NAME>:<port>`; without them it stays `http`.

`Authorization: Bearer <TK_SUPERVISOR_TOKEN>` (the scheme in any case, the token compared in constant time) authorises every route, an unknown path included. Without it, a request is `401 {ok:false,error:"Unauthorized"}`, except: the sign-in routes (`POST /auth/token`, `POST /auth/account`, `POST /auth/signin`) answer before any auth check; a `GET /` without auth, and an HTML `GET /status` without auth (Story 30.6), get the `401` HTML sign-in page; and a valid `tk_session` cookie authorises the `GET` routes and, with the page's CSRF token, `POST /runs/{id}/cancel`, `POST /inbox/{key}/reply` (Story 31.6), `POST /engagements` and `POST /engagements/{id}/input` (Story 32.1), `POST /chat/{engagement}` (Story 32.2), never `POST /jobs` (see the sign-in section below). The token and the header never appear in a log line, an answer or an event. Run ids are queue run ids; answers also carry `studio_run_id`.

A cookie session sits beside the bearer header, never instead of it: the bearer still authorises every route, exactly as above.

The intended usage, as the sign-in page states it:

The studio is operated by the person whose Claude subscription is signed in on this box, from their own seat: no token is intermediated and there is no API-key tier.

The session cookie is `tk_session`: a base64url `{sub, exp}` signed with HMAC-SHA256 under `TK_SUPERVISOR_SESSION_SECRET`, `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800` (7 days). An expired or badly signed cookie counts as none. A valid cookie authorises `GET /`, `GET /jobs`, `GET /runs/{id}`, `GET /status`, `GET /events` (JSON and SSE), `GET /agents`, `GET /board` (Story 30.5), `GET /inbox` (Story 31.5), `GET /office`, `GET /office/events`, `GET /engagements` and `GET /engagements/{id}` (Story 32.1), `GET /chat/{engagement}` (Story 32.2) and `GET /app[/…]` (Story 30.2), answered as with the bearer. A `GET /app[/…]` without auth answers the `401` sign-in page with the requested path and query in a hidden `next` field of each form; a successful form sign-in (`POST /auth/account`, `POST /auth/signin`, `POST /auth/token`) then answers `303` → `next` instead of `/`, but only when `next` is a same-origin path (it starts with `/`, not `//` or `/\`, and holds no `\`, no control character and no scheme): any other `next` returns to `/`. A JSON sign-in still answers `{ok:true,username}`. A cookie also authorises five POSTs, each only with the CSRF token the page embeds (form field `csrf` or header `X-CSRF-Token`; an HMAC of the cookie's signature, never the cookie): `POST /runs/{id}/cancel`, `POST /inbox/{key}/reply` (Story 31.6), `POST /engagements` and `POST /engagements/{id}/input` (Story 32.1), and `POST /chat/{engagement}` (Story 32.2). Without the token, `403 {ok:false,error:"CsrfRefused"}` and nothing is cancelled, posted or written. A cookie session's page has a cancel form for each live run. A cookie never authorises `POST /jobs` or any other route (`401`). Secrets and cookie values never appear in a log line, a page, a notification or a worker's environment.

There is no sign-out. A session lasts up to 7 days. Rotating `TK_SUPERVISOR_SESSION_SECRET` (then restarting `serve`) revokes every session at once. Rotating `TK_SUPERVISOR_TOKEN` or resetting the account does not end a session already signed in (a token-form session is never re-checked against the current token); only its expiry or a secret rotation does. To revoke after a token leak, rotate `TK_SUPERVISOR_SESSION_SECRET` too and restart `serve`.

**Hand-over (the operator's steps).** (1) Enable HTTPS certificates once in the Tailscale admin console (DNS → HTTPS Certificates). (2) Set `TK_SUPERVISOR_SESSION_SECRET` (random, at least 32 bytes, else `SessionSecretWeak`; it is now required, so set it before the next logon) and `TK_SUPERVISOR_TLS_CERT`, `TK_SUPERVISOR_TLS_KEY` (where `tailscale cert` writes the files) and `TK_SUPERVISOR_TLS_NAME` (the MagicDNS name, e.g. `box.tailnet.ts.net`), all in the User environment. Set the TLS variables only after `tailscale cert --cert-file <TLS_CERT> --key-file <TLS_KEY> <TLS_NAME>` has produced the two files: `serve` refuses to start while either is missing or unreadable (`TlsCertUnreadable`). Until the TLS variables are set and `serve` answers `https`, browser sign-in is refused: the token form returns the sign-in page with no cookie, and the page notes that browser sign-in needs https. `start.ps1` runs `tailscale cert` in the main script before the keeper starts (bounded at 120 s; a failure is only a warning). **The certificate rule (Story 27.5, DW-21):** `serve` reads the certificate's `notAfter` at start and every hour; within 14 days of expiry, while no run is `running` or `external` (a paused run does not hold it) and no renewal was requested in the last 24 h, it records `cert-renew-requested {cert, not_after, days_left}` and exits 75. Within 3 days of expiry it renews even during a live run, naming the runs it overrode (`overrode: [run ids]` on `cert-renew-requested`). The keeper then runs the same bounded `tailscale cert` (one function shared with the main script) and restarts `serve` at once, without its back-off; the next `serve` records `cert-renewed {not_after_before, not_after}` or `cert-renew-failed {not_after}`. These events have no run: they are in the queue's `service_events` table. No restart of `start.ps1` is needed on a long uptime. Then open `https://<TLS_NAME>:8787/` on the phone: the first visit creates the account (username and password); later visits sign in with it, and the token form stays for the operator's own browser. **The reset:** locked out, or the password lost, delete `<TK_STUDIO_HOME or ~/.tk-studio>/supervisor/account.json` from the console; the next visit creates the account again (no restart needed), and the bearer token keeps working throughout.

The API never drives or claims a run: `drain` and the tick do. Smoke test from another tailnet device: `curl -H "Authorization: Bearer $TK_SUPERVISOR_TOKEN" http://$TK_SUPERVISOR_BIND:8787/status`; with TLS on, `curl -H "Authorization: Bearer $TK_SUPERVISOR_TOKEN" https://$TK_SUPERVISOR_TLS_NAME:8787/status`.

## Queue, lock and restart rules

The queue is a SQLite file (`bun:sqlite`) at `TK_SUPERVISOR_DB`. It holds `jobs` (the resolved definition per job and checkout), `runs`, `events`, `service_events`, `locks`, and `agents` with its one-row `agents_meta` (the derived agent registry and the time of its last rebuild, below). Unset, every command fails with `QueueDbMissing`. A path inside the studio store (`TK_STUDIO_HOME` when set, and `~/.tk-studio` always), inside `TK_STUDIO_ROOT`, or inside any git checkout is refused with `QueueDbPlacementRefused` before the file is created. On Windows and macOS the comparison ignores case. Both exit 2.

- **The agent registry (Story 29.2).** `agents` is derived only, never edited by hand: `src/registry.ts` rebuilds it whole, in one transaction with one `rebuilt_at` (also stored in `agents_meta`, so a rebuild over zero projects still records its time), on every `recover` (so every tick), after every claim, after every end a `run` drove (its `finally`), after a `drain`, and after a cancel (the HTTP cancel starts that rebuild and answers without waiting on it). `rebuilt_at` is the snapshot time, taken before the registry and the runs are read; a rebuild whose snapshot is older than the stored `rebuilt_at` (an overlapping rebuild finished first) writes nothing (`RebuildSuperseded`, the table unchanged); a stored `rebuilt_at` in the future (a clock that moved back) never blocks a rebuild. The projects are the host registry's (`registry.py show`, each entry's root); a project the registry drops disappears on the next rebuild. Each project gets seven rows, `agent_id` `<project-id>/<role>`, with `model`, `effort` and `advisor` from its route: `pipeline.py resolve --directory <root>` (the shipped defaults), or, while a run of the project is live (`running`, `paused` or `external`, the most recently created) and its served root holds `.bmad-loop/routing.current.json` written for that run (a `written_at` before the run's `created`, a file copied from the checkout, counts as no file), that file's legs, with `current_run` (the queue run id) and `current_story` (the file's `story`); otherwise both are `null`. The one role → leg table (`ROLE_LEGS`, contract §5.1 legs):

  | role | from | model / effort / advisor |
  |---|---|---|
  | `orchestrator` | leg `supervise` | the leg's |
  | `session` | leg `session` | the leg's |
  | `implementer` | leg `implementer` | the leg's |
  | `reviewer` | leg `reviewers` | the leg's |
  | `consult` | leg `consult` | the leg's |
  | `advisor` | the `session` leg's `advisor` field | that value as `model`; `effort` and `advisor` `null` |
  | `planner` | leg `planner` | the leg's |

  The legs `seam`, `review` and `triage` map to no role; a missing field is `null`. `persona` is the role's `display_name` in `apps/supervisor/personas.json` (`{"<role>": {"display_name": "…"}}`, shipped with a name per role; the sprites are EP-30's), `null` when the file or the role is missing; malformed JSON is named `PersonasInvalid` and every persona is `null`. `live_state` is the raw (ungraced) office state of the row's role at the rebuild (Story 29.3, below; `offline` for a project with no run, and on every row when the projection throws, named `OfficeProjectionFailed` among the problems) and `jira_account` is `""` (EP-31's). Under `bun test` the rebuild points skip it unless a test injects the deps (`RunOptions.agents`). The plugin and onboarding are unchanged.
- **The office projection (Story 29.3).** `src/office.ts` projects, for every registry agent, the queue's events of its project's run and the engine's files into one of eight states: `offline`, `idle`, `thinking`, `reading`, `typing`, `running`, `waiting-for-human`, `blocked`. - **Atomic transitions.** Every state change and its `events` row commit in one `BEGIN IMMEDIATE` transaction. `complete|partial|blocked|cancelled` are terminal and immutable.
- **Idempotent minting.** While a run of the same job on the same checkout is `queued`, `running`, `paused` or `external`, a new `submit`, `run` or tick mints nothing and gets that run's id (`minted: false`). `run` adopts a submitted run.
- **Owners.** An owner is host + pid + a random per-process nonce, plus the process start time where the platform exposes it (Linux `/proc/<pid>/stat`; Windows the creation time read natively, `GetProcessTimes` through `bun:ffi` (`src/winproc.ts`, Story 27.5), formatted as PowerShell's `ToString('o')` UTC with 7 fractional digits; the bounded `powershell -NoProfile -NonInteractive` read only when the FFI cannot load; absent when the read fails). A worker's record lands pid first (with its `worker` event, `{pid, guard_s}`: it no longer carries `start`), its start time after it on the `worker_start` column (DW-19): a supervisor killed between the two leaves a usable record. "Mine" compares the nonce, never the pid, so a restarted supervisor that reuses a dead owner's pid still recovers its runs. Another owner is alive when it is on this host, its pid answers `kill(pid, 0)`, and its recorded start time (when present) matches. An owner on another host counts as alive and is named.
- **One engine per checkout.** A run takes the checkout lock before the `jobrun` verb that mints or executes. A live holder leaves the run `queued` with the holder named in its `reason` and in the answer (`holder`), exit 1. A holder is a `running` run whose owner process is alive, a `running` run whose owner is dead but whose recorded worker (Story 21.6, under **Restart**) may still run — its pid alive with a matching or unreadable start time, its POSIX process group still alive after the leader exited, or, on sbx, its in-VM deadline not yet passed; the claim only probes, never signals, and names the worker in the `reason` — or a detached bmad-loop engine: when a `tk-studio-launch` run's status block names `.bmad-loop/runs/<id>`, the lock passes to that engine and is held while `launch.py status --directory` lists the id in `live[]`. A failed probe counts as live and is named. A claim that finds a stale lock (its run no longer `running` under a live owner) held by a `tk-studio-launch` run probes the launch core first. A live engine, or an unverified one when the probe fails, takes the lock over, and the claimer waits naming it. A `tk-studio-launch` run that reached the minting verb but ends without naming `.bmad-loop/runs/<id>` (a timeout, a missing status block, a `blocked` launch) probes the launch core before its lock is released, by the launch-orphan rule under **Restart**. Every owner and engine probe runs outside the queue's transactions. A run already `running` under another live owner is answered with its id and state, and nothing is driven (exit 1).
- **Mirroring.** The queue run ends in the studio run's terminal state. A studio run still non-terminal when `run` returns (for example a one-shot scheduled `at` a later time) ends the queue run `blocked`, naming the studio run. It is never left `queued`. A start failure after the lock was claimed ends the queue run `blocked` with the error, and the answer names its `run_id`.

- **Restart.** `run`, `recover`, `drain` and the tick recover on start (the tick once over the whole queue, before any per-job gating and not under `--dry-run`; its runs then skip the per-run recovery). Each requires `TK_STUDIO_ROOT` and the contract pin first; without them it exits 2 and recovers nothing. A `queued` or `running` run whose owner process no longer exists is handled like this:
  - First, the run's recorded worker (below) is killed if it still runs as recorded: its pid is alive and its start time equals the recorded one. POSIX: `SIGKILL` to its process group; win32: `taskkill /F /T /PID`. On POSIX, when the recorded leader has exited but its process group still has members (`kill(-pgid, 0)`; a pgid stays reserved while any member exists), the group is `SIGKILL`ed (`group killed`). A dead pid with no live group, or a live pid with another start time (a reused pid), is never signalled; the outcome is in the run's event (`worker`). A pid that is alive but whose start time cannot be read, whose kill failed, or that still runs 5 s after the kill (`kill failed`, `still running after wait`) may still be the worker, so the run is left as it is (`held` in the answer) and nothing is released under it. Never by name.
  - **sbx.** The recorded pid of an sbx run is the host `sbx exec`; the worker inside the microVM outlives it until its in-VM `timeout`. So an sbx run is held (`held`, outcome `in-VM deadline not passed`, run and lock untouched) until its in-VM deadline: the recorded spawn time (the `worker` event) + the guard seconds passed to that spawn (`worker_guard_s`; a record without them uses the job's own guard) + the 10 s `-k` grace — decided from that deadline, never from whether the host pid is alive. Once the deadline has passed, a lingering host `sbx exec` is killed as above (best effort, recorded) and the run ends `partial` naming the wall-clock guard (`orphaned: supervisor restart; guard: max_wall_clock_seconds (600s)`), or `; no worker recorded (…)` when none was spawned. An sbx run is never resumed on restart. The same predicate holds a claim (under **One engine per checkout**).
  - A studio run is recorded (a skill run): it **resumes** (Story 21.6) when, checked in this order, a session id is recorded, it has not yet been resumed (**one resume per run**), the studio run is still resumable (`status` answers `queued`/`running`), its transcript exists (restored from the backup first, below), and its guards leave budget. A resume takes the run over in one transaction (owner = this process, the checkout lock re-owned and never released in between, state stays `running`, a `resumed` event with the resume count), so the pacer still sees it live. Only the process that won the takeover then checks the budget, so concurrent recoverers (a tick and a `drain`) account the interrupted counts at most once: when the job has `max_turns` or `max_tokens`, `account` with the interrupted iteration's counts not yet accounted (an `accounted` event; counts that cannot be read are a failed `account`, never zero), the remaining wall clock being the guard minus `counters.wall_clock_seconds`, or minus the time since the first worker spawned when `account` reports none (the supervisor's downtime counts); a job with neither is never accounted, and its remaining wall clock is the guard minus the time since the first worker spawned. The ids that check accounted are carried into the resumed run, so its iteration never counts them again. A trip found there ends the owned run `partial` naming the guard (`orphaned: supervisor restart; guard: max_turns (40)`), its studio run finished `partial` too. Then the caller drives it: `claude -p --resume <session-id>` with a short continuation prompt as the one `-p` item, every other flag unchanged, on the queue run's stored tier, sandbox, model, effort and permission mode (rebuilt through `resolve` and the registry root, so an sbx VM root never falls back to the caller's spelling), on the same checkout, under the remaining wall clock (on sbx the in-VM `timeout` gets it too); then `account` (only message ids not already accounted) and `finish` as for any run. `recover`, `drain` and the tick drive each resumed run before anything else; `run` drives its own job's resumed run first and other jobs' resumes alongside its own run.
  - A `tk-studio-launch` run is never resumed beside the engine it may have started: before any resume check, the launch core is probed outside any transaction (the launch-orphan rule). A live engine refuses the resume (`; launch engine live: <id>`), and so does an unverified one when the probe fails (`; launch engine unverified: <detail>`); the run then ends as below and its lock passes to that engine. An empty `live[]` leaves the resume checks as they were. The same probe runs before an in-process silent-exit resume (**Silent worker exit**), and that run's end hands the lock to the engine likewise.
  - Otherwise the queue run ends `partial` with reason `orphaned: supervisor restart`, followed by the cause when a skill run could not resume: `; no session recorded`, `; resume cap reached (1)`, `; transcript missing: <session-id> (…)`, `; guard: max_turns (40)` (the guard named as for any trip), `; no wake answer recorded`. A studio run already terminal is not resumed: the queue run ends in the studio run's state. A core run is never resumed (it has no claude session): `cancel` and `orphaned: supervisor restart`, unchanged. The studio run is ended too if it is non-terminal: a skill run with `finish --state partial` and the same reason, a core run with `cancel`. A failed studio call is recorded in the event, and the queue run still ends. The end goes through the same path as any end: the `orphaned` event carries `studio_outcome` when the studio run reached a terminal state, and a `stopped` event is written in the same transaction when the job's `stop.on_status` lists it.
  - `verb_started` is set but no studio run is recorded: the job's studio runs absent from the stored snapshot are looked up. The earliest one minted at or after `verb_started` is adopted (a later one may belong to someone else), recorded, and ended as above. None found: the run is re-queued. A candidate whose mint time cannot be read makes the pick ambiguous, which counts as a failed lookup. The lookup failed: the run ends `partial` naming the failed lookup. A run that may have executed is never re-queued.
  - Neither is set, or the run is `queued`: it is re-queued (`requeued: supervisor restart`): owner cleared, lock released.
  - Ending an orphaned `tk-studio-launch` run first probes `launch.py status --directory`. A non-empty `live[]` hands the lock to that engine. A failed probe hands it to an unverified engine, which a claim re-probes: a non-empty `live[]` or a failed probe still counts as live.

**Recorded before the worker works (Story 21.6).** A driven run records on its queue run, each with its own event and transaction: the wake answer (`wake`: directive, routing, state), a session id pre-minted with `crypto.randomUUID()` (`session_id`, recorded just before the spawn and passed as `--session-id`), and the spawned worker's pid (POSIX: its process group; win32: the pid) with that pid's start time and the wall-clock guard seconds passed to that spawn (`worker_pid`, `worker_start`, `worker_guard_s`, recorded as soon as it is spawned). An existing queue file gains these nullable columns when it is opened. If the worker record fails, the worker's process tree is killed at once and the run ends `blocked` naming `worker record failed: <cause>`: no worker runs unrecorded. What remains unrecorded: the few milliseconds between the spawn and the worker record, the `uv run … jobrun.py` children (they are never recorded, so a killed supervisor's in-flight verb is not killed by `recover`), and the ids between an `account` verb and its `accounted` event: a supervisor killed between the two can have those ids counted again on restart.

**Silent worker exit (AC2).** A worker that ran and printed no status block — not an auth block (`MAX_LOGIN_MISSING`), not a preflight stop (`ran: false`), not a host wall-clock timeout or an sbx 124/137 wall-clock trip, which keep their outcome and are never resumed — gets the same resume-or-partial rule in process: one `--resume <session-id>` under the remaining wall clock, the silent iteration accounted first when the job has `max_turns` or `max_tokens` (a job with neither is never accounted, so an sbx silent exit with no JSON result still resumes; a guarded one whose counts cannot be read ends `partial` naming `guard: account failed — …`). The check's `account` is attempted once per iteration: answered or failed, it is not run again before `finish`, and a failure is named once. A `tk-studio-launch` run with a live or unverified engine is never resumed (under **Restart**). On sbx the host `sbx exec` exiting never proves the in-VM worker ended: before the resume checks a read-only `sbx exec <sandbox> ps -eo pid=,args=` (argv only, filtered on the host for the session id) runs, and a process carrying the session id — or a failed check (non-zero, spawn error, timeout) — refuses the resume: the run ends `partial` naming `…; sbx worker may still run in the VM: <pid | probe failed: detail>` and keeps its checkout lock until the recorded worker's in-VM deadline (the **sbx** rule under **Restart**), after which `claim` or `recover` frees it. A second silent exit, or one that cannot resume, ends `partial` with the reason keeping the named failure and the cause: `conformance failure (AD-11): … ; resume cap reached (1)`. The resume is recorded before it runs; if that record fails, it does not run (`…; resume not recorded: <cause>`), so a later restart cannot exceed the cap.

**Transcript backup (AC3).** Before a host resume, a session transcript the CLI has garbage-collected (`projects/*/<session-id>.jsonl` missing under `CLAUDE_CONFIG_DIR`) is restored from `TK_SUPERVISOR_TRANSCRIPT_BACKUP`: exactly one `<backup>/<slug>/<session-id>.jsonl` is copied back into `projects/<slug>/`, with its `<session-id>/subagents/`. That variable names runbook §6's nightly copy of `%USERPROFILE%\.claude\projects` (`<DEST>\claude-projects`, robocopy `/E`) — an existing host job; the supervisor only reads it (this answers CAP-9's backup question). Unset, no copy, or several copies: the run ends `partial` naming `transcript missing: <session-id>`. The backup never covers the sbx microVM: an sbx transcript is looked up inside the VM (`sbx exec <sandbox> printenv HOME`, then `sbx exec <sandbox> find <home>/.claude/projects -name <session-id>.jsonl`, argv only), and a missing one ends `partial` naming it.

How it runs a worker:
- The permission mode defaults to `auto`. An explicit `--permission-mode <mode>` on `run` or `submit` is recorded on the queue run it mints or adopts while that run is `queued` (`runs.permission_mode`), so a run left `queued` (a lock wait) and later driven by `drain` or the tick keeps that mode. A `bypassPermissions` request on the host tier is refused with `HostBypassRefused` before any process starts. No flag is passed that overrides `permissions.deny` in `~/.claude/settings.json`.
- Auth comes only from the Max login, checked with `claude auth status --json`. The worker's environment never carries `ANTHROPIC_API_KEY`.
- The worker runs with `--output-format json`. The status block is read from the result text, and `total_cost_usd` is passed on to `finish` with the studio's run id. Story 27.5 (DW-15): each iteration's cost is recorded on its `accounted` event (`cost_usd`; a job with no turn/token guard gets one cost-only `accounted {turns: 0, tokens: 0, message_ids: [], cost_usd}` per iteration), and `finish` carries the sum across every iteration, those of a process a restart replaced included (`launched` events are never counted). An engine run the paused-run pass archives has its metered cost recorded first (`accounted {cost_usd, engine_run_id, source: "engine"}`), so the final close-out's cost is those plus the latest engine's.
- A refused `finish` (the studio run already terminal, e.g. a skill that finished its own run, DW-23) leaves the queue run's reason as the worker's own status-block reason; the refusal goes on a `finish-refused {error, actual_state}` event, and the queue run ends in the actual state.
- Model and effort: `--model`/`--effort` on `run` or `submit` override the resolved job's `routing` for that run; otherwise `routing.model`/`routing.effort` are forwarded verbatim (flags and payload, contract §5). With neither, no `--model`/`--effort` is passed. The supervisor never chooses a model.
- `finish` emits the `job-run` ledger event. The supervisor never emits it.

## The board (Story 30.5)

`GET /board?project=<id>` (`src/board.ts`) puts a served project's plan, its runs and its money on one answer, for the web's Board screen (and 30.6's home). It reads files and the queue only: never git, never a write, never a plugin import (AD-2). The project's root is its registry entry's `root` (`registry.py show`).

- **The plan.** `<root>/_bmad-output/planning-artifacts/plan/`: every `EP-NNN.md` and `ST-NNN.md` entity's frontmatter (`id`, `title`, `status`, `source`, a story's `parent`); `index.md` is not read (the entities are the truth). A story's `key` is `N.M` from its `source` `epics.md#story-N.M`, an epic's number `N` from `epics.md#epic-N`. Epics in id order, each with its stories (`parent`) in key order; a story with no epic in the plan is not shown. The statuses are the canonical ones as the entities read. No plan directory (a transcribed plan owned by another project included): `epics: []` and `plan.reason` `no plan directory: _bmad-output/planning-artifacts/plan`, the triage still filled.
- **The findings.** `<root>/_bmad-output/implementation-artifacts/deferred-work.md`, the engine's `deferredwork.py` rule: a `### DW-NN: <title>` entry ends at the next heading of any level; it is open when the first word of its `status:` line is `open` (a legacy bullet, or an entry with no `status:` line, is not); its story is `N.M` of its `source_spec` file name. A story lists its open entries `{id, title, severity}`; an epic's `findings` counts its stories' entries, so closing an entry drains the count.
- **The spend.** The ledger `<TK_STUDIO_HOME or ~/.tk-studio>/measurements/<user>-<machine>.jsonl` (this machine's, as the status page names it), read whole: its `job-run` events whose envelope `project` is the project (the studio's raw project key, as `ledger.py` writes it: never `safe_name`d), one per `payload.run_id` (the last line wins: a repeat finish emits twice, DW-5), `payload.total_cost_usd` summed per epic `N` of a `run-epic-N` `job_id`. Any other job, an envelope with no `project`, or a run with no cost counts toward no epic: an epic is never guessed. `spend_usd` is `0` with none.
- **The band.** `<root>/.tk-studio/budget-bands.yaml` may carry an optional top-level block mapping keyed by the plan's epic id, beside the story `bands:` (which `launch.py` alone reads):

  ```yaml
  epics:
    EP-030:
      usd_estimate: 40
  ```

  `band_usd` is that `usd_estimate`; absent, malformed (not a block mapping, not a number) or not positive, it is `null` and the web shows the spend alone. The figure is the operator's: the tracked file ships no entry.
- **The runs.** The project's queue runs, composed on every request. A run names a story by its `plan-status` events' `story_key`, its awaited ruling's or its pause's story, and (a live run) the office projection's stories that are not `pending`; each story's `run` is the latest created such run, except that a live story `done` (a close-out relaunch marks earlier stories done from their landed spec files) names it only when no other run names it otherwise: `{run_id, state, pr, host_verify, ended_at}`, `pr` the run's PR (`ended`, else the latest `closed_out`, else the PR on its `paused` event; `null` with none), `host_verify` the latest `host-verify` event's outcome (`green`, `red`, `skipped`, `null` with none), `ended_at` its end time (`last_run`'s rule) or `null` while live.
- **The triage.** Every live run (`queued`, `running`, `paused`, `external`) of the project is in exactly one column: **Needs-you** when it is `paused`, its latest ruling event is `awaiting-ruling`, or its latest `host-verify` is red and was recorded after the run's latest `launched` (a run with no `launched` counts any); **Working** otherwise. **Done** holds the terminal runs whose `ended_at` falls on the supervisor host's local day (the injected clock); a terminal run ended today with a red host leg (by the same rule) goes in Needs-you instead. An item is `{run_id, state, story_key, pr, ruling}`: `story_key` the awaited ruling's story, else the pause's, else the live run's current story, else its latest `plan-status` story; `ruling` (live runs only) the run's wait reason by the office projection's own rule (`runWaitReason` in `office.ts`: the awaited ruling's reason, else state.json's `paused_reason`, else the standing pause's engine reason, else the unresolved journal escalation's reason), else `null`.
- **The engagements (Story 32.1, contract 0.1.27, additive).** After the run items, **Needs-you** lists the served root's engagement records (`_bmad-output/engagements/<id>/engagement.yaml`, `src/engagement.ts`) waiting on the owner — state `awaiting-answers` (the questions) or `quoted` (the approval) — newest first, each `{engagement, state, title}` (`title` the request's first non-empty line, trimmed, at most 80 characters). No other state is listed and Working and Done never carry one. The records are cached per root on the directory's `mtimeMs` plus each record's `(mtimeMs, size)`.
- **The cache.** The plan part is cached per plan directory on a signature of the directory's `mtimeMs` plus each entity's `(mtimeMs, size)` (a superset of the directory mtime: an in-place edit does not move it), and rebuilt on any change; the findings on the deferred-work file's `(size, mtimeMs)`, the spend on the ledger's. Runs and triage are composed per request.

## Worktrees and PRs

Story 27.1 (supersedes 23.2): every run works in its own git worktree of the project and ends as a pull request against its base. Two loops never share a working tree, a run never switches the branch under a running service, and agent work arrives PR-only.

- **Layout.** `<TK_SUPERVISOR_WORK>/worktrees/<project id>/<queue run id>`, on branch `supervisor/run-<queue run id>`. `TK_SUPERVISOR_WORK` is required for every run: unset, or the project root or a folder inside it, the claimed run ends `blocked` naming it (`worktree work folder: WorkDirMissing: …`).
- **The run flow.** Claim the checkout lock → resolve `base_ref` → cut the worktree → materialise it → (the editor-in-the-loop snapshot) → `wake`/`submit` on the registered root → the worker in the worktree → close-out. The registry, `wake`, the studio verbs and the checkout lock keep the registered root; only the worker's cwd, `payload.directory` and the sbx VM path (`toVmPath(<worktree>)`, `env -C`) are the worktree, so the engine's `--project` is the worktree. The lock stays one per checkout.
- **base_ref.** The submission's `base_ref`; none given, the repository's default branch, resolved at claim from the checkout (`git symbolic-ref --short refs/remotes/origin/HEAD`, `origin/` stripped, else `gh repo view --json defaultBranchRef`) and recorded on the run with `base_ref_source: default` (a `base-ref` event). A `base_ref` that is the default branch (compared as that branch name, ignoring case: on Windows `MAIN` resolves to `main`) is refused first when GitHub says it is not protected (`gh api repos/{owner}/{repo}/branches/<default branch>`, its `protected`): `blocked`, `worktree protection: base_ref '<ref>' is the repository's default branch and is not protected on GitHub — refused`. The `base_ref` must then name a branch (`refs/heads/<b>` or `refs/remotes/origin/<b>` in the checkout, after `refs/heads/`, `refs/remotes/origin/` and `origin/` are stripped): a tag or a commit SHA ends the run `blocked` at prepare (`worktree base_ref: base_ref '<ref>' names no branch …`), since its PR needs a branch to target. That branch must be on origin (`refs/remotes/origin/<b>`), else its PR would have no base on GitHub (`… is not on origin …`), and the `base_ref` as written must resolve to a commit in the checkout (`git rev-parse --verify <base_ref>^{commit}`), else the cut cannot work (`… does not resolve to a commit in the checkout …`: a bare `rel` with only `origin/rel` is refused, `origin/rel` is accepted); both end the run `blocked` at prepare. Every `gh` call (`repo view`, `api`, `pr list`, `pr create`, `pr ready`) is pinned to origin's repository: `GH_REPO` from `git remote get-url origin` (https and ssh forms), so an `upstream` remote beside `origin` is never the one read or targeted; an origin that cannot be parsed (a local path, an ssh host alias) leaves gh's own default.
- **Cut.** From the project checkout, never switched: `git worktree add --relative-paths <path> -b supervisor/run-<id> <base_ref>`. Relative gitdir paths always: the host and the engine microVM see different absolute paths, so the worktree's `.git` file reads `gitdir: ../../…/<project>/.git/worktrees/<id>` (git 2.48 or later). The flag also writes `extensions.relativeworktrees` into the project's shared `.git/config`, which the .NET 8 SDK's source-control query (Microsoft.Build.Tasks.Git, run by every `dotnet build`) refuses in every checkout of that repository: a .NET project sets `EnableSourceControlManagerQueries=false` in its root `Directory.Build.props` (hole 48). The path is recorded on the run (`worktree`, a `worktree` event); an adopted or resumed run keeps the one it has, and one cut but never fully materialised (no `materialised` event: a crash mid-way) is materialised again before the drive.
- **Materialise.** The engine's untracked runtime, by the studio's own motions: the drift check first (`drift_check.py --directory <worktree>`), then `tk install` at the pin inside the worktree only when that check reports drift (`uv run <plugin>/skills/tk-studio-install/scripts/install_base.py --directory <worktree>`; hole 42: a fresh worktree of a project whose committed base is at the pin is already clean, and an install would re-render committed config into a dirty tree the launch refuses — the `materialised` event's `install` says `ran` or `skipped: drift-clean`), then `.bmad-loop/policy.toml`, `.bmad-loop/routing.current.json` and the local overlay `.tk-studio/config.local.yaml` copied from the checkout when present (skipped when absent; a copy, never a junction or a link into the checkout), then `tk activate` clean inside it (`drift_check.py --directory <worktree>`, `result: clean`). On sbx the worktree must have a VM path (under the operator's read-write mount of `<TK_SUPERVISOR_WORK>/worktrees`). Any failed step ends the run `blocked` before `wake`, naming it (`worktree <base_ref|protection|vm path|add|install|copy|activate drift>: …`); the run never falls back to the checkout.
- **Relaunch after a pause (Story 27.3).** A paused run whose story landed is closed out by the paused-run pass and relaunched under the same queue run in its kept worktree, on the same `supervisor/run-<id>` branch: the draft PR recorded on its `paused` event is the run's PR still (never a second `gh pr create`), marked ready at the final `ended`.
- **Launch runs.** A `tk-studio-launch` run whose status block names `.bmad-loop/runs/<id>` (and is not `blocked`) writes a `launched` event (the status block, the engine run id) instead of `ended`: it stays `running` and live for the pacer, its driver lets go of it, and the checkout lock passes to the engine (probed in the worktree). `ended` is written once, after the close-out. Its studio run is not finished at launch return either: on the engine's end the sweep calls `jobrun finish` with the deferred state and reason, the launch status block (the PR URL added to its artifacts) and the metered cost (the `finish` outcome is on `ended`). A `blocked` launch ends at once.
- **Secrets into the sandbox (EP-31, Story 31.1).** A variable of the supervisor's own environment whose name starts with `TK_ATLASSIAN_` reaches the sbx worker, and so the engine it starts, through `sbx exec -e <NAME>` by name only: the CLI reads the value from the spawning environment, so no value sits on a command line, in an event or in a file the worktree could carry. Set them as User environment variables (`setx TK_ATLASSIAN_SITE …`, `setx TK_ATLASSIAN_AGENT_EMAIL …`, `setx TK_ATLASSIAN_AGENT_TOKEN …`, `setx TK_ATLASSIAN_CLOUD_ID …`): on each worker spawn the supervisor reads the User environment from the registry (`reg query HKCU\Environment`) for any pass-through variable its own environment lacks (hole 60: a tab restarted inside a running Windows Terminal inherits the terminal's stale environment, so a `setx` alone never reached it), so no restart is needed for a new or rotated secret; the console's own value wins when both exist, and an empty value is not passed. Other prefixes are not passed: the list is `SBX_ENV_PASSTHROUGH_PREFIXES` in `src/server.ts`. **The owner seat stays on the host (Story 31.6).** `TK_STUDIO_ATLASSIAN_OWNER_EMAIL` and `TK_STUDIO_ATLASSIAN_OWNER_TOKEN` sit outside the `TK_ATLASSIAN_` prefix, so the sandbox pass-through never forwards them, and `buildWorkerEnv` strips every `TK_STUDIO_ATLASSIAN_OWNER_*` variable from a worker's (and the login preflight's and host verify's) environment: only the supervisor's own `POST /inbox/{key}/reply` passes them, to the one `track.py reply` child it spawns on the host (with `TK_ATLASSIAN_CLOUD_ID` for the gateway). Set them with `setx` like the agent seat's; an absent one refuses the reply by name, and the reply is never posted with the agent's token.
- **Pin and hold (Story 27.2, sbx).** The worker pins its sandbox (`sbx run -d --name <sb>`, a `pinned` event) before its login preflight. Story 33.2: a drained run's pin runs before the claim (a `pinned` event once while the pin stands, a `pin-failed` once per failure episode on that sandbox, its `error` updated in place on a repeat failure), and a failed pin leaves the run `queued` with a `claim-refused` naming it (**Draining**); the drive then pins it no second time. A relaunch's or a resume's pin still runs in the drive, and its failure ends the run `blocked` naming it. When a launch run returns, the engine's in-VM pid is read from `<worktree>/.bmad-loop/runs/<engine id>/engine.pid` (`"<pid> <start>"`, read-only), else from `sbx exec <sb> pgrep -a -f "bmad-loop run"` matched to the engine run id; it is recorded on the run (`engine_pid`, `engine_start`, an `engine-pid` event with the sandbox). Neither naming exactly one pid records `engine pid: unknown`: no hold, nothing killed later, the probes as before. With a pid, the supervisor holds its own `sbx exec <sb> tail --pid=<pid> -f /dev/null` open for the engine's life (a `hold` event), so the microVM stays up after the worker's `sbx exec` returns; `recover` respawns it after a restart for every launched or paused sbx run whose engine pid still runs as recorded (its start time matched) and whose recorded hold no longer runs. The pin is released (`sbx stop <sb>`, a `pin-released` event) once, at the run's deferred `ended` (or at the end of a run with no engine, or a late close-out), never at launch return or on `paused`, and only when no other `queued`/`running`/`paused`/`external` run records the same sandbox, nor an ended run whose engine is still alive after its kill (else `pin-kept`, naming them). Every end path of a run recording a sandbox asks for the release, including an external run's end, a drain refusal's `blocked` end and a resume's `blocked` end. The release follows the sandbox, not the run: while a pin on it is outstanding (some run recording it pinned it and no `pin-released` since — e.g. one an ended run left `pin-kept`), the last run recording it to end stops it, even one that never pinned (a queued run cancelled before its claim, a `pin-failed` end). Story 33.3 (contract 0.1.28): both pin sites go through one seam (`pinWithRestart`), which reads `sbx ls` before the pin. When the sandbox was already listed as running (its first column exactly, status `running`; a failed `sbx ls` reads as not running) the seam probes its login (`sbx exec <sb> env -u ANTHROPIC_API_KEY claude auth status --json`); not logged in, it stops and starts the sandbox once (`sbx stop`, `sbx run -d --name`), probes again and records `pin-restart {sandbox, probe_before, probe_after, pass_at}` (each probe `null` or the preflight's gap text), then the caller's preflight judges as before. Never twice: not when this drain pass (or this drive's recorder) already restarted the sandbox, not when the run's open episode already carries a `pin-restart` for it, and never while another run holds it `running`/`paused`/`external` or an ended run's engine still lives there. A failed `sbx stop`/`sbx run` in the restart is a pin failure (`pin-failed`). Every pin writes the supervisor's pin record `<TK_STUDIO_HOME or ~/.tk-studio>/sandboxes/<sb>.pin` (`{sandbox, since, run_id, supervisor_pid}`, atomic, never throws); a release that stopped the sandbox removes it. `tk-studio-launch check` warns about a running engine sandbox without one.
- **Engine-end sweep.** `run`, `recover`, `drain` (and so every tick) probe each launched `running` run and each `paused` run with `uv run <plugin>/lib/launch.py status --directory <worktree> --run-id <engine>`. A terminal `run.status` (`finished`, `stopped`, `interrupted`, `crashed`) closes the run out and ends it (the state the launch reported); `paused_stage`/`paused_reason` closes it out as a draft and leaves it `paused` (the PR URL on the `paused` event); a still-running engine or a failed probe is left alone. One process closes a run out at a time; a PR already recorded is marked ready (`gh pr ready`), never opened twice. The close-out's result is never lost: when the run's transition after it cannot be written, it is recorded as a `closed_out` event — on a run a cancel ended meanwhile, as that run's close-out (never run again); otherwise with the pending transition, which the next sweep writes from the record (no second push, PR, `finish` or probe of the removed worktree). A launched or paused run whose worktree is gone with no such record (its transition and the record both failed) is never probed there: no engine can run in it, so it is closed out (from the checkout, below) and ended with the state the launch reported. A launched run carries an owner only as a close-out lease: `recover` leaves it to the sweep, which re-takes a dead lease.
- **Host verify leg (Story 27.4).** An sbx-tier run's engine runs on Linux in the microVM, so when it ends on its own (the sweep's ended path: not paused, not an engine the supervisor killed, whatever its status reads) the supervisor runs the project's own `verify.host` on the host, in the run's worktree, before the close-out pushes and opens the PR. The command is read from the project's tracked `.tk-studio/config.yaml` at the run's base (`git show <base_ref>:.tk-studio/config.yaml` in the checkout: never the worktree, so a run cannot weaken the gate that judges it, and never the plugin, AD-2): `verify: {host: "<one command line>"}`, split into argv on whitespace with `"…"`/`'…'` grouping and backslashes literal, never run through a shell (a `.sh` script is written `bash scripts/verify.sh`; with no shell, a bare `bash` is whichever PATH finds first, and on a Windows host with WSL that can be the WSL launcher `C:\Windows\System32\bash.exe`, which runs the script inside Linux and misses Windows-only defects, and the Store's `bash.exe` App execution alias only prints an install prompt; so on a Windows host the leg puts Git's `usr\bin` first on its PATH (edited under the key the environment spells, `Path` for a console-started supervisor: a second `PATH` key beside it reached the child as a PATH of Git's `usr\bin` alone, hole 54) when a `Git\cmd` or `Git\bin` entry is on it, and a bare first token that directory holds (`bash`, `sh`) is spawned by its full path there (hole 46 put the directory first, hole 52 found that Windows resolves a bare name through the parent's PATH, never the child's, so the prefix alone still ran the stub; the `host-verify` event's `git_bash` names the directory and `resolved` the path spawned), else confirm which `bash` resolves or name Git Bash's `bash.exe`; the other Store stubs stay, so a project script that needs Python probes `python3`, `python` and `py` for one that runs (hole 50); a `.cmd`/`.bat` shim such as `npm`, `npx` or `pnpm` cannot start without a shell, so name a real executable such as `bun`, `node` or `uv`). A command whose first token is quoted (a path with spaces) is wrapped whole in YAML quotes, e.g. `host: '"C:\Program Files\x\bun.exe" test'`: unwrapped, the YAML does not parse and the leg is skipped `config unreadable: …` (the PR opens ready). It runs argv-only (`windowsHide`, console-hosted, the tree killed past the guard) with the worker's env, under a host-tier worker's wall clock (`worker_guard_s`, else the job's `max_wall_clock_seconds`, else 600). One `host-verify` event per completed-engine close-out records `{command, argv, cwd, exit, duration_ms, signal?, guard?, error?, green, stdout_tail, stderr_tail}` (`signal`: the signal that killed the command, not the guard) (the last 20 lines of each, clipped, URL userinfo redacted), or `{skipped: true, reason}`: `host-tier run: the worker ran on the host`, `worktree gone`, `no .tk-studio/config.yaml at <base_ref>`, `config unreadable: …`, `no verify.host`, `verify.host is not a non-empty string`. Green (exit 0) or skipped: the PR opens or is marked ready as before; a PR already open (a resumed or relaunched run's draft, or an adopted one) is marked ready (`gh pr ready <pr>`) and its body regenerated (`gh pr edit <pr> --body-file`) so it carries the `## Host verify` section, a failure of either recorded in the close-out, never thrown (a close-out given no verify, such as a late close-out with none recorded, only marks it ready). Red (a non-zero exit, the guard tripped, or a failure to start) ends the run `partial` with ``host verify red: `<command>` <exited n | timed out (<guard>) | failed to start: … | killed by <signal>>; last lines: …`` (the last 5 stderr lines, else stdout) — on `ended`, on the deferred `jobrun finish` and in the notification — overriding whatever end was computed; the branch is still pushed, a new PR opens with `--draft`, and a PR already open (a paused run's draft, or an adopted one) is never marked ready: it is converted back to a draft (`gh pr ready <pr> --undo`) and gets `gh pr edit <pr> --body-file` with the regenerated body. A `host-verify` already recorded for the completion (a close-out lost after it ran) is reused on the next sweep (even after a later recorded kill), never re-run, and the late close-out of a terminal run is given it too (a red draft never marked ready). The command runs under a small capture wrapper that writes both streams to files, so a timed-out command's tails keep what it printed before the hang. The PR body's `## Host verify` section carries the result (red: the command, exit or guard, duration and the tails fenced, the fence longer than any backtick run in them); the close-out record carries `host_verify: green|red|skipped`. **The engine gate (Story 34.1, contract 0.1.29).** The same base config may declare `verify: {host: "<one command line>", engine: "<one command line>"}` (TUA's is `engine: bash scripts/engine-gate.sh`: the headless import, then the GoDotTest suite). `verify.engine` is the host leg's engine command; it is not `engine.verify_commands` (Story 33.5, the in-sandbox list the readiness check reconciles): two keys, never merged. It runs only after the `verify.host` command is green, in the same worktree, split the same way (argv, never a shell), through the same capture wrapper, as its own step under the full worker guard again (each step bounded by the guard: a project whose engine gate needs more raises its job's `max_wall_clock_seconds`). Its env is the host step's (the worker's env, Git's `usr\bin` first on Windows) with the folder of `GODOT` (from the supervisor's own environment: start the supervisor after setting the `GODOT` user variable) prepended to PATH under the key the environment spells (one key, hole 54); the leg never resolves `godot` itself, the project's command names what it runs, and a bare first token Git's `usr\bin` holds is spawned by its full path there exactly as for `verify.host` (hole 52). Every ran `host-verify` event carries `engine: {verdict: green|red|skipped, reason?, command?, argv?, cwd?, exit?, duration_ms?, signal?, guard?, error?, stdout_tail?, stderr_tail?, godot_dir}` (`godot_dir` the prepended folder, `null` when `GODOT` is unset or not an absolute path: the command still runs with PATH unchanged); a skipped leg (`{skipped: true, reason}`) carries none. Skip reasons: `no verify.engine`, `verify.engine is not a non-empty string`, `verify.host red` (the engine is never spawned after a red host command). The leg's `green` is the host command green and the engine not red, so an engine red is a red leg everywhere a red `verify.host` is (the run ends `partial` with `host_verify: red`, the PR a draft, the board, the office and the re-run's `pr_ready` follow it) with the reason ``host verify red (engine): `<engine command>` <exited n | timed out (<guard>) | failed to start: … | killed by <signal>>; last lines: …``. The PR body's `## Host verify` section gains an `Engine gate: green | red | skipped (<reason>)` line, on red with the engine command, exit or guard, duration and its tails fenced. `tk-studio doctor`'s `engine` row says whether `GODOT` names a binary that answers `--version`. The paused path, the late close-out, a cancel, a drive failure and `mirror`'s own end run no leg.
- **Close-out.** The commits ahead of base (`git log --oneline <base_ref>..HEAD` in the worktree). None: no push, no PR, `no_changes: true` on `ended`. Otherwise `git push origin supervisor/run-<id>` (never forced), then `gh pr list --head supervisor/run-<id> --state open --json url`: an open PR from the run branch that no record names (an earlier close-out opened it, then crashed or failed to record it) is adopted as the run's PR and marked ready (`gh pr ready`; left a draft while paused), never opened twice. Only when none is open, `gh pr create --base <base_ref> --head supervisor/run-<id> --body-file <temp file>` (`--draft` while paused; the body through a temp file, removed afterwards, so a long body never meets the Windows command-line limit), whose body carries, in order, the launch status block (fenced JSON), `Engine run: <id>`, the landed commits and the metered cost (the engine's `.bmad-loop/runs/<id>/run.json` `total_cost_usd` when an engine is named and metered, read before the worktree is removed; else the worker's cost; else "not metered"). A close-out run again after its worktree was removed (its record lost) reads the commits from the checkout (`git log --oneline <base_ref>..supervisor/run-<id>`), pushes the branch by name from there, and counts the removal as done (`git worktree prune`). The PR URL is `pr` on the `ended` event and its notification; a late close-out (after `closeout: skipped`) records its PR only as `pr` on the appended `closed_out` event, which sends no notification. The close-out record is `closeout`. The supervisor never merges. The worktree is removed (`git worktree remove`) after the PR or "no changes", unless the run is paused (kept for the resume) or a step failed (recorded, kept). Every other run (any skill, a core job, a start failure after the cut) closes out the same way when it ends. A cancel (`POST /runs/{id}/cancel`) closes the run out after stopping its engine and before the `cancelled` end (its PR body: the launch status block and the metered cost, as the sweep's). A run `recover` ends as orphaned is closed out by the orphan close-out (above) once nothing around it is live: no host verify leg, recorded `closed_out` with `orphaned: true`, its sbx pin released. The checkout lock never points at a removed worktree: an end whose close-out ran with its engine confirmed dead releases the lock (the engine id kept on the run) instead of handing it to that engine, a late close-out that removes the worktree releases the engine lock the run still held, and an engine is probed at the run's root once its worktree is gone.
- **Never beside a live worker or engine.** The close-out is skipped (`closeout: {result: "skipped", why, worktree: "kept"}`: no push, no PR, no removal) while anything may still work the worktree: an sbx worker that may still run in the VM (`hold_lock`), on a cancel or a start failure after the cut a recorded worker that may still run, an engine the status block names that is not waited for (a `blocked` launch) and that the probe finds, a live driver, an engine stop that failed or is not confirmed by the probe, or a probe that finds an engine; and on a cancel when another process holds the run's close-out. The engine-end sweep picks such an ended run up and closes it out once its driver, worker and engine are all dead, taken atomically (a `closing-out` lease event) and recorded as an appended `closed_out` event (the PR URL or "no changes"); the terminal row is never updated. A close-out that throws after the sweep took a run lets go of it, so a later sweep takes it again: a running or paused run's owner is cleared, and a terminal run's `closing-out` lease is let go of by an appended `closing-out` event with no owner (the terminal row is never updated). A cancel of a run that is neither running nor paused (a `queued` run `recover` requeued after its cut) skips its close-out naming that (`the run is <state>: the engine-end sweep closes it out`), and the sweep closes it out; `the run is held by another close-out` is named only when another process holds a running or paused run's close-out. A cancelled `paused` run marks its draft PR ready (`gh pr ready`), never opening another.

## The plan follows the run (Story 27.5)

When a run's PR opens, the supervisor sets `review` on every story the run marked done in the plan of the project that owns it, through that project's planning adapter (`uv run $TK_STUDIO_ROOT/plugins/tk-studio/lib/plansync.py status --directory <owner root> --id ST-NNN --status review --note "run <id> PR <url>" --caller tk-studio-supervisor`, argv only); when the PR merges it sets `done`. Two passes run after the orphan close-out at every `run`, `recover` and `drain` (so every tick):

- **Review.** Each terminal run (never `external`) with a worktree recorded, whose PR is on its `ended` event (else the latest `closed_out`: a late close-out), and no `plan-status` `review` event yet. The owner is read from the run project's `_bmad-output/planning-artifacts/epics.md` frontmatter at the run branch: `status: transcribed` with `source: "<org>/<repo> …"` names the registry entry `<repo>`; otherwise it is the run's own project. The stories are the specs changed on `supervisor/run-<id>` against `base_ref` (`git diff --name-only <base_ref>...supervisor/run-<id>`, the paths the paused-run pass resolves) whose frontmatter reads `status: done` at the run branch and not at the merge-base (`git merge-base <base_ref> supervisor/run-<id>`; a spec already done there, merely edited by the run, is not the run's), one per story `N.M`; each maps to the owner plan's single `ST-*.md` whose `source` is `epics.md#story-N.M`.
- **Merge.** Each run with a `review` event and no `done` event: `gh pr view <pr> --json state,mergedAt`. `MERGED` → the `done` calls for the stories resolved at review (read again once the `done` lease is held); `CLOSED` → one `{phase: "done", skipped: true, reason: "pr closed unmerged"}`; `OPEN` or a `gh` failure → nothing, asked again next tick.
- **Lease.** Each phase of a run is taken before anything is called: a `plan-lease {phase, owner}` event appended in one IMMEDIATE transaction (refused while the phase is recorded or another live process holds the lease, and `done` refused while the run's `review` lease is held by a live process: a review still calling the verb story by story), so overlapping `run`/`recover`/`drain` call the verb once per story per phase and `done` is never set on a partial review. A pass that recorded lets the lease go settled (`plan-lease {phase, owner: null, released, settled: true}`). A transient failure records nothing and lets the lease go (`plan-lease {phase, owner: null, released}`) for the next tick: an `epics.md` or spec that cannot be read at the run branch (or a spec at the merge-base) for any reason but "does not exist", a `git diff` or `git merge-base` that fails, a registry lookup that fails (a timeout, no JSON, an unreadable registry — only the registry's own "is not registered" is an absent owner), or a `plansync.py status` that timed out, failed to start or answered no JSON (a traceback) before the pass recorded anything (after it, the failure is recorded `ok: false` with its error).
- **Events.** One `plan-status` event per story per phase, on the run (`from_state` = `to_state`: the run's state never changes): `{phase, pr, owner, directory, story_key, id, ok, previous_status?, error?, blocked?, skipped?, reason?}`. A refusal (`{ok:false, error}`, exit 2) or a blocked re-sync (`{ok:false, blocked:true, reason}`) is `ok: false` and never retried for that phase. An owner not in the registry, or with no `_bmad-output/planning-artifacts/plan/`, records one skipped event per phase naming it and calls nothing; so do a story with no (or several) plan entities, a phase whose transient failure persists past 24 released (not settled) leases (e.g. a deleted run branch: one skip `gave up after <n> attempts: <reason>`, after which the phase is settled), and a run that marked no story done.

The supervisor's own runs resolve to tk-studio (its `epics.md` is transcribed from `thkennedy/tk-studio`): until tk-studio is registered on the host, they record the skip.

## Worker tiers

Each run picks a tier: `host` (the default) or `sbx`. The tier comes from the submission or the supervisor's own per-job config, never from the plugin (AD-2).

- **host**: `claude -p <prompt> --output-format json --permission-mode auto|acceptEdits|…`, spawned directly by the supervisor under the Max login. Bypass is refused (`HostBypassRefused`).
- **sbx**: the same argv inside a Docker Sandboxes microVM: `sbx exec <sandbox> timeout -k 10 <guard-s> env -u ANTHROPIC_API_KEY -C <vm-root> claude -p <prompt> …`. It is argv only with no shell, so the prompt stays one argv item. Before its login probe the worker pins the sandbox, `sbx run -d --name <sandbox>` (Story 27.2, **Worktrees and PRs**). For a drained run the pin runs before the claim (Story 33.2), and a failed pin leaves the run `queued` with a `claim-refused` naming it; a relaunch's or a resume's failed pin still ends the run `blocked` naming it. The login probe runs through the same wrapper (`sbx exec <sandbox> env -u ANTHROPIC_API_KEY claude auth status --json`). `<vm-root>` is derived from the registry root the way sbx mounts it: a drive path `<D>:\GitHub\<p>` becomes `/<d>/GitHub/<p>`, and a POSIX path is unchanged. The skill's payload `directory` is that VM path. Bypass is permitted, but only when requested; the default is still `auto`. A deny profile must lie inside the project root, and it is forwarded as its VM path. A profile outside the root is refused with `DenyProfileRefused`. The VM worker is always `claude`, since `CLAUDE_BIN` is host-only.

Every option resolves in this order: the flag, then the value stored on the queue run, then the per-job config, then the default (`host`, `auto`). A config entry's `permission_mode` applies only when the run's tier is that entry's own tier (no `tier` means host). Model and effort have no config layer. `submit` and `run` resolve them before any process starts and before anything is queued. Each of these refusals exits 2 with nothing queued:
- `HostBypassRefused`, with `state: blocked`
- `TierRefused`, for an unknown `--tier`
- `SbxSandboxMissing`, when the sbx tier has no `--sandbox`
- `VmPathUnderivable`, when the sbx tier runs on a root with no microVM path (e.g. a UNC share)
- `SupervisorConfigInvalid`

The queue run records the resolved `tier` and `sandbox`, and the submission's `model` and `effort` (nullable `runs` columns). A change on a `queued` run writes one `run-options` event. An existing queue file gains the new columns when it is opened. `drain` and the tick drive the run with the stored values, re-checked after the claim. An invalid stored value ends the run `blocked`, naming it, except that a drained run whose stored placement is refused with `TierRefused` or `SbxSandboxMissing` stays `queued` with a `claim-refused` naming it (Story 33.2, **Draining**).

Per-job config (`TK_SUPERVISOR_CONFIG`, YAML; placeholders shown):

```yaml
jobs:
  "<project-id>/<job-id>":
    tier: sbx                        # host | sbx
    sandbox: claude-<project>        # required for sbx
    permission_mode: acceptEdits     # auto | acceptEdits | default | plan | bypassPermissions (sbx only)
```

A host tree kill stops only the host `sbx exec` process, so the VM side enforces the same wall-clock guard itself: GNU `timeout -k 10 <guard-s>` inside the VM ends the worker's process group (see Guards).

Live checks on the agent PC (not verifiable in CI):
- **AC1, console hosting.** Run `bun src/cli.ts run studio-health --directory <root>` from the console-hosted supervisor window. While the worker runs, record the `claude -p` process's session id, for example with `Get-Process claude | Select-Object Id, SessionId, StartTime`. It must be non-zero, meaning not Session 0 and not a headless Task Scheduler spawn (runbook §8).
- **AC5, the first sbx run (runbook §3.5).** Run `bun src/cli.ts run studio-health --directory <root> --tier sbx --sandbox claude-<project> --permission-mode bypassPermissions`. It must end `complete` with bypass. Then run `sbx exec claude-<project> bash -lc 'ls -a ~ ; ls ~/.ssh ~/.aws ~/.azure ~/.config/gcloud 2>&1'` and record that the credential folders are absent.

## Starting at logon (`start.ps1`)

The supervisor is console-hosted in the studio account's own session, never a scheduled task that runs whether the user is logged on or not, and never started from a Claude desktop-app session. A shortcut in `shell:startup` (Win+R, `shell:startup`) runs, with `<repo>` this checkout:

```
wt.exe -w studio nt --title supervisor pwsh -NoExit -File <repo>\start.ps1
```

`start.ps1` prints that exact command (with `<repo>` resolved), then:

1. reads every variable in **Environment** from the User scope (`[Environment]::GetEnvironmentVariable(<name>,'User')`, else the process value) and exports it to its children. A missing `TK_SUPERVISOR_BIND`, `TK_SUPERVISOR_TOKEN` or `TK_SUPERVISOR_SESSION_SECRET` fails loudly, naming the variable, never a value. An unset `TK_SUPERVISOR_TRANSCRIPT_BACKUP` (the nightly backup's `claude-projects` folder) is a warning. When the three TLS variables are set, it runs `tailscale cert --cert-file <TLS_CERT> --key-file <TLS_KEY> <TLS_NAME>` (bounded at 120 s; a failure is a warning) to renew the 90-day certificate before the keeper starts. The `-ServeOnly` keeper runs the same function when `serve` exits 75 (the certificate rule, **Sign-in from the phone**), then restarts `serve` at once without the back-off.
2. starts the API keeper in the same console (never hidden): `start.ps1 -ServeOnly`, a child that inherits the variables step 1 exported and loops `bun src/cli.ts serve` in its own foreground. It restarts `serve` with a back-off whenever it exits, independent of `recover`, the tick and `drain` (which drive runs to completion, for hours), so `/status` answers throughout. `start.ps1` checks the keeper once per pacer pass, restarts it with a back-off if it has exited, and stops the keeper's own process tree (never by name) when it ends.
3. starts the Docker Sandboxes daemon from `$HOME` (`sbx daemon start -d`) when a read-only `sbx ls` exits non-zero, or gives no answer within 30 s (that probe alone is killed, with a warning naming the timeout).
4. runs `bun src/cli.ts recover` (the restart rule with resumes) once, to completion, before the pacer's first tick; its report goes to the console.
5. loops the pacer in the foreground: `bun src/tick.ts`, then `bun src/cli.ts drain` (API-submitted runs), then sleeps `-IntervalSeconds` (default 60; a script parameter, not an environment variable). Every tick and every `drain` still recovers at its own start. Story 33.7: each pacer step runs under the log tee with `--pass` (`bun src/log.ts --tag <tick|drain> --pass -- …`; step 4's `recover` never does, so it is never counted), which logs `pass: <ms> ms, exit <code>` before its `stopped` line; a step over 10 minutes also logs `warning: pass <step> took <ms> ms (over 10 min), driving <run ids>` (the queue run ids its output named, at most 5 then `+<n> more`, else `no run named`) and sends that line once through the notifier. The last pass of each step is kept in `<TK_SUPERVISOR_WORK>\supervisor\pacer.json` (`{last_tick_ms, last_drain_ms, last_pass_at}`, written atomically), served on `GET /status` as `pacer` and shown on the status page.

Only step 1's checks end the script: a missing `TK_SUPERVISOR_BIND`, `TK_SUPERVISOR_TOKEN` or `TK_SUPERVISOR_SESSION_SECRET`, or no `bun` on `PATH`. Nothing after them does. Right after logon Tailscale may not have bound its 100.x address yet, so `serve` can fail to bind: the keeper warns, naming its exit code, and retries it with a back-off (5 s doubling to 600 s; a `serve` that stayed up 60 s resets it) while the pacer keeps running; a `serve` that exits later is restarted the same way. A failed `recover` is a warning too, retried with the same back-off (checked once per pacer pass) until one pass succeeds (every tick also recovers at its own start). A failed tick or `drain` is a warning; the pacer goes on. The script prints variable names and exit codes, never a value.

**The log file (Story 33.1).** Every line the console shows is also appended to `<TK_SUPERVISOR_WORK>\supervisor\logs\supervisor-<YYYY-MM-DD>.log`, one file per UTC day; the first line of a new day keeps the newest 14 day files (any other file in the folder is never touched). Each line is `<ISO UTC time> [<tag>] <text>`: `[pacer]` and `[keeper]` are `start.ps1`'s own lines (the main script and its `-ServeOnly` keeper, through `Write-SupervisorLog`); `[serve]`, `[tick]` and `[drain]` are the bun processes', run under the tee `bun src/log.ts --tag <serve|tick|drain> -- <script>` (`recover` is tagged `drain`: it is the drain's rule), which echoes each child line to the same console stream, appends it, and exits with the child's code, so `$LASTEXITCODE` and the exit-75 rule are unchanged. Each end is explicit: `started` (`started (keeper)`, `started: bun <args>`), `stopped (<why>)` (`Ctrl+C`, an error's message, `exit <code>`, `signal <sig>`, or `keeper tree stopped by the pacer`) and `uncaught: <error>` (from the script's own `catch`, from `cli.ts`'s and `tick.ts`'s `uncaughtException`/`unhandledRejection` handlers, which exit 70, and from the tee when a failed child printed an error line). Every line is redacted before it is written, by the page's rule (`redactCredentials`): a `TK_SUPERVISOR_*TOKEN*`/`*SECRET*` value or a token never reaches the file. With `TK_SUPERVISOR_WORK` unset nothing is written and the start warns once. `GET /status`'s `log` and the page's "Supervisor log" section show the last 20 lines; `tk-studio doctor` reads the newest file's last `stopped` or `uncaught` line when the API does not answer.

The tab stays open (`-NoExit`); Ctrl+C stops the pacer and the API keeper. After a reboot and auto-logon, the smoke test from another tailnet device is `curl -H "Authorization: Bearer <token>" http://<tailscale-ip>:<port>/status`, or `https://<TLS_NAME>:<port>/status` once TLS is set.

## Run hygiene

- **Editor-in-the-loop snapshot.** A run submitted with `--editor-in-the-loop` (CLI `submit`, no value) or `editor_in_the_loop: true` (`POST /jobs`) is flagged on its queue run, like `tier`. After the claim and before `wake`/`submit`, a flagged run on a Godot project (`project.godot` in the root or a first-level folder, e.g. `game/`) is copied with `robocopy <root> <TK_SUPERVISOR_WORK>/snapshots/<project id>/<queue run id> /E /R:3 /W:5` (exit 0–7 is success; `/R:3 /W:5` bounds robocopy's retries, so one locked file never holds the run and its checkout lock for the hour-long snapshot timeout); the path is a `snapshot` event on the run. Once per queue run: an adopted or resumed run that already has one takes none. A flagged non-Godot run takes no snapshot and records why (`snapshot-skipped`). A failed snapshot (robocopy exit 8 or above, no work folder, or a work folder that is the project root or lies inside it, refused before robocopy runs) ends the run `blocked` naming `snapshot failed: …` before `wake`: no flagged Godot run starts without its snapshot.
- **Notification.** Every terminal run (complete, partial, blocked, cancelled, orphaned) sends one notification through the notifier `TK_SUPERVISOR_NOTIFY` selects: ntfy (a POST to the topic URL) or Telegram (Bot API `sendMessage`). It names the queue run, its job, its state, its reason, and its PR: the first GitHub pull-request URL among the status block's `artifacts[]`, reduced to its canonical `https://github.com/<owner>/<repo>/pull/<n>` (any trailing path, query or fragment dropped; recorded as `pr` on the `ended` event), omitted when there is none. The text is capped at 3800 UTF-8 bytes (under Telegram's 4096-character and ntfy's 4096-byte limits): a longer reason is cut, ending `… [reason truncated]`; the run id, state and PR are kept whole. A `notify-failed` error never carries the Telegram token, its Bot API URL, or the ntfy topic URL (nor its userinfo or `auth` query). The outcome is an event: `notified`, `notify-failed` (the run's state never changes), or `notify-skipped` (no notifier configured).
- **Per-run transcript copy.** A host run's session transcript is copied to `TK_SUPERVISOR_TRANSCRIPT_BACKUP` in the nightly layout (`<backup>/<slug>/<session-id>.jsonl` plus `<session-id>/subagents/`), so a later resume restores it from there (`transcript-copied`). An sbx transcript is VM-resident and is skipped (`transcript-copy-skipped`); a missing variable or transcript is `transcript-copy-failed`. The nightly task stays the catch-all.
- **Once per run.** The end hygiene is a sweep: after every end in the driving process (`run`, `drain`, the tick), after an API cancel (the cancelled run's end only: the answer never waits on other runs' ends), and in `recover`/`drain`, each terminal run whose `notified` marker is null is leased atomically by one process (`lease <time> pid <pid>@<host>`), then notified and copied, outside any queue transaction, and the lease is finalised (`done …`) once both outcomes are recorded; an outcome event that cannot be written (e.g. the file is busy) leaves the lease to go stale and be re-claimed. A process that dies between the lease and the send leaves a lease that goes stale after 10 minutes; a later sweep re-claims it atomically and sends then, so a crash delays that notification, never loses it. A stage whose outcome event is already recorded is not repeated on re-claim (only a crash between the send and its event can repeat a notification). A fresh lease is never re-claimed. A trigger allows only NULL → lease, stale lease → lease, and lease → done. Runs already terminal when a queue file gains the marker are marked done and never notified.

## Guards and the pacer

The studio's guards are data (`guards`, `stop`, `cadence.hint_seconds`); the supervisor enforces them (contract §4). Every guard trip ends the run `partial`, with `reason` naming the guard that tripped and its value, e.g. `guard: max_wall_clock_seconds (600s)` or `guard: max_turns (40)`.

- **Wall clock (skill jobs).** The worker runs under the job's `max_wall_clock_seconds` (default 600), capped by the tick's `--timeout-cap-s`. A trip kills the worker's whole process tree: on POSIX the worker leads its own process group and the group is killed; on win32 `taskkill /F /T` (no `detached`, so the worker keeps its console). The reason names the bound that tripped: the job guard, or `guard: --timeout-cap-s (<n>s)` when the cap was lower. On sbx the in-VM `timeout` ends the VM worker too; when it fires first, `sbx exec` exits 124 (or 137 after `-k`) with no status block, and once the guard's time has passed on the host (the worker's own time, from its spawn — not the auth preflight or drift check before it) that is the same wall-clock trip (`partial`, the guard named); an earlier 124/137 (an OOM or another SIGKILL) is a silent exit: the resume-or-partial rule under **Restart** (Story 21.6). On sbx a host-side kill (a guard trip, or a SIGINT/SIGTERM to the supervisor) ends only the host `sbx exec`: the in-VM worker ends only at its in-VM `timeout` (the guard plus the VM start lag plus the 10 s `-k` grace), so after a trip it can briefly outlive the released checkout lock, and after a supervisor signal or death it runs on until its in-VM guard (`recover` and `claim` hold that run's lock until then, under **Restart**). On POSIX a SIGINT/SIGTERM/SIGHUP to the supervisor while a worker runs SIGKILLs the process groups of its own live children (never by name), then the supervisor exits on that signal as before. A signal the supervisor inherited as ignored (e.g. SIGHUP under `nohup`) stays ignored before, during and after a worker: it is never handled (read from `/proc/self/status` on Linux; where that cannot be read, SIGHUP is never handled).
- **Wall clock (core jobs).** A core job runs inside `wake`, where jobrun enforces the guard itself. The `wake`/`submit` verb timeout (the guard + 120 s) is the supervisor's backstop. When it trips, a core run's studio run is `cancel`led (never `finish`ed) and the queue run ends `partial` naming the guard in its reason and its `ended` event (`guards_tripped`); the `ended` event's `studio_outcome` records the studio's real state, `cancelled`, and `stop.on_status` is matched against that state, not `partial`. A skill run caught by the backstop is finished `partial`, the reason naming the guard.
- **Turns and tokens.** When the job has `max_turns` or `max_tokens`, each worker iteration (one `claude -p` run) is accounted before `finish`: `jobrun.py account --run-id <studio run> --turns N --tokens N`. On the host the counts come from the worker's session transcript, `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/*/<session_id>.jsonl` (exactly one match), plus every `*.jsonl` directly in its sibling `<session_id>/subagents/` directory (the worker's subagents; none counts zero, an unreadable one is a named failure), merged by message id: turns are distinct assistant message ids, tokens the sum of input, output and cache tokens over them. On sbx the transcript is inside the VM, so the counts come from the JSON result's `num_turns` and `usage`. `within_budget: false` ends the run `partial` naming every exceeded guard; the status block is still recorded. A missing or ambiguous transcript, or a failed `account`, is named as `guard: account failed — <cause>`: a clean run ends `partial`, an already-`blocked` run stays `blocked`. The iteration's own reason (e.g. a missing status block, a missing Max login) is never dropped; guard text is appended after it (`<reason>; guard: …`). A wall-clock trip is not accounted.
- **Pacer.** The tick paces self-paced jobs from the queue database, not the studio's `status`. Per (job, checkout) it skips while a queue run is `running`, `paused`, `external` or `queued` under a live owner, or an ended run of the job still holds its checkout's `run` lock (a worker that may still run, a live driver: Story 27.5, DW-11). An ownerless `queued` run (a lock wait, a recovery re-queue, a hand `submit`) is driven: `runJob` adopts it through its idempotent mint, nothing new is minted, and the hint is not re-applied. Otherwise it skips until `hint_seconds` have passed since its latest terminal queue run ended (the `ended` event's time). A studio run started outside the queue (the MCP `tk_job` `wake`/`submit`, or `jobrun.py` by hand) is recorded `external` on the next tick and counted live until its studio run ends (Story 27.2, DW-6 closed; **Queue, lock and restart rules**); only between that start and the next tick can the pacer not see it.
- **Engine kill (Story 27.2, sbx).** A tripped guard on an sbx launch run (the in-VM 124/137, the host timer, the wall clock or a turn/token guard), like a cancel, kills the engine's process group inside the microVM by its recorded pid (else the worktree's only `engine.pid`): `sbx exec <sb> kill -TERM -- -<pid>`, a bounded wait, then `kill -KILL -- -<pid>` (sent to the group once even when its leader went on TERM, so members ignoring TERM never survive a `killed`), each liveness probe `sbx exec <sb> cat /proc/<pid>/stat` with its start time compared to the recorded one (a reused or dead pid is never signalled; no pid known, nothing is killed). Argv only, never a shell or a pattern kill. The kill and its outcome are an `engine-kill` event; a pid still alive after the wait is `engine alive after kill`, and a first probe that cannot be read is `start time unreadable` (nothing signalled); both are recorded-worker outcomes that may still run, so the run keeps its lock (`hold_lock`, DW-3). That hold lasts while the pid runs, not to the in-VM deadline the lock records: while a run's last `engine-kill` is `engine alive after kill` or `start time unreadable`, every path that would free its lock, close it out or stop its sandbox (`recordedWorker` for `claim`/`recover`, the late close-out, the pin release) probes the pid again (`sbx exec <sb> cat /proc/<pid>/stat`, its start time matched; an unreadable probe counts as alive). Once the probe shows it gone (an `engine-gone` event) they proceed as before. When the KILL reached a leader still alive after TERM (so its own SIGTERM teardown never ran) and the engine run id is known (the run's, or the one the launch status block names), the engine's agent tmux session is killed too, `sbx exec <sb> tmux kill-session -t =bmad-loop-<engine id>` (best effort: a non-zero exit is recorded in the kill's detail). An engine the kill left gone (`killed`, `not running`, or a later `engine-gone`) never writes its own end, so the engine-end sweep reads its in-progress status as ended and the run ends with its launch's recorded end (the trip's state and guard reason), closed out and its pin released as for any ended engine. No guard bounds the engine itself beyond these.
- **Stop on status.** When a run ends in a state listed in the job's `stop.on_status`, a `stopped` event (`from_state` = `to_state` = that state, detail `{condition: "on_status", state, job_id}`) is written to `events`, in the same transaction as the run's `ended` event. The stop holds until a later run the studio actually ran reaches a terminal state; a not-woken or refused run, or an orphan, never clears it. The tick skips a stopped job first (before driving any queued run, before minting) and logs the condition, but only while the job's current `stop.on_status` still lists the stopped state: removing `on_status`, or dropping that state from it, resumes the job. `run`/`submit` by hand still meet the studio's own stop refusal.
