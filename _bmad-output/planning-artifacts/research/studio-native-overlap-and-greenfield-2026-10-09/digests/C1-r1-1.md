## What being a plugin costs (sourced)

- Whole-marketplace clone on add and refresh (`marketplaces/<name>/` is "the clone or download of a marketplace"); LFS files are left as pointers (v2.1.274) and submodules without plugin files are now skipped (v2.1.295), and `claude plugin marketplace add --sparse` exists (mentioned v2.1.287), but the default remains a repository clone. S5, S6.
- A separate copy per version under `cache/`, `${CLAUDE_PLUGIN_ROOT}` moving on each version, 14-day orphan sweep that only runs while at least one install record exists. S5.
- Version-string pinning means pushed commits do not reach users until the string changes; omitting it tracks the SHA. Either way, third-party marketplaces do not auto-update by default, and when enabled the pass runs on a random delay of up to ten minutes with a `/reload-plugins` (monitors: restart) step. S1, S5.
- Project-scope enablement does not install: each collaborator (and each sandbox image) must install at user/local scope or the `/plugin` Errors tab shows "enabled in project settings but isn't installed here". S5.
- Windows friction: forward-slash substitution rules, backslash paths rejected on macOS/Linux, `claude plugin validate` quoting warnings unless `shell: "powershell"`, plus the 2026 issue stream (EBUSY Defender race, drive-letter casing fixed v2.1.295, case-sensitive `projectPath` still open as #74912, bare `npx` ENOENT, SSH-less `owner/repo` installs fixed v2.1.296). `command` sources run under `cmd.exe` on Windows (given in brief, not re-verified this run). S1, S5, S6, S7.
- Update/record fragility reported in 2026 (all closed): stale `installPath` after autoUpdate (#52218), marketplace update not picking up pushes (#72162), marketplace dir wiped on path mismatch (#71948), `--scope project` install clobbering `installed_plugins.json` (#75392). S7.
- Every model-invocable skill/agent/command in the plugin costs context on every turn in every session where it is enabled; no per-skill enable inside a plugin (#47747 closed). S3, S7.
- Cloud sessions ignore local plugins and never add repo-listed marketplaces; claude.ai/Cowork refuse a plugin with `bin/`. S1, S3, S5.
- Node deps auto-install is mandatory and constrained (registry only, no scripts, 60 s); Python deps are the plugin's own job via a hook into `${CLAUDE_PLUGIN_DATA}`. S5.

## Options with benefits and drawbacks

### O-A stay a plugin (git marketplace, as today)
Benefits: Claude-Code-native version gate and cache isolation (S5); `claude plugin update`, `--json`, `eval`, context-cost reporting (S3, S6); `bin/`, monitors, channels, mods, `userConfig` all available (S1, S6); one-command install line that `claude plugin validate` now even suggests for READMEs (S6 v2.1.295); eligible for claude.ai sync and the Anthropic directory (S5, S1).
Drawbacks: whole-repo clone and per-version cache copies (S5); no auto-update by default and up-to-ten-minute delay when on (S5); project-scope enable does not install, so every sandbox image needs a user-scope install step anyway (S5); the installer the studio must build anyway would then sit beside a second updater (the marketplace) — two sources of truth for "what version is installed" [inference]; Windows issue stream (S7); monitors do not run in non-interactive sessions, so unattended Docker runs get none of that plugin-only surface anyway (S1).

### O-B skills + CLI delivered by the installer (no manifest)
Benefits: installer is the single distribution and updater; skills editable in place; per-project vs per-user choice is the installer's (S4 scopes); no clone, no cache, no `${CLAUDE_PLUGIN_ROOT}` churn; `claude plugin validate` still lints the skills dir (S4); `npx skills`-style ecosystem compatibility (S10); matches BMad's primary route (S8).
Drawbacks / must rebuild: namespacing is lost (collisions resolved by enterprise > personal > project, S4); no `${CLAUDE_PLUGIN_ROOT}`/`${CLAUDE_PLUGIN_DATA}` (use `${CLAUDE_SKILL_DIR}`, S4); hooks must be merged into the user's `settings.json` by the installer or carried in skill frontmatter (active only after invocation, S4); agents go to `.claude/agents/`; no one-unit enable/disable, no `plugin eval`, no `bin/`, monitors, channels, mods, `userConfig` (S1); lockstep gate and drift check become installer-owned (they are not provided by Claude Code for plain skills); no trust auto-prompt (S5).

### O-C hybrid: minimal plugin for hooks/agents + installer-managed skills
Two documented shapes, both avoiding the marketplace clone:
1. Skills-dir plugin: the installer writes `~/.claude/skills/tk-studio/` (or `.claude/skills/tk-studio/`) containing `.claude-plugin/plugin.json`, `hooks/`, `agents/`, `.mcp.json` and `skills/`. Claude Code loads it as `tk-studio@skills-dir`, namespaced, in place, never copied, no marketplace, no install record (S4, S5); `claude plugin init` already scaffolds there (S6). Benefits: keeps namespacing, hook/agent/MCP bundling, `${CLAUDE_PLUGIN_ROOT}` [inference: in-place plugins receive a root pointing at the source dir per S5; not stated specifically for skills-dir], one-unit enable/disable, `claude plugin validate`/`eval`, editable in place, installer-owned versioning and drift. Drawbacks: at project scope monitors never load, MCP needs per-server approval, bundles are skipped, no parent-dir search, trust dialog required (S5); personal scope has none of these restrictions but is per-machine, which fits a one-maintainer Windows box and a sandbox image that bakes `~/.claude/skills` [inference]; Claude Code computes no version for it, so the lockstep gate is entirely the installer's; `bin/` support for skills-dir plugins is not stated (S1) — verify.
2. Inline `settings`-source marketplace + `command`-source plugin in link mode: the marketplace is declared inline in settings (no clone, S5), the plugin's `command` is the studio CLI printing its install dir, re-resolved each session and hot-reloaded on hash change (S5, S6 v2.1.229). Benefits: stays a "real" marketplace plugin (bin/, monitors, auto-reload) with the installer as the only mover. Drawbacks: command runs under `cmd.exe` on Windows (given in brief); version is a hash of output, manifest `version` cannot pin (S1, S5); one extra background command per session; newest and least-exercised path (added 2026-08-12).

## Direction of travel (sourced)

- Docs wording keeps skills as the content unit and plugins as the packaging/distribution unit: "Skills, subagents, hooks, and MCP servers all work on their own, without a plugin" (S3); the skills page lists plugins as one of four distribution routes alongside committing `.claude/skills/`, managed settings, and claude.ai account enablement (S4).
- But the newest extension surfaces are plugin-only and arriving fast: mods (v2.1.287, 2026-10-01; 247-comment feature thread), monitors, channels, `bin/`, workflows, `userConfig`, `claude plugin eval` (v2.1.269), `--marketplace` install shorthand (v2.1.292), claude.ai plugin sync to terminal (v2.1.275). The CHANGELOG from v2.1.287 to v2.1.296 is dominated by mod/plugin entries (S6).
- The skills-dir plugin form (`@skills-dir`, `claude plugin init` into `.claude/skills`) is Anthropic's own bridge: skills-folder placement with plugin semantics (S4, S5, S6).
- Ecosystem: the skills CLI / agentskills.io standard is the cross-tool lingua franca (79 agents, S10); BMad leads with it and keeps marketplaces as secondary (S8); the largest "framework for Claude Code" (Ruflo) treats the plugin path as a lite trial tier and its own installer as production (S12); SuperClaude has not shipped a plugin route (S11). Anthropic's own skills repo ships as a marketplace for Claude Code (S9).
- [inference] Nothing retrieved suggests plugins become required for the studio's core (skills, agents, hooks, MCP). They are required for mods, monitors, channels, `bin/` — none of which run in unattended/non-interactive sessions (monitors) or on claude.ai/Cowork (`bin/`).
