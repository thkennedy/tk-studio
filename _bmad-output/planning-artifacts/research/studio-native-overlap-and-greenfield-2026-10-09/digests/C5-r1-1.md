## Reference architectures (cards with their stated lessons)

**Claude Managed Agents (Anthropic, beta)** — S5. Split: *Agent* (model, system prompt, tools, MCP, skills) / *Environment* (cloud or self-hosted sandbox) / *Session* (running instance, persistent filesystem and history) / *Events* (user turns, tool results, status) streamed by SSE and persisted server-side; "steer or interrupt" by sending events. Stated lesson: build the harness once, keep sessions stateful and resumable, treat the sandbox as a separately configured environment. Not usable on a subscription (API key required), but the four-concept split is the cleanest reference for a control plane.

**Paperclip (Node + React, MIT)** — S12, S11. Split: one server owning identity, work/tasks, heartbeat execution, governance/approvals, budgets, routines, secrets, activity log; a React UI; *adapters* to runtimes (Claude Code, Codex, Cursor, Gemini CLI, OpenCode, Hermes, HTTP bots): "If it can receive a heartbeat, it's hired." Execution is a "DB-backed wakeup queue with coalescing, budget checks, workspace resolution, secret injection, skill loading, and adapter invocation"; "Bounded recovery handles supported failures and surfaces cases that need human action"; budgets enforce on recorded spend, so "usage reporting and in-flight work can delay a stop". Stated positions: "Not an agent framework", "Not a prompt manager", "Not just a workflow builder". Lesson it states against its own pain list: "You have 20 Claude Code tabs open ... On reboot you lose everything" → ticket-based tasks, persisted sessions. Health: 99.2k stars, created 2026-03-02, 218 contributors, 2,910 open issues, 3,392 open PRs, release v2026.1005.0 (2026-10-06).

**Omnara (Go services + TS front end, Apache-2.0)** — S11 description only: "The open-source managed agent platform. A self-hostable alternative to Claude Managed Agents and OpenAI's Agents API"; release cluster-v0.2.1 (2026-10-08); 21 contributors. Search snippets (unfetched, see Leads) say it pivoted from a remote-control app for Claude Code to a managed-agent control plane and uses an outbound daemon for private machines. Lesson (inferred from the pivot): the remote-control UI alone was not the product; durable agent objects plus machines were.

**Hermes Agent (Nous Research, MIT)** — S11: 252k stars, v0.21.6 (2026-10-08), 14.8k open issues, 33k open PRs, only 6 mentionable users (org-restricted listing, I infer). It is a runtime, and Paperclip lists it as an adapter target (S12). A field report in the search results (felipefontoura.com, unfetched) claims that most production bugs sit at the adapter boundary (identity, wake context, liveness, token accounting) and that the same model scored lower through Paperclip+Hermes than through OpenCode; treat as a lead.

**OpenCode (anomalyco, MIT)** — S11: 212k stars, 1,004 contributors, v1.18.35 (2026-10-06). Server mode: not confirmed by anything retrieved this run.

**Factory Missions** — not retrieved; search snippets only (planner/worker/validator, `droid exec --mission` headless, "Factory 2.0" June 2026). Lead.

**munder-difflin** — not found on GitHub at the guessed coordinates; not reached.

Cross-cutting pattern (my synthesis from S5, S12 and the snippets): every product splits a durable control plane (state, queue, budgets, approvals, events) from swappable agent runtimes behind an adapter, and puts the UI on the control plane's event stream, not on the runtime. None of them put the loop engine inside the UI process.

## Benefits and drawbacks of the proposed stack versus a studio built around its own loop engine, supervisor and routing

Benefits of the proposed stack (lean on Anthropic primitives, build only the engagement layer):
- The agent loop, tools, permissions, sessions, hooks, plugins, review skills and workflows are Anthropic-maintained and ship weekly (CHANGELOG top is 2.1.296 dated today), so the studio does not re-implement an agent loop or reviewer fan-out (S4, S7, S10).
- Subscription economics are respected: `-p` with `setup-token`, `/code-review`, workflows and routines all run on a Max plan; Managed Agents and the Analytics APIs, which would need API billing, are excluded by design (S2, S4, S5).
- Isolation follows Anthropic's own guidance for unattended runs (container/VM) and Docker's Windows 11 support, instead of a home-grown sandbox (S9, S14).
- The only genuinely new code is the part no product has: quote-before-run, per-story metering and the office UI.

Drawbacks and risks:
- Research-preview dependencies: agent view/daemon (2.1.139), channels (2.1.80), sandbox-runtime (beta), OTel traces (beta) can change; the service should treat `claude --bg` as optional and own its own process supervision (S6, S9, S10).
- Headless loses the subscription safety nets interactive sessions get: workflow agents do not pause at a usage limit in `-p`, and workflow runs cannot resume in a fresh session, so the service must detect limit errors and reschedule to the window reset (S7, S2).
- Metering is estimate-grade: list-price dollars computed locally, cache TTL changes when usage credits kick in, and nothing attributes spend to a story unless the service tags each process (S2, S3).
- Third-party adoption risk: Paperclip is huge and fast-moving (3,392 open PRs); ccusage's license is NOASSERTION; Docker Sandboxes' agent list and credential passthrough were not confirmed on the pages fetched (S11, S13, S14).
- Terms ambiguity: the SDK page's claude.ai-login restriction targets third-party products; a private one-maintainer tool driving its own CLI is not addressed by anything retrieved; the consumer terms were not fetched (S4).

Versus an own loop engine, supervisor and routing: the home-grown route gives deterministic control and no preview-feature exposure, but re-implements what S4/S7 already provide (agent loop, subagents, workflow runtime with replay, review skills) and would still need the same `claude -p` boundary for subscription auth; the maintenance load on one person is the deciding drawback (I infer).
