# Red team: the skills-dir plugin verdict (2026-10-09)

Conclusion under attack: the studio should stop shipping as a marketplace plugin and have its installer write a `tk-studio@skills-dir` plugin (18 skills + 2 agents, nothing else) at `~/.claude/skills/tk-studio/`, loaded in place with no install record, the installer owning versioning/lockstep/drift, with Docker Sandboxes images or homes carrying the same folder. Budget: 19 surface calls used, one over the 18 allowed because one Bash call carried two `gh api` searches (8 WebFetch, one of them a 404; 2 WebSearch; 9 `gh api`: 1 CHANGELOG, 4 issue searches, 3 GraphQL issue-body batches, 1 README). Local `claude plugin --help`, `claude plugin list --json`, `claude plugin validate/details` against a scratch `--plugin-dir` plugin, and CHANGELOG greps were free.

Reviewer had no run context and no supporting evidence, by design. Constraint used: Claude Code 2.1.286 on this Windows 11 host; `claude plugin list --json` here shows `tk-studio@tk-studio` v0.2.16 installed at both user and project scope from the git marketplace.

## Findings (strongest first)

### F1. A same-named marketplace install silently wins over the skills-dir copy, and this machine has one at two scopes
- **Attacks:** "Claude Code loads it as `tk-studio@skills-dir` ... the git marketplace is dropped (or kept only for developers)".
- **Evidence:** The loading reference's name-conflict order: "3. An installed marketplace plugin. A skills-directory plugin of the same name gets the same `Not loaded` row, naming the installed plugin"; the comparison is by manifest `name` ("Because the order compares manifest names"). [source: https://code.claude.com/docs/en/plugins/loading, Anthropic, undated]. Locally, `claude plugin list --json` (2.1.286) returns two records for `tk-studio@tk-studio` 0.2.16, `scope: "project"` (projectPath `C:\GitHub\tk-studio`) and `scope: "user"`, both `enabled: true`. Today's install path also writes `extraKnownMarketplaces` + `enabledPlugins` into consuming projects' committed `.claude/settings.json`; the loading page says an `enabledPlugins` `true` in project settings persists and, where not installed, shows `Plugin "<name>" is enabled in project settings but isn't installed here`.
- **Weight:** material. "Kept only for developers" is exactly the machine where both copies coexist, and the failure mode is a `/plugin` Errors-tab row, not a startup error. Any project that still carries `"tk-studio@tk-studio": true` plus a user-scope install record keeps shadowing the new copy on every machine that ever ran today's install.
- **Mitigation the conclusion would need:** the installer must uninstall `tk-studio@tk-studio` at user, project and local scope on every host it touches, scrub `enabledPlugins`/`extraKnownMarketplaces` entries from consuming projects, and the drift check must fail on any surviving marketplace record; or give the skills-dir manifest a different `name` (which changes every `/tk-studio:*` command prefix). Developers who keep the marketplace cannot also be dogfooding the skills-dir copy.

### F2. Docker Sandboxes already own `/home/agent/.claude/skills` as a mounted, shared, possibly read-write store
- **Attacks:** "Unattended runs happen inside Docker Sandboxes microVMs whose image or home directory carries the same `~/.claude/skills/tk-studio/` folder."
- **Evidence:** Docker's "Share agent skills" page: "Shared agent skills are experimental."; the supported-agent table maps Claude Code host `~/.claude/skills` to sandbox `/home/agent/.claude/skills`; the store is mounted at launch "at the path the agent reads inside the sandbox"; `sbx skills import` copies each skill subdirectory into a persistent store and "Importing replaces the complete skill directory rather than merging files."; modes `readonly`/`readwrite`/`off` via `--skills`, set at creation only; "A sandbox with `readwrite` access can modify skills that other sandboxes load"; Windows store path `%LOCALAPPDATA%\DockerSandboxes\sandboxes\state\agent-skills`; "Running `sbx reset` clears the shared store." [source: https://docs.docker.com/ai/sandboxes/workflows/agent-skills/, Docker, undated]. The two renderings of the page disagree on the default: the Markdown copy says "mount the shared store read-only by default", the HTML copy as summarised by search says sandboxes created with sbx 0.37.0 or later mount it read-write by default and mention `--no-share-skills`. Separately, a Docker forum thread (2026-02-20/21) confirms the sandbox "has its own `$HOME` (typically `/home/agent`)" and "a read-only mount of your host `~/.claude` may not be discovered by Claude Code"; the documented route is a template via `docker sandbox save`. [source: https://forums.docker.com/t/docker-sandbox-claude-missing-plugins-rules-user-level-config-such-as-claude-md/151158, Docker Community Forums, 2026-02-20]
- **Weight:** material. A folder baked into the image at `/home/agent/.claude/skills/tk-studio` sits under a mount point sbx controls; whether it survives depends on the skills mode at sandbox creation, which the installer does not own. In `readwrite` mode an unattended agent can edit the studio for every later sandbox; in `off` mode the image copy is the only copy and must be rebuilt per release; in `readonly` mode the real distribution channel is `sbx skills import` from the host, not the image.
- **Mitigation the conclusion would need:** state the sbx skills mode explicitly (`--skills=off` plus image bake, or `readonly` plus installer-driven `sbx skills import`), pin the sbx version, and extend the drift check to hash the store copy at `%LOCALAPPDATA%\DockerSandboxes\sandboxes\state\agent-skills`.

### F3. The documented sharing paths do not include installer-written skills-dir plugins; skills-dir is documented as the no-marketplace development path
- **Attacks:** "should stop distributing itself as a marketplace plugin" and the framing of skills-dir as a distribution form.
- **Evidence:** The create page's "Share your plugin" section lists exactly three ways: send the directory or a `.zip`, "List it in your own marketplace", "Submit it to Anthropic's directory". Skills-dir loading is documented under the heading "Develop without a marketplace" > "Make a plugin load in every session", scaffolded by `claude plugin init`, and "Decide when to use a plugin" says "Make a plugin when you want to share the setup with teammates, install it in several projects, or publish versioned releases." [source: https://code.claude.com/docs/en/plugins/create, Anthropic, undated]. The precedent checked (obra/superpowers README) offers marketplace or harness plugin-manager installs for every one of 15+ harnesses and no `~/.claude/skills` path. [source: https://github.com/obra/superpowers/blob/main/README.md, obra, undated]
- **Weight:** moderate. Not a deprecation signal (none found, see below), but the conclusion steps outside every documented distribution path and outside the only large-skill-set precedent examined. The practical loss is one-command install for anyone who is not running the bootstrap, and the `extraKnownMarketplaces` auto-prompt on folder trust.
- **Mitigation the conclusion would need:** an explicit statement that the bootstrap script is the only install path and that the marketplace is not just "kept for developers" but deleted, to avoid F1.

### F4. User-scope skills-dir plugins load with no trust step, no enable step, and global effect; a first-party scaffold already caused silent cross-session changes
- **Attacks:** "writes a 'skills-dir plugin' at user scope ... loaded in every session of every project".
- **Evidence:** Loading reference: project-scope skills-dir plugins need the workspace trust dialog and have MCP and monitor restrictions, then "Personal-scope plugins have none of these restrictions." A skills-dir plugin is on by "The manifest's `defaultEnabled`, unless a settings file sets `"<name>@skills-dir"`" [source: https://code.claude.com/docs/en/plugins/loading]. Issue #91863 (2026-09-03, has repro): "A skills-directory plugin (a directory in `~/.claude/skills/`, loaded in place) whose `output-styles/*.md` declares `force-for-plugin: true` sets the output style for every session ... neither plugin below was ever enabled, and both still forced their style" [source: https://github.com/anthropics/claude-code/issues/91863, anthropics/claude-code, 2026-09-03]. The skills page: "A skill can grant itself broad tool access, so review the `allowed-tools` of skills checked into a repository" [source: https://code.claude.com/docs/en/skills].
- **Weight:** moderate. The conclusion ships no hooks/MCP/output styles, which shrinks the surface, but an installer that writes into `~/.claude/skills/` bypasses the marketplace add prompt, the per-plugin install step and the project trust gate, and nothing in the product reviews what lands there. Future additions (an output style, a hook) would become global on the next bootstrap run without any prompt.
- **Mitigation the conclusion would need:** the installer prints a manifest of what it wrote and its hash; the conformance suite asserts the plugin contains only `skills/`, `agents/`, `.claude-plugin/plugin.json` (the "nothing else" clause as a test, not a promise); `allowed-tools` reviewed in CI.

### F5. The non-CLI surfaces this maintainer uses do not reliably load `@skills-dir` or `~/.claude` content
- **Attacks:** "Claude Code loads it ... in every session" on a Windows host that also runs the Claude desktop app (MSIX).
- **Evidence:** #100448 (2026-10-08, Windows, 2.1.292): "A plugin directory under a project's .claude/skills/ (origin @skills-dir) loads correctly in the CLI but never loads in the VS Code extension" and the Manage Plugins toggle "writes `\"(suppressed)@skills-dir\": true` to `~/.claude/settings.json`" [source: https://github.com/anthropics/claude-code/issues/100448]. #95791 (2026-09-21, Windows): project skills-dir plugins "silently suppressed" in VS Code when trust was accepted from a terminal with a different drive-letter case; "/plugin shows a single `(suppressed)@skills-dir` entry" [source: https://github.com/anthropics/claude-code/issues/95791]. #94635 (2026-09-16, regression 2.1.260-2.1.270): in Desktop Code-tab sessions "skills from marketplace plugins installed under `~/.claude` are never loaded"; log line "10 ~/.claude plugin(s) left to the CLI's own loader (not passed as --plugin-dir)" [source: https://github.com/anthropics/claude-code/issues/94635]. #91789 (2026-09-03): `~/.claude/skills/` not discovered in Desktop Remote (SSH) sessions [source: https://github.com/anthropics/claude-code/issues/91789]. Documented: "Cowork sessions and cloud sessions, including routines, don't read `~/.claude/skills/` on your machine." [source: https://code.claude.com/docs/en/skills]. #80407 (2026-07-23): Desktop Home/Cowork sessions use a separate Anthropic-managed bundle "gated by its own `manifest.json`" [source: https://github.com/anthropics/claude-code/issues/80407].
- **Weight:** moderate. The two `@skills-dir`-specific defects are project-scope, and #94635 is the marketplace path failing (which cuts the other way), so the user-scope CLI claim stands; but "every session" is false for Cowork, cloud, routines and Desktop Remote, and `@skills-dir` handling on the VS Code/Desktop loaders is demonstrably younger than marketplace handling.
- **Mitigation the conclusion would need:** scope the claim to terminal/`-p`/`--bg` sessions and the sandbox; add a smoke test from the Desktop Code tab on this host.

### F6. In-place loading removes the versioned cache, so an install is live mid-write and running sessions get mixed versions
- **Attacks:** "loads it ... in place, never copied ... the installer owns versioning, the lockstep gate and the drift check outright".
- **Evidence:** "`--plugin-dir` and skills-directory plugins: the directory loads in place and is never copied." For marketplace plugins, "`${CLAUDE_PLUGIN_ROOT}` points at a version directory, a plugin's root path changes with every version" and on update "Claude Code writes an `.orphaned_at` marker into the previous version directory. It removes that directory in a background cleanup 14 days later, so a session that already loaded the old version keeps running." Also "Claude Code doesn't take the version from a repository that encloses the install path, such as a git-managed `~/.claude`." [source: https://code.claude.com/docs/en/plugins/loading]. #95306 (2026-09-18, Windows 2.1.276) measured a per-skill-directory poll under `~/.claude/skills` (~45 syscalls/s each) [source: https://github.com/anthropics/claude-code/issues/95306], so handles on those directories are live while sessions idle.
- **Weight:** moderate. The installer must reinvent the version directory plus atomic swap that the cache gave for free; on NTFS a directory rename under an open poller can fail, and a bootstrap that copies files into the live folder gives a running session skill bodies from two releases.
- **Mitigation the conclusion would need:** write to `~/.claude/skills/tk-studio.<ver>/`, then swap by rename with retry, and keep the previous tree for in-flight sessions; or accept "restart all sessions" as part of the install contract.

### F7. Measured idle-CPU cost on Windows is far higher for directories under `~/.claude/skills` than for cached plugins
- **Attacks:** moving 18 skills from the plugin cache into `~/.claude/skills` on an always-on box with many sessions.
- **Evidence:** #95306's bisect table (Windows 11, 2.1.276, 40-second idle averages): "+ 11 plugins (junction to `plugins/`, `enabledPlugins` copied) | 2.0 % | 243" versus "+ 40 user skills (junction to `skills/`) | 4.9 % | 2,670"; "~45 syscalls/s and ~0.07-0.1 % of a core per skill directory, regardless of how many files are inside." [source: https://github.com/anthropics/claude-code/issues/95306, 2026-09-18, open, labels bug/has repro/platform:windows/perf:cpu]
- **Weight:** weak to moderate. The report measured plain user skills, not skills-dir plugin subfolders; whether the poller treats `~/.claude/skills/tk-studio/skills/*` the same is not shown. If it does, 18 skills cost roughly 1.5-2 % of a core per idle session on this host, times the number of persistent sessions.
- **Mitigation the conclusion would need:** measure with `psutil` as the issue did, before and after, on this machine.

### F8. `~/.claude/skills` is also the claude.ai skills-sync working directory, which has a record of moving user folders to `.trash`
- **Attacks:** placing the installer-owned folder in `~/.claude/skills/`.
- **Evidence:** CHANGELOG 2.1.280: "Fixed skills in `~/.claude/skills/` being moved to `~/.claude/skills/.trash/` when a `manifest.json` in that folder listed their names" [source: https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md, Anthropic]. #98526 (2026-09-30): sync "every removed copy is moved into `~/.claude/skills/.trash/<epoch-ms>-<pid>-<suffix>/`" on a 10-minute interval when two accounts disagree [source: https://github.com/anthropics/claude-code/issues/98526]. `~/.claude/skills/synced/` exists on this host.
- **Weight:** weak. The defect was fixed and the churn case needs two accounts; but the folder shares a namespace with code that deletes directories by name, which the marketplace cache does not.
- **Mitigation the conclusion would need:** the drift check already covers disappearance; add `.trash` recovery to the installer's self-heal.

### F9. The conformance suite's `installed_plugins.json` check has no equivalent record, only a CLI listing
- **Attacks:** "no install record" against "the studio's conformance suite today checks ... via `~/.claude/plugins/installed_plugins.json`".
- **Evidence:** "`installed_plugins.json` records each install with its `scope`, `installPath`, and `version`"; skills-dir plugins are not installs. The sweep that cleans orphaned versions "runs only while `installed_plugins.json` records at least one install." [source: https://code.claude.com/docs/en/plugins/loading]. Counter-evidence: `claude plugin list` "prints session-only and skills-directory plugins in their own sections with `Status: ✔ loaded` or the load error" [source: https://code.claude.com/docs/en/plugins/create]; #100448 shows the block verbatim ("Skills-directory plugins (.claude/skills/*): ... Version: 0.1.0 Scope: project Path: ... Status: ✓ loaded"); local probe: `claude --plugin-dir <scratch> plugin list --json` emitted the uninstalled plugin as `{"id":"zz-redteam-probe@inline","scope":"session","enabled":true,"installPath":...}` and `claude plugin details zz-redteam-probe` printed its component inventory and token cost; `claude plugin eval --help` says "installed and skills-dir plugins both resolve".
- **Weight:** weak. The check must be rewritten, but `claude plugin list --json` is a machine-readable replacement and validate/details/eval all resolve in-place plugins.

## Searched for and not found
- Any deprecation or "development-only" wording for `@skills-dir` in the docs or CHANGELOG. The opposite: 2.1.157 "Plugins in `.claude/skills` directories are now automatically loaded, no marketplace required" and `claude plugin init` scaffolds there; the origin name `skills-dir` is reserved alongside `inline` and `synced`.
- Any statement that `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` or `agents/` are withheld from skills-dir plugins. The manifest reference says `${CLAUDE_PLUGIN_ROOT}` substitutes "Anywhere in the Markdown body" of skill, command and agent content and "On Windows, the substituted paths use forward slashes". The open Windows `CLAUDE_PLUGIN_ROOT` defects found (#98498 MSIX, #95673, #68295/#70150/#76973 closed) all concern hooks or stdio MCP servers, which the conclusion drops.
- Any report of `uv run` from a skill body failing on Windows, or of Git Bash vs PowerShell breaking a skills-dir plugin. The skills page's only Windows gate is `shell: bash` without Git Bash, which this host has.
- Any report that user-scope skills-dir plugins fail in `-p` or `--bg` sessions. #66039 (2026-06-07) is the reverse: `--bg` lost project-scope marketplace plugins while "User-scope-installed plugins from the same marketplace ARE listed."
- A maintainer post-mortem on distributing a large skill set outside a marketplace. Superpowers lists marketplace/plugin-manager installs only; no project was found that moved from marketplace to installer-written `~/.claude/skills`.
- Evidence that staying on the marketplace is safer for updates. Found the reverse: #93108 (update compares only the version string), #17361 (cache never refreshes), #94547 (truncated cache when the same plugin@version is installed at user and project scope, which is this host's current state).
- Whether a user-scope skills-dir plugin loads under `--setting-sources` lists that omit `user`, or under `CLAUDE_CONFIG_DIR` (closed issues #31649/#36172/#20993 show `~/.claude/skills` was once hard-coded; no current report).
- The `${CLAUDE_PLUGIN_DATA}` id form for a skills-dir plugin (whether it is `tk-studio` or `tk-studio-skills-dir`); the manifest reference only gives the sanitisation rule.
