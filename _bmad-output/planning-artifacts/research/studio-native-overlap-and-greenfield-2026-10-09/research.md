# Research: native overlap, the plugin question, Jev, and a greenfield studio

**Decisions this research serves:** C, whether tk-studio stays a Claude Code plugin; D, the overlap map between what the studio built and what Anthropic or the ecosystem now ships, Jev included; E, the greenfield design.

Every `[n]` resolves in the source appendix (§12). The digests under `digests/` carry the full source lists; the appendix lists the sources this report leans on. Validation was `normal`: load-bearing claims were spot-checked where a second source was within budget, and two fresh-context red teams attacked the plugin verdict and the greenfield stack (§10). Internal evidence (C6) is cited to repository files, not the web.

## 1. Executive summary

### Decision C: stop distributing through the marketplace; keep the plugin form

**The evidence says: keep tk-studio a plugin in form, drop the marketplace as the delivery path.** The installer writes a *skills-dir plugin* (a folder with `.claude-plugin/plugin.json` under `~/.claude/skills/`) that Claude Code loads as `tk-studio@skills-dir`: namespaced, agents bundled, loaded in place, never copied, no clone, no install record [2][3]. Three findings drive it:

1. **The plugin system gives the studio almost nothing it uses.** Anthropic's own docs: skills, subagents, hooks and MCP servers "all work on their own, without a plugin"; the plugin-only surface is `bin/`, monitors, channels, `userConfig`, workflows, mods and `plugin eval`, and monitors run only in interactive sessions while claude.ai and Cowork refuse any plugin with `bin/` [1][4]. The studio's plugin uses none of those: ten skills substitute `${CLAUDE_PLUGIN_ROOT}` to find their scripts, two thin agents are bundled, and the drift check reads the install record [79].
2. **The marketplace is what costs.** The whole repository is cloned on add and refresh, one cache copy is kept per version, third-party marketplaces never auto-update by default (and run on a random delay of up to ten minutes when they do), a project-scope enable does not install, and 2026's Windows issue stream lands on this path (Defender `EBUSY`, drive-letter casing fixed only on 2026-10-08, case-sensitive `projectPath` still open) [3][5][6]. The run-1 red team added the live MAX_PATH failure on this Windows build.
3. **Comparable tools treat the marketplace as the secondary path.** BMad leads with `npx skills add`; Ruflo labels its plugin path "lite, slash commands only" and its installer "production"; SuperClaude ships an installer with the plugin route "planned, no ETA" [7][10][9].

The one open mechanic was settled by Tim's local probe: a skills-dir plugin receives `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_SKILL_DIR}` as forward-slash paths on this Windows box [80], so the ten skills need no change. The red team's findings and the three rules they added are in §10.

### Decision D: the overlap map

**The ecosystem now covers the studio's commodity half and none of its differentiating half.** Official Claude Code covers session hosting (agent view and the background daemon, research preview, 2026-05), the consult leg (the advisor, experimental, subscription-billed), phone steering and approvals (Remote Control, channels), raw metering (`/usage`, `/cost`, OpenTelemetry), review (`/code-review`, `ultrareview`) and research fan-out (`/deep-research`) [29][33][27][36]. Nothing official covers a durable job queue with a public contract, a pacer or budget bands, a story-aware review gate, the measurement ledger and evolve loop, a drift check against a pinned third-party base, the planning adapter, a conformance suite, the office, or the engagement loop [27][29][36]. The unofficial map says the same from the other side: bmad-loop is the studio's own engine and is converging on native Windows; Paperclip has the best queue, budgets and approvals but no native Windows and breaking changes every fortnight; Munder Difflin and agent-office are working offices with the wrong unit of display; ccusage parses what the meter parses; nothing anywhere implements quote-before-run, the evolve loop, the adapter or a conformance suite [43][41][42][45][61].

**Jev** is TypeSafe AI's typed decision model (a state plus closed questions returns a choice with probabilities in 70 to 500 ms by the vendor's figures; no independent benchmark exists) [13][14]. The Claude Code routers built on it are loopback proxies that forward the OAuth token and rewrite the model per turn; Claude Code's legal page says developers "may not collect, store, or intermediate Claude.ai credentials or session tokens" and that Max limits "assume ordinary, individual usage"; Anthropic documents no per-model quota weighting, the routers' savings are API-dollar figures, and the most careful author withdrew his headline claim after measuring routing capturing 3 percent of the headroom [22][23][17]. Verdict: not for model routing. The fit, if any, is a sub-cent typed-decision oracle behind the gate (sizing, finding severity, "is this deviation material?") in shadow mode, with a vendor, a secret per sandbox and prompt text leaving the microVM as the price [14][19].

### Decision E: the greenfield design

**Built from scratch today, the studio would have the same shape it has, with thinner commodity layers and the spend moved to the three things nothing provides.** The outside assistant, given no knowledge of what exists, proposed: Claude Code headless (`claude -p`, stream-json, `--json-schema`, `--permission-prompts none`) under a `setup-token` subscription token; Docker Sandboxes microVMs for bypass on Windows; a small purpose-built service with a job table, leases and reboot restart, one Claude per story in a worktree; per-class model and effort with `opusplan`, the headless advisor and fallback chains; `/code-review` per story and `ultrareview` at milestones; OpenTelemetry tagged per story plus stream-json usage, reported as list-price-equivalent and window share; ntfy; a Next.js static export over SSE; one plugin plus a separately installed service [62][65][63][64]. That is the current studio minus the pieces the internal record calls commodity (sign-in and OAuth, the plugin release plane, sandbox keepalive glue, miniyaml, process-tree plumbing) [70][74][77] and plus the three builds no one has made: the quote-before-run engagement loop, per-story metering under a subscription, and the story-aware office with partial-delivery reporting [63][61]. A rewrite buys none of that; an incremental thinning does. The two riskiest adoptions are the research-preview daemon and Docker Sandboxes' undocumented headless contract, and the lesson the internal record presses hardest is to verify where production runs: Windows [29][66][70].

## 2. C1: plugin or not

**What a plugin uniquely provides** (official docs, current to within a week [1][2][3][4]): namespacing (`tk-studio:<skill>`), `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}` substitution in hooks, MCP configs and skill bodies, bundled hooks, agents and MCP enabled as one unit, `bin/` on the Bash PATH, monitors, channels, LSP, themes, workflows, mods (v2.1.287), `userConfig` with secure storage, one-unit enable and disable with context-cost reporting, a Claude-computed version with `claude plugin update`, `claude plugin eval`, the `extraKnownMarketplaces` trust auto-prompt, claude.ai sync and directory listing. **What a skills folder provides without a manifest:** skills with `${CLAUDE_SKILL_DIR}` and `${CLAUDE_PROJECT_DIR}`, standalone agents under `.claude/agents/`, hooks in `settings.json` or skill frontmatter, `claude plugin validate` on the directory [2][4].

**The middle path.** A folder containing `.claude-plugin/plugin.json` under `~/.claude/skills/` or `.claude/skills/` loads as the plugin `<name>@skills-dir`, "so it can bundle agents, hooks, and MCP servers"; it is namespaced, loads in place and "is never copied", and needs no marketplace or install record; `claude plugin init` has scaffolded into `.claude/skills` since v2.1.157 (June) [2][3][5]. Project-scope skills-dir plugins load only from the primary working directory after the trust dialog, skip bundled MCP and never load monitors; "Personal-scope plugins have none of these restrictions" [3]. Not stated anywhere: whether `${CLAUDE_PLUGIN_ROOT}` and `bin/` apply to a skills-dir plugin [4].

**What being a marketplace plugin costs** [3][4][5][6]: a clone of the whole repository on add and refresh with a 120 s budget and user-side-only sparse checkout; one copy per version with `${CLAUDE_PLUGIN_ROOT}` moving and a 14-day orphan sweep; a manifest version that pins until changed; auto-update off by default for every non-Anthropic marketplace and on a random delay of up to ten minutes when on; project-scope enablement that does not install (every machine and sandbox image installs at user or local scope); `command` sources that re-run every session under `cmd.exe` on Windows; Node dependencies auto-installed into the cache only; and the 2026 Windows issue stream (Defender `EBUSY`, bare `npx` `ENOENT`, drive-letter casing fixed v2.1.295 on 2026-10-08, case-sensitive `projectPath` open, SSH-less installs fixed v2.1.296).

**How comparable tools distribute** [7][8][9][10][11]: BMad lists `npx skills add` first and keeps its Claude Code marketplace secondary, with `bmad setup` driving updates; the `npx skills` CLI installs SKILL.md folders into 79 agents with no hooks, agents or namespaces; Ruflo (74k stars) documents its plugin path as "lite, slash commands only" and its CLI installer as "Production use"; SuperClaude (24k) ships `pipx install` plus an installer and has no plugin route; Anthropic's own skills repository ships as a marketplace.

**Direction of travel** [1][5]: docs keep skills as the content unit and plugins as packaging; the newest surfaces are plugin-only and fast-moving (mods with a 247-comment thread, claude.ai plugin sync v2.1.275, `--marketplace` shorthand v2.1.292); nothing retrieved makes plugins required for skills, agents, hooks or MCP, and the plugin-only surfaces do not reach unattended or claude.ai sessions.

**Internal fact** [79]: the studio's plugin uses `CLAUDE_PLUGIN_ROOT` in ten of eighteen skills, bundles two agents, and uses no hooks, MCP, monitors, `bin/` or `CLAUDE_PLUGIN_DATA`; the drift check gates on `installed_plugins.json` and the catalog.

## 3. C2: Jev and auto-model routing

**What Jev is** [13][14]: TypeSafe AI's "System One" model, launched 2026-09-15 in early access with $40 million raised; the API takes a `state` and typed questions (Choice, Score, Noul) and returns a decision with a probability distribution and a confidence, never text; vendor-claimed 70 to 500 ms and $0.042 per million input tokens; no independent benchmark exists in anything reached, and an unattributed "68 percent accuracy" figure circulates. OpenRouter's `typesafe/jev-router` (2026-09-25) picks a model and reasoning effort per request behind an OpenRouter key, which is off the table under "never an API key" [15].

**The Claude Code routers** [16][17][18][19][20]: four of five are loopback proxies set through `ANTHROPIC_BASE_URL` that forward the OAuth header untouched and rewrite `model` once per fresh user turn; tool-loop continuations keep the tier; sub-agents are pinned separately; all fail open. The original (gargpratyush, 578 stars) has been idle since 2026-09-19 with 44 open issues; flaviusapop documents sub-agents still routed after a manual pin and that "Every CLI's UI shows the model it asked for, never the one the proxy routed to"; @ediri runs on Mac and Linux only; 33Audits defaults to a local heuristic with no key, and withdrew its "75 percent cheaper" claim after finding a malformed request, its surviving measurement being that default routing captured 3 percent of the headroom because the cache guard pins a conversation to its first tier. The one non-proxy, drewpayment's hooks-module plugin, needs the early-access `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` flag and a TypeSafe or Vercel key, and asks two questions per turn (capability tier, risk of a careless answer). All but the local heuristic send the turn text to TypeSafe, whose retention terms were not reached.

**Policy, quoted** [21][22]: the Claude Code legal page says OAuth "is designed to support ordinary use of Claude Code and other native Anthropic applications", that developers "may not collect, store, or intermediate Claude.ai credentials or session tokens", that "Advertised usage limits for Pro and Max plans assume ordinary, individual usage", and that "The Claude Code binary must not be modified"; gateways through `ANTHROPIC_BASE_URL` are a recognised deployment shape. The Consumer Terms (2025-10-08) bar access "through automated or non-human means" except through an API key or where Anthropic permits. Secondary coverage reports enforcement against third-party harnesses in February and April 2026 (not fetched) [26]. **Quota** [23]: the Pro and Max support article documents a five-hour and a weekly limit shared across Claude and Claude Code and a separate weekly Fable limit, and nothing about per-model weighting; every router's savings are API list-price dollars.

**Native alternatives** [24][5]: no automatic model routing by difficulty exists in Claude Code as of v2.1.296, and the model-config page says so. What exists: `/model` aliases including `opusplan`; effort levels low to max (default medium on the 5.5 models, with Anthropic stating Opus 5.5 at medium matches or exceeds Opus 5 at high); `model` and `effort` in subagent, skill and command frontmatter; `CLAUDE_CODE_SUBAGENT_MODEL` and `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL` (v2.1.296); the Agent tool's `effort` parameter (v2.1.292); fallback chains on overload only; auto mode as a permission classifier; `/advisor` with a saved advisor model (v2.1.295).

**How a studio would use typed decisions** [14][19]: not for routing (the routing table already sizes legs, proxies break transcript pricing and intermediate the token); as a decision oracle behind the gate for sizing a request XS to XL at intake, classifying review-finding severity and the fuzzy escalation sub-questions, each a narrow Choice or Score thresholded in studio code and run in shadow mode first; calibration from outcomes (33Audits' content-free ledger with bounded drift) is a pattern the studio can apply to its own routing table without Jev.

**Benefits and drawbacks.**

| Option | Benefits | Drawbacks |
|---|---|---|
| Adopt a Jev router for the unattended legs | Cheapest tier per turn, fail-open; the plugin form adds a risk signal; the local-heuristic form needs no key [17][19] | Re-decides inside legs the table already sized; proxies intermediate the OAuth token and show the wrong model in transcripts, breaking the meter; a key in every microVM; turn text leaves to a second vendor; no evidence routing stretches a Max week; the most-starred router is idle; the plugin needs an early-access flag [16][18][22][23] |
| Jev as a decision oracle behind the gate | No proxy, no token exposure, no change to model selection or pricing; sub-cent and sub-second; typed probabilities the gate can log; sizing and severity are low-blast-radius first uses [14] | A vendor and a secret per sandbox; prompts leave under unread terms; no independent accuracy evidence, so every use needs a shadow-mode evaluation; the objective triggers gain nothing [13][14] |
| Stay native | Per-leg `model` and `effort`, the Agent tool's `effort`, `opusplan`, fallback chains and the advisor express everything the table needs; zero policy, credential or transcript-fidelity risk; effort is the first lever by Anthropic's own data [24][33] | No per-turn difficulty signal; escalation stays rule-based; per-model quota remains unknown either way [23] |

## 6. C5: the greenfield design

**Primitives that exist** (status, subscription, unattended, Windows) [62][65][63][64][66][67]: `claude -p` with stream-json in and out, `--json-schema`, `--permission-prompts none` (v2.1.259, for unattended hosts) and `--max-budget-usd` (GA, subscription through `setup-token`); the background daemon (research preview, Windows fixes through v2.1.295); `/loop` (session-bound, 7-day expiry); `/goal` (GA, pauses at usage limits); dynamic workflows (all paid plans, no mid-run input, no usage-limit pause headless, same-session resume only); routines (cloud, fresh clone, 1-hour minimum); the built-in Bash sandbox (macOS, Linux, WSL2; "On native Windows, Claude Code runs commands unsandboxed"); `sandbox-runtime` (beta, no native Windows); Docker Sandboxes (Windows 11 with the Windows Hypervisor Platform, winget install, free local compute, named by Anthropic as able to run Claude Code, but with no supported-agent list, status label or credential-passthrough statement on Docker's pages); worktrees; effort levels and `opusplan`; the advisor's headless text form; `/code-review` and `claude ultrareview --json`; OTel with `OTEL_RESOURCE_ATTRIBUTES` on every metric (subscription cost population not stated); ntfy; Paperclip; Backlog.md; the plugin tooling.

**What does not exist, with what was searched** [63][64][36][41][61]: a quote-before-run engagement loop; per-story metering under a subscription (Anthropic: the session cost "isn't relevant for billing", `/usage` attributes by skill not story, OTel gives list-price per request); a story-aware office; partial-delivery reporting; a deviation-scoring gate; a conformance suite for headless plugin behaviour (`plugin eval` asserts nothing about `-p`); a GA, crash-recovering, Windows-native supervisor on a subscription.

**Reference architectures** [35][41][54]: Managed Agents (agent, environment, session, events over SSE; API-only), Paperclip (server, adapters, React UI), Omnara (pivoted from a remote-control app to a control plane). Every one splits a durable control plane (state, queue, budgets, approvals, events) from swappable runtimes behind an adapter and puts the UI on the control plane's event stream; none puts the loop engine inside the UI process.

**Benefits and drawbacks of the proposed stack against a studio built around its own engine, supervisor and routing**: the agent loop, tools, permissions, sessions, hooks, review skills and workflows are Anthropic-maintained and ship weekly; subscription economics are respected by construction; isolation follows Anthropic's own guidance; the only new code is the engagement layer. Against: research-preview dependencies (daemon, channels, `sandbox-runtime`, OTel traces) can change; headless loses the interactive safety nets (workflow agents fail at usage limits in `-p`), so the service must detect limit errors and reschedule to the window reset; metering is estimate-grade; Paperclip and Docker Sandboxes carry adoption risk; the SDK page's login restriction targets third-party products and does not address a private one-maintainer tool [62][36][63][41].

## 7. C6: lessons from what we built (internal record)

**Decisions that moved** [70][71][72][74]: ClaudeOS as the driver was retired after six weeks ("extract, do not adopt"); the separate supervisor repository (2026-09-27) is now proposed to fold back; "no bootstrap script" (AD-1, 2026-07-26) gave way to one installer as a hard gate; "the studio grows no UI and no daemon" gave way to the gamified front end as the primary surface; Hermes moved from front door to an agent the front end wraps; the plugin distribution (AD-1) is under O5; the host permission mode moved four times in two months (bypass, auto, allow rule, folder trust); the zero-fork line was bent by base patches; the session leg moved Opus to Sonnet and back to Opus 5.5 for the trial.

**Five lessons that constrain a from-scratch design** [70][73][75][74]: verify where production runs (the gate is Linux-only while Windows is the host; three Windows-only defects reached branches and every PR now needs an attended host run); the unattended-Windows envelope is non-negotiable (MSIX AppData virtualisation, `claude -p` hanging under Task Scheduler, silent REPL exit, transcript GC, folder trust per repo root that headless cannot answer, CRLF through sandbox mounts, MAX_PATH from 150-character spec names, `.cmd` not spawnable, junction hazards); billing is the Max subscription only and bypass lives only in Docker Sandboxes; engine lifetime and the project model must be owned by a service (engines died with a host `sbx exec`; one lock per checkout and project root equal to checkout root block two loops on one tree; launch owns neither its bootstrap output nor a paused story's close-out); status-block discipline is load-bearing (every self-inflicted outage was diagnosed from a `blocked` block; surfaces that asked questions or ended `complete` on a refusal were the recurring defect class).

**Mechanisms that proved their worth** [77][72][76][74][70]: the measurement membrane (23 proposals, 14 adopted, Epics 11 to 17 implement named proposals; 16 loop-deficiency entries drove the hole fixes); the meter and measured routing (review share of 40 to 53 percent named the routing lever; the session leg's spend halved on evidence); the supervisor's durable queue and restart rule, proven live on 2026-10-09 and after the 2026-10-08 reboot; conformance through a driver (ISS-002); the drift check (ISS-004, PROP-015/016/017); base patches over an unforked upstream.

**Commodity the studio would rather not own** [74][72][77][75]: sandbox and daemon keepalive glue, git identity, hook rewriting, NuGet rules; the plugin release plane (two epics; version gate, roster, archive zip, catalog lockstep, `installPath` quirks); sign-in, OAuth, TLS, cookies, certificate renewal; miniyaml and the stdlib-only defect class; process-tree kill and race plumbing; patches over upstream bmad-loop behaviour; the Jira, backlog-md and migrate adapters built ahead of any live consumer (inference). **Differentiators** [78][77]: jobs as data with budget guards and the status block, the measurement membrane, the deficiency and deferred-work ledgers, conformance as a shipped artifact, the drift check, the meter and review-share lever, the durable queue with one resume per run, base patches, the Windows unattended runbook, and the engagement vision.

**Structural holes a rewrite designs away** [73][74]: the gate not on the production OS; engine lifetime bound to a host exec and a daemon's start context; project root equal to checkout root with one lock per checkout and no worktrees; a permission model dependent on an interactive trust dialog and a classifier; launch not owning bootstrap output or close-out; file names from title slugs; budget truth split between the policy template and the bands; formats not pinned at onboarding; runs started outside the queue invisible to the pacer; cost not carried across a resume; TLS not service-managed; worker ownership not tied to a process group; shipped surfaces able to outrun the version gate; exit-code-only headless postures; the plugin plane's drift and "Unknown command" headless.

## 8. Cross-dimension insights

1. **The plugin question and the installer answer each other.** C1's skills-dir plugin needs an installer to write and version it; run 1's installer (bootstrap, meta-CLI, roster) exists for the service and front end already. One installer writing one folder removes the marketplace clone (run-1 red team), the per-version cache, the no-update-all problem, the plugin release plane's two epics of upkeep (C6) and the sandbox provisioning step that installs the plugin at user scope today. The price is that Claude computes no version, which the roster and drift check already own.
2. **Official overlap is strongest exactly where the internal record calls the work commodity.** Session hosting, phone steering, approvals, raw metering, review fan-out and research fan-out are covered (C3); sign-in and OAuth, sandbox keepalive and transcript backup are the things C6 says the studio would rather not own. The differentiators (queue contract, pacer and bands, story-aware gate, ledger and evolve loop, drift against a pinned base, adapter, conformance, office, engagement) have no equivalent anywhere (C3, C4).
3. **Jev confirms the routing table, not a router.** The only measured router capture is 3 percent, the policy text is against intermediated tokens, quota per model is undocumented, and the studio's escalation triggers are objective (C2). The one place a typed decision helps is the fuzzy judgment the gate makes today in prose.
4. **The greenfield stack is the current studio with thinner commodity layers.** The outside proposal and the inside record converge: keep the shape (headless Claude in microVMs under a durable service with an event-stream front end), adopt native primitives for hosting, consult, review, metering and research fan-out, and spend on the three builds nothing provides (C5, C6). That is an evolution plan, not a rewrite.
5. **Windows is the recurring tax, again.** Paperclip is macOS, Linux and WSL2; bmad-loop's README still says WSL; the built-in sandbox and `sandbox-runtime` skip native Windows; the daemon needed fixes through v2.1.295; @ediri's router is Mac and Linux (C2, C3, C4, C5). Every adoption carries a "prove it on the box" step, which is C6's first lesson.
6. **Terms are the unexamined dependency.** Three dimensions touched the same clause: "ordinary, individual usage" of a subscription and the ban on intermediating tokens (C2, C3, C5). The studio's unattended multi-sandbox use is not addressed by anything retrieved; the red team on the greenfield stack was asked to hunt for enforcement evidence (§10).

## 10. Contrary evidence

Two fresh-context red teams were launched (each received only its conclusion and a search budget): one against the skills-dir plugin verdict (§2, R1), one against the greenfield stack (§6, R7). **The plugin verdict (digest `digests/C1-redteam-1.md`, 9 findings, 24 sources).** Three findings are material or moderate; R1 survives with three added rules.

1. **A same-named marketplace install silently shadows the skills-dir copy (material).** The loading reference's name-conflict order puts an installed marketplace plugin above a skills-directory plugin of the same manifest name, which then shows only as "Not loaded" in the Errors tab; this host has `tk-studio@tk-studio` installed at both user and project scope, and today's install path writes `enabledPlugins` and `extraKnownMarketplaces` into consuming projects' committed settings [3][40]. **Rule:** the installer uninstalls every marketplace copy of `tk-studio` and the repository drops the committed `extraKnownMarketplaces` and `enabledPlugins` entries; developers use the installer too (a link mode pointing at the checkout), not a second marketplace copy.
2. **Docker Sandboxes mount the host's `~/.claude/skills` into the microVM as an experimental shared store** (`readonly`, `readwrite` or `off`, fixed at creation; a `readwrite` sandbox "can modify skills that other sandboxes load"; the two page renderings disagree on the default) [66]. **Rule:** sandboxes consume the host folder through that mount set `readonly`, so one install serves the host and every sandbox; the drift check covers the sandbox store state under `%LOCALAPPDATA%\DockerSandboxes`.
3. **Skills-dir is documented under "Develop without a marketplace"; the sharing page lists only a zip, a marketplace or Anthropic's directory (moderate)** [1][2]. The only large-skill-set precedent checked (Superpowers) installs through marketplaces. **Weighed:** a positioning risk, not a capability gap; no deprecation signal exists and `claude plugin init` targets the form; accepted, with "watch for a deprecation" in the staleness work order.

Also noted: user-scope skills-dir plugins bypass every trust and enable step (a scaffolded one altered every session, #91863), and a Windows report measured about 45 syscalls per second per skill directory under `~/.claude/skills` against far less for cached plugins (#95306) [6]. Weighed: the installer is the trust step (it is the only writer), and the syscall cost is one more "prove it on the box" item. Not found by the red team: any withholding of `${CLAUDE_PLUGIN_ROOT}` or agents from skills-dir plugins, `uv run` failures from skill bodies on Windows, user-scope failures in `-p` or `--bg`; marketplace update defects it found cut in the verdict's favour.

**The greenfield stack (digest `digests/C5-redteam-1.md`, 23 calls, several findings material).** R7 survives as an evolution plan; R8 is promoted from "read the terms" to a standing risk.

1. **The "Max subscription, never an API key" premise is the fragile part (material).** The legal page says Pro and Max limits "assume ordinary, individual usage" and that developers, "including those using the Agent SDK, should use API key authentication", with enforcement "without prior notice", while explicitly permitting sign-in to the unmodified binary with one's own subscription [22]. The policy moved four times in 2026 (January bans, a February clarification, the 2026-04-04 third-party cut-off, a May 13 announcement of API-rate "Agent SDK credits" covering `claude -p`, paused June 15), and the headless docs say `--bare`, which "never reads OAuth credentials", "will become the default for `-p` in a future release" [26][40]. **Weighed:** nothing retrieved forbids own-seat scripted `claude -p`, and no suspension for parallel headless use alone was found; but the studio's economics rest on a clause Anthropic has rewritten four times this year. R8 becomes: record the reading in the ADR, keep an API-key fallback leg designed (not built), and watch `--bare` and the credits programme in the staleness work order.
2. **Headless runs fail rather than wait at usage limits, and every parallel story shares one window (material).** Workflows do not pause in `-p`; `--max-budget-usd` caps a client-side list-price estimate that is "not relevant for billing" on Max; issue #38335 (877 comments, open) reports Max limits exhausted abnormally fast; #89798 a workflow crash at the session limit; #100882 headless usage control without reset times [36][63][6]. **Weighed:** the service must own limit detection and rescheduling to the window reset (already R7's rule), and the pacer's job is to keep parallel stories inside one window, which the existing supervisor already does and a native daemon does not.
3. **Docker Sandboxes on Windows is a 0.x product with an active failure backlog (material).** 56 open Windows issues in the release tracker, including sandboxd failing to start after a Fast Startup cycle (2026-10-07), docker.sock self-connect, empty mounted workspaces, I/O performance and Remote Control broken inside a sandbox; versions 0.43 to 0.47 in three weeks; no GA statement [66][67]. **Weighed:** this is the studio's lived experience (holes 7 and 13); the sandbox tier stays, its glue stays studio-owned, and "sandbox stability" joins the staleness work order.

Also noted: Paperclip stores and renews Claude tokens server-side, which the legal page names as prohibited, and its Windows subscription fixes are unmerged pull requests [41][22]; `--resume` can spawn twin processes (#75761) and Windows children can be orphaned (#76353), which attack lease and crash recovery [6]. Weighed: Paperclip moves from "wrap candidate" to "borrow ideas only" (R3 unchanged), and the supervisor's process-group ownership (DW-3) stays on the hole list.
