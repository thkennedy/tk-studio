## Executive answer (10 lines)

1. **What Hermes gives the studio that would otherwise be built:** a running Telegram front door with allowlists and DM pairing (already configured here, home channel = Tim's DM); an OpenAI-compatible API server with a Runs API (SSE events, approvals, idempotency keys, stop) and a Sessions REST API; a per-profile "agent roster" (profiles = Bots) with inter-agent DMs (`message_agent`), cross-machine peers (`hermes peer`), an A2A server/client, and a durable SQLite Kanban board with a dispatcher, review loop, dependency graph, dashboard REST and live WebSocket; skills with slash-command invocation and `.env`-backed secrets; bounded MEMORY.md/USER.md memory plus FTS5 session search; cron with deliver-to-channel; `hermes send` for scriptable Telegram pushes without a gateway or LLM.
2. **Hard constraint it satisfies:** every job-dispatch surface Hermes exposes runs a *Hermes* agent turn (API server, webhooks, kanban workers, A2A). None of them can be pointed at the Bun supervisor as a worker. So "Hermes must not run `claude -p` for pipeline work" is enforceable only by convention (toolset limits, approval mode), not by a registration mechanism.
3. **"Agents registered so it can see them" means profiles.** A Hermes agent is a profile directory; Bot Mode, the kanban orchestrator, `message_agent`, and `hermes peer` all enumerate profiles (plus peers' profiles). The supervisor and `claude -p` workers cannot be registered as agents; the kanban "external CLI worker lane" for Claude Code/Codex is documented as *not yet a paved path*. On this box there is currently **only the default profile** (no `profiles/` directory).
4. **What it costs to adopt:** a second always-on Python process (gateway, ~Scheduled Task on Windows) with ~25k commits/2 months of upstream churn, weekly stable releases, and a main-branch install here; a Nous Portal subscription (provider `nous`, model `anthropic/claude-opus-5.5`); one more auth and trust boundary on the box (API key, webhook HMAC, dashboard token, `local` terminal backend with no sandbox on Windows, Tirith unavailable natively); and `auth.adopt_external_logins: true`, which lets Hermes borrow and refresh Claude Code's OAuth credentials, a documented way to invalidate the other program's login.
5. **What it cannot do (today, native Windows):** embed a chat into a Next.js page without a server-side proxy (API server is the only documented path; dashboard chat tab is contradictory across docs and the TUI gateway WebSocket is called internal); deliver cron/webhook results to a generic HTTP URL (only chat platforms, GitHub comment, log; `hooks.outbound` is notify-only); run a sandboxed terminal natively (needs Docker/SSH/WSL); or hand an approval decision to the supervisor except through its own API (`/v1/runs/{id}/approval`) or an MCP bridge.
6. **Cleanest integration if Hermes stays:** Next.js server route -> `127.0.0.1:8642` (API server, bearer key kept server-side) using `/v1/runs` + `/v1/runs/{id}/events` or `/api/sessions/{id}/chat/stream`; one user skill (`tk-submit`) that POSTs job JSON to the supervisor via `terminal`/`execute_code` with a `required_environment_variables` secret; supervisor -> Telegram via `hermes send` (no gateway needed) or via a signed inbound webhook route with `deliver: telegram`.
7. **Cleanest integration if Hermes goes:** nothing in the engagement loop depends on Hermes-only primitives; the Telegram gateway, memory nudges, and skills hub are the pieces with no cheap substitute.
8. **Decision-relevant churn:** v0.21.6 (2026-10-08) is the first cut of a new stable pipeline, rolls up 2,106 PRs since 2026-09-24, fixes four dashboard-auth issues (rate-limit bypass via spoofed `X-Forwarded-For`, login-code redirect session takeover), and defers curated notes to v0.22.0.
9. **Billing stance for the hub:** Nous Portal subscription covers model + Tool Gateway; Anthropic OAuth is documented as Claude Max + purchased extra-usage credits only (Pro not supported), and always bills as extra usage.
10. **Recommendation shape (not a ruling):** Option C (Hermes as optional adapter behind a supervisor-owned chat) preserves the Telegram/skills/memory value while keeping the supervisor as the single dispatch authority; Option A makes Hermes a second brain with its own queue (kanban) that duplicates the supervisor; Option B is cheapest to own but rebuilds Telegram allowlisting and pairing.

## 1. "Agents registered so it can see them": what Hermes means by agents

- A **profile** is the persistent home for one agent's config, memory, skills, credentials and sessions under `~/.hermes/profiles/<name>/`; an **agent** is the running instance of a profile; a **Bot Mode bot** is a profile the desktop roster presents with a title/avatar and a pinned "Bot Chat"; a **messaging bot** is a platform account (bot token); a **subagent** is a `delegate_task` child conversation, not a profile. | source: user-guide/profiles.md:19-43 | confidence: high
- Bot Mode is a desktop plugin over profiles; `hermes -p <bot> chat` opens the same agent; routines are cron jobs named `[bot:<name>] …`. Creating a Bot = creating a profile with title, description, model pin, SOUL.md, per-skill/toolset/MCP enablement, and copied static API keys (OAuth logins are not copied). | source: user-guide/bot-mode.md:12-16,46-57,370-381 | confidence: high
- **`message_agent`** (bot-to-bot DM) exists only in sessions titled exactly `Bot Chat` on an install where at least one `profile.yaml` carries `ui_meta: { hermes-bots: … }`; headless installs never get it unless both markers are created by hand (`hermes -p <bot> chat -c "Bot Chat" --create-if-missing` + the YAML block). Delivery is fire-and-forget with `delivery_id`; on `api_server` sessions the reply is polled via `process(action="wait")`. | source: user-guide/bot-mode.md:173-206 | confidence: high
- The teammate roster (profile names and title/description roles) is injected into every Bot Chat system prompt; a Desktop with several Connections propagates rosters across machines. | source: user-guide/bot-mode.md:173,236 | confidence: high
- **Peers** (`hermes peer add <name> --url http://host:8377 --key <API_SERVER_KEY>`) register another machine's Hermes API server; `peer dm`, `peer run --idempotency-key`, `peer status`, `peer stop`. Once registered, the peer roster is taught to every Bot Chat and `message_agent(target="peer/profile")` works. Peer key lives in `.env` as `HERMES_PEER_<NAME>_KEY`; names/URLs in `config.yaml` under `bot_peers`. | source: user-guide/bot-mode.md:242-275; reference/cli-commands.md:532-567 | confidence: high
- **Kanban** registers no agents: `task.assignee` is matched against `hermes profile list` at claim time; the orchestrator discovers roles from `hermes profile describe` text; unknown assignees are left `ready` with a `skipped_nonspawnable` event. - **External CLI worker lane (Claude Code/Codex/OpenCode) is explicitly "not yet a paved path"**; `spawn_fn` is pluggable but wrapping exit codes into `kanban_complete`/`kanban_block`, workspace mapping and auth are per-integration work; refs issue #19931 and closed PR #19924. | source: user-guide/features/kanban-worker-lanes.md:133-139 | confidence: high
- There is **no `agents.json` and no `hermes agents` CLI**; `/agents` (alias `/tasks`) only lists running `delegate_task` subagents and background processes. | source: reference/cli-commands.md:45-110 (no such command); user-guide/features/delegation.md:433-477; reference/slash-commands.md:67 | confidence: high
- The **channel directory** (`home:channel_directory.json`) maps chat IDs to names for cron/`hermes send` delivery; it is refreshed by the running gateway and is not an agent registry. | source: developer-guide/gateway-internals.md:19; guides/pipe-script-output.md:228-236 | confidence: high
- **A2A** (Linux Foundation Agent2Agent v1.0) is the only "register an external agent" mechanism: `a2a_agents:` in config (url, bearer, capabilities) for outbound `a2a_call`/`a2a_orchestrate`; inbound Agent Card at `/.well-known/agent-card.json` on port 9900 with per-peer tokens, HMAC push notifications, prompt-injection framing. ## Benefits and drawbacks of three options

Scoring: + benefit, − drawback; "cost" = engineering/ops effort to reach the planned design (Telegram front door, office front end, engagement loop) while keeping the supervisor the only thing that runs `claude -p`.

**(A) Hermes as front door and chat brain, wrapped by the office front end**
- + Telegram gateway, pairing, allowlists, home channel, cron delivery, and `hermes send` already exist and run on this box today. | source: §3
- + Bounded memory + FTS5 session search + skills give a product-owner conversation continuity with no code; one `tk-submit` skill can POST job JSON with a `.env` bearer via `terminal`/`execute_code`. | source: §4
- + API server gives the Next.js chat a Runs/SSE/approval/idempotency contract and `/health/detailed` for the status page. | source: §2
- − The supervisor cannot be a Hermes agent; every Hermes dispatch surface (API runs, webhooks, kanban workers, A2A) executes a *Hermes* turn with Hermes tools. Preventing `claude -p` relies on toolset restriction and `approvals.deny` globs, not on architecture; the bundled `claude-code` skill is installed by default. | source: §1, §4
- − Two queues: Hermes kanban (durable, dispatcher, review loop) versus the supervisor's SQLite job queue; Hermes' is profile-only and its dashboard REST is unauthenticated. | source: §1, §3
- − Churn: weekly stables, ~25k commits/2 months, main-branch install here, four dashboard-auth fixes in the latest release; Windows native lacks sandboxing and Tirith; `adopt_external_logins` can invalidate the Claude Code login the supervisor depends on. | source: §5, §6
- Cost to adopt: low for Telegram + API proxy; medium for keeping prompts/toolsets pinned across updates; ongoing ops of a second always-on process.

**(B) Hermes dropped: front end talks to the supervisor and Claude Code directly**
- + One dispatch authority, one auth boundary, one process to run as a Scheduled Task; no third-party subscription; no borrowed-credential risk.
- + Claude Code already offers `-p --output-format stream-json`, `--resume`, Remote Control, channels; the supervisor's SSE stream can feed the office scene directly. | source: autonomous-ai-agents-claude-code.md:150-230 (Claude Code flags as documented by Hermes); inference for the rest
- − Must rebuild: Telegram bot with allowlist/pairing, push delivery, product-owner memory (Hermes' is ~1,300 tokens of files + FTS5; cheap to replicate but not free), skill-style slash commands, cron delivery.
- − Loses Hermes' multi-model Portal routing and Tool Gateway (web search, images, TTS) for the chat brain.
- Cost to adopt: medium one-off (Telegram + memory + notifications), lowest ongoing.

**(C) Hermes as optional adapter behind a chat interface the supervisor owns**
- + Supervisor stays the single queue and the only `claude -p` runner; Hermes is reached only through surfaces the supervisor controls: `hermes send` for Telegram pushes (no gateway/LLM), inbound webhook route with `deliver: telegram` for "notify Tim", API server `/v1/runs` for optional brainstorming/clarifying turns, `hooks.outbound` or an MCP server on the supervisor for events. | source: §2
- + Hermes can be removed without touching the engagement loop; its memory/skills are used only for the conversational layer.
- − Telegram *inbound* still needs a Hermes agent turn (there is no "forward raw message to URL" platform mode short of writing a platform plugin or implementing the experimental relay connector); so intake via Telegram = Hermes turn → `tk-submit` skill → supervisor. | source: §2 (webhooks/relay/plugins)
- − Two processes and two auth boundaries remain; the `claude-code` skill and `adopt_external_logins` must be disabled explicitly; API server must be enabled and keyed.
- Cost to adopt: low-medium; guardrails: `platform_toolsets.telegram` minus terminal/code, `skills` allowlist, `approvals.mode: manual`, `auth.adopt_external_logins: false`, API server on loopback only, dashboard loopback only.

Facts the ruling should not ignore: (1) "registered agents" in Hermes are profiles, and the supervisor/`claude -p` workers cannot become one; (2) the only Hermes→external HTTP pushes are notify-only outbound hooks, script-only cron, or a custom plugin; (3) native Windows has no sandbox and the docs disagree about the dashboard chat tab; (4) `adopt_external_logins` is a live cross-tool credential hazard on this box.
