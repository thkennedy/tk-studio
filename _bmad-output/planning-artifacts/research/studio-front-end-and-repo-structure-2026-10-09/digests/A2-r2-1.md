## Answers per lead

1. Claude Code does not document a git-fetch-vs-reclone distinction per plugin source; what it documents is that every install has a computed version and an update is applied only when that version changes: "`claude plugin update` and background auto-update compute the version again and don't replace the cached copy when it matches what `installed_plugins.json` records" [https://code.claude.com/docs/en/plugins/loading]. The version is "The `version` field in the plugin's manifest" first, then the marketplace entry, then for `github`/`url`/`git-subdir` "The commit SHA of the source, shortened to 12 characters" (git-subdir also hashes the subdirectory path) and for `archive` "The SHA-256 digest ... the `sha256` pin in the marketplace entry, or the digest of the downloaded file when there is no pin" [same]; the only re-fetch behaviour spelled out is for the marketplace clone, which is cloned again and swapped when the background check "finds new commits, or fails because it can't reach or authenticate to the remote" [https://code.claude.com/docs/en/plugins/host-marketplace]. Hosted-file limits: `marketplace.json` 5 MiB / 10 s; archive zip 256 MiB / 120 s / at most five `https://` redirects; extraction 100,000 entries, 512 MiB per file, 1 GiB total, 50x ratio; `archive` requires v2.1.224+ and "Pin each archive with `sha256` so Claude Code refuses a changed download" [host-marketplace]. Users stay current via auto-update (off by default for third-party marketplaces; user toggle or admin `autoUpdate`; runs after a random delay of up to ten minutes after the first message, then "Plugin updated: <name> · Run /reload-plugins to apply") or by running `/plugin marketplace update <name>` / `claude plugin update <plugin>@<name>`; "Don't set `version` in both `plugin.json` and the marketplace entry" [host-marketplace, loading]. Notably, the docs name "`<plugin>--v<version>` tags" as the convention dependency ranges resolve against [host-marketplace].

2. The schema gives `include-v-in-tag` and `include-component-in-tag` as booleans that each "Defaults to `true`", `tag-separator` as a free string ("Customize the separator between the component and version in the GitHub tag") with no stated default, pattern or length limit, and `release-type` as an unconstrained string [https://github.com/googleapis/release-please/blob/main/schemas/config.json]. The code sets `DEFAULT_SEPARATOR = '-'` and parses tags with `(?<separator>[^a-zA-Z0-9])`, a single-character class, so `--` is accepted on output but a tag `tk-studio--v1.2.3` parses back as component `tk-studio-` + separator `-` [https://github.com/googleapis/release-please/blob/main/src/util/tag-name.ts]; whether that breaks latest-release lookup was not traced this run, so treat `--` as unsupported until tested. The README's release-type table lists `bazel, dart, elixir, go, helm, java, maven, node, expo, ocaml, php, python, ruby, rust, sfdx, simple` (`simple` = "A repository with a version.txt and a CHANGELOG.md") plus two rows my filter missed [https://github.com/googleapis/release-please/blob/main/README.md]. The action's current major is `v5` (`v5.0.0`, 2026-04-22) [https://github.com/googleapis/release-please-action/releases].

3. For `"private": true` packages changesets does nothing unless told: "By default Changesets will not version or tag private packages (that is, `{ version: false, tag: false }`)"; set `privatePackages: { version: true, tag: true }` and keep a minimal `package.json` with `name`, `private`, `version` [https://github.com/changesets/changesets/blob/main/docs/versioning-apps.md]. The non-publishing tag command is documented as `changeset git-tag`, which "does not publish anything to npm" and emits fixed-format tags `pkg-name@version-number` [https://github.com/changesets/changesets/blob/main/docs/command-line-options.md]. In changesets/action, `create-github-releases` ("Whether to create Github releases after publish") is only consulted when a `publish-script` is set; without one it logs "Not publishing because publish-script is not set.", and releases are built from the Changesets CLI's `CHANGESETS_OUTPUT` [https://github.com/changesets/action/blob/main/src/index.ts, .../src/run.ts]. So releases without npm are possible only by supplying a publish-script that runs the Changesets CLI and produces that output; whether `git-tag` produces it was not verified.

4. `git subtree add` creates the prefix by importing the subproject and "A new commit is created automatically, joining the imported project's history with your own. With '--squash', import only a single commit from the subproject, rather than its entire history." [https://github.com/git/git/blob/master/contrib/subtree/git-subtree.adoc]; `--squash` exists to "reduce log clutter" and lets you "switch back and forth between different versions of a subtree", and `split` can later extract "a new, synthetic project history" deterministically ("Repeated splits of exactly the same history are guaranteed to be identical") [same]. The manpage retrieved does not describe how path-limited `git log` behaves on imported files; my unverified belief is that `git log -- <prefix>/file` stops at the join commit without `--follow`, because imported commits store the files at the subproject root. The `git merge --allow-unrelated-histories` text could not be retrieved this run (two raw fetches of git's Documentation returned nothing), so the comparison is unsettled.

5. Transfer carries "issues, pull requests, wiki, stars, and watchers", keeps webhooks, secrets and deploy keys "associated", and "All links to the previous repository location are automatically redirected to the new location" with git commands redirecting too; the redirect is "permanently deleted" if you create a repo or fork at the old name; GitHub Pages are not redirected and packages "may lose their link" [https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository]. Releases are not named in the transferred list, but the page says the new owner can "administer the repository's contents, issues, pull requests, releases, projects, and settings", consistent with releases moving with the repository (medium confidence). Archiving creates no redirect; the repository stays at its URL read-only, with "releases" among the frozen objects and forking/starring still allowed [https://docs.github.com/en/repositories/archiving-a-github-repository/archiving-repositories]. No GitHub mechanism to move individual releases or assets between repositories was found in the retrieved pages.

6. The pattern: one job that `needs:` every conditional job, runs `if: ${{ !cancelled() }}`, and fails when `toJSON(needs.*.result)` contains `failure` or `cancelled`; without the condition "GitHub will skip the 'final-status' job if any of its 'needs' fail" and "A job that is skipped will report its status as 'Success'", so it "will not prevent a pull request from merging" [https://jakewharton.com/fan-in-to-a-single-required-github-action/, 2025-05-07]. Path-filtering at the `on:` trigger instead leaves required checks pending ("it blocks the PR from merging") per a GitHub community thread [https://github.com/orgs/community/discussions/44490, low confidence, snippet]. To reproduce "admins not enforced" with rulesets, add a bypass actor: "This can be users with a certain role, such as repository administrator, or it can be specific teams or GitHub Apps" [https://docs.github.com/.../about-rulesets], choosing "Always allow" or "For pull requests only" (the latter still forces a PR but lets the actor merge past the rules) [https://docs.github.com/.../creating-rulesets-for-a-repository]; a one-person studio whose only admin is itself should prefer "For pull requests only" to keep PR-only main while retaining an escape hatch.

7. In a uv workspace, bump one member with `uv version --package <PACKAGE> --bump patch` (`--dry-run`, `--frozen`, `--no-sync` available; by default it "will perform a lock and sync") [local `uv version --help`, uv 0.12.19; https://docs.astral.sh/uv/guides/package/], build it with `uv build --package <PACKAGE>` and publish with `uv publish`, which uploads `dist/*` by default, so clear `dist/` first; trusted publishing needs no credentials and PyPI retries ignore identical files [same two sources]. For releases, `gh release list -R <repo> --limit 200 --exclude-drafts --json tagName,publishedAt --jq '[.[] | select(.tagName|startswith("tk-studio--v"))] | sort_by(.publishedAt) | reverse | .[0]'` returned `tk-studio--v0.2.16` live; note `--limit` defaults to 30, ordering is by date (`--order`, default `desc`) not semver, and `isLatest` is a single repo-wide flag [local `gh release list --help`, gh 2.101.0; live run].

## Benefits and drawbacks (updates)

(a) One repo with tag-prefixed releases: the chosen `tk-studio--vX.Y.Z` prefix matches Claude Code's documented `<plugin>--v<version>` dependency-resolution convention [host-marketplace], which is a point in its favour, but it collides with release-please's one-character separator parser and `-` default [tag-name.ts, config.json], so release-please would need either a one-character separator (breaking continuity with the eleven existing `--v` tags) or `skip-github-release` plus custom tagging. changesets fixes tags as `pkg-name@version` and only makes Releases via a publish-script [command-line-options.md, action src], so it is a poor fit for this prefix. The archive source handles a per-release zip URL comfortably (256 MiB, sha256 pin, manifest-first versioning) [host-marketplace, loading]. The gate-job pattern plus a ruleset bypass actor reproduces today's protections in one repo [Jake Wharton; GitHub rulesets docs]. `gh release list` needs a raised `--limit` and semver-aware sorting once several apps share one release list, and only one release per repo carries `isLatest` [gh help; live run]. Migration via `git subtree add` keeps full history and remains reversible with `split` [git-subtree.adoc].

(b) Separate repos: transfers redirect web and git URLs (until the old name is reused) and keep hooks, secrets and deploy keys [transferring-a-repository]; archiving an emptied service repo keeps its URL and releases readable with no redirect [archiving-repositories]. Nothing found lets releases or assets move between repos, so old download URLs stay valid only if the old repo stays (archived).

(c) One repo plus a meta release: no new evidence beyond `isLatest` being repo-wide [gh help], which a meta release would naturally own.
