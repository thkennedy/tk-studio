## Migration recipe

Evidence supports the filter-repo path end to end except the final merge flag (see note). Run from a scratch directory on the Windows box (filter-repo is a Python tool; run it under uv).

1. Fresh clone of the service repo, since filter-repo "will abort if run from a repo that is not a fresh clone"; add `--no-local` if cloning from a local path [git-filter-repo docs]:
   `git clone --no-local <service-remote-or-local-path> svc-rewrite`
2. Rewrite every path under the target directory and prefix every tag [git-filter-repo docs: `--to-subdirectory-filter` = `--path-rename :<dir>/`; `--tag-rename '':'<prefix>'`]:
   `cd svc-rewrite && git filter-repo --to-subdirectory-filter apps/service --tag-rename 'v':'service--v'`
   (Use `'':'service--'` instead if the old tags lack a `v`.) Side effects documented: `refs/remotes/origin/*` become local branches and `origin` is removed; signed tags are downgraded to annotated tags; lightweight tags are renamed by refname.
3. In the monorepo, fetch the rewritten history and tags, then merge the unrelated history:
   `git remote add svc ../svc-rewrite && git fetch svc --tags`
   `git merge --allow-unrelated-histories svc/main` — the flag name comes from the brief; I did not retrieve the git-merge manual this run, so treat it as unverified until checked.
   `git remote remove svc`
4. Push the merged main and the prefixed tags through the monorepo's protected-main PR flow.
5. Archive the old repo after updating its README and description to point at the new location; archiving is reversible and makes issues, PRs, code, and releases read-only [GitHub archiving docs]. The docs say nothing about redirects for archived repos.

What it preserves: every commit of the service, now rooted under `apps/service`, with authorship intact; every tag, now prefixed. What it loses: tag and commit signatures (filter-repo states they cannot continue to work); the old repo's GitHub Releases and their assets stay on the old repo (the archiving page lists releases among the read-only items; migration of release objects was not evidenced); `#NNN` issue/PR references in old commit messages will now point at the monorepo's numbering (unverified belief, not retrieved).

`git subtree add --prefix=<dir> <remote> <branch>` alternative: not evidenced this run (the git-scm page returned 404 and the manpage mirror redirected past my budget). Unverified belief from training: it also joins the full history via a merge commit, does not rename tags, and leaves the imported files' history reachable only through that merge, so `git log -- apps/service/<file>` needs `--follow`-style tricks. Treat as a lead.

## Benefits and drawbacks

(a) One repo, tag-prefixed releases per app
- Benefits: the plugin's `tk-studio--vX.Y.Z` zip gate is directly supported by a per-app `on.push.tags` workflow and by `gh release download <tag> -p` [GitHub workflow-syntax; gh manual]; the marketplace can keep pointing at the plugin inside the monorepo via a relative path or `git-subdir` with sparse/partial checkout, or at the Release zip via `archive` + `sha256` [marketplace-reference]; one PR flow and one protected main covers all three apps [rulesets doc]; release-please manifest mode gives per-package versions and per-package Releases out of the box [release-please docs].
- Drawbacks: path filters do not apply to tag pushes, so each app needs its own tag glob and CI must not rely on `paths:` for release jobs [workflow-syntax]; required status checks cannot be scoped per path on a user-owned repo, so the service's checks become repo-wide gates unless a single always-reporting gate job is used (gate-job pattern is an unverified belief) [rulesets doc]; "latest release" becomes ambiguous across apps for `gh release download` without a tag [gh manual]; release tooling conventions (`-v`, `@`) do not match `--v`, so either the prefix changes or the Release step stays scripted [release-please docs; changesets tags].

(b) Separate repos
- Benefits: each repo's protection, required checks, and "latest release" are unambiguous [rulesets doc; gh manual]; the plugin repo stays a plain marketplace root with no `path`/`git-subdir` indirection [marketplace-reference]; no history rewrite or tag prefixing needed [git-filter-repo docs].
- Drawbacks: a plugin in another repo still needs `github`/`git-subdir`/`archive` wiring for cross-repo marketplace entries [marketplace-reference]; cross-app changes need coordinated PRs and tags in two or three places (no new evidence needed; structural).

(c) One repo plus a thin meta release pinning a compatible set
- Benefits: consumers download one manifest asset by one tag and then fetch each app's pinned asset with `gh release download <app-tag> -p` [gh manual]; release-please's `linked-versions` plugin is the nearest native primitive ("sets them to the highest version in the group") if lockstep is acceptable [release-please docs].
- Drawbacks: no retrieved tool creates a cross-app compatibility manifest natively, so the meta release is a fourth hand-maintained tag and workflow (inference from the tool cards above); it inherits every drawback of (a) and adds a third thing that can drift.
