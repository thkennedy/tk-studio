## Answers per lead

1. **Unkey "split monos" and other first-person split/merge accounts.** RFC 0010 (James Perkins, 2025-04-07) argues for splitting on build time, dependency tangle, onboarding, cross-project conflicts; proposes Core / SDKs / Infra / Documentation / Marketing. The org today shows the split was partial: `sdks` (created 16 days after the RFC) and `marketing`/`marketing-site` exist, but the dashboard (`web/`) and docs (`docs/`) still live in unkeyed/unkey, which has since become a Go-first tree. The RFC excerpt lists no costs; the page itself was unreachable this run (DNS), so status is unconfirmed. The only full first-person merge-back account retrieved is Proton (2022-08-18): polyrepo costs were mirrored git ops per feature, builds against unmerged deps, no atomic rollback; merge costs were a full CI rewrite, manual porting, a week of failing pipelines, no measured outcome. Wix "60 repos to one" and Segment's "back to a monorepo" surfaced only as undated snippets (leads).
2. **Nordmann and counter-arguments.** "Always Go With a Monorepo" (2026-07-15): one repo regardless of team size; split only for a mechanical reason the filesystem cannot give (declared-dependency import enforcement); costs of splitting are ordered multi-PR changes, a version-pin matrix, lost atomic refactors, style/ownership drift; AI assistants lose the whole dependency graph; per-directory CLAUDE.md gives scoped rules without splitting. The reasoned counter in this run is Unkey's RFC (build time, CI scoping, per-repo dependency upgrades) and, implicitly, Hermes's maintenance-load argument for pushing third-party plugins out of tree. Nordmann himself concedes the one real pro-split point (mechanical boundary enforcement).
3. **Why slopus/happy keeps happy-desktop separate.** No stated reason exists in READMEs, issues or PRs. Observable facts: the desktop is a different product ("Happy Harness", multi-provider) on a different runtime (happy-agent, also its own repo) with its own download channel and DEVELOPMENT.md; meanwhile the CLI and relay server, which had been separate repos, were folded into the happy monorepo on 2026-02-14. The pattern is: shared-protocol mobile+CLI+server in one monorepo; desktop app and agent runtime, each with distinct release artifacts, in their own repos.
4. **Vibe Kanban cadence.** Yes to both. GitHub Releases stopped at v0.1.44 (2026-04-24); the only release since is 0.1.45 on npm (2026-09-19, after a -permtest prerelease on 09-16). Commits: 10 in one week (mid-Sept) and zero in the other eleven of the last twelve weeks; last commit 2026-09-19. From ~21 npm releases in five weeks (Feb–Mar 2026) to one in five months.

## Benefits and drawbacks (updates)

- **Split repos — benefits confirmed this round:** faster incremental builds and CI scoped per repo (Unkey RFC); mechanical boundary enforcement via declared dependencies (conceded by Nordmann); independent release artifacts and cadences per surface (Happy desktop vs mobile; Supabase engines; Hermes desktop/Termux/Store decoupled from the CLI tag); containment of maintenance load for third-party integrations (Hermes CONTRIBUTING).
- **Split repos — costs confirmed this round:** cross-cutting change becomes several ordered PRs and a version-pin matrix (Nordmann); no atomic rollback across histories (Proton); AI assistant loses the whole-graph view (Nordmann); pin-bump machinery becomes a standing operational cost — nightly bot with a per-night cap and manual check dispatch (Anthropic), SHA-bump PRs re-reviewed per upstream range (Hermes), compose pins lagging upstream by multiple minors (Supabase).
- **Monorepo — costs confirmed this round:** merge/migration is a CI rewrite plus a cut-over weekend and manual porting (Proton); Python-in-JS-monorepo caching is coarse unless lock files are inputs, and any lock change invalidates every project (@nxlv/python README; PostHog lists uv.lock as an input and accepts that).
- **The pattern that recurs:** product core (UI + API + docs) in one repo; things with a different runtime, language, release artifact or ownership (SDKs, marketing site, desktop app, engines, third-party plugins) in their own repos — Unkey post-RFC, Happy, Supabase, Hermes; PostHog reaches a similar effect in-tree by excluding its desktop workspace from the root install.
- **Release-cadence signal:** a project that stops cutting GitHub Releases and publishes only to npm once in five months (Vibe Kanban) should be treated as dormant for dependency decisions.
