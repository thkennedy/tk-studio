## Proposed state vocabulary

Semantic visual states (eight, plus two overlays): `offline`, `idle`, `thinking`, `reading`, `typing`, `running`, `waiting-for-human`, `blocked`, with terminal overlays `done` and `failed`, and transient badges (not states) for handoffs and mode changes. "Reading/typing/running" split borrows Pixel Agents' tool-class mapping; "waiting-for-human" borrows its bubble; "expiry timestamp per state" borrows AI Town's `activity.until`; "active = seen within window" borrows Hermes' 5-minute rule. Rows marked "inference" have no retrieved precedent for that exact mapping.

## Hosting options

Common facts: the Bun service already terminates TLS with a per-machine `machine.tailnet.ts.net` certificate (90-day, file renewal is yours — Tailscale KB). A host-only, `Secure; HttpOnly` cookie is returned only to the host that set it (MDN Set-Cookie). Over HTTP/1.1 a browser allows about 6 connections per domain, so the office must share one `/events` stream per tab (MDN SSE); Bun's `http2` needs `tls`, which is already present (Bun docs).

### A. Next.js static export served by Bun.serve on the same origin
- Benefits: one process, one origin, one certificate; cookie is first-party and same-site, so `SameSite=Lax` (the browsers' default) and no CORS, and `EventSource` needs no `withCredentials` (WHATWG: that knob only matters cross-origin). Next docs say the export runs on any static server; Bun `routes` can serve `Bun.file()`s and bundled HTML imports.
- Drawbacks: static export forbids `cookies()`, rewrites, redirects, headers, proxy, Server Actions and request-dependent Route Handlers (Next docs), so sign-in, session checks and all data fetching stay in the Bun API with client-side fetching (SWR per Next docs). Bun documents no "serve this directory" primitive, so a wildcard route must emulate nginx's `$uri`, `$uri.html`, `$uri/index.html` resolution yourself; `idleTimeout` 10 s must be disabled per SSE request with `server.timeout(req, 0)`.
- Cookie behaviour: unchanged from today's status page.

### B. Next.js server reverse-proxied by the Bun service
- Benefits: full Next feature set (server components with live data, `cookies()`, Route Handlers) while the browser still sees one origin and one cookie; Bun's `fetch` fallback can forward unmatched paths.
- Drawbacks: a second long-running Node process to supervise on the always-on box; the Bun docs page retrieved documents no reverse-proxy or WebSocket-upgrade forwarding helper, so streaming passthrough (SSE bodies, Hermes `/api/pty` WebSocket if proxied) is hand-written and must honour the chunking/buffering cautions in the WHATWG spec; Next can only read the session cookie if Bun forwards `Cookie` and Next trusts the proxy.
- Cookie behaviour: same as A at the browser; internally the cookie crosses a loopback hop.

### C. Separate origin (another port on the same node, or another MagicDNS host)
- Benefits: no coupling between the Bun release cycle and the UI; `next dev` works unmodified.
- Drawbacks: a host-only cookie is not sent to a different host (MDN); the MDN page is silent on ports, so same-host-different-port behaviour is unverified here; cross-site use requires `SameSite=None; Secure` plus CORS with credentials and `EventSource(..., {withCredentials: true})` (WHATWG). A second host means a second `tailscale cert` with its own 90-day manual renewal and a second Certificate Transparency entry (Tailscale KB). Whether a `Domain=<tailnet>.ts.net` cookie is allowed depends on `ts.net` being a public suffix — not verified this run.
- Cookie behaviour: the riskiest of the three; every failure mode in MDN's Secure/SameSite/Domain rules applies.

### Transport split regardless of option
SSE carries the office state (built-in reconnect and `Last-Event-ID`, heartbeat comment ≤15 s per WHATWG, 10 s as Hermes does; snapshot-then-deltas with re-baseline when the cursor is older than the retained window per the SharpAPI pattern). The Hermes chat embed is a WebSocket (`/api/pty`) or plain OpenAI-style HTTP/SSE (`/v1/chat/completions`), by Hermes' own docs; a WebSocket is not needed for the office state itself.
