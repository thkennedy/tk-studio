# Digest A1 round 1 — comparable repository structures

Scope: how open-source projects that ship a plugin, a service/daemon and a web UI lay out their repositories, version and release each deployable, and what a newcomer runs. Evidence is from the GitHub REST API (live, 2026-10-09), the projects' own README files, and the official docs for Bun, uv, Turborepo and Claude Code plugins. Budget used: 17 tool calls, 7 primary sources plus two search result pages (aggregators, not cited). Items I could not evidence this run are marked as such or left in "Looked for and could not find".

### Split example: MoJ Sirius ADR 0003
- One monorepo whose every change forced a full rebuild and retest was split into component repos for faster CI and independent releases; stated costs were stronger contracts and maintaining more repos [https://docs.sirius.opg.service.justice.gov.uk/documentation/architecture-decisions/0003-breaking-down-the-monorepo].
- Teaches: the split is justified by rebuild coupling, not by cadence alone; a one-person studio with a task graph (filtered builds) removes the stated trigger.

## Benefits and drawbacks

### Single repo with per-app releases (Omnara, Happy core, OpenCode, PostHog, n8n)
Benefits
- Newcomer gate is met trivially: `git clone` + `docker compose up` (Omnara [https://github.com/omnara-ai/omnara/blob/HEAD/README.md], Windmill [https://github.com/windmill-labs/windmill/blob/HEAD/README.md]).
- Independent cadence per deployable is routine: tag prefixes plus one workflow per deployable (Omnara omnarad-/cluster-/sdk- [https://api.github.com/repos/omnara-ai/omnara/releases?per_page=5]; Happy cli- [https://api.github.com/repos/slopus/happy/releases?per_page=5]; OpenCode vscode-v [https://api.github.com/repos/anomalyco/opencode/tags?per_page=10]).
- A Claude Code marketplace can point at a plugin folder inside that repo with `git-subdir` plus `ref`/`sha`, or at a pinned zip with `archive` plus sha256, so the plugin's own release stays independent [https://code.claude.com/docs/en/plugins/marketplace-reference].
- Mixed Python + TypeScript in one root has working precedents (PostHog, Hermes) and first-party tooling (uv workspaces, Turborepo uv support) [https://api.github.com/repos/PostHog/posthog/contents/], [https://turborepo.dev/docs/guides/tools/python].
Drawbacks
- Tag namespaces get crowded and schemes drift unless fixed early (PostHog's four schemes [https://api.github.com/repos/PostHog/posthog/tags?per_page=10]; Vibe Kanban's malformed tags [https://api.github.com/repos/BloopAI/vibe-kanban/tags?per_page=10]; Hermes's CalVer-to-semver switch [https://api.github.com/repos/NousResearch/hermes-agent/releases?per_page=5]).
- Release automation grows with deployables (n8n and PostHog each exceed 100 workflow files; Omnara needs 9, bmad-loop 2) [https://api.github.com/repos/n8n-io/n8n/contents/.github/workflows], [https://api.github.com/repos/omnara-ai/omnara/contents/.github/workflows].
- Without a task graph, every change retests everything, which is the documented trigger for a split [https://docs.sirius.opg.service.justice.gov.uk/documentation/architecture-decisions/0003-breaking-down-the-monorepo]; Turborepo's Python graph is still experimental [https://turborepo.dev/docs/guides/tools/python].
- uv workspaces impose one requires-python and one lockfile across members and are "not suited" to conflicting requirements [https://docs.astral.sh/uv/concepts/projects/workspaces/].

### Separate repositories (BMad org, MoJ Sirius, Hermes plugin satellites)
Benefits
- Each repo keeps its own cadence and release workflow with no coordination (bmad-loop weekly vs BMAD-METHOD monthly [https://api.github.com/repos/bmad-code-org/bmad-loop/releases?per_page=5]).
- Unmaintained parts can be shed or handed off without touching core (Hermes plugin repos "leaves Hermes core Oct 15, 2026" [https://api.github.com/orgs/NousResearch/repos]).
- Independent releases and smaller rebuilds were the stated benefits in the only ADR retrieved [https://docs.sirius.opg.service.justice.gov.uk/documentation/architecture-decisions/0003-breaking-down-the-monorepo].
Drawbacks
- Newcomers must learn which repo is source and which is distribution (BMad README points Claude Code users at a 0-star bmad-plugins repo, and an older bmad-plugins-marketplace still exists) [https://github.com/bmad-code-org/BMAD-METHOD/blob/HEAD/README.md], [https://api.github.com/orgs/bmad-code-org/repos].
- Interfaces must become explicit contracts and every sub-repo needs upkeep [https://docs.sirius.opg.service.justice.gov.uk/documentation/architecture-decisions/0003-breaking-down-the-monorepo].
- Installing a service from a git tag shifts upgrade friction to users (`uv tool upgrade` needs `--reinstall`) [https://github.com/bmad-code-org/bmad-loop/blob/HEAD/README.md].

### Hybrid (core monorepo plus satellites: Happy, Omnara + codex, Hermes + plugins, official marketplace + external_plugins)
Benefits
- Core deployables that share code and release together stay in one place; platform- or toolchain-specific satellites (Tauri desktop, Rust integration) live apart (Happy happy-desktop [https://api.github.com/orgs/slopus/repos]; Omnara codex [https://api.github.com/orgs/omnara-ai/repos]).
- The official marketplace shows the hybrid is first-class for plugins: in-repo plugins/ plus SHA-bumped external pointers [https://api.github.com/repos/anthropics/claude-plugins-official/contents/].
Drawbacks
- Duplication and ambiguity creep in (packages/happy-agent inside the monorepo and a separate slopus/happy-agent repo) [https://github.com/slopus/happy/blob/HEAD/package.json], [https://api.github.com/orgs/slopus/repos].
- No project retrieved this run documents why a given satellite was split out, so the boundary rule is implicit.

### Reading for the operator's case (plugin zip with tag prefix + Bun service + planned web UI)
- The nearest precedents for "one repo, three cadences" are Omnara (three prefixes, three workflows) and OpenCode (core lockstep plus vscode-v) [https://api.github.com/repos/omnara-ai/omnara/releases?per_page=5], [https://api.github.com/repos/anomalyco/opencode/tags?per_page=10].
- The marketplace reference supports the existing pinned-zip release directly (`archive` + sha256) and a monorepo subfolder directly (`git-subdir` + tag + sha), so moving the supervisor into the plugin's repo does not force a change to how the plugin ships [https://code.claude.com/docs/en/plugins/marketplace-reference].
- Bun workspaces give linking, catalogs and `--filter` but no task cache; projects on Bun (OpenCode) and pnpm (n8n, Supabase, PostHog) add Turborepo for that [https://bun.sh/docs/install/workspaces], [https://api.github.com/repos/anomalyco/opencode/contents/].
