## Pattern cards

### 1. Bootstrap script + self-updating launcher (irm | iex, curl | sh)
- How it works: a one-line script downloads a platform binary (or source tree) into a per-user directory, puts a launcher on PATH, and the installed tool later updates itself. Claude Code installs to `%USERPROFILE%\.local\bin\claude.exe` + `.local\share\claude\versions\`, needs no Administrator, and auto-updates in the background [https://code.claude.com/docs/en/setup]. uv installs via `install.ps1`, pins by version-in-URL, and `uv self update` re-runs the installer [https://docs.astral.sh/uv/getting-started/installation/]. Hermes Agent installs to `%LOCALAPPDATA%\hermes`, carries its own `uv.exe`, and offers `hermes update` and `hermes doctor` [https://github.com/NousResearch/hermes-agent].
- Who uses it: Anthropic (Claude Code), Astral (uv), Nous Research (Hermes Agent) — all three ship the PowerShell form as the primary Windows path [sources above].
- Windows fitness: high for per-user developer tools; uv's page notes the `-ExecutionPolicy ByPass` prerequisite [https://docs.astral.sh/uv/getting-started/installation/]; Hermes documents antivirus false positives on the bundled `uv.exe` and advises whitelisting the folder, not the hash, because the binary changes on every update [https://github.com/NousResearch/hermes-agent].
- Failure and rollback: Claude Code keeps the two newest versions side by side behind a launcher, `claude doctor` shows the last update attempt, `minimumVersion` prevents channel-switch downgrades, and `DISABLE_UPDATES` freezes everything for self-distributed deployments [https://code.claude.com/docs/en/setup]. uv and Hermes pages describe no rollback [https://docs.astral.sh/uv/getting-started/installation/, https://github.com/NousResearch/hermes-agent].
- Integrity: Claude Code publishes a GPG-signed `manifest.json` of SHA256s from 2.1.89 and Authenticode-signs the Windows binary [https://code.claude.com/docs/en/setup]; uv's install page documents no verification, though its release zips carry GitHub attestations verifiable with `gh attestation verify` [https://docs.astral.sh/uv/getting-started/installation/, https://github.com/NousResearch/hermes-agent]. Criticisms and mitigations as in the security findings above [https://github.com/in-toto/witness/issues/418, https://arp242.net/curl-to-sh.html, https://spin.atomicobject.com/security-spectrum-curl-sh/, https://github.com/Flagsmith/flagsmith-cli/issues/59].
- Verdict: the dominant 2025–26 pattern for exactly this class of tool; acceptable when the script pins a version, verifies a hash against a signed or separately hosted manifest, and the installed tool owns subsequent updates.

### 2. `uv tool install` / `uvx` as the delivery channel for a Python orchestrator CLI
- How it works: the studio CLI is a Python package; `uv tool install studio` (or `uvx studio`) creates an isolated environment and exposes the entry point; install-time constraints persist and `uv tool upgrade` honours them; `uvx` caches the first-resolved version until `@latest` [https://docs.astral.sh/uv/concepts/tools/].
- Who uses it: Astral documents ruff and black; Hermes Agent embeds uv to manage Python 3.14 and dependencies on Windows [https://docs.astral.sh/uv/concepts/tools/, https://github.com/NousResearch/hermes-agent].
- Windows fitness: uv itself is on winget and scoop and has a PowerShell installer [https://docs.astral.sh/uv/getting-started/installation/]; uv releases roughly weekly (three releases 2026-10-02 to 10-08) [https://api.github.com/repos/astral-sh/uv/releases].
- Failure and rollback: `uv tool upgrade` reinstalls executables even when unchanged; environments are disposable and recreated; downgrade is a reinstall with a different constraint [https://docs.astral.sh/uv/concepts/tools/]. No transactional rollback is documented.
- Verdict: a strong vehicle for the "one command" if the orchestrator is Python; it does not by itself manage Bun or the plugin, so it is the shell of a meta-installer, not the whole.

### 3. Claude Code plugin marketplace (`claude plugin install` / `update`)
- How it works: a git repo with `.claude-plugin/marketplace.json` is added by `owner/repo[#ref]`, git URL, local path or hosted JSON; plugins install by name at user/project/local scope; `#ref` pins the marketplace to a branch or tag [https://code.claude.com/docs/en/plugins/install].
- Update semantics: third-party marketplaces do not auto-update by default; `claude plugin update <plugin>@<marketplace>` updates one plugin; no update-all command; a running session keeps the loaded version until `/reload-plugins` or restart [https://code.claude.com/docs/en/plugins/install].
- Windows fitness: identical on all surfaces because it is Claude Code's own mechanism; scriptable from a setup script with `--scope project` and `--yes` [https://code.claude.com/docs/en/plugins/install].
- Failure and rollback: none documented beyond the **Errors** tab and `claude plugin list` status; a pinned `#ref` is the only version control lever found [https://code.claude.com/docs/en/plugins/install]. No plugin checksum or signature mechanism appears on the install or overview pages [https://code.claude.com/docs/en/plugins/install, https://code.claude.com/docs/en/plugins].
- Verdict: use it as the plugin leg of the installer, driven by the meta-installer; pin the marketplace to a tag and let the meta-updater move the tag, since Claude Code will not update third-party plugins on its own.

### 4. winget manifest (portable / zip-with-nested-portable) for the bootstrap tool
- How it works: a YAML manifest at schema 1.12.0 with a required `InstallerSha256`; `InstallerType: zip` + `NestedInstallerType: portable` can expose several binaries with `PortableCommandAlias`; `ArchiveBinariesDependOnPath` controls PATH vs symlink; winget does not refresh PATH in the installing shell [https://learn.microsoft.com/en-us/windows/package-manager/package/manifest, https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.12.0/installer.md].
- Who uses it: uv (`astral-sh.uv`) and Claude Code (`Anthropic.ClaudeCode`) both list winget as a secondary channel [https://docs.astral.sh/uv/getting-started/installation/, https://code.claude.com/docs/en/setup].
- Windows fitness: native; Microsoft is building "Windows Developer Configurations" on top of it (secondary reporting, low confidence) [https://www.windowslatest.com/2026/09/22/...].
- Failure and rollback: winget upgrades can fail while the executable is running (Windows file lock) and winget installs of Claude Code do not auto-update [https://code.claude.com/docs/en/setup]; community submission requires silent install and one PR per version [https://learn.microsoft.com/en-us/windows/package-manager/package/manifest].
- Verdict: good as the discoverable front door for the bootstrap binary only; a poor place to express a compatible multi-component set, since each package version is a separate PR and the manifest has no notion of a component roster.

### 5. MSIX vs MSI for the Bun console-hosted service
- Facts: MSIX forbids per-user Windows services, permits only session-0 services under system accounts, requires the app to run as the interactive user, blocks HKLM and install-directory writes, and virtualises AppData [https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-prepare]. Hermes ships an MSIX/App Installer package in addition to its script, with separate "update ownership" [https://github.com/NousResearch/hermes-agent].
- Verdict (researcher inference from the above): a console-hosted Bun process that writes logs and state next to itself and is started by the user fits a per-user portable layout, not MSIX; MSI is only warranted if a true Windows service is required. No Microsoft page retrieved this run compares MSI and MSIX for services directly.

### 6. Tool-version manifest + lockfile (mise.toml / mise.lock; asdf-style)
- How it works: `[tools]` lists version requests; `mise.lock` records resolved versions, URLs and checksums; `mise install --locked` reproduces them; `mise lock --bump <tool>` advances one tool inside its request; `[tasks]` with `run_windows` gives cross-platform commands [https://github.com/jdx/mise/blob/main/docs/dev-tools/mise-lock.md, https://mise.jdx.dev/configuration.html].
- Who uses it: mise itself at 34,800 stars with near-daily releases [https://api.github.com/repos/jdx/mise/releases].
- Windows fitness: the configuration page does not state Windows support; the only Windows signal retrieved is the `run_windows` task key [https://mise.jdx.dev/configuration.html]. Treat as unverified for Windows this round.
- Failure and rollback: "A locked install is not an offline install"; rollback is a lockfile revert plus `mise install --locked` [https://github.com/jdx/mise/blob/main/docs/dev-tools/mise-lock.md].
- Verdict: the cleanest expression of a "compatible version set" (a committed lockfile with checksums) among the patterns retrieved; adopting mise adds a fourth runtime the newcomer must trust, so the pattern (a committed roster with checksums) is more transferable than the tool.

### 7. Channel manifest with component fallback (rustup)
- How it works: a channel (stable/beta/nightly) resolves to a toolchain manifest listing components; `rust-toolchain.toml` pins channel, profile, components and targets and is committed; when a nightly is missing a component rustup searches back for the newest build that has them all, or the user forces, minimises, or pins a date [https://rust-lang.github.io/rustup/concepts/channels.html, https://github.com/rust-lang/rustup/blob/master/doc/user-guide/src/overrides.md].
- Windows fitness: not examined this round.
- Failure and rollback: the component-fallback rule is the documented failure behaviour; nothing retrieved about interrupted updates [https://rust-lang.github.io/rustup/concepts/channels.html].
- Verdict: the model to copy for "meta-release = roster of component versions": the meta-release manifest, not the components, is what a channel points at.

### 8. Product auto-updater with a delayed stable track (Tailscale, Claude Code)
- How it works: Tailscale updates through the original install mechanism, about a week after release, toggled per device [https://tailscale.com/kb/1067/update]; Claude Code offers `latest` and a ~one-week `stable` channel plus a `minimumVersion` floor [https://code.claude.com/docs/en/setup].
- Failure and rollback: Tailscale documents none; Claude Code keeps two versions on disk and a floor, not an explicit rollback command [https://tailscale.com/kb/1067/update, https://code.claude.com/docs/en/setup].
- Verdict: a two-channel scheme with a delayed stable is cheap to replicate in a meta-updater (two JSON pointers) and is what both products converged on.

## Benefits and drawbacks

For the Bun + uv + Python helpers + Claude Code plugin stack. Effort figures are the researcher's judgment for a single maintainer, not sourced evidence.

- Bootstrap script + self-updating meta-CLI (pattern 1, wrapping patterns 2 and 3)
  - Benefits: matches what Claude Code, uv and Hermes already do on Windows, so the newcomer's muscle memory is `irm ... | iex` [https://code.claude.com/docs/en/setup, https://docs.astral.sh/uv/getting-started/installation/, https://github.com/NousResearch/hermes-agent]; no Administrator; one script can install uv, then `uv tool install` the studio CLI, then have that CLI install Bun, the service, the front end and run `claude plugin marketplace add ...#<tag>` + `claude plugin install ... --yes` [https://docs.astral.sh/uv/concepts/tools/, https://code.claude.com/docs/en/plugins/install].
  - Drawbacks: inherits the `curl | sh` criticism unless the script pins a version and checks a sha256 against a release-hosted `checksums.txt` or signed manifest [https://github.com/Flagsmith/flagsmith-cli/issues/59, https://code.claude.com/docs/en/setup]; bundled binaries trip antivirus (Hermes' uv.exe case) [https://github.com/NousResearch/hermes-agent]; Windows locks running executables, so the updater must stop the Bun service before swapping it (observed for winget upgrades of Claude Code) [https://code.claude.com/docs/en/setup].
  - Cost (judgment): low to build (one PowerShell + one sh script, one Python CLI with `install`, `update`, `doctor`); moderate to maintain because every component's install path is yours to keep working.

- Compatible version set as a committed roster (patterns 6 and 7 applied to your own meta-release)
  - Benefits: a `studio.lock`-style file per meta-release that records plugin tag, service version, front-end version, uv/Python/Bun versions and sha256s, published as a release asset, gives one updater a single thing to fetch and verify; this is what `mise.lock` records and what rustup's channel-to-manifest indirection achieves [https://github.com/jdx/mise/blob/main/docs/dev-tools/mise-lock.md, https://rust-lang.github.io/rustup/concepts/channels.html]; rollback becomes "install the previous roster".
  - Drawbacks: you now cut meta-releases, not component releases; a rustup-style "find the newest set where all components exist" rule is extra logic [https://rust-lang.github.io/rustup/concepts/channels.html].
  - Cost (judgment): low for the file format; the discipline cost is in release process.

- Claude Code plugin marketplace alone as the installer (pattern 3)
  - Benefits: zero new infrastructure for the plugin leg; `#ref` pinning and `--scope project` exist [https://code.claude.com/docs/en/plugins/install].
  - Drawbacks: it only installs the plugin; third-party marketplaces do not auto-update; no update-all; no integrity verification documented; a `command` plugin source could launch your meta-installer but needs `--yes` in scripts [https://code.claude.com/docs/en/plugins/install]. Cannot be the single entry point for Bun and uv components.

- winget package for the bootstrap binary (pattern 4)
  - Benefits: discoverable, hash-verified by manifest, supports zip-with-portable binaries and command aliases [https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.12.0/installer.md]; aligns with Microsoft's one-command developer setup direction (low-confidence secondary reporting) [https://www.windowslatest.com/2026/09/22/...].
  - Drawbacks: one PR per version into the community repo, silent-install requirement, PATH not refreshed in the current shell, running-executable upgrade failures, and no roster concept [https://learn.microsoft.com/en-us/windows/package-manager/package/manifest, https://code.claude.com/docs/en/setup]. Cost (judgment): low once, then a PR per bootstrap release; defer until the script path is stable.

- MSIX packaging (pattern 5)
  - Benefits: clean install/uninstall and Store-grade signing.
  - Drawbacks: no per-user services, no install-dir writes, private AppData, interactive-user requirement [https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-prepare]; a console-hosted Bun service and a mutable plugin directory conflict with this model. Cost (judgment): highest of the options; not justified for a one-person studio now.

- mise as the runtime manager (pattern 6 literally)
  - Benefits: lockfile with checksums, tasks with `run_windows`, near-daily maintenance [https://github.com/jdx/mise/blob/main/docs/dev-tools/mise-lock.md, https://mise.jdx.dev/configuration.html, https://api.github.com/repos/jdx/mise/releases].
  - Drawbacks: Windows support not evidenced on the page retrieved; adds a fourth tool the newcomer must install before the one command runs [https://mise.jdx.dev/configuration.html].
