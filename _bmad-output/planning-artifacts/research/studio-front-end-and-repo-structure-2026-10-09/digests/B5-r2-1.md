## Answers per lead

1. Jules sessions API — settled. Eight states: `QUEUED`, `PLANNING`, `AWAITING_PLAN_APPROVAL`, `AWAITING_USER_FEEDBACK`, `IN_PROGRESS`, `PAUSED`, `COMPLETED`, `FAILED`. The gate is opt-in: `requirePlanApproval: true` at creation, else "plans are auto-approved". Approval is a separate verb (`:approvePlan`), input is a separate verb (`:sendMessage`), and "needs input" is a first-class state distinct from "needs approval". This is the cleanest machine-readable model of the intake → clarify → scope → approve → execute loop found in any product this run.

2. Replit AI billing — settled. Plan Mode is not categorically free: "In the paid path, Plan Mode can perform billable reasoning even when it does not change code." Billing unit is the checkpoint (one per Build Mode request, no intermediate charges), confirmation is requested "before a paid action starts", and each checkpoint's cost is visible on hover in the Agent tab. No numeric per-checkpoint range on the page; whether clarifying questions are billed is not stated.

3. Codex plan mode — partly settled (official page redirected; evidence is search snippets of the official guide plus openai/codex repo items). `/plan` or `Shift+Tab` enters plan mode; the official guide frames it as gathering context and asking clarifying questions before a plan, and recommends asking Codex to question you first. Repo-level prompt rules: explore before asking; never mix `request_user_input` with plan content; a revised plan fully replaces the prior one; a bare clarifying question re-shows the prior plan unchanged. Approval is a client-side "Implement this plan?" per a third-party integrator; no server-side plan-exit event. Known friction: users miss the pause for questions; notify hook does not fire on plan-mode prompts.

4. Claude Code permission modes and advisor — settled. Plan mode blocks edits "until you approve the plan"; the approval prompt has three options (use auto mode / auto-accept edits / bypass variant; manually approve edits; keep planning); `Ctrl+G` edits the plan in your editor before execution; plan files live under `~/.claude/plans/` or `plansDirectory`. Clarifying questions are a tool (`AskUserQuestion`) rather than a plan phase; the docs only say auto mode "nudges Claude to keep working without stopping for clarifying questions" unless a prompt or skill relies on them, and the tool is denied in non-interactive sessions. The advisor page exists: an experimental, Anthropic-API-only server tool where Claude consults a stronger model at decision points (before committing to an approach, on recurring errors, before declaring done), enabled by `/advisor`, `advisorModel`, or `--advisor`, with a published model-pairing ranking, advisor-rate billing, and an `Advising` / Reviewed / Declined / Unavailable transcript line. It is positioned against `opusplan` (stronger model during plan mode only) and subagents.

5. Devin — settled on sizing and Coach; partly on confidence; negative on per-task estimates. Sizes XS–XL are post-hoc classifications by ACU consumed (XS ≤ 2, XL > 20 on the main table; enterprise ×10; a variant table shows 2.25/18), with L/XL "flagged as unhealthy" and the standing advice to split. Confidence Scores are a green/yellow/red "likelihood of completing tasks" that improves as you answer Devin's questions, available in batch via Jira/Linear; no finer scale was found. Devin Coach pre-checks prompts in the input box, applies one-click fixes, and gives admins analytics on suggestion outcomes and blockers, tied to Usage policies with per-user ACU limits and efficiency-graded auto-approval. No pre-start per-task ACU estimate was found; the related control is a hard per-session ACU cap with an acknowledgement modal.

6. Factory Droid Missions — partly settled. The announcement describes conversational scoping with clarifying questions, plan approval before execution, an orchestrator → milestones → features decomposition, validation at every milestone, automatic follow-up work when validation fails, and a human "unblocking workers when they get stuck" with a Mission Control progress log. It does not define how blockers are raised to the human mid-run or how partial delivery is reported. The page date extracted as 2025-02-26 is outside the freshness window and the year is unverified; the docs overview was not fetched (budget).

7. Agency clarifying-question checklist and fixed-bid vs T&M — partly settled, querynow not found. No result mentioned querynow. Named-firm substitutes: Azumo's workflow-first question set (user, goal, trigger point, input/output, human-approves vs system-acts, frequency, existing tools) and Rioja's six-section scope document ending in Acceptance Tests with explicit "reject vague criteria". A community skill formalises the question budget (max 3, multiple choice, default plus impact). No named-firm fixed-bid vs time-and-materials guidance was retrieved this run.

8. Reference-class forecasting — settled for Flyvbjerg and Budzier; ProKanban not found. The 2011/2013 paper: 1,471 projects, mean cost overrun 27%, one in six with ~200% cost and ~70% schedule overrun; the 2022 JMIS follow-up on 5,392 projects finds a power-law distribution. For counts vs points, the retrieved sources are Thoughtworks and Allan Kelly's write-up of Duarte's data (counts and points roughly equally variable; counting works when items cluster around a typical size), not ProKanban.

9. Cursor gate leakage and Copilot change-request precedent — Cursor settled, Copilot unsettled. Cursor forum threads document plan mode switching to agent mode without consent, including a follow-up answer to a scoping question being read as "go" and a mode switch that proceeded despite the tool reporting rejection; staff acknowledged no hard setting blocks it and a fix was in progress; the suggested mitigations (Q&A in a read-only mode, pinned model, explicit "stay in plan mode", separate branch) are themselves the design lesson. The Copilot rule that issue comments after assignment are ignored was not on either fetched docs page; the about page does establish one PR per task, a 59-minute session cap, and steering via chat during the session.

## Engagement-loop template (updated)

Each step names the precedent from this round and the design rule it supports. Steps are states, not prompts: the Cursor evidence is that a gate enforced by model interpretation leaks; the Jules evidence is that a gate enforced by a state enum plus a dedicated approval verb does not.

1. Intake (state: QUEUED → PLANNING). Create the engagement with an explicit `requirePlanApproval`-style flag defaulting to true for paid work (Jules defaults to auto-approve; a studio should not). Record the trigger, inputs, outputs, tools, exclusions and acceptance tests up front (Rioja's six sections; Azumo's "does a human approve the result or does the system act?").
2. Clarifying questions (state: AWAITING_USER_FEEDBACK, distinct from approval). Explore before asking (Codex rule); cap the batch (3 per the skills.sh pattern, 4 per the Codex maintainer prompt); prefer multiple choice with a default and the impact of each answer; never mix questions with the plan body (Codex rule). Surface the pause loudly: Codex users miss it, and the Codex notify hook does not fire on it. Tie answers to a visible readiness signal (Devin's green/yellow/red confidence that rises as questions are answered).
3. Scope of work (plan artifact). Written to a file the client can edit before approval (Claude Code `Ctrl+G`, `~/.claude/plans/`). A revision replaces the prior plan wholesale; a question does not alter it (Codex template). Decompose into milestones and features with validation at each milestone (Factory).
4. Quote. Size by expected consumption in a small number of buckets and treat the top buckets as a signal to split, not to price (Devin XS ≤ 2 ACU ... XL > 20 ACU; L/XL flagged unhealthy). Count items rather than point them when items are similar-sized (Thoughtworks / Duarte via Kelly). Price the tail, not the mean: reference class is 27% mean overrun with one in six at ~200% (Flyvbjerg and Budzier), so a fixed quote needs either a hard cap with an acknowledgement (Devin enterprise per-session cap) or an explicit overrun clause. State whether scoping itself is billable (Replit: plan mode "can perform billable reasoning even when it does not change code") and confirm "before a paid action starts" (Replit).
5. Approval (state: AWAITING_PLAN_APPROVAL → IN_PROGRESS). A dedicated approval action (`:approvePlan`), with the post-approval autonomy level chosen at the gate (Claude Code: use auto mode / manually approve edits / keep planning). Any message that is not the approval verb must not advance the state (Cursor failure mode). Leaving planning without approving is an explicit exit, not a side effect (Claude Code `Shift+Tab`).
6. Milestones and execution. Orchestrator → milestones → features, workers validate, failures spawn follow-up work before moving on, progress log visible (Factory Mission Control); one branch and one PR per task with a time cap (Copilot: one PR per task, 59 minutes) so partial work is always a reviewable artifact. Escalate hard decisions to a stronger reviewer at decision points rather than throughout (Claude Code advisor: before committing to an approach, on recurring errors, before declaring done).
7. Acceptance (state: COMPLETED, with outputs). Deliverable is the PR object (Jules `outputs.pullRequest`); acceptance tests were fixed at scope time (Rioja; Devin "explicit success criteria": tests pass, CI green); an independent completion check precedes "done" (advisor). Billing closes at the checkpoint, with the cost of each checkpoint visible (Replit hover).
8. Change requests. Typed inputs: question (no state change), revision (new plan replaces old, back to approval), go (approval verb only). Mid-run input is a dedicated verb on the live session (Jules `:sendMessage`); after the session ends a change is a new task with its own quote (Copilot one-PR-per-task shape; Copilot's issue-comment rule remains to be confirmed).
9. Blockers and partial delivery (states: PAUSED, AWAITING_USER_FEEDBACK, FAILED). Blocked means a state the client can see and a question they can answer (Jules), and the human's role is "unblocking workers" (Factory). Partial delivery reporting (done / not done / why) is undocumented in every product fetched this run and is therefore a studio differentiator to specify, not copy.
