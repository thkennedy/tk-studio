## Notes

- Claim 1: the only reservation is age. The accepted answer dates from 2019 and the answerer appears Microsoft-affiliated rather than GitHub staff; the OP's own experiment is the independent evidence. No source retrieved this run disputes it.
- Claim 2: independence is weaker than for the others. Both confirming artifacts are Anthropic-published, but they are repository facts (a live catalog file and a release changelog), not a second copy of the docs page. No third-party page describing the `archive` source with `sha256` was found within budget; the one third-party schema surfaced (instagit.com, derived from claude-plugins-community) describes an `http` source with a `checksum` field, which does not match the claim's field names and may be stale. The CHANGELOG also records a fix for `metadata.pluginRoot` ("bare plugin source names now resolve under it"), so bare names under a `pluginRoot` are an alternative to writing `./plugins/<name>`.
- Claim 3: the dev.to article confirms the two flags in exactly the merge-into-monorepo use but does not explain `--tag-rename` semantics or mention signatures. The signature half rests on search-surfaced snippets (Embedded Artistry blog; git.git commit message at code.googlesource.com) that were not fetched in full. Newer git has `fast-import --signed-commits=<mode>` (including `strip-if-invalid`) and GitLab issues (gitlab-org/git #510, #619) propose preserving or re-signing; this does not dispute the claim, since `--to-subdirectory-filter` changes every tree and so invalidates every commit signature regardless.
- Claim 4: verified only indirectly. The independent evidence is that GitHub has shipped no native mechanism, in branch protection or rulesets, for path-conditional required checks as of 2026-10-06, and the request remains in backlog. No retrieved source addresses rulesets by name or the user-owned repository distinction. Search also surfaced a Mergify post ("path filters are not a CI gate", June 2026) describing the problem as current, and GitHub's own troubleshooting page (same publisher as the original, so not counted) which advises against path filtering on required workflows.
- Claim 5: per-package versions and per-package releases are confirmed by the Microsoft blog (per-package `release_created` and `tag_name` outputs, per-package GitHub release). The `<component>-v<version>` format was confirmed only by the googleapis troubleshooting doc (same publisher as the original: "releases will use a component prefix for the release and tag like my-component-v1.2.3") and by third-party skill pages surfaced in search. The word "default" is the unverified part: one third-party guide (playbooks.com/laurigates "release-please-configuration") says the error `Duplicate release tag: v2.0.0` arises when `include-component-in-tag: true` is missing at the root, which implies the component prefix must be switched on explicitly in at least some setups; the Microsoft blog likewise sets `monorepo-tags: true` (the action input that maps to `include-component-in-tag`). Treat "default" as not independently confirmed; recommend setting `include-component-in-tag: true` explicitly.
