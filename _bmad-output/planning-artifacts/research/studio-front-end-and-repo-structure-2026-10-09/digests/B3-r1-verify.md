## Notes

- Claim B3.1: AI Town `activity.until` and `ACTION_TIMEOUT = 120_000` ms verified directly in the primary source at HEAD (rows 1); note the repo is the same one the original cited, so this is a live re-read rather than a second publisher. Hermes "active in the last 5 minutes" is confirmed only in the same publisher's docs source at HEAD (row 2); the dashboard-side constant was not located within budget. Pixel Agents' PreToolUse promote / grace-timer demote was not re-checked (budget spent on Hermes and Bun). The 8-state vocabulary is the digest's design and was not assessed.
- Claim B3.2: v0.21.6 (2026-10-08) verified via the Releases API (row 3). Port 8642, `/v1/capabilities`, 10 s SSE keepalive (`CHAT_COMPLETIONS_SSE_KEEPALIVE_SECONDS = 10.0`) and the CORS allow-list are all source constants (row 4); the default bind host string was not captured, so "127.0.0.1" rests on the docstring's "localhost". `/api/pty` PTY-over-WebSocket with ticket auth verified in `web_server_chat.py` (row 5); the ticket gate is the auth-enabled path (loopback no-auth mode may not require it). Profiles as separate home dirs under `~/.hermes/profiles/` verified (row 6). The docs conflict on Windows PTY is real at HEAD and resolved in favour of native support: windows-native.md (touched 2026-10-06) says ConPTY via pywinpty; windows-wsl-quickstart.md (touched 2026-09-20) still says WSL2-only and is stale (row 7).
- Claim B3.3: Non-200 -> permanent failure verified in Chromium's implementation (row 8): anything other than 200 + `text/event-stream` cancels the loader and the cancellation path dispatches `error` without reconnecting. The ~6-per-host HTTP/1.1 cap verified in two independent implementations: Chromium `g_max_sockets_per_group = {6 ...}` and Firefox `network.http.max-persistent-connections-per-server = 6` (row 9). Bun's `idleTimeout` default 10 s applying mid-stream verified through open PR #41602 (2026-09-06), which also records `idleTimeout: 0` as the workaround (row 10).
- Claim B3.4: Both stream routes and all six listed event types are literal strings in `api_server_runs.py` / `api_server.py` (row 11); re-attachment works by sequence-number backlog replay. The ~5-minute buffer value is unverified: retention is `store_type.RETENTION_SECONDS` defined in `api_server_run_idempotency.py`, which was not fetched (row 12). pywinpty as a core dependency verified in pyproject.toml, with the `pty` extra now an explicit no-op alias (row 13); the windows-native doc's last commit is 2026-10-06 (row 7), which is a last-touched date, not an authorship date. `API_SERVER_ENABLED` / `API_SERVER_KEY` exist in config and source, but "mandatory key" enforcement was not read. Dashboard plugins (tabs, shell/page slots, FastAPI routers under `/api/plugins/<name>/`) verified in docs source plus `web_server.py` gating code (row 14). "Not embeddable" is not enforced by any `frame-ancestors`/X-Frame header in the dashboard server; it should be read as "no embeddable chat component exists" (row 15).
- Claim B3.5: OVERTURNED sub-claim: Bun.serve does have static-directory serving — a `{ dir: "./public" }` route value on a `/prefix/*` path ("Directory routes", routing.mdx at HEAD; issues #40892/#40893 dated 2026-08-29 show it shipping) (row 16). Corrected statement: Bun.serve routes support exact, `:param`, wildcard and `/*` catch-all handlers plus `{ dir }` directory routes; there is no implicit fallback, but a directory route is a one-line declaration, not hand-rolled file serving. Route precedence (exact > param > wildcard > `/*`) confirmed only in the same vendor's docs source; no independent test file located. "No built-in WebSocket proxying" is unverified (negative claim; issue search surfaced nothing either way). `tailscale serve --https --bg --set-path` verified on the local 1.102.4 binary (row 17). `ts.net` on the PSL verified against the live list dated 2026-10-07 (row 18). Cookie port non-isolation verified by independent empirical reports; note Firefox ships WPT tests for the port-bound-cookies proposal, a possible future change (row 19). The iOS 18 background-EventSource failure remains a single-source Apple Forums anecdote with no WebKit ticket found (row 20).
