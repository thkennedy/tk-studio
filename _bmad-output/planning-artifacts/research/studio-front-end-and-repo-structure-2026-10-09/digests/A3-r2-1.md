## Answers per lead

1. **Claude Code `command` plugin source.** It is a plugin-only source type (fields `command`, `timeout`, `mode`) whose command Claude Code runs "through `sh`, or through `cmd.exe` on Windows, from the user's home directory"; it must print one absolute path and exit 0 within `timeout` (1–600 s, default 60), the string is capped at 500 printable-ASCII characters, and users see the whole string before accepting it [https://code.claude.com/docs/en/plugins/marketplace-reference]. It runs on install and update, once per session in the background, and when the cached version is missing; a changed output hash installs a new version and hot-reloads the session [https://code.claude.com/docs/en/plugins/loading]. Unattended acceptance is `claude plugin install <plugin>@<marketplace> --yes`, which exists precisely because "A script has no one to answer that prompt" [https://code.claude.com/docs/en/plugins/install]. As a trigger for a meta-installer it works only once the meta-CLI is already on `PATH` (the command must be "an absolute path or a command on `PATH`"), must be idempotent and fast because it re-runs every session, cannot use `link` mode on Windows, and is excluded from the marketplace-wide **Update marketplace** action [https://code.claude.com/docs/en/plugins/marketplace-reference; https://code.claude.com/docs/en/plugins/install]. Inference, not evidence: it is a sound "render/verify the plugin directory" hook for the meta-CLI, not the newcomer's first bootstrap.

2. **Plugin loading and auto-update.** Auto-update fires in an interactive session after the first message with a random delay of up to ten minutes, only for marketplaces whose `autoUpdate` is on (settings entry, then `known_marketplaces.json`, then default: on for official, off for all third-party marketplaces); `DISABLE_UPDATES=1`, `DISABLE_AUTOUPDATER=1` or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` disable the pass unless `FORCE_AUTOUPDATE_PLUGINS=1` [https://code.claude.com/docs/en/plugins/loading]. Version is manifest `version` first, then entry `version`, then source-derived: for `github`/`url`/`git-subdir` the commit SHA shortened to 12 characters (git-subdir adds a hash of the subdirectory path); `claude plugin update` recomputes it and leaves the cached copy alone when it matches `installed_plugins.json`, so a pinned manifest version freezes users until the string changes, and leaving `version` out of both lets users track commits [https://code.claude.com/docs/en/plugins/loading]. The page does not spell out the git mechanics of a `git-subdir` refresh beyond "sparse checkout"/partial clone on install and SHA-based version comparison on update [https://code.claude.com/docs/en/plugins/marketplace-reference]. Files live under `~/.claude/plugins` (`CLAUDE_CODE_PLUGIN_CACHE_DIR`) in `cache/<marketplace>/<plugin>/<version>/`, and superseded versions are swept 14 days after an `.orphaned_at` marker [https://code.claude.com/docs/en/plugins/loading]. There is no update-all command; command-source plugins are updated one at a time [https://code.claude.com/docs/en/plugins/install].

3. **Hermes Agent.** Ownership is split by channel: the PowerShell script installs a git checkout under `%LOCALAPPDATA%\hermes\hermes-agent\` and "Source checkouts update through the managed Git path (`hermes update`)", while the MSIX `.appinstaller` "records its update source" and Store packages have "separate Store ownership" [https://hermes-agent.nousresearch.com/docs/getting-started/installation]. The script does not vendor `uv.exe` in the repo; it downloads the pinned `uv` 0.12.3 release zip (with a pinned mirror), verifies an embedded SHA-256, refuses any `uv` on PATH, and stores it in a versioned slot `tools\uv-0.12.3-win32-x64\`; Git is likewise a pinned, hash-verified PortableGit used only on the process PATH; only `%LOCALAPPDATA%\hermes\bin` (launchers) goes on the user PATH, and re-running the script fast-forwards the checkout (backing up stray commits to `refs/hermes-update-backups/`) instead of reinstalling [https://hermes-agent.nousresearch.com/install.ps1]. Toolchain versions come from `pm/lock.json`, and a `.hermes-bootstrap-complete` JSON marker records `pinnedCommit`/`pinnedBranch`/`completedAt` [https://hermes-agent.nousresearch.com/install.ps1]. `hermes doctor` is documented only as reporting "installation provenance" and storage problems; a concrete Windows checklist was not found [https://hermes-agent.nousresearch.com/docs/getting-started/installation].

4. **uv installer.** `UV_INSTALL_DIR` moves only the binary (PowerShell: set `$env:UV_INSTALL_DIR` before `irm https://astral.sh/uv/install.ps1 | iex`); `UV_NO_MODIFY_PATH=1` stops profile edits now and in later `uv self update`; `UV_UNMANAGED_INSTALL=<path>` installs to a fixed path, changes no profiles or environment, and "will also disable self-updates (via `uv self update`)" [https://docs.astral.sh/uv/reference/installer/]. `INSTALLER_NO_MODIFY_PATH`, the receipt file, specific-version install, and `uv tool upgrade --all` are not on that page and were not retrieved this run; `https://astral.sh/uv/install.ps1` 301-redirects to `https://releases.astral.sh/installers/uv/latest/uv-installer.ps1`, which I did not fetch within budget. Unsettled.

5. **Alternatives.** *gh extensions*: distribution is a `gh-` repo with a root executable or release binaries named `gh-<name>-<os>-<arch>` (`.exe` required on Windows); `gh extension upgrade --all` exists; no hash or signature verification is documented, only "audit the source code" [https://docs.github.com/en/github-cli/github-cli/creating-github-cli-extensions; https://docs.github.com/en/github-cli/github-cli/using-github-cli-extensions]. Benefit: zero extra installer if `gh` is present; drawbacks: depends on `gh` and its auth, bash-script extensions need an interpreter on Windows, and integrity rests on GitHub TLS. *Scoop*: hash verification is first-class in manifests and the autoupdate tooling can read a `sha256sum.txt` sidecar, but auto-excavation covers only known buckets, so a private bucket needs its own excavator run [https://github.com/ScoopInstaller/Scoop/wiki/App-Manifest-Autoupdate]; install-time mismatch behaviour, shims and the `current` junction were not on the page fetched. *bunx / bun create / bun install -g* and *pipx*: not retrieved this run; no claim.

6. **Windows Developer Configurations.** The primary artefact is `microsoft/WindowsDeveloperConfig` (MIT, 3,087 stars, pushed 2026-10-09): "Opinionated setups for Windows dev boxes. Idempotent. CI-tested.", entered with `irm https://aka.ms/devconfig/standard/setup.ps1 | iex`, which installs the tool set listed in Findings plus WSL with one restart [https://github.com/microsoft/WindowsDeveloperConfig]. It does use WinGet Configuration (DSC) files: every focused workload is a `configuration.winget` applied with `winget configure -f ... --accept-configuration-agreements --disable-interactivity` [https://github.com/microsoft/WindowsDeveloperConfig]. A third party can author and ship the same file format (the workload files are plain repository files), and the repo carries a `CONTRIBUTING.md`, but nothing retrieved shows Microsoft hosting third-party configurations under `aka.ms/devconfig`; the Build 2026 GA framing came only from press results this run and is left as a lead.

7. **Attestation and SHA-256 in a PowerShell bootstrap.** `gh attestation verify <file> --repo owner/repo` checks a local artifact's sha256 digest against GitHub-hosted Sigstore attestations (SLSA provenance v1 by default), with `--bundle` for offline use and `--signer-workflow`/`--signer-repo` when a reusable workflow signed it [https://cli.github.com/manual/gh_attestation_verify]. The concrete, current example is Hermes's `install.ps1`: per-artifact SHA-256 pins are embedded in the versioned script (uv 0.12.3 x64 `b23350c7…`, PortableGit 2.53.0+3 `b365da79…`), the download's digest is compared and a mismatch aborts with "download digest mismatch for … (expected …, got …)" [https://hermes-agent.nousresearch.com/install.ps1]. I did not find a well-known project's `install.ps1` that reads a release-hosted `checksums.txt`; uv's own script was not fetched (redirect, budget).

8. **Swapping a running executable on Windows.** The documented constraint is that a running executable "can be renamed, but it cannot be unlinked", so the established pattern is rename-then-replace: move the running file aside, copy the new one onto the freed name, and have a spawned copy (opened with `FILE_FLAG_DELETE_ON_CLOSE`) delete the old file after the parent exits; `MOVEFILE_DELAY_UNTIL_REBOOT` is privileged and batch-file cleanup is racy [https://docs.rs/self-replace/latest/self_replace/]. The launcher-plus-versions-folder variant is what Hermes does for its toolchain (user PATH holds only `bin\` launchers; tools sit in versioned slots like `tools\uv-0.12.3-win32-x64\`) [https://hermes-agent.nousresearch.com/install.ps1], and Claude Code's plugin cache is the same shape (`cache/<marketplace>/<plugin>/<version>/` with a 14-day orphan sweep) [https://code.claude.com/docs/en/plugins/loading]. Stop-service-then-swap was not evidenced from a primary source this run.

## Benefits and drawbacks (updates)

- **The `command` source narrows, not replaces, the bootstrap.** It can make `claude plugin install studio@tk --yes` call the meta-CLI (install/verify, then print the plugin dir), and its per-session re-run gives hot updates without the auto-update pass [https://code.claude.com/docs/en/plugins/loading]. But the meta-CLI must already be on PATH, the command runs under `cmd.exe` from `%USERPROFILE%`, Windows forbids `link` mode and UNC paths, and the command must stay cheap and idempotent because it re-runs every session [https://code.claude.com/docs/en/plugins/marketplace-reference]. The bootstrap script therefore stays the first step; the plugin becomes a consumer of the meta-CLI.
- **Third-party marketplaces do not auto-update by default** and there is no update-all command, so the one updater must itself run `claude plugin update <plugin>@<marketplace>` (or rely on a command-source re-run) [https://code.claude.com/docs/en/plugins/loading; https://code.claude.com/docs/en/plugins/install]. This strengthens the case for the meta-CLI owning `update`.
- **Version string is the lever for lockstep.** A pinned manifest `version` freezes the plugin until changed; omitting it tracks commits [https://code.claude.com/docs/en/plugins/loading]. The meta-CLI (or release tooling) should write the plugin's `version` from the same roster that pins the Bun service and the Python helpers, so Claude Code's recompute-and-compare agrees with the roster.
- **Hermes supplies a worked Windows blueprint for the committed-roster pattern**: hash-pinned `uv` and Git downloaded into versioned slots, PATH-isolated from whatever the user has, only a launcher directory on the user PATH, a JSON provenance marker, and re-run-equals-update [https://hermes-agent.nousresearch.com/install.ps1]. Its drawback for the studio: no release version is pinned (tip of `main`), and MSIX/Store channels keep separate updaters [https://hermes-agent.nousresearch.com/docs/getting-started/installation].
- **uv ownership choice is binary.** If the meta-CLI owns uv, install it with `UV_UNMANAGED_INSTALL` into the studio's own directory and accept that `uv self update` is disabled; if the user's uv is reused, the roster can only check its version, not pin it [https://docs.astral.sh/uv/reference/installer/].
- **`irm | iex` has Microsoft's own imprimatur for dev-box setup** (`aka.ms/devconfig/.../setup.ps1`), with WinGet Configuration files as the declarative layer beneath [https://github.com/microsoft/WindowsDeveloperConfig]. This weakens the round-1 integrity criticism as a reason to avoid the pattern on Windows, provided the script pins hashes (Hermes model) or verifies attestations (`gh attestation verify`) for what it downloads [https://hermes-agent.nousresearch.com/install.ps1; https://cli.github.com/manual/gh_attestation_verify].
- **Self-update of a compiled meta-CLI needs the rename-then-replace dance or a launcher**; neither is free on Windows, and reboot-deferred moves need privilege [https://docs.rs/self-replace/latest/self_replace/]. A launcher + versions folder (as Hermes and the Claude plugin cache use) avoids locking the hot path at the cost of a second binary.
- **gh extensions are a thin alternative distribution for the meta-CLI** with `--all` upgrades, but no documented hash verification and a hard dependency on `gh` [https://docs.github.com/en/github-cli/github-cli/using-github-cli-extensions].
