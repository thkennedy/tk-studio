# Red team: the one-repository verdict (2026-10-09)

Conclusion under attack: a one-person Windows-first project should fold the plugin, the Bun supervisor and a future Next.js front end into ONE GitHub repo (`tk-studio`) that is also the plugin's git marketplace, with per-app tag-triggered releases, one fan-in required check, `git subtree add` for the supervisor's history, an `irm | iex` bootstrap plus self-updating meta-CLI and a committed version roster. Budget: 20 surface calls used (9 WebSearch, 9 WebFetch, 2 `gh api graphql`).

Red-team posture: I was given no supporting evidence. Everything below is disconfirming or complicating evidence; the synthesis weighs it.

## Findings (strongest first)

### F1. The marketplace is the repo, so every plugin install and every refresh clones the WHOLE monorepo, and refreshes are full re-clones
- **Attacks:** "served to users from the repository's own git marketplace (`claude plugin marketplace add thkennedy/tk-studio`)" combined with putting a Bun service and a Next.js app in the same repo.
- **Evidence:**
  - Official troubleshooting doc: "For a git source, Claude Code clones the whole repository, so relative paths resolve." And: "Cloning a marketplace, and re-cloning one to update it, gets 120 seconds by default. For a large repository or a slow connection, raise the limit." The only size escape is user-side: "If the repository is a monorepo, limit the checkout to the directories you name with `claude plugin marketplace add <source> --sparse <paths>`." [source: https://code.claude.com/docs/en/plugins/troubleshooting, Anthropic, undated, accessed 2026-10-09]
  - Host-marketplace doc on background auto-update: "The check finds new commits, or fails because it can't reach or authenticate to the remote: Claude Code clones the marketplace again and replaces the existing checkout with the new clone... The re-clone can time out on large repositories." So every merge to the marketplace's ref (including the unattended supervisor loop's PR merges) triggers a full re-clone on every auto-updating user's machine. [source: https://code.claude.com/docs/en/plugins/host-marketplace, Anthropic, undated]
  - Requests to make installs sparse or shallow were all closed "not planned" by the stale bot, never implemented at install level: #28426 "Implement sparse checkout for plugin marketplace repositories" (closed NOT_PLANNED 2026-03-25); #40864 "Use sparse checkout for plugin installs - only fetch shipping assets, not entire repo" (closed NOT_PLANNED 2026-05-02; body: "it performs a full git clone of the source repository. This means every file in the repo - tests, CI configs, development tooling... is downloaded to the user's machine"); #46458 "marketplace update should use shallow clone" (closed NOT_PLANNED 2026-05-23). [source: https://github.com/anthropics/claude-code/issues/28426, /40864, /46458, GitHub, verified via `gh api`]
  - Live case of a plugin inside a product repo going wrong, on this exact OS: ChromeDevTools/chrome-devtools-mcp ships its Claude plugin from the product repo; "Its plugin payload is about 100 KB. The clone attempts to pull a submodule chain whose upstream repositories are 1.6 GB and 4.4 GB... on Windows without long-path support fails outright at the 260-character MAX_PATH limit." Consequence: "the marketplace checkout can never be refreshed... the checkout stays stale permanently. `claude plugin update` then reports 'already at the latest version' while printing a warning the user has no way to act on." Environment: Claude Code 2.1.292, Windows 11 Pro build 26300, `core.longpaths` unset. [source: https://github.com/anthropics/claude-code/issues/100214, opened 2026-10-07, OPEN; https://github.com/ChromeDevTools/chrome-devtools-mcp/issues/3021, opened 2026-10-07, OPEN; precursor https://github.com/ChromeDevTools/chrome-devtools-mcp/issues/2829, 2026-09-24, closed "completed" by raising `CLAUDE_CODE_PLUGIN_GIT_TIMEOUT_MS`]
  - Git LFS is a trap in a marketplace repo: "The clone never downloads LFS content, so LFS-tracked files arrive as pointer files." [host-marketplace doc]
- **Weight:** material. Production detail, current docs, not fixed, and the worst case (MAX_PATH, stale-forever) is Windows-specific. The submodule case is the extreme; but the mechanism (full clone + full re-clone per commit, 120 s budget, user-side-only `--sparse`) applies to any repo that grows a Next.js app, fixtures, screenshots, or a long Bun history. Sparse checkout also has to be requested by each user at add time; the marketplace cannot declare it.
- **Mitigation the conclusion would need:** keep the marketplace repo tiny and submodule/LFS-free, or move the marketplace manifest to a separate small repo (the `archive` + `sha256` source the conclusion already plans makes the plugin payload independent of where `marketplace.json` lives); tell users to add `thkennedy/tk-studio#stable` so supervisor-loop merges on `main` don't trigger re-clones; document `--sparse plugins/tk-studio` and `CLAUDE_CODE_PLUGIN_GIT_TIMEOUT_MS`; set `core.longpaths` / `LongPathsEnabled` in the bootstrap.

### F2. An installed plugin is only its own subdirectory; nothing in the rest of the monorepo is reachable at runtime
- **Attacks:** the implied benefit of co-location (plugin scripts sharing code, schemas, or the committed version roster with the supervisor/meta-CLI).
- **Evidence:**
  - A plugin author who runs exactly this shape (one repo, one marketplace.json, N plugins): "Claude Code installs only the plugin's source subdirectory, copied to `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` (checked against a marketplace that ships three plugins from one repo: each cache holds only its own folder). A plugin under `plugins/claude/` therefore cannot import `../../packages/core` at runtime. The core is vendored into each plugin... with `scripts/check-vendor.mjs` failing CI on drift." [source: https://github.com/cyl-castillo/testigo/issues/25, 2026-09-24]
  - Marketplace-builder playbook rule: "No shipped file escapes its plugin via `${CLAUDE_PLUGIN_ROOT}/../..` (resolves in the dev monorepo, breaks once installed)." [source: https://devteam.bryanfinster.com/docs/marketplace-builder-plugin-playbook/, undated]
  - Official symlink rules: links "Outside the marketplace: the symlink is skipped for security"; links elsewhere in the marketplace are dereferenced and copied; "On Windows, use `mklink /D` from an elevated Command Prompt or enable Developer Mode." [host-marketplace doc]
- **Weight:** moderate. Direct production detail from a maintainer running the proposed layout. It does not refute "one repo"; it refutes the idea that one repo buys runtime sharing, and it adds a vendoring/drift-check chore the conclusion does not mention. Tests in `plugins/tk-studio` that pass against the monorepo tree can pass for the wrong reason.
- **Mitigation:** treat `plugins/tk-studio` as a sealed package (CI installs it from the built zip into a clean `CLAUDE_CONFIG_DIR` and runs the tests there); vendor shared bits with a drift check.

### F3. GitHub has one "latest" release per repository; three apps will fight over it
- **Attacks:** "Each app keeps an independent version and its own GitHub Release" in one repo.
- **Evidence:** "The latest release is the most recent non-prerelease, non-draft release, sorted by the created_at attribute. The created_at attribute is the date of the commit used for the release" (so a supervisor release cut from an older commit can rank below a plugin release, and vice versa). `make_latest` must be set per release to control it. [source: https://docs.github.com/en/rest/releases/releases, GitHub, current] Real case: a monorepo released 1.1.0 for one workspace and `/releases/latest` kept showing 1.0.0; maintainer: all packages share one release channel, "so only one of them could be marked as the latest." [source: https://github.com/qiwi/multi-semantic-release/issues/71, GitHub, undated]
- **Weight:** moderate. Not fixable by naming. It bites anything that resolves "latest" (`gh release download` without `--tag`, the Releases page badge, shields, a bootstrap that fetches the meta-CLI's latest asset). The roster-of-versions design sidesteps it only if nothing, including the bootstrap that fetches the meta-CLI itself, ever asks GitHub for "latest".
- **Mitigation:** set `make_latest: false` on two of the three release workflows (or on all, and point everything at tags); the bootstrap must resolve the meta-CLI by tag prefix, not `/releases/latest`.

### F4. The fan-in gate on a user-owned repo: skipped counts as success, and bypass is all-or-nothing
- **Attacks:** "protected `main` uses a single fan-in gate job as the only required status check" and the PR-only flow driven by unattended agents.
- **Evidence:**
  - GitHub docs: required checks "must have a `successful`, `skipped`, or `neutral` status" before merging; GitHub's status-checks reference says a skipped job reports Success, and the troubleshooting page warns against path/branch filtering on workflows that must pass before merge. [source: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches and https://docs.github.com/en/pull-requests/reference/status-checks, GitHub, current] A gate written as `if: always()` that only fails on `needs.*.result == 'failure'` passes on `cancelled` and `skipped`. Mergify's critique of the stub-job pattern: a check that is green because it never ran is indistinguishable from one whose event was dropped. [source: https://mergify.com/blog/path-filters-are-not-a-ci-gate, Mergify, undated]
  - User-owned repos cannot have bypass actors: "Actors may only be added to bypass lists when the repository belongs to an organization." By default protections "do not apply to people with admin permissions to the repository" unless "Do not allow bypassing the above settings" is enabled. [about-protected-branches, GitHub] On a one-maintainer repo the only admin is the maintainer, whose token the unattended agents and the merge step use, so protection is either advisory (admin bypass on) or absolute for the maintainer too (bypass off, no hotfix lane). The rulesets page I fetched states availability only "for customers on GitHub Team and GitHub Enterprise plans" (org-level context); I could not extract the plan-availability sentence for branch protection on a private personal repo, so that remains unverified. [source: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets, GitHub]
  - Tag-triggered release workflows cannot be path-scoped at all: "Path filters are not evaluated for pushes of tags." Fine for the `supervisor--v*` globs, but a tag push also runs any workflow with a bare `push:` trigger that lacks a `branches`/`tags` filter ("If you define neither... the workflow will run for events affecting either branches or tags"). [source: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax, GitHub, current]
- **Weight:** moderate. The gate pattern itself is the documented workaround; the risk is in the details and in who can merge. The bypass point is a structural property of user-owned repos and directly affects three apps sharing one `main`.
- **Mitigation:** gate must assert each `needs.<job>.result == 'success'` except jobs the change-detection step deliberately skipped; decide explicitly whether admin bypass stays on; keep every non-release workflow filtered to `branches:` so tags don't fan out.

### F5. `git subtree add` keeps blame but loses path-limited history; the git project itself still has an open fix
- **Attacks:** "folded in with `git subtree add` (full history preserved)".
- **Evidence:** A 2026 patch on the git list describes that after a subtree merge, path-limited `git log --follow` "shows only outer-repo commits, while `git blame prefix/test.c` does find the original commits"; the patch (making log check each merge parent for renames as blame does) was still awaiting review when I looked. [source: https://lore.kernel.ime.usp.br/git/agLU58gbG1y7KLz-@collabora.com/, git mailing list, 2026] GitLab bug: files added via subtree show history under Blame but an empty History view; `--follow -m` needed. [source: https://gitlab.com/gitlab-org/gitlab/-/issues/421655, GitLab] LWN on the udev/systemd subtree merge: `git log subtree/X/Y/Z` shows changes since the merge and `git log X/Y/Z` shows changes before it; the paths diverge forever. [source: https://lwn.net/Articles/490579, LWN, 2012] The filter-repo README's canonical alternative: rewrite each source to a leading directory and prefix its tags so they don't collide on merge. [source: filter-repo README via https://git.blob42.xyz/Archives/git-filter-repo/raw/commit/b04ba30e4619ed863cc7a2f04fc50d4b20c84f7c/README.md]
- **Weight:** moderate. Long-standing, reproducible, matters most for AI agents that run `git log -- path` to understand a file (they will see history starting at the subtree merge unless they know to add `-m --follow`). Tag collisions (`v1.2.0` in both repos) are not addressed by `subtree add` at all. No source says it blocks the merge; it degrades the "full history" promise.
- **Mitigation:** `git filter-repo --to-subdirectory-filter supervisor` with a tag-rename prefix on a throwaway clone, then `git merge --allow-unrelated-histories`; or accept and document `git log -m --follow`.

### F6. Self-updating binaries on Windows fail in known ways, including Claude Code's own updater, and the supervisor runs as a service from the checkout the updater would touch
- **Attacks:** "a small self-updating meta-CLI" that "installs and updates all three apps" on Windows, plus running the supervisor from a live git checkout.
- **Evidence:** restic's Windows self-update regressed in 0.15 on the final rename step; workaround was pre-creating an empty target file. [source: https://forum.restic.net/t/self-update-windows-started-failing-after-release-of-0-15/5836, restic forum] go-update: a leftover open handle made the rename fail with "in use". [source: https://github.com/inconshreveable/go-update/issues/14] Anytype CLI users hit "failed to replace binary"; maintainers: happens when the CLI "runs as a service or a process is still active after the service stops." [source: https://community.anytype.io/t/headless-anytype-client-for-server-based-automation/28263?page=3] A Claude Code auto-update on Windows (2.1.154 to 2.1.156) reportedly replaced `claude.exe` with a binary that printed Bun's help text; fresh terminals were unusable until rollback. [source: https://claudeissues.com/issue/63402-auto-update-on-windows-shipped-a-binary-that-boots-into-buns-cli-instead-of-clau, third-party mirror of the tracker, 2026-05; not verified against github.com] Claude Code's own plugin cache has a Windows-flavoured failure: "the new copy or the version folder stayed busy while the install ran (ENOTEMPTY) - usually a scanner still reading the freshly downloaded files." [troubleshooting doc]
- **Weight:** moderate. All production detail; none is specific to monorepo vs polyrepo, but the conclusion adds a third moving part (meta-CLI) whose failure mode is "every app's update path is broken at once", and a console-hosted service that must be stopped before its checkout is updated.
- **Mitigation:** rename-aside-then-swap, keep the previous binary for rollback, verify the new binary runs before deleting the old, stop the service before touching its checkout (or run the service from a versioned release directory, not the git checkout).

### F7. A documented split of a monorepo, and what the opposite camp says
- **Attacks:** the general "one repo" direction.
- **Evidence:** MoJ Sirius ADR 0003 (2020-11-17, Accepted): "any changes to a component of Sirius require all of the components to be rebuilt and retested"; decision: "The Sirius Repository will be split into component parts" to speed local and CI builds, with "Allows us to release components independently" as a listed benefit and "requires the team to keep sub repos maintained" as the cost. [source: https://docs.sirius.opg.service.justice.gov.uk/documentation/architecture-decisions/0003-breaking-down-the-monorepo, UK MoJ OPG, 2020-11-17] Counter-evidence the synthesis should weigh: Genkit's "WHY_MONOREPO" argues a cross-cutting change in split repos becomes coordinated PRs each waiting on the core release, versus one PR/one CI run in a monorepo. [source: https://glama.ai/mcp/servers/@firebase/genkit/blob/3e0317eac483aa2c1b63652b2d15323196620468/py/docs/WHY_MONOREPO.md, Firebase Genkit maintainers] An essay describes teams oscillating between the two and attributes the churn to feedback loops, not repo shape. [source: https://mufridk.medium.com/there-and-back-again-transitioning-from-monorepo-to-multirepo-and-back-again-436af8fe8a33, Medium]
- **Weight:** weak-to-moderate. Team-scale accounts, no single-maintainer retrospective found. The Sirius symptom ("rebuild and retest everything") is exactly what a single fan-in gate produces unless each app's jobs are path-conditional, which brings back the F4 skipped-equals-success problem.

### F8. Windows link semantics inside the repo: Bun/npm workspace junctions, Developer Mode, and worktree cleanup
- **Attacks:** "Bun/TypeScript supervisor" and "planned Next.js web front end" sharing one repo on Windows with agents that create and remove worktrees.
- **Evidence:** A Bun discussion reports junctions inside `node_modules` pointing at a repo producing startup errors on Windows while a copied folder and WSL worked. [source: https://github.com/oven-sh/bun/discussions/10172, GitHub] Anthropic's own doc requires elevated `mklink /D` or Developer Mode for symlinks on Windows. [host-marketplace doc] A report says npm-workspace junctions created in a git worktree were followed by `git worktree remove --force` and source files in the main repo were deleted. [source: https://claudeissues.com/issue/60604-windows-agent-created-node-modules-junctions-from-git-worktrees-cause-source-fil, third-party mirror, unverified] The chrome-devtools case above shows MAX_PATH killing a nested checkout when `core.longpaths` is unset, which is the default on this machine's git. [issue 100214]
- **Weight:** weak-to-moderate. The junction-deletion report is mirror-only and about npm, not Bun; the rest is documented behaviour. It argues for keeping the Node-heavy apps' dependency trees out of any path that agents or `git worktree` recurse into.

### F9. `irm | iex` and "roster" bootstraps: criticism exists but is thin
- **Attacks:** "`irm ... | iex` on Windows" bootstrap.
- **Evidence:** The only criticism found was automated agent-skill security audits (clawhub.ai, skills.sh) noting that `Invoke-RestMethod | Invoke-Expression` runs a mutable script with no pinned release, signature or digest, and HTTPS does not protect against a compromised publishing pipeline. Defender/SmartScreen false positives on unsigned updater binaries are documented in vendor forums (Advanced Installer thread: Defender flagged `updater.exe`; a Defold user reported detection even on a signed build). [sources: https://cdn.advancedinstaller.com/forums/viewtopic.php?p=135696; https://forum.defold.com/t/exe-file-is-a-virus/322; scanner pages on skills.sh / clawhub.ai]
- **Weight:** weak. Opinion and forum anecdotes, nothing specific to this design. Worth one line: publish the checksum of the bootstrap script itself and a download-verify-run alternative.

## Searched for and not found
- A first-person retrospective of merging a service and a plugin/CLI into one repo and later re-splitting, with CI/release breakage detail (queries: "monorepo regret retrospective split back", "service and library coupled releases CI"). Only the Sirius ADR (F7) and general essays turned up.
- Any tool choking on a `--v` double-hyphen tag separator (queries on release-please / semantic-release / changesets tag prefixes). Nothing. Contrary to the attack, Claude Code's own plugin-dependency convention is `<plugin>--v<version>` git tags (host-marketplace doc), so the proposed `tk-studio--vX.Y.Z` form aligns with the harness.
- Docker Sandboxes (microVM) performance or file-sync problems with a large mounted repo or `node_modules` on Windows (query "Docker Sandboxes claude code microVM mounted workspace Windows performance"). Only launch posts and older Docker Desktop bind-mount threads; nothing sandbox-specific.
- Reports of marketplace install/update breaking specifically because the repo contains a Bun lockfile or a Next.js app. Nothing; the failures found were size, submodules, LFS and MAX_PATH (F1).
- Authoritative material on PATH not refreshing after an installer edits it on Windows. Nothing beyond general knowledge.
- A GitHub docs sentence confirming branch protection/rulesets availability on a private user-owned Free-plan repo (two fetches of the protected-branches and rulesets pages did not surface it). Flagged unverified in F4.
- Not searched for lack of budget: roster/manifest drift stories (mise.lock, rustup, asdf), Claude Code context pollution from large repos, secret-scanning / CODEOWNERS limits on personal repos.
