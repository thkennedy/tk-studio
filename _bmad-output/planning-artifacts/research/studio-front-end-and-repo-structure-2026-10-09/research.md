# Research: studio front end and repository structure

**Decisions this research serves:** A, the repository structure for the plugin, the supervisor and the front end, with per-app releases and one installer; B, the gamified studio front end, Next.js first, wrapping Hermes chat, designed around the contract-studio engagement loop.

Every `[n]` resolves in the source appendix. Confidence is per claim: high (verified or primary, fresh), medium (single credible source, or primary but older than the pack's freshness bar), low (snippet, weak publisher or disputed). Claims the verifiers could not reach are marked **unverified** in the text.

## 1. Executive summary

### Decision A: one repository, three apps, per-app releases, one installer

**The evidence says: consolidate into `tk-studio`.** Fold the supervisor in with `git subtree add` (full history, one join commit), keep the plugin at `plugins/tk-studio` with its pinned zip release and `tk-studio--vX.Y.Z` tags, add the front end as a third app, cut each app's GitHub Release from its own tag prefix with one tag-triggered workflow per app, protect `main` with a single fan-in gate job as the only required check, and ship a bootstrap script plus a self-updating meta-CLI that installs and updates all three apps from a committed roster of compatible versions. Archive the old supervisor repository.

Three findings drive that answer:

1. **Comparable projects do exactly this, and the ones that split moved back.** Omnara ships three deployables from one repository with the tag prefixes `omnarad-`, `cluster-` and `sdk-` and one release workflow each; its newcomer path is `git clone` then `docker compose up` [1][2]. OpenCode cuts a weekly lockstep core release and a separate `vscode-v` prefix from one Bun monorepo [3]. Happy archived its separate CLI and server repositories on 2026-02-14 and folded both into its monorepo [5]. PostHog carries four tag schemes and n8n two release lines in one repository [6][7]. The only written rationales for splitting a product's own code are rebuild coupling at team scale (Ministry of Justice Sirius, 2020) [8] and build time plus cross-project dependency tangles in a company (Unkey RFC 0010, 2025, executed only partially) [9]; Hermes's eviction of third-party plugins is a maintenance-load rule for outside contributions, not a split of its own apps [12]. None of these conditions holds for one maintainer with three apps and a task graph. The only full merge-back account (Proton, 2022) puts the cost at a CI rewrite and a cut-over weekend [11]. The current pro-monorepo argument is explicit about AI assistants: a split loses the whole dependency graph [10].
2. **Claude Code's marketplace is built for a plugin inside a bigger repository.** A plugin may be a relative subfolder of the marketplace repository; `git-subdir` does a sparse, partial checkout of a subfolder of another repository; the `archive` source takes a zip over HTTPS with a SHA-256 pin, up to 256 MiB; and Claude Code's own docs name `<plugin>--v<version>` tags as the convention dependency ranges resolve against, so the existing prefix is idiomatic [29][30][31]. The official marketplace itself is a monorepo of 53 in-repo plugins beside 262 SHA-pinned external pointers [17].
3. **The migration is cheap, and the costs are known.** `git filter-repo --to-subdirectory-filter` plus `--tag-rename` rewrites the supervisor's history under its new folder with prefixed tags, the pattern an independent monorepo-merge walkthrough uses, and a merge with `--allow-unrelated-histories` joins it [50][51]; `git subtree add` is the one-commit fallback [52]. GitHub archiving freezes the old repository at its URL [54]. Known costs: path filters are not evaluated for tag pushes, so each app's workflow selects by tag glob [33][34]; GitHub has no path-conditional required checks, so one fan-in gate job (with `if: ${{ !cancelled() }}`, failing on any failed need) is the required check [37][38]; release-please's parser takes a single-character separator, so `tk-studio--v` tags stay scripted rather than release-please-managed [43][42].

**Biggest caveat (from the red team, §11):** the plugin's distribution must not depend on cloning the monorepo. Claude Code clones the whole marketplace repository on every install and every refresh, within a 120 s budget, with sparse checkout available only as a user-side flag, and a plugin shipped from a product repository is failing today on this exact Windows build at the MAX_PATH limit [239][240]. The verdict survives because the pinned-zip `archive` source and the meta-CLI deliver the plugin without that clone, and the repository carries no submodules or LFS; the ADR must make that a design rule, not an accident. Two further corrections: `git filter-repo` replaces `git subtree add` as the first-choice migration because subtree merges lose path-limited `git log` history that agents rely on [249], and bypass actors do not exist on user-owned repositories, so the gate job's semantics and the admin-bypass choice are explicit decisions [246].

**The installer** is a bootstrap script (`irm … | iex` on Windows, the form Claude Code, uv, Hermes and Microsoft's own dev-box setup use [56][57][61][63]) that installs a small self-updating meta-CLI; the meta-CLI reads a committed roster (versions, URLs, checksums, the shape of `mise.lock` and rustup's channel manifests [72][73]) to install and update the plugin, the service and the front end. Hermes's `install.ps1` is the worked Windows blueprint: hash-pinned downloads into versioned tool slots, only a launcher directory on the user PATH, a JSON provenance marker, re-run equals update [62]. The meta-CLI must own the plugin leg: third-party marketplaces do not auto-update by default and there is no update-all command [30][75][74].

### Decision B: the front end

**The evidence says: a Next.js static export served by the Bun supervisor on one origin; a hybrid renderer (DOM for HUD, bubbles and boards, one plain PixiJS canvas for the floor); SSE for office state; Hermes consumed through its API server, server-to-server; the engagement loop implemented as a state machine with a dedicated approval verb.**

1. **No precedent renders story or epic progress; the vocabulary to extend exists.** Pixel Agents (9.6k stars, MIT) publishes an AsyncAPI contract and accepts an external producer over `POST /api/hooks/claude` [84][86]; claude-office is the only Next.js + PixiJS precedent and the only one with a vendor-neutral REST ingest and a fixture simulator [88][89]; AI Town's rule set (one authoritative mutator, diffs per step, interpolation buffers, ordered inputs) is the architecture lesson [92]; Paperclip's goals → projects → tickets → approvals model is the nearest to the studio's epics and stories [102][103].
2. **Hosting and transport are constrained by the cookie and by SSE.** A static export forbids cookies, rewrites, headers and Server Actions, so sign-in and data stay in the Bun API [117]; cookies have no port isolation and `ts.net` is on the Public Suffix List, so one origin with host-only cookies is the safe shape [147][149]; an EventSource dies permanently on a non-200 response and silently on iOS 18 when backgrounded, so the client needs a heartbeat watchdog and re-authentication [133][150].
3. **Every agent product gates on a plan; none quotes a price; prompt-interpreted gates leak.** Jules exposes an eight-state session enum with `AWAITING_PLAN_APPROVAL`, `AWAITING_USER_FEEDBACK` and a dedicated `:approvePlan` verb [185]; Cursor's plan mode, enforced by model interpretation, switches to editing without consent in multiple reports and has no hard setting [179][180]; ProKanban's 50/85/95 Monte Carlo band from item counts is the quote the studio can compute from its own metered history [193], priced for the tail (one IT project in six overruns cost by about 200 percent) [198][199].

**Biggest caveat:** PixiJS v8 has no primary recipe for integer zoom on phones and an open mobile blurriness issue [115][132]; `@pixi/react` is effectively unmaintained [110][111]; LimeZu's character pack does not name sit or typing animations on its page [160]; `tailscale serve` with two path mounts is undocumented [144].

## 2. A1: how comparable projects structure plugin, service and UI

**Layouts observed (GitHub API, 2026-10-09).** One repository is the norm for product cores: OpenCode (Bun workspaces, 32 packages under `packages/` on 2026-10-09, Turborepo) [3][264]; Vibe Kanban (Cargo workspace of 33 crates plus an npm wrapper) [21]; Happy (pnpm monorepo of app, CLI, server, wire) [4][5]; Omnara (Go monorepo with `frontend/`, `skills/`, compose) [1][2]; Hermes (uv plus npm workspaces in one repo, no Turborepo) [13]; bmad-loop (one repo that is both a uv package and a Claude Code plugin) [15]; Coder (CLI, server, web UI) [27]; Windmill (backend, frontend, CLI, five clients) [28]; n8n [7]; PostHog (uv + pnpm + Rust + Turborepo) [6][20]; the official Claude Code marketplace [17]. Satellites appear where the runtime or ownership differs: Happy's desktop app and agent runtime [5]; Omnara's Codex integration [1]; Supabase's engines, each its own repo in its own language, consumed by the monorepo only as pinned Docker images that lag upstream by several versions [19]; Hermes's third-party plugins, pushed out of core for "maintenance load, not quality" [12]. BMad's distribution is deliberately multi-repo, and its README sends Claude Code users to a 0-star `bmad-plugins` repo while an older marketplace repo still exists, which is the newcomer-confusion cost in the wild [16].

**Release and version.** Per-deployable tag prefixes plus one workflow per deployable is routine (Omnara [1], Happy `cli-` [4], OpenCode `vscode-v` [3], PostHog `desktop-v`/`agent-skills-v`/`release-` [6], n8n per-package tags [7]). Lockstep versioning works when one artifact carries everything (Coder, Windmill [27][28]). Tag namespaces drift without a convention fixed early: PostHog's four schemes [6], Vibe Kanban's malformed tags [21], Hermes's CalVer-to-SemVer switch, which its catalog rules make necessary (plugin `requires_hermes` floors must be SemVer) but which the v0.21.6 release notes attribute to "the new stable release pipeline" [13][14][264].

**Newcomer paths.** `git clone` + `docker compose up` (Omnara, Windmill) [2][28]; one-line install scripts (OpenCode, Hermes, Coder, n8n) [3][13][27][7]; `npx`/`npm -g` wrappers (Vibe Kanban, Happy) [21][4]; `uv tool install … @git+…@tag` (bmad-loop, whose README warns that upgrades need `--reinstall`) [15].

**Mixed Python + TypeScript in one root.** PostHog runs one root uv workspace (`exclude-newer = "7 days"`) and lets Turborepo cache per-product pytest tasks with `uv.lock` as an input; it does not use Turborepo's experimental Python workspaces [20][26]. Hermes does the same without Turborepo [13]. Bun workspaces link local packages and support catalogs and `--filter` but have no task graph or cache [22]. pnpm falls back to junctions on Windows without Developer Mode [23]. The Nx Python plugin is active but community-maintained and warns that the whole lockfile must be a task input [24]. uv workspaces impose one `requires-python` and one lockfile [25].

**Rationales.** Split: rebuild coupling (MoJ, 2020) [8]; build time, dependency management, onboarding, cross-project conflicts (Unkey, 2025; the dashboard and docs nevertheless stayed in the core repo) [9]; shedding unmaintained third-party code (Hermes) [12]. Merge: mirrored git operations per feature, builds against unmerged dependencies, no atomic rollback (Proton, 2022; cost a full CI rewrite) [11]; cross-cutting changes become ordered multi-PR projects, version-pin matrices, lost atomic refactors, and an AI assistant that cannot see the whole graph (Nordmann, 2026) [10]. The pin-bump machinery that split repos require is a standing cost: Anthropic's nightly bot opens up to 60 SHA-bump PRs a night across 262 external plugins [18]; Hermes re-reviews every SHA bump [14]; Supabase's compose pins lag upstream [19].

**Verification (A1-r1-verify).** A1.1 verified from Omnara's live workflow files, tag counts and `compose.yaml` (the CLI is a fourth tag stream) [264]; A1.2 verified with one number corrected (OpenCode has 32 package directories, not 28; `vscode-v` 13 tags, Happy `cli-` 15 tags, PostHog's four prefixes 190, 2803, 2 and 11 tags) [264]; A1.5: Nordmann verified by a same-day Hacker News submission and a Wayback capture [265], Happy's fold-in verified by GraphQL `archivedAt` 2026-02-14T07:55Z on both old repositories [264], Proton's account confirmed in date, author, CI rewrite and Saturday cut-over by a Wayback capture but with no second write-up anywhere [266]; A1.6 verified (PostHog's `exclude-newer`, `uv.lock` as a Turborepo input, zero hits for the experimental flag; the marketplace's 315, 262 and 60; pnpm's junction fallback from `symlink-dir`) with the Hermes rationale disputed as above [264]. A1.3 (the Sirius ADR) could not be independently reached: its source repository is private and the Wayback Machine was unreachable for the URL, so it rests on the primary page alone.

**Benefits and drawbacks.**

| Approach | Benefits | Drawbacks |
|---|---|---|
| One repo, per-app releases (Omnara, Happy core, OpenCode, PostHog, n8n) | Newcomer gate met trivially [2]; per-app cadence routine [1][4][3]; marketplace supports in-repo plugin folders and pinned zips [29]; mixed uv + Bun has precedents and first-party tooling [20][25]; AI assistant sees the whole graph [10] | Tag namespaces need a convention fixed early [6][21]; release automation grows with deployables [7]; without a task graph every change retests everything, the documented split trigger [8]; uv workspaces share one `requires-python` [25] |
| Separate repos (BMad org, MoJ, Hermes satellites) | Independent cadence with no coordination [15]; unmaintained parts shed without touching core [12]; mechanical boundary enforcement, the one split reason Nordmann concedes [10] | Newcomers must learn which repo is source and which is distribution [16]; interfaces become explicit contracts and every sub-repo needs upkeep [8]; pin-bump bots and lagging pins [18][19]; cross-cutting changes become ordered multi-PR projects [10] |
| Hybrid (core monorepo plus satellites: Happy, Omnara, Hermes, official marketplace) | Shared-code core stays together, different-runtime apps live apart [5][17] | Duplication and ambiguity creep in (two things named `happy-agent`) [5]; no project documents its boundary rule [5] |

## 3. A2: per-app releases in one repository, migration, marketplace layout

**Marketplace constraints (Claude Code docs, live 2026-10).** The marketplace root is the directory holding `.claude-plugin/marketplace.json`; relative sources resolve from it; a `url`-type marketplace fetches only the JSON, so relative sources need a git-type marketplace [29]. Plugin sources: relative path (subfolder of the marketplace repo), `github`, `url`, `git-subdir` (sparse and partial checkout so "a plugin in a large monorepo installs without downloading the rest of the repository"), `npm`, `archive` (HTTPS zip plus 64-hex `sha256`, refused on mismatch, root at top or one level down, v2.1.224+), `command` (v2.1.229+) [29]. `ref` is a branch or tag and `sha` a full commit; with both, the SHA wins [29]. `metadata.pluginRoot` (v2.1.239+) lets entries use bare names under `./plugins` [29]. Hosted limits: `marketplace.json` 5 MiB; archive zip 256 MiB, 120 s, five HTTPS redirects, and a cross-origin redirect drops configured headers [31]. Version is manifest `version`, then entry `version`, then a source-derived hash; `claude plugin update` recomputes and leaves the cache alone when it matches, so a pinned manifest version freezes users until the string changes [30]. Windows: `command` sources run through `cmd.exe`, `link` mode is refused, substituted paths use forward slashes [29][32]. Verified: relative subfolder sources are what the official catalog ships, and `archive` with SHA-256 is in the Claude Code changelog [17][29].

**GitHub Actions, Releases and protection.** Path filters are not evaluated for tag pushes (docs, and an independent experiment) [33][34]; a workflow with only `on.push.tags` never fires on branches [33]; `gh release download` without a tag takes the repo-wide latest, so consumers name the tag [39]; `gh release list` orders by date with a default limit of 30 and one repo-wide `isLatest`; a live prefix filter on `thkennedy/tk-studio` returned `tk-studio--v0.2.16` as the newest of 11 [40]. Rulesets offer required PRs, required status checks, linear history and signed commits, but no path condition, and per-team file patterns are unavailable on user-owned repositories [35]; the native request for path-conditional required checks is still "In Backlog" [37]. The fan-in pattern: one `final-status` job that `needs:` every job, runs `if: ${{ !cancelled() }}` and fails when any need failed or was cancelled, because a skipped job reports Success and would not block a merge [38]. Bypass actors (admin role, "for pull requests only") would reproduce today's admins-not-enforced setting while keeping PR-only main [36], but bypass lists exist only on organisation-owned repositories, so this does not apply to `thkennedy/tk-studio` (§11, finding 4 [246]).

**Release tooling.** release-please manifest mode gives per-path versions and one GitHub Release per package, confirmed independently [41][44]; `include-component-in-tag` and `include-v-in-tag` default to true in the schema, `tag-separator` has no stated default [42]; the parser captures one non-alphanumeric separator character, so `tk-studio--v1.2.3` parses as component `tk-studio-` plus `-` [43]. changesets will not version or tag private packages unless `privatePackages` is set, fixes tags as `pkg@version`, and creates Releases only inside a publish-script path [45][46][47]. semantic-release's monorepo plugins have been dormant since mid-2024 [48]. GoReleaser's monorepo mode is Pro-only [49]. `bun publish` is a packaging step, not an orchestrator; Bun itself tags `bun-v1.4.2` [260]. uv: `uv version --package … --bump`, `uv build --package`, `uv publish` with trusted publishing [55].

**Migration.** `git subtree add --prefix=<dir> <remote> <branch>` imports the subproject and "a new commit is created automatically, joining the imported project's history with your own"; `--squash` imports one commit instead; `split` re-extracts a synthetic history deterministically [52]. `git filter-repo --to-subdirectory-filter DIR --tag-rename '':'prefix-'` rewrites paths and prefixes tags, used for monorepo merges in an independent walkthrough; signed tags lose their signatures; filter-repo requires a fresh clone [50][51]. Transfer redirects web and git URLs and carries issues, PRs, hooks and secrets until the old name is reused; archiving creates no redirect but keeps code, releases and tags readable at the old URL [53][54]. Nothing retrieved moves GitHub Releases or assets between repositories [53].

**Benefits and drawbacks.**

| Approach | Benefits | Drawbacks |
|---|---|---|
| One repo, tag-prefixed releases per app | The `tk-studio--vX.Y.Z` zip gate is directly supported by `on.push.tags` globs and `gh release download <tag>` [33][39]; the prefix matches Claude Code's documented `<plugin>--v<version>` convention [31]; the marketplace keeps pointing at the in-repo folder or the Release zip [29]; one PR flow and one protected main [35]; `git subtree add` keeps full history and is reversible [52] | Path filters ignore tags, so release jobs select by glob [33]; no path-scoped required checks, so a gate job is mandatory [37][38]; "latest release" is repo-wide [39][40]; release-please cannot parse `--`, changesets cannot emit it, so the Release step stays scripted [43][46] |
| Separate repos | Each repo's protection, checks and latest release are unambiguous [35][39]; plain marketplace root, no rewrite [29] | Cross-repo marketplace entries still need `github`/`git-subdir`/`archive` wiring [29]; coordinated PRs and tags in three places; pin-bump upkeep [18] |
| One repo plus a meta release pinning a compatible set | Consumers fetch one manifest by one tag, then each app's asset [39]; the natural owner of `isLatest` [40] | No tool makes a cross-app compatibility manifest natively; a fourth tag and workflow to maintain; the roster (A3) does this job without a fourth release |

## 4. A3: one installer and updater

**Patterns retrieved.** (1) Bootstrap script plus self-updating launcher: Claude Code (`irm https://claude.ai/install.ps1 | iex`, no admin, side-by-side versions under `~/.local/share/claude/versions/`, `latest` and `stable` channels, a `minimumVersion` floor, a per-release `manifest.json` of SHA-256s, GPG-signed from 2.1.89 per the docs; the two-versions retention and the 2.1.89 boundary have no independent source) [56][79]; uv (`install.ps1`, version in the URL, `uv self update`, `UV_UNMANAGED_INSTALL` disables self-update) [57][60]; Hermes (`install.ps1` pins uv 0.12.3 and PortableGit by SHA-256, refuses any uv on PATH, versioned tool slots, only `%LOCALAPPDATA%\hermes\bin` on the user PATH, a `.hermes-bootstrap-complete` JSON marker, re-run fast-forwards the checkout) [61][62]; Microsoft's `WindowsDeveloperConfig` (`irm https://aka.ms/devconfig/standard/setup.ps1 | iex` over WinGet Configuration files) [63]. (2) `uv tool install` as a CLI channel: install-time constraints persist and `uv tool upgrade` respects them (maintainer-confirmed) [58][59]. (3) The marketplace: scriptable with `--scope project` and `--yes`; third-party auto-update off by default; `claude plugin update <plugin>@<marketplace>` per plugin; no update-all (open feature request; an earlier one closed not-planned) [75][30][74]; a `command` source re-runs every session, needs the meta-CLI already on PATH, runs under `cmd.exe` from the home directory, and cannot use `link` mode on Windows, so it is a hook for an installed meta-CLI, not the first bootstrap [29][30]. (4) winget: `InstallerSha256` required, zip-with-portable packages, PATH not refreshed in the installing shell (verified), one PR per version, no roster concept [67][68][69]. (5) MSIX: no per-user services, no install-directory writes, HKLM writes diverted to a private hive (mechanism disputed between redirect and fail; outcome agreed), private AppData [70][71]. (6) Roster with checksums: `mise.lock` records resolved versions, URLs and checksums and `mise install --locked` reproduces them [72]; rustup resolves a channel to a manifest of components and falls back to the newest build that has them all [73]. (7) Delayed stable track: Tailscale updates about a week after release; Claude Code's `stable` channel is about a week old [81][56]. Integrity: `gh attestation verify <file> --repo owner/repo` checks a download against Sigstore attestations [64]; the `curl | sh` criticisms (poisoned origin, differential serving, truncated script) are mitigated by a pinned version plus a hash checked against a separately trusted manifest [76][77][78]. Swapping a running executable on Windows: it can be renamed, not unlinked, so rename-then-replace or a launcher plus versions folder [66]. gh extensions upgrade with `--all` but document no hash verification [65]. Scoop's autoupdate needs a self-hosted excavator for a private bucket [80].

**Benefits and drawbacks.**

| Approach | Benefits | Drawbacks |
|---|---|---|
| Bootstrap script + self-updating meta-CLI (wrapping uv tool install and the marketplace) | Matches what Claude Code, uv, Hermes and Microsoft ship on Windows [56][57][61][63]; no admin; one script installs uv, the meta-CLI, Bun, the service, the front end, and runs `claude plugin marketplace add …#tag` + `claude plugin install … --yes` [75]; Hermes's script is a copyable blueprint [62] | Inherits the `curl | sh` criticism unless it pins and hashes [76][78]; bundled binaries trip antivirus (Hermes documents it) [61]; Windows locks running executables, so the updater stops the service before swapping [56][66]; every component's install path is yours to keep working |
| Committed roster of a compatible set (mise.lock / rustup shape) | One file per meta-release with tags, versions, URLs and SHA-256s; rollback is "install the previous roster" [72][73]; the plugin's manifest `version` can be written from the same roster so Claude Code's recompute agrees [30] | You cut meta-releases as well as app releases; a "newest set where all components exist" rule is extra logic [73] |
| Marketplace alone | Zero new infrastructure for the plugin leg [75] | Installs only the plugin; no auto-update for third-party marketplaces; no update-all; no checksum verification documented [30][74][75] |
| winget package for the bootstrap binary | Discoverable, hash-verified, portable zip support [67][68] | One PR per version, silent install required, PATH not refreshed, upgrade fails while running, no roster [68][69][56] |
| MSIX | Clean install and uninstall, signing | No per-user services, no install-dir writes, private AppData; a console-hosted Bun service and a mutable plugin directory conflict with it [70][71] |
| mise as the runtime manager | Lockfile with checksums, `run_windows` tasks [72] | A fourth tool before the one command runs; Windows support not evidenced on the pages read [72] |

## 5. B1: agent-office precedents

**Named precedents.** Pixel Agents (`pixel-agents-hq/pixel-agents`, 9,602 stars, MIT, pushed 2026-10-09, v1.4.1 2026-08-15): VS Code extension plus standalone CLI serving a Canvas 2D office over WebSocket; hooks-first (SessionStart, PreToolUse, PermissionRequest, Stop) with a JSONL fallback, both normalised to one `AgentEvent`; an AsyncAPI 3.0 contract of 52 interfaces whose `AgentStatus` carries `active | waiting` plus `awaitingInput`, tool messages, subagents keyed by the parent's tool call, team info and context usage [82][83][84]. A non-hook producer is documented: `POST http://127.0.0.1:<port>/api/hooks/claude` with a Bearer from `~/.pixel-agents/server.json` (3100 is the documented example; the CLI's default port is OS-assigned, so a producer reads the port from that file), raw Claude-hook JSON, 64 KB cap; the shipped `claude-hook.ts` hook script fans each event out to every live server listed under `~/.pixel-agents/servers/` with a 2 s timeout [86][85][205]. Timers: `SESSION_END_GRACE_MS` 2000, `PERMISSION_TIMER_DELAY_MS` 7000, `TEXT_IDLE_DELAY_MS` 5000, `TOOL_DONE_DELAY_MS` 300, heuristics suppressed when hooks deliver [85]. External furniture packs load from a per-item `manifest.json` [87]. Its six characters derive from JIK-A-4's Metro City pack and the repo carries no attribution file (medium) [83]. claude-office (`paulrobello/claude-office`, 553 stars, MIT, pushed 2026-09-14): Next.js + PixiJS + Zustand front, FastAPI back; `POST /api/v1/events` with a 23-type discriminated union, per-session rate limit 1000 per 60 s, immediate `accepted` and background processing; WebSocket fan-out; `make simulate` replays five scenarios; a `KanbanTask` model and Needs-you / Working / Done / Ended columns [88][89][90]. AgentRoom: a one-day Tauri port of Pixel Agents, dormant since 2026-03-05, licence unresolved [91].

**Prior art and new entrants.** AI Town: the engine is "the only mutator of game state", 16 ms ticks batched into 1 s steps, diffs per step, `HistoricalObject` buffers for client interpolation, an ordered `inputs` queue with status, LLM work that may only act by submitting inputs; stated limits are game state under a few dozen KB and about 1.5 s input latency [92]; `activity.until` expiries and `ACTION_TIMEOUT` 120 s bound stuck states [93]. New since September: `AgentSystemLabs/agent-office` (687 stars in two weeks, cartoon 3D, hosts PTYs, one floor per repo, cork boards of issues and PRs, "Work in progress") [94]; a cluster of weekend projects (paperclip-office, "view-only pixel office pane … your checklist, and this branch's PR") [99]. Large neighbours: munder-difflin (8,602 stars, Electron + Pixi, PTYs, a file-based "hive" event plane with a single committer, per-agent inbox/outbox, append-only `log.jsonl`, a `tasks.json` ledger, FIPA-lite message envelopes, LimeZu assets in a public MIT repo under a split `LICENSE-ASSETS` notice) [95][96][97][98]; clawd-on-desk (6,397 stars, AGPL, so no code reuse), starnet (keyless relay with sealed frames for a phone feed) [107][104]. Anthropic's `claude agents` (research preview) groups local sessions into Ready for review / Needs input / Working / Completed and `claude agents --json [--all]` is a scriptable feed with attach, logs, respawn, rm, stop and daemon companions [100][101]. Paperclip (MIT, 98,950 stars) models goals → projects → ticket tasks with approvals, heartbeat runs and budgets; paperclip-office projects office state from the latest run event, issue status and pending approvals, with "stuck" as no run events for N minutes and a human-only Decision box [102][103]. The JetBrains port is transcript-watching only [105]. Generative Agents is historical; its transferable idea is replay as a first-class mode [106].

**Gap.** No precedent renders task, story or epic progress; the nearest are cork boards, a current-ticket label, a kanban model in claude-office's state, and paperclip-office's issue projection [94][95][90][103].

**Benefits and drawbacks by event source.**

## 10. Cross-dimension insights

1. **The roster closes the repo question's last gap.** A2 found no tool that makes a cross-app compatibility manifest and warned that a "meta release" would be a fourth hand-maintained tag [41][46]; A3 found that a committed roster with checksums (the `mise.lock` and rustup shape) is the cleanest expression of a compatible set and that the meta-CLI must own plugin updates anyway [72][73][30]. One roster file per meta-release, published as a release asset and consumed by the meta-CLI, replaces the meta release and lets the plugin's manifest `version` be written from the same source Claude Code recomputes against [30].
2. **The supervisor already is the hosting answer.** B3's one-origin recommendation (static export served by Bun, host-only cookie, SSE with `server.timeout(req, 0)`) means the front end is a build artifact the service serves, not a fourth process [117][135][147]. That removes the strongest structural reason to keep the front end's release independent of the service's and makes the per-app release scheme simpler: the front end's release is an asset the service's roster pins.
3. **The engagement loop is the studio's missing render.** B1 found no precedent that renders story or epic progress [94][95]; B5 found no product that reports partial delivery or quotes before running [175][189]; B3's vocabulary derives progress from the journal's terminal kinds. The differentiator is one data model (engagement states plus story and epic progress) projected into both the office scene and a DOM board, fed by the queue and journal the supervisor already writes.
4. **Prompt-interpreted gates are the one thing not to copy.** Cursor's leaking plan mode [179][180] and Jules's timer auto-approve [184] are the two failure modes; the supervisor's queue states and the Jules enum [185] are the fix, and the same state machine drives the office's `waiting-for-human` bubble that never auto-expires.
5. **Licensing and repository visibility interact.** If `tk-studio` may go public, LimeZu files cannot be in it and LPC credits must ship in the app (B4) [159][153]; that argues for a gitignored asset folder plus a roster entry for the asset bundle, which the meta-CLI (A3) fetches from a private location after a purchase check, since itch.io documents purchase verification but no download endpoint [169].
6. **Windows is the recurring tax.** uv and Bun workspaces are silent on Windows [22][25]; pnpm needs Developer Mode or junctions [23]; `command` plugin sources run under `cmd.exe` and refuse `link` mode [29]; running executables can only be renamed [66]; Hermes's PTY on native Windows was a documentation contradiction for weeks [137][139]. Every recommendation below assumes the agent PC's Windows-first constraint and names the mitigation.

## 11. Contrary evidence

The red-team skeptic received the one-repository conclusion and a search budget, and no supporting evidence. It returned nine findings (digest `A-redteam-1.md`, 33 sources). Three change the design; none overturns the verdict.

1. **The marketplace is the repo, so every plugin install and refresh clones the whole monorepo (material).** Claude Code's troubleshooting page: "For a git source, Claude Code clones the whole repository"; cloning or re-cloning a marketplace "gets 120 seconds by default"; background auto-update re-clones on any new commit; sparse checkout exists only as a user-side `--sparse` flag; the install-level sparse and shallow clone requests were closed not planned [239][241][31]. Live case on this exact OS: ChromeDevTools ships a 100 KB plugin from its product repository, the clone recurses submodules of 1.6 GB and 4.4 GB and fails at MAX_PATH on Windows 11 build 26300 with `core.longpaths` unset, and "the checkout stays stale permanently" while `claude plugin update` reports up to date (two open issues, 2026-10-07) [240]. Git LFS content arrives as pointer files [31]. **Weighed:** the mechanism is real and its worst case is Windows-specific; the trigger (submodules) does not exist in tk-studio and the repository is small today. It changes the distribution design, not the verdict: the plugin must reach users without cloning the monorepo. The `archive` + `sha256` source the studio already releases does that, served from a hosted `marketplace.json` (a `url` marketplace fetches only the JSON [29]); `thkennedy/tk-studio` is public (checked live 2026-10-09), so its release assets need no auth and this route works today; the meta-CLI's pinned-zip install (`gh release download` by tag) covers the case where the repository is ever made private, because a release-asset download answers a redirect to another origin (a live HEAD on a tk-studio asset returned 302 to `release-assets.githubusercontent.com` [261]) and a cross-origin redirect carries none of the headers configured on the marketplace source [31]. Users who add the git marketplace pin `#stable` or a tag so merges on `main` do not trigger re-clones; the repository stays free of submodules and LFS; the bootstrap turns on long paths. The in-repo marketplace remains the catalog of record and the developer path.
2. **An installed plugin is only its own subdirectory (moderate).** A maintainer running one repo with three plugins reports each cache holds only its own folder, so `../../packages/core` cannot be imported at runtime; they vendor shared code behind a CI drift check [242][243]; symlinks outside the marketplace are skipped [31]. **Weighed:** true, and already the studio's shape: `plugins/tk-studio` is stdlib-only and self-contained. It becomes a rule: nothing under `plugins/tk-studio` reaches outside it, the roster is the meta-CLI's file, and CI installs the plugin from the built zip into a clean `CLAUDE_CONFIG_DIR` before running conformance, so tests cannot pass against the monorepo tree for the wrong reason.
3. **One "latest" release per repository (moderate).** GitHub's latest is the newest non-draft, non-prerelease release ordered by `created_at`, which is the date of the release's commit rather than its publish time, so whichever app's release commit is newest owns "latest" regardless of which app a consumer meant; a monorepo on multi-semantic-release hit exactly this [244][245]. **Weighed:** real and not fixable by naming. Every release workflow sets `make_latest: false` and nothing, including the bootstrap that fetches the meta-CLI, resolves `/releases/latest`.
4. **The fan-in gate and bypass on a user-owned repository (moderate).** Required checks pass on `success`, `skipped` or `neutral`; a gate that fails only on `failure` passes when a job was skipped or cancelled; Mergify's critique: a check that is green because it never ran is indistinguishable from a dropped event [246][247][248]. Bypass lists exist only for organisation-owned repositories, so on a user-owned repository protection either exempts admins or binds them too [246]. A tag push also runs every workflow with a bare `push:` trigger [33]. **Weighed:** the A2 suggestion of a ruleset bypass actor does not apply to a user-owned repository (corrected in the ledger); the fan-in pattern stands with two rules: the gate asserts `success` for every job the change-detection step did not deliberately skip, and every non-release workflow filters to `branches:`. Whether admin bypass stays on is a choice the ADR puts to Tim.
5. **`git subtree add` keeps blame but loses path-limited history (moderate).** After a subtree merge, `git log -- prefix/file` shows only outer-repository commits unless run with `-m --follow`, while `git blame` finds the originals; a git mailing-list patch to fix it is pending; GitLab shows an empty History view for such files; the paths diverge forever [249][250][251]. **Weighed:** this matters for AI agents that read `git log -- path`. The recommendation moves to `git filter-repo --to-subdirectory-filter` plus `--tag-rename` on a throwaway clone and a merge with `--allow-unrelated-histories` [50][51], which keeps path history under the prefix; `subtree add` stays the fallback. Signed tags are not in use, so the signature loss does not apply.
6. **Self-updating binaries on Windows fail in known ways, and a service running from its checkout cannot be replaced (moderate).** restic's self-update regressed on the final rename; go-update failed with "in use" from a leftover handle; a CLI running as a service cannot replace its binary; Claude Code's plugin cache hits `ENOTEMPTY` when a scanner holds files; a mirror-only report of a Claude Code auto-update shipping a broken binary [252][253][239][254]. **Weighed:** none is specific to one repository versus several; the meta-CLI renames aside, keeps the previous version, verifies before deleting, and stops the service first; newcomers run the service from a versioned release directory rather than a git checkout (the single-checkout decision stays for the dev box).
7. **The documented split and the counter-camp (weak to moderate).** Sirius split because every change rebuilt everything [8]; Genkit's WHY_MONOREPO argues the opposite for cross-cutting changes; an essay attributes oscillation to feedback loops, not repository shape [255][256]. **Weighed:** the Sirius symptom is what one undifferentiated gate produces; per-app jobs with change detection and the gate rule in finding 4 remove it.
8. **Windows link semantics (weak to moderate).** Junctions inside `node_modules` pointing at a repository broke Bun startup in one report; symlinks need Developer Mode or elevation; a mirror-only report of worktree removal following junctions [257][31][258]. **Weighed:** keep `node_modules` out of any tree agents or `git worktree` recurse into; Bun's own migration guide says `bun install` uses hardlinks on Windows and Linux, with symlinks only for `file:` dependencies [262].
9. **`irm | iex` criticism (weak).** Automated audits note an unpinned mutable script; Defender and SmartScreen false positives on unsigned updaters [259]. **Weighed:** one line in the installer design: publish the bootstrap script's checksum and a download-verify-run alternative; the Hermes blueprint already pins and hashes what it downloads [62].

**Searched for and not found by the red team:** a first-person account of merging a service and a plugin and later re-splitting; any tool choking on a `--v` separator (Claude Code's own `<plugin>--v<version>` convention supports the verdict, while A2's reading of release-please's parser stands as code-level evidence [43]); Docker Sandboxes problems with large mounted repositories; marketplace breakage caused by a Bun lockfile or a Next.js app; a GitHub statement on branch-protection availability for a private personal repository (unverified).

## 12. Recommendations

Each binds to the decision and to the downstream artifact that consumes it (the ADR `briefs/adr-repository-structure-2026-10-09.md` and the front-end brief), with its confidence basis.

**Decision A (ADR).**

- **R1. One repository.** Confidence high: twelve live layouts, three split rationales that do not apply, one merge-back account, and the Happy fold-in of 2026-02 [1][3][5][8][9][11][10]. Consumed by the ADR's options and verdict.
- **R2. Migrate the supervisor with `git filter-repo`** (`--to-subdirectory-filter apps/supervisor --tag-rename 'v':'supervisor--v'` on a throwaway clone, then `git merge --allow-unrelated-histories`), which keeps path-limited history and prefixes the old tags; `git subtree add` is the fallback if filter-repo misbehaves on the box, at the cost of `git log -- path` stopping at the join commit without `-m --follow` [50][51][52][249]. Archive the old repository afterwards [54]. Confidence high on both mechanisms (independent walkthrough, git's own docs); the `--allow-unrelated-histories` text was not retrieved. Consumed by the ADR's migration plan.
- **R3. Per-app release scheme:** `tk-studio--vX.Y.Z` (plugin, pinned zip), `supervisor--vX.Y.Z`, `studio-web--vX.Y.Z`, one `on.push.tags` workflow per prefix, `make_latest: false` on every release so no app owns the repository's "latest", the existing Python release script generalised, no release-please for the `--` prefix [33][43][31][244]. Confidence high on the mechanics, medium on tooling (release-please's `--` effect on lookup not traced). Consumed by the ADR's release scheme.
- **R4. Protection:** protection on `main` with required PR and one fan-in `gate` job as the only required check; the gate asserts `success` for every job that change detection did not deliberately skip (skipped and neutral otherwise count as passing); every non-release workflow filters to `branches:`; bypass lists are unavailable on a user-owned repository, so the ADR asks Tim whether admins stay exempt, as today, or are bound too [35][38][246][247][33]. Confidence high.
- **R5. Installer:** bootstrap `install.ps1`/`install.sh` (checksum published, download-verify-run alternative) → pinned meta-CLI (`uv tool install` or a single binary behind a launcher with versioned slots) → committed `studio.lock`-style roster with SHA-256s → plugin from the pinned zip (`archive` + `sha256` from a hosted `marketplace.json`, which works today because the repository is public; `gh release download <tag>` as the fallback if it is ever private) → `claude plugin install tk-studio@tk-studio --yes`; the meta-CLI resolves everything by tag, never `/releases/latest`; `latest` and `stable` pointers; enable long paths (the MAX_PATH failure is live on this Windows build [240]); stop the service, rename aside, keep the previous version and verify before deleting; newcomers run the service from a versioned release directory [56][62][72][75][64][66][239][240][244][252]. Confidence high on the pattern (four independent shippers), medium on the Windows swap mechanics. Consumed by the ADR's installer design and a later installer story.
- **R6. Layout inside the repo** (judgment bound to the evidence): `plugins/tk-studio` unchanged and sealed (nothing inside reaches outside it; CI installs the built zip into a clean `CLAUDE_CONFIG_DIR` and runs conformance there) [242]; the marketplace root stays the repository root, with no submodules and no LFS [239][31]; `apps/supervisor` (Bun, own `package.json`, own lockfile; mirror PostHog's exclusion of a nested workspace from any root install; `node_modules` outside any path agents or worktrees recurse into) [20][257]; `apps/studio-web` (Next.js, static export built into the supervisor's served tree); `tools/installer`; one root `pyproject.toml` only if a uv workspace is wanted, otherwise keep the plugin's stdlib-only `uv run` scripts as they are [25]. No Turborepo until there are enough tasks to cache [26].

**Decision B (front-end brief).**

- **R7. Stack:** Next.js (`output: 'export'`) served by the supervisor on one origin behind `tailscale serve`; hybrid DOM + one plain PixiJS v8 canvas behind `next/dynamic` with `ssr: false`, nearest scaling, integer zoom from `devicePixelRatio` with `roundPixels` (recipe to be proven on a phone); no `@pixi/react`, no Phaser, no Godot web [117][135][109][113][111]. Confidence high on hosting and Next rules, medium on the phone recipe [115][132].
- **R8. Event contract:** adopt Pixel Agents' `ServerMessage` subset as the base vocabulary, extend with story, epic and engagement identifiers; a claude-office-style REST ingest with a discriminated union and a fixture simulator; AI Town's rules (one mutator, snapshot then deltas, history buffers, ordered inputs) [84][89][92]. Confidence high.
- **R9. Transport:** one SSE `/events` stream per tab, snapshot-then-deltas with `Last-Event-ID` and a replay buffer (Hermes keeps about five minutes for its run events [136]; the studio's window is a design parameter), a heartbeat at or under 15 s, `server.timeout(req, 0)`, a client watchdog that recreates the stream on `visibilitychange` and re-authenticates on failure [133][135][150]. Confidence high on the spec, medium on iOS (forum evidence) and on the buffer length.
- **R10. Hermes:** loopback API server, key held by the supervisor, Runs API consumed server-to-server and re-emitted; `/v1/capabilities` gated; no dashboard embed; a dashboard plugin only if a Hermes-side panel is ever wanted [136][138]. Confidence high.
- **R11. Assets:** LimeZu Modern Office plus Modern Interiors purchased, kept out of git, fetched by the meta-CLI from a private location, credited in-app; LPC or PixelLab for anything committed, with LPC credits shipped and edited SA frames kept as SA asset files; verify LimeZu sit and typing frames before committing to the look [159][160][153][164]. Confidence high on terms, medium on coverage.
- **R12. Engagement loop:** a state machine with the Jules enum, a dedicated approval verb, questions as a distinct state, autonomy chosen at approval, a 50/85/95 quote band from the meter's per-story history with the tail priced, and a partial-delivery report (done, not done, why) as the studio's own closeout [185][182][193][198]. Confidence high on the gate model, medium on the quote (the studio's own throughput history is short).
