# The studio's analytics: how long, how much, and what changed (design addendum, 2026-11-08)

An addendum to the studio design spec of 2026-10-09 (`../studio-design-spec-2026-10-09/README.md`) and to the front-end addendum of 2026-11-07 (`../studio-design-spec-2026-11-07-front-end/README.md`). It is the brief and the UX notes for Epic 40, the analytics section of the studio web. Nothing here overrides a ruling of either (D1 to D10 stand, the Epic 39 choices stand); it extends §6.3 (the studio web), §6.7 (measurement) and §7.1 (the data model) with what the owner asked for on 2026-11-08, and it records the choices Epic 40 makes so that the stories can cite them.

**Sources this addendum stands on.** The design spec of 2026-10-09 and the owner's answers (`../studio-design-spec-2026-10-09/decisions-answers.md`: D4 "both, with dollars as the shadow figure" for the quote basis; D5 PixiJS for the office and React DOM for text, desktop, laptop and iPad first, a phone UI only after the full web UI works; D7 one account; D9 the supervisor is the only writer; D10 the tailnet). The front-end addendum of 2026-11-07 (routes under `/app`, the settings page of Story 39.8 and its `settings-changed` service event, the owner's rule of 2026-11-05 that every pending state carries a human-readable label, never a bare symbol). The research of 2026-11-08 (`../../research/studio-analytics-2026-11-08/research.md`): which metrics an agentic development loop should track, graded by evidence, what the industry measures (DORA, SPACE, the OpenTelemetry GenAI conventions, LangSmith, Langfuse, Helicone, Claude Code's own cost surfaces, GitHub Actions), and the comparison method for a few samples per story. The `dataviz` skill's method (form first, one hue for magnitude, categorical only for identity, no dual axis, a legend and a table twin for every chart, the validated palette in light and dark). The routing kb (`kb/execution-pipeline-model-routing.md`: judge on dollars, never on token counters; "the binding constraint on a subscription plan is weekly plan usage, not dollars") and the trial record (`kb/trial-record-opus-5-5.md`: the one before/after comparison the studio has made so far, by hand, with its caveats). The code of Epics 29 to 38 as it is on `main` (§1), read at `b9c977af`.

## 0. The owner's words (2026-11-08)

> "I want a detailed analytics section in the web UI. I want to know how long things are taking, how much they are costing me (dollars and tokens) and also I want you to do some research and see what other metrics would be useful to track and also inform settings. I want data displayed in a user-friendly format such as a per-story and also over time values which will allow me to see how changes are impacting different metrics. For example say I change the model for a certain leg and let it run for a few days I want to be able to see the changes clearly - is it developing faster, slower, or no change? How has the cost been impacted? Things like this".

Four asks sit in that: **time** (how long each thing takes), **money** (dollars and tokens), **the right metrics** (researched, and the ones that bear on a setting), and **the comparison** (per story and over time, so that a change on day X reads as faster, slower or no change, and what it cost). Epic 40 is measured against those four.

## 3. The shape Epic 40 gives it

### 3.1 Principles (the rulings restated for this surface)

1. **The supervisor computes; the web never parses a file** (D9, spec §3). The analytics are a read model the supervisor builds on the host from the sources of §1 into one store, and serves over `GET /analytics/...`. The browser renders answers; it opens no spec, no ledger, no database.
2. **Facts are stored, statistics are derived.** The store holds one row per stage occurrence, per story, per host-leg suite, per run and per change; medians, ranges and verdicts are computed in the supervisor at request time from those rows and never stored, so a corrected row corrects every figure. Elapsed is derived from `started` and `ended`, as the Stage Log rule says.
3. **Dollars at list price, named as such** (D4: dollars are the shadow figure). Every dollar figure is what the API would have billed at `prices.json`'s dated prices for the tokens the transcripts show; the page says "at list price (the Max plan pays)" once per view. Tokens are shown beside dollars, with cache reads split out where the source has them (the meter's per-leg usage; the Stage Log's `tokens_in` cannot be split and is labelled "including cache reads").
4. **One origin, one account, one cookie** (D7). New routes sit beside the existing ones in `apps/supervisor/src/api.ts`, cookie + CSRF for the owner's browser, bearer for tools; the contract grows additively (0.1.36, after Epic 39's 0.1.35).
5. **The comparison is honest with few samples** (research doc §7). A before/after reads as per-story points with the change marked, medians and ranges per band on each side, the count on each side, and a verdict in words that says "not enough stories yet" below the minimum; never a bare average, never a dual axis, never a trend line through three points.
6. **Every number says what it means in words** (the owner's rule of 2026-11-05, extended): each metric has a one-line definition shown in its tooltip and in a definitions drawer, and every pending state says what it is loading ("Building the analytics from the Stage Logs (first time, about a minute)").
7. **Charts by the dataviz method** (D5: React DOM for text; charts are SVG in the DOM, never the office canvas): the form picked by the data's job (a stat tile for a headline, dots over time for per-story values, small multiples per stage, a dumbbell for before→after, a table twin for everything), one hue for magnitude, the fixed categorical order only where series are the subject, the status colours only for green and red legs, the validated palette in light and dark, a hover layer and keyboard focus on every mark, filters in one row above everything they scope.

### 3.2 The owner's day (the flows this epic serves)

- **F-G, the glance at cost and time.** Open `/app/analytics`: the last 30 days in five tiles (stories landed, median cycle time, median cost per story, first-leg green share, spend in the range, each with its change against the previous 30 days), then the stages (median minutes and dollars per stage with the range), then the recent stories. Switch the range to 7 or 90 days or all; switch the band to S, M or L; every tile and table follows.
- **F-H, one story.** From the board or the story page: this story's cycle, hands-on time, cost, tokens, review passes, findings, host-leg time, against its band's median and range, in words ("14.35 USD: above the band's median of 11.20; the range over 9 M stories is 8.68 to 38.96").
- **F-I, the trend.** Open the over-time view: one small chart per stage (plan, dev, review, gate, host leg, close-out, queue wait), each a line of the per-story value with a rolling median, every change marked as a vertical hairline with its label ("dev leg → opus-5-5 / high, 2026-11-12"). Hover a point: the story, the value, its band, the route it ran on.
- **F-J, the question.** "I changed the dev leg's model on day X." Open the comparison view from the change's mark, from the settings page, or from the list of changes: before and after, per metric, with the count, the median and the range on each side, the per-story points under them, and the verdict: "Faster: the median dev time fell from 52 to 41 minutes over 6 and 5 M stories; the ranges do not overlap. Cost: no clear change (14.2 against 13.9 USD; the ranges overlap)." Or: "Not enough stories yet: 2 of 3 on the new route."
- **F-K, the setting.** On `/app/settings`, beside each leg's model and effort: "Last 10 stories on this route: median dev 48 min, 14.20 USD, 1.2 review passes; changed 3 days ago → compare". The owner changes a model knowing what the current route costs, and finds the comparison waiting once enough stories have run.

### 3.3 The metrics (what is shown, what each says, which knob it informs)

The research doc's §2 grades the candidates; the ones Epic 40 shows, by source and by the setting they bear on:

| Metric | In words | Source (§1) | Informs |
|---|---|---|---|
| Cycle time | From the plan's first start to the merge | Stage Log (`rollup.cycle_s`) | the guards, the rhythm (one story per run) |
| Hands-on time per stage | The stage's span; a consult inside its pass counted once | Stage Log rows | the leg's model and effort |
| Queue wait | From `enqueued` to `claimed` | queue events | the pacer, the operator's rhythm |
| Host-leg time and per-suite time-to-green | The leg's `duration_ms`; each suite's seconds; green on the first leg or not | `host-verify`, `suite_durations` | `host_verify_seconds`, the gate's coverage, the Windows classes |
| Cost per story, per stage, per band | USD at list price; tokens in (cache reads included), tokens out; cache share where known | Stage Log, meter, `accounted` | the leg's model, the band estimates (`usd_estimate`) |
| Cost per landed story | The epic's spend over its landed stories, retries and failed attempts included | Stage Log + queue | the band estimates, the quote basis |
| Review passes and findings | Passes per story; findings accepted, patched, rejected per pass; follow-up damped | journal, gate files | `max_followup_reviews` per band (38.7), `review_cycles_max` |

### 3.4 The store and the backfill (Story 40.1)

- **One SQLite file beside the queue**: `C:/agent-work/supervisor/analytics.db` (`TK_SUPERVISOR_ANALYTICS`, defaulting to `analytics.db` beside the queue's path), never inside a checkout. Tables: `stories` (one row per project and story key: the plan id, epic, band, status, first start, merged at, cycle, hands-on, queue wait, attempts, passes, findings, deviation, consults, halts, guard trips, host-leg seconds and first-leg green, PR number and size, tokens, dollars by source, the route per stage as JSON, `source`), `stages` (one row per Stage Log row with its key), `legs` (one row per suite per host leg), `runs` (one row per queue run), `changes` (one row per change: `settings-changed` events, routing and band and price commits from git, guard changes from the job files, supervisor restarts, the owner's notes), `meta` (built at, the sources' high-water marks).
- **Built by a lib verb the supervisor runs on the host**: `uv run plugins/tk-studio/lib/analytics.py build --directory ROOT --queue PATH --store PATH` (stdlib only, like `report.py`; it reuses `plansync.stage_rows`, `report.rollup` and `meter`'s price table), incremental and idempotent (rows keyed by the Stage Log key, the run id, the change id; a rebuilt row replaces its earlier self). The supervisor runs it after each ended run's `stage-post` pass (`planstatus.ts`), when the store is absent at serve start, and on `POST /analytics/rebuild`. `backfill` is the same verb over everything from the first spec folder: the Stage Log era (Epic 35 onward, per stage), the queue era (2026-10-07 onward, per run, with the worker's `accounted` cost and the leg's duration even where no Stage Log exists), and, if the owner wants it, the trial record's twelve stories as seeded rows marked `source: kb` (§4 choice 3).
- **The web reads none of it directly** (D9). The supervisor's `analytics.ts` opens the store read-only (`bun:sqlite`, as `queue.ts` does) and answers the routes of 3.5.

### 3.5 The API (Story 40.2; contract 0.1.36, additive)

| `GET /analytics/stories?project=&from=&to=&band=&epic=` | one row per story with every column of the `stories` table and the band's median and range for the comparison strip |
| `GET /analytics/stories/{id}` | one story's row, its stage rows, its legs, its runs and the band figures |
| `GET /analytics/stages?project=&stage=&from=&to=&band=` | the per-story points of one stage (or all) over time with a rolling median of the last five |
| `GET /analytics/changes?project=` | the annotations: `{id, at, kind, leg?, field?, from?, to?, by, source, note?}` |
| `POST /analytics/notes {project, at, text}` | the owner's own annotation (cookie + CSRF, or bearer); recorded as an `analytics-note` service event and a `changes` row |
| `GET /analytics/compare?project=&change=<id>&metric=&band=&n=` | before and after a change: `{before: {n, median, q1, q3, min, max, values[]}, after: {…}, verdict, verdict_text, caveat}`; the same by route value: `&stage=dev&route=claude-opus-5-5/high` against another |
| `GET /analytics/export.csv?project=&table=stories|stages|legs|runs|changes` | the table twin as CSV (the owner's spreadsheet) |
| `POST /analytics/rebuild {project?, backfill?: true}` | runs the verb once; refused by name while one runs (`AnalyticsBuildRunning`); answers the `meta` row |

The verdict rule (research doc §7): a verdict needs at least three landed stories on each side of the same band; "faster" or "slower" (or "cheaper", "dearer") when the medians differ by more than a fifth and the interquartile ranges do not overlap; otherwise "no clear change"; below three on either side, "not enough stories yet (n of 3)". The text always carries both counts, both medians and both ranges.

### 3.7 The chart kit (the library choice)

The web draws charts as SVG in React components, `apps/studio-web/src/charts/` (dots, line with rolling median, small multiples, dumbbell, thin bar, stat tile with sparkline, annotation rule, tooltip, table twin), over `d3-scale`, `d3-shape` and `d3-array` as the only new dependencies (each tree-shakable and small; `d3-array` gives `median`, `quantile` and `bisector`). No chart framework: the data is small (hundreds of points), the dataviz rules (thin marks, selective labels, a table twin, a hover layer, the palette) are easier to meet by hand than to override in a library's defaults, and D5's split holds (charts are DOM text and SVG, never the office canvas). The alternative weighed: Observable Plot (framework-agnostic, concise facets and rules), set aside for its size and for drawing outside React's tree; Recharts and visx, set aside for the same reason as any framework here. `bun run verify` builds the kit; the verify leg's `bun run verify` in `apps/studio-web` covers it.

## 4. Choices made here (for the owner's review)

1. **Dollars lead, at list price, with the basis stated once per view** (D4's shadow figure made the headline, because the owner asked for dollars). Tokens stand beside them. The alternative, tokens first with dollars folded away, was set aside: the kb's rule is to judge on dollars, and tokens cannot compare routes of different prices.
2. **A separate store beside the queue, built by a lib verb** (3.4), rather than tables inside `queue.db` (the queue stays the event record and its schema is the supervisor's; a rebuildable store beside it can be deleted and rebuilt without touching the queue) or reading the files on every request (slow across 23 specs and a 1,400-line ledger, and it would put parsers in the request path; D9 wants one builder).
3. **The backfill horizon.** Automatic: the Stage Log era per stage (Epic 35 onward, 2026-10-29) and the queue era per run (2026-10-07 onward, Epics 29 onward). Offered, not automatic: the twelve trial-record stories of Epics 20 to 22 as seeded rows marked `source: kb` (their dollars and wall-clock come from handoffs, not transcripts). The owner's call whether the seeded rows are wanted.
4. **Retention: everything, no cap.** The data is a few hundred rows per epic; the page's default range is 30 days, the presets go to "all". A cap is a later setting if the store ever matters.
5. **The chart kit over a chart library** (3.7).
6. **The verdict rule** (3.5): three per side to speak, a fifth and non-overlapping interquartile ranges to say faster or slower, the same band on both sides. The owner's call whether three is right; the numbers are one constant each.
7. **Changes come from the record, plus the owner's note.** The `settings-changed` events of 39.8 are the primary annotations from Epic 39 on; git gives the earlier ones (routing, bands, prices); the job files give the guards; the owner can add a note for anything else ("ran the sweep by hand"). No annotation is inferred from the data.
8. **Per project, switchable.** The store keys every row by project; the page carries the project switcher the board has. The universe awaits appears when its runs go through the supervisor (its Stage Logs then land in its own specs); its hand-run history is not backfilled unless the owner asks (§5 Q4).

## 5. Open questions for the owner (asked through the plan PR, not blocking)

- Q1 **The weekly quota.** The real constraint on the Max plan is the weekly usage, not dollars (`kb/execution-pipeline-model-routing.md:70-73`). The research doc §4 names what Claude Code exposes: `/usage` in the terminal (plan limits, the prompt-cache line), and the OpenTelemetry export on every plan (`claude_code.cost.usage`, `claude_code.token.usage` with the cache types, the `api_request` event with `cost_usd`, the four token counts, `effort` and `duration_ms`); the Admin usage APIs cover API keys only, never a Max sign-in. None gives the quota share as a number the supervisor can read. Options: (a) leave it out of this epic and show list-price dollars only; (b) an OpenTelemetry collector on the box receiving the sandbox sessions' export into the store (a setup step and a dependency; it would also give the cache split and the per-request duration live, which nothing else does after the close-out); (c) the owner types the weekly reset's percentage into a note once a week. The plan assumes (a) and records (b) as the next step if the owner wants the live stream.
- Q2 **The hero number.** Median cost per landed story, or median cycle time? The plan puts cost first on the overview; the owner reads the tiles in the order he cares about.
- Q3 **The seeded trial rows** (choice 3): wanted or not.
- Q4 **The universe awaits.** Analytics per project from this epic on (choice 8); should its earlier stories' Stage Logs, where they exist in its repository, be backfilled into the store as a second project?
- Q5 **A weekly digest.** A notifier line each Monday with the week's tiles ("4 stories, median 61 min, 14.20 USD, all legs green first time") is cheap once the store exists; not asked for, so not planned.
