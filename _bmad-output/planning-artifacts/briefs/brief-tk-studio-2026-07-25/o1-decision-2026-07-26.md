# O1 Ruling — Distribution Mechanism (2026-07-26)

Tim's rulings from the party-mode debate on O1. Supersedes A1's evaluation plan; A1's option analysis remains the background record.

## The reframe (governs everything below)

No pre-decision measurement. This whole system is an experiment: defects are accrued over time through real usage, so speculating on where and how much will drift is pointless. **The measurement mechanism is a first-class member of the solution.** The seed's "measure M1's vendor cycle vs an M2 prototype" experiment is **formally dropped** — instrument, don't predict.

Primary requirements, in order:

1. **Ease of onboarding** — a new teammate goes clone → trust folder → marketplace auto-prompt installs the studio layer → first activation runs the health/drift check → it guides them through `tk install` for the BMad base. The onboarding funnel is itself instrumented (time-to-ready, failed steps, retries): onboarding is the first measurement event.
2. **Measurement reconciliation as the team grows** — individual installs report; a defined flow consolidates.

## Mechanism: the composite (blessed as the working answer)

- **tk-studio layer:** Claude Code plugin from a git marketplace (`extraKnownMarketplaces` auto-prompt on folder trust gives the zero-effort onboarding story).
- **BMad base:** thin lockfile pin; the **upstream installer runs at the pin** — zero forks, pure BMad. Simplicity bias holds: the wrapper stays thin and disposable (v7 horizon).
- **Front door:** the activation health/drift/measurement check, mechanism-independent, cross-checks **both planes** (installed BMad vs lockfile pin; installed plugin vs marketplace version) — the three-way reconciliation cost of the composite is accepted and priced in.
- This is the working answer the experiment will correct — not a final answer; the measurement loop exists to revise it.

## Measurement subsystem (v1)

**Event taxonomy (approved):**
- install outcomes
- drift detections
- activation / headless failures
- onboarding funnel timings
- plus an explicit **`tk report` verb** for human-authored defect reports ("the skill did the wrong thing") — a separate animal from passive telemetry.

**Ledger:** per-user-per-machine append-only JSONL (`measurements/<user>-<machine>.jsonl`), atomic writes, never a shared file. Sanitization at emission — the ClaudeOS anonymization spine applies to teammate telemetry (no hypocrisy problem).

**Reconciliation flow (Tim's design):**
1. A skill takes the local JSONL, creates a **feature branch, commits it, opens a PR** into the shared repo.
2. A **consolidation skill** examines the accumulated PRs and **creates issues from the data that lead to specific fixes**.
3. PR review is the promotion membrane — the legacy council JSONL-reconciliation-queue / promotion-gate pattern pointed at ourselves, riding plain git governance instead of new infrastructure.

**BMad base updates (Tim's design):** performed by someone, delegated to a skill — bump the pin, run the upstream installer, produce an **integration PR** for review. This recovers M1's one genuine virtue (a reviewable upstream diff) without owning a fork.

## Skills implied (naming/contract at architecture)

- measurement-push skill (ledger → branch → commit → PR)
- consolidation skill (PRs → issues → fix candidates)
- base-update skill (pin bump → upstream install → integration PR)
- the activation health/drift check (front door; also the onboarding guide)

Extract the legacy council from its archive into its **own new private git repo** (it should not live inside ClaudeOS; ClaudeOS was only the transfer container). Frees the harvest: vendor/verify tooling, issue ledger, JSONL reconciliation queue.
