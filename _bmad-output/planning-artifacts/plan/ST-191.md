As the owner,
I want the supervisor to start every declared job that carries a schedule when its time comes, with nobody posting it,
So that the hourly sync-back and every later timed job (the nightly pass first) run by the clock, and a job that ships with a schedule is proven by one run that nothing but the schedule started (hole 126).

**Acceptance Criteria:**

**Given** the pacer (`apps/supervisor/start.ps1:406-408`: `bun src/tick.ts`, `bun src/cli.ts drain`, a sleep of `-IntervalSeconds`), the tick step (`apps/supervisor/src/tick.ts`: `:95` `declaredJobsFrom`, the contract §4 `resolve` enumeration of the project's declared jobs; `:111` `isSelfPaced`; `:58` the comment that cron and fixed-interval jobs are not ticked), the directive (`plugins/tk-studio/lib/jobrun.py:291` `_directive`), the one submit path (`apps/supervisor/src/cli.ts:1025` `submitJob`) and the idempotent mint (`queue.ts:1163` `enqueue`)
**When** Story 41.1 lands
**Then** `apps/supervisor/src/timer.ts` (new) holds a five-field cron evaluator (`*`, single values, ranges `a-b`, lists `a,b`, steps `*/n` and `a-b/n`; minute 0-59, hour 0-23, day of month 1-31, month 1-12, day of week 0-7 with 0 and 7 both Sunday; when both day fields are restricted either may match, as cron does; no names, no `@` shorthands) with `latestDue(schedule, nowMs)` and `nextDue(schedule, nowMs)`, read in UTC (the queue's own clock; no daylight-saving gap or double fire; the README says so and gives the box's local hour for each declared schedule), and the same two functions for `trigger: loop` with `cadence.mode: fixed` (due every `interval_seconds` from the instant the job was armed); a schedule it cannot read is a named problem and never a fire; the tick step gains a timed branch that, for every declared job of every served project whose definition is `trigger: cron` or `trigger: loop` with `cadence.mode: fixed` (a shipped job the project does not declare is never fired; the self-paced branch is unchanged), keeps one row in a new queue table `timers` (job, checkout, schedule, armed_at, last_due, last_fired_at, last_run_id, missed, waiting_since, waiting_on, problem): the first sight of a job, or of a changed schedule, arms it at now and fires nothing (so a restart, a first declaration or an edit never starts a run by itself); on a later pass with `latestDue` after `last_due` it submits the job through `submitJob` exactly as `POST /jobs` does (the same validation, placement, tier and stop conditions; the studio's stop conditions still decide whether the job may run), the `enqueued` event's detail carrying `submitted_by: "timer"`, `due` (the instant, ISO), `late_s` and `missed` (the count of due instants passed since `last_due` beyond the one fired: a supervisor that was down for three hours fires an hourly job once, with `missed: 2`, never three times), and the same pass's `drain` drives the run; the comment at `tick.ts:58` is replaced by what is true.

**Given** that a pass can be late (a worker session of up to 3600 s and a host verify leg of up to 7200 s run inside the driver's pass), that the checkout's `run` lock admits one run, and that claim refusals are recorded once per cause with a notifier line (Story 33.2)
**When** a job is due while the checkout is busy or the submit is refused
**Then** a new optional job field `cadence.on_busy: "wait" | "skip"` (default `wait`; `plugins/tk-studio/contracts/job.schema.json`, validated in `job.py`, additive) decides: busy means another run holds the checkout's `run` lock or a run of the same checkout is queued, and for `skip` also a host verify leg live anywhere on the box (`queue.ts:1780` `verifyLegLive`); `wait` mints nothing while busy (the row carries `waiting_since` and `waiting_on: <run id>`; no `claim-refused` line is written for it) and fires once on the first pass that finds the checkout free, with the `due` it waited from; `skip` consumes the instant with one `timer-skipped {job, due, reason}` service event and waits for the next one; a submit the studio refuses (a stop condition, a missing placement, an unsigned sandbox) is one `timer-refused {job, cause}` service event per cause, updated in place while the cause stands, with one notifier line when the cause is new, and the instant is retried on the next pass; `GET /status` gains `timers[]` (job, project, schedule, next_due, last_fired_at, last_run_id, late_s, missed, waiting_on, problem) and `bun src/cli.ts timers` prints the same rows as a table whose columns are words; `apps/supervisor/test/timer.test.ts` pins, with an injected clock and a fake submit: the evaluator's table (`0 * * * *`, `*/10 * * * *`, `0 6 * * 1-5`, a list, a step over a range, the day-of-month-or-day-of-week rule, an unreadable schedule), arm on first sight, exactly one fire across a boundary however many passes cross it, three missed instants as one run, `wait` and `skip` against a held lock and a live leg, the re-arm on an edited schedule, the refusal updated in place, and an undeclared job never firing; every `bun test` the story adds or documents names `--timeout`; `apps/supervisor/README.md` gains **Timed jobs (Story 41.1)** and `start.ps1`'s help names the timed branch; the contract §4 gains the binding paragraph and the `enqueued` detail's four keys (0.1.37, additive); no Windows scheduled task is added.

**Given** the hourly `atlassian-sync-back` the owner chose (`SYNC: A`, TKSTUDIO-262), declared in `.tk-studio/config.yaml` since Story 39.2's landing and started until now by a hand `post_job.py tk-studio atlassian-sync-back` at each landing
**When** this story's PR has merged and the supervisor has been restarted on it
**Then** the first hour boundary that finds the checkout free yields one `atlassian-sync-back` queue run whose `enqueued` detail reads `submitted_by: "timer"` and `due: <that hour>`, with no `POST /jobs`, no `submit` verb and no hand tick behind it, and the run ends as its job defines; the landing's docs record the run id, `due` and `late_s` as the proof "one run that nothing but the schedule started", the runbook's hand tick is retired in the same docs PR, hole 126's ledger entry reads `closed by Story 41.1 (#PR)`, and Story 41.2 is queued only after that proof is in the merged docs; if the checkout is never free at a boundary within a day, the docs say so and name the `waiting_on` run instead of a proof, and the next story still waits.
