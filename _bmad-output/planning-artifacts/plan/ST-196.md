As the owner,
I want the pass declared for tk-studio on a nightly schedule, its first night recorded as the test, and each night's cost and effect shown on the analytics pages beside the stories',
So that the dreaming pass runs while I am away, and I can see what it costs and what it removes without opening a log.

**Acceptance Criteria:**

**Given** the shipped type (Story 41.4), the timer (41.1), the holds (41.5), the supervisor's per-job config (hole 90) and the owner's answers on this plan's PR (the night's hour, the ceilings)
**When** Story 41.6 lands
**Then** `.tk-studio/jobs/maintenance-hygiene.json` (the project's instance) names the schedule (default `0 8 * * *`, 08:00 UTC, the small hours of the box's local night; the owner's hour if given) and the ceilings, `.tk-studio/config.yaml` declares `maintenance-hygiene` in `jobs:` with a dated comment and gains `hygiene: {max_sites: 6}`, the landing's operator step places `tk-studio/maintenance-hygiene {tier: sbx, sandbox: claude-tk-studio}` in the supervisor's per-job config before the merge (the docs record it; the story's code never reads or writes that file), and `kb/agent-pc-setup-runbook.md` gains the pass's operating section: how to pause it (remove the declaration, or the `stop` hold), how to reopen a skipped row, how to decline a night's PR, what each `timer-held` line means; with `cadence.on_busy: "skip"` a night that finds a run holding the checkout, a run queued for it or a host verify leg live is skipped with its `timer-skipped` event, so the pass never runs beside a live host leg and never takes the checkout from the owner's own work.

**Given** DW-179's test ("the first night's PR is the test") and Story 41.1's proof form
**When** the first scheduled instant after this story's landing has passed with the checkout free
**Then** the landing's docs record the first night: a `maintenance-hygiene` run whose `enqueued` detail reads `submitted_by: "timer"`, the row it took, its `hygiene-night` event, and either its PR with a green host leg or its skip with the reason; DW-179's status reads `closed by Story 41.6 (#PR)` with that run's id; Story 41.7 is queued only after the first night is in the merged docs; a first night that fails is recorded as it was, the pass is paused by the docs' named step, and the failure is a ledger entry, not a retry loop.

**Given** Epic 40's store and pages (`analytics.py build`, 40.1; `GET /analytics/summary`, 40.2; the overview, 40.3; the over-time view with the changes marked, 40.4) and the web's label maps
**When** this story lands
**Then** `analytics.py build` takes each hygiene run as a `stories` row under a new column `source` (`story` for every row the store has, `hygiene` for these; the store is rebuilt from the records, so the column needs no migration) (story_key `hygiene-<nnn>`, band S, its cycle time, cost, tokens, host leg and PR figures as any story's), kept out of the band medians and of the verdict rule's samples (a test pins that the band S median is the same with and without them), and each merged hygiene PR as a `changes` row (`kind: hygiene`, the class in the note) the over-time view marks like any change; `GET /analytics/summary` gains `hygiene {nights, consolidated, skipped, cost_usd, tokens, lines_removed}` for the window, and the overview shows it as one line in words ("Hygiene, last 30 days: 12 nights, 9 classes consolidated, 3 skipped, 1,140 lines removed, 71.20 USD"); the web's label maps gain words for the new source and kind, and its test pins that neither `hygiene` key renders raw; nothing else on the analytics pages changes and no new page is added.
