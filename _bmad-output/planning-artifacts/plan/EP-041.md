Tim's decisions: on DW-86 (TKSTUDIO-219, 2026-11-05) duplicates are a cost, not a fault, the studio "shouldn't launch a crusade to unify everything under a single execution path with no duplicates", and the fix is a scheduled self-evolution ("dreaming") pass, nightly to begin with, that takes the safe low-hanging fruit the way an engineer who comes across a duplicate does; on DW-179 (TKSTUDIO-260, 2026-11-09): "A - Let's plan for it to be epic 41. Also let's plan on using Fable 5.2 for it". **The reading of "using Fable 5.2 for it", stated here for the owner to correct:** Fable 5.2 (`claude-fable-5-2`) is both (a) the model that builds Epic 41, meaning the engine legs of every `run-epic-41` story run and the launch session that drives them, and (b) the model the nightly pass itself runs on once it exists. What reading (a) changes: today every leg runs on `claude-opus-5-5` by `.bmad-loop/routing.toml` `[defaults]`; a `[[rules]]` table with `match = "41-*"` (`plugins/tk-studio/lib/pipeline.py:286`, `fnmatch` on the story key, ahead of `[defaults]`) puts every leg of Epic 41's stories on `claude-fable-5-2` with the efforts left as they are, and a `"model": "claude-fable-5-2"` field on `.tk-studio/jobs/run-epic-41.json` puts the launch session on it (the job definition's own `model` is the runtime tier of `routing.resolve_routing`, `plugins/tk-studio/lib/routing.py:65`, read by `jobrun._job_routing`, `jobrun.py:331`). What reading (b) changes: the nightly job's definition carries `model: claude-fable-5-2` and `effort: high` for its session, and a second rule `match = "hygiene-*"` puts its engine legs on the same model. So a way to pin a model per job exists in two halves (the job's `model` and `effort` fields for the session, a routing rule on the story key for the legs) and neither needs a new mechanism; what does not exist is the model itself in the studio: `pipeline.py:89-90` `MODELS` and `:97` `MODEL_RANK` do not list `claude-fable-5-2` and `:170` refuses a route that names a model outside the list, `plugins/tk-studio/lib/prices.json` (dated 2026-09-28) has no row for it so the meter cannot price a run on it, `job.py:294-296` checks only that a job's `model` is a non-empty string (a mistyped pin is found at spawn, not at resolve), and Epic 39's settings page (39.8) writes and shows only `[defaults]`, so a rule would override what the page shows without a word. Story 41.2 closes those four. The default this plan takes: Stories 41.1 and 41.2 run on the route in force (Opus 5.5), since the id cannot be routed before 41.2 lands, and Stories 41.3 to 41.7 and every night after run on Fable 5.2; the alternative, if the owner wants all seven built on it, is a hand-made chore PR before the first `POST /jobs` carrying 41.2's first criterion (the id, the rank, the sourced price, the `41-*` rule, the job's `model` field), named in this plan's PR as a question.
