## Intent

Every engine sandbox today gets its own marketplace copy of the plugin: `provision-engine.sh` runs `claude plugin marketplace add` and `install` at user scope. AD-21 and the red team's rule 2 replace that with Docker Sandboxes' read-only skills mount. The host's skills-dir folder, written by `tk-studio install` (25.2), is what each microVM loads as `tk-studio@skills-dir`. So provisioning stops installing the plugin and instead verifies the mount, failing loudly when it is absent. The runbook documents `sbx create` with the mount read-only, along with the "sandbox store" drift case. The live proof on one recreated sandbox is an operator step (SPEC ruling 4): the story lands with the exact commands, and the operator closes the step separately.

## Acceptance Criteria

- AC1. **Given** `tools/sbx-engine/provision-engine.sh` **When** it provisions a sandbox **Then** it no longer installs the plugin at user scope inside the microVM; it verifies the mounted skills folder is present and read-only and that `tk-studio@skills-dir` loads inside the sandbox, and fails loudly naming the mount when it is absent
- AC2. **Given** runbook §3.8 and §3.5 **When** the story lands **Then** `sbx create` is documented with the skills mount set read-only, the per-sandbox plugin install is removed from the provisioning list, and the "sandbox store" drift case (the mounted folder differing from the host's) is named with its fix
- AC3. **Given** one existing sandbox on the box **When** the operator recreates it with the mount (exact commands provided; from PowerShell, with the daemon running) **Then** `tk activate` inside it is clean on four planes, a headless drive of one skill from inside it substitutes `${CLAUDE_PLUGIN_ROOT}` to the mounted path, and the per-sandbox syscall cost of the skills folder is measured once and recorded in the kb (the red team's "prove it on the box" item)

- `/proc/mounts` has `host /home/agent/.claude/skills virtiofs ro,nosuid,nodev,relatime`. So the skills mount already exists read-only at `$HOME/.claude/skills`, and it is **empty**.

**The skills mount (Docker docs, digest `_bmad-output/planning-artifacts/research/studio-native-overlap-and-greenfield-2026-10-09/digests/C1-redteam-1.md` F2)**
- Source: https://docs.docker.com/ai/sandboxes/workflows/agent-skills/, which calls the feature experimental.
- Host `~/.claude/skills` maps to sandbox `/home/agent/.claude/skills`.
- Modes are `--skills readonly|readwrite|off`, set **at creation only**. The docs disagree on the default (read-only in one rendering; read-write since sbx 0.37.0 in another, with `--no-share-skills`).
- The store is a persistent copy at `%LOCALAPPDATA%\DockerSandboxes\sandboxes\state\agent-skills`, filled by `sbx skills import`. "Importing replaces the complete skill directory." `sbx reset` clears it.
- SPEC ruling 5: this story discovers the exact flag and records it.

**The check to write: `tools/sbx-engine/check-skills-mount.sh`** (new, called by provision-engine.sh)
- It checks three things in order. Each failure prints one line naming the mount and the fix, and exits non-zero:
  1. `$HOME/.claude/skills` is a mount point, found by a `/proc/mounts` row whose target is that path.
  2. Its options include `ro`.
  3. `tk-studio/.claude-plugin/plugin.json` exists under it.
- Then it requires `claude plugin list` to show `tk-studio@skills-dir` with `✔ loaded`. The 25.2 probe output is in `kb/offline-install-runbook.md` l.219–224.
- Make the paths overridable for tests: a `SKILLS_MOUNT` path, a `PROC_MOUNTS` file and the PATH's `claude`. That way the lib test drives it with a fake mounts file and a fake `claude`.
- A surviving marketplace copy fails the check with a fix that names `claude plugin uninstall tk-studio@tk-studio --scope user` (and `--scope project`). The check never runs that uninstall itself (see Risks).

**Drift check (read-only seam, unchanged by default)**

## Risks and open decisions

- **Block If** documenting the "sandbox store" case needs a new drift-check case, field or plane, or any `skills_plane.py`/`drift_check.py` change. That is a driver-contract §6 surface (AD-19): HALT and consult. Do not add one.
- **Block If** the docs show the skills store is a copy filled only by `sbx skills import`, and keeping it current would need the installer's plugin leg to run `sbx` (a 25.2/25.4 surface). Record it as a deviation with `affects: 25-7` and document the manual `sbx skills import` fix. Never add an sbx call to the installer in this story, and never run an sbx command that could auto-start the daemon (§3.5).
- **Block If** the check would need to *uninstall* an existing marketplace copy inside the sandbox. AC1 says only "verifies". The check fails and names the uninstall; changing that is the operator's call.
- **Never recreate or exec a sandbox from this session.** The dev session runs inside the tk-studio engine sandbox, and recreating it kills the live run. AC3 names "one existing sandbox". The kb commands should recommend a sandbox with no run in flight.
- The docs are experimental and disagree on the default mode. If docs.docker.com is unreachable under the `balanced` policy, record the flag as found in the digest (`--skills readonly`) and mark it to be confirmed by `sbx create --help` on the box. Do not fabricate a version.
- 25-7 rewrites the README and the install runbooks. Keep this story's runbook edits to §3.5, §3.8 and the new kb section only.
