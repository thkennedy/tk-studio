## Intent

Design spec §7.3 and §6.3: EP-30's office must render a live picture without reading raw events. This story adds `apps/supervisor/src/office.ts`. It projects the queue's events of each live run, plus the engine's journal in the run's served root, into the eight office states. It does this for every registry agent (Story 29.2's `agents` rows), with per-story `done`/`failed` overlays and `done / total` progress. The result is served as a `GET /office` snapshot and a `GET /office/events` SSE stream: snapshot first, then deltas, with `Last-Event-ID` replay and a 10 s heartbeat. The status page gains a text section. The raw `GET /events` stream and the plugin are unchanged. The projection reads files only; it never goes through the engine and never writes the queue.

## Acceptance Criteria

AC1. **Given** the queue's events of a run and the engine's journal in the run's served root (`.bmad-loop/runs/<engine run id>/` at the bmad-loop pin of `bmad.lock`: the journal and run files the engine writes; the planner's Code Map names the exact files and kinds, read from the host side of the worktrees mount, never through the engine), **when** the supervisor projects them, **then** each agent of the registry has one of `offline`, `idle`, `thinking`, `reading`, `typing`, `running`, `waiting-for-human`, `blocked`, with the overlays `done` and `failed` per story, by one mapping table in `apps/supervisor/src/office.ts` (queued or lock-wait is `idle`; the launch and planner legs `thinking`; a dev session's implementer `typing` and its reviewers `reading`; the verify and host-verify legs `running`; `paused`, `awaiting-ruling` and an `escalate` `waiting-for-human`; a `blocked` run `blocked`; no run `offline`); promotion is instant, demotion goes through a grace timer (20 s, injectable), and `waiting-for-human` never expires on its own.

AC2. **Given** a run's stories (the spec folder's manifest at the run's base, the denominator fixed when the launch validated it), **when** the journal's terminal kinds land (a story landed, failed, deferred), **then** progress per story and per epic is `done / total` with the current story named, and the quote band of §7.1 is not computed here (EP-32's).

AC3. **Given** a consumer, **when** it reads `GET /office` (a snapshot: the agents with their states, the live runs with story and epic progress, the time) or opens `GET /office/events` with `Accept: text/event-stream`, **then** the stream sends the snapshot first, then one event per state or progress change (`office.agent`, `office.progress`, `office.run`), honours `Last-Event-ID` (a reconnect replays from that seq, the snapshot again when it is too old), sends a heartbeat comment every 10 s, and closes cleanly on the client's close; the raw `GET /events` stream is unchanged; `bun test` pins the mapping table against recorded event and journal fixtures, the grace timer with an injected clock, the snapshot-then-deltas order, the replay and the heartbeat; the read-only status page shows each live run's agent states as text.

- **Per epic.** The fields are `{spec_folder, done, deferred, failed, total, current_story}`, where `done` counts landed stories only. The run is one epic.
- No quote band and no cost: those are EP-32's.

**Grace (AC1).** The rank order is offline 0 < idle 1 < {thinking, reading, typing, running} 2 < blocked 3 < waiting-for-human 4.
- A change to an equal or higher rank applies at once. A change within rank 2 is instant too.
- A lower raw state applies only after it has held for `graceMs` (default 20 000, injectable) on the injected clock. A raw state that comes back up before then cancels the demotion.
- `waiting-for-human` has no timer of its own. It leaves only when the raw state drops (the run resumes or ends), and then through the same grace.

**`office.ts` (new):** no HTTP and no HTML.
- `OFFICE_STATES` and `OFFICE_MAP`.
- `readJournal(dir)` and `readEngineState(dir)`, both cached.
- `projectOffice(queue, deps)`: pure over the reads. It returns `{at, agents: [{agent_id, project, role, state, current_run, current_story}], runs: [{run_id, project, state, engine_run_id, epic, stories}], problems}`. The agents are `readAgents(queue)` rows (`registry.ts:225`) with `state` overlaid, so every registry id appears exactly once. A project with live runs but no registry rows adds no agents.
- `class OfficeHub({queue, now, graceMs, pollMs, bufferSize})`:
  - It holds the graced view, an in-memory monotonic `seq`, a `boot` id (process start ms) and a ring buffer of the last `bufferSize` (default 1000) delta events.
  - `refresh()` re-projects, applies grace, diffs against the last view, and appends one event per change:
    - `office.agent` `{agent_id, state, from, at, current_run, current_story}`
    - `office.progress` `{run_id, epic, story?}`, sent on any progress or overlay change of a story
    - `office.run` `{run_id, project, state, from}`, sent when a run appears, changes state or leaves the live set
  - `snapshot()` calls `refresh()`, then returns the view plus the current id.
  - `since(id)` returns the buffered events after `id`, or `null` when `id` is too old, from another `boot`, or malformed.
  - It polls only while at least one stream is subscribed.
  - It never writes the queue, `service_events` or the store.
