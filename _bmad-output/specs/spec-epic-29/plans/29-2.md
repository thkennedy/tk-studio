## Intent

Design spec §7.2: the supervisor owns one registry of the agents it can run per project, so the web (EP-30), a driver and the operator all name the same agents by the same ids. This story derives an `agents` table in the queue file from each served project's resolved routing legs. It rebuilds the table on every `recover` and on every claim and end, and serves it read-only through `GET /agents` and a text section on the status page. The table is derived only: the plugin and onboarding do not change, and `live_state` stays `offline` until Story 29.3 projects it.

## Acceptance Criteria

AC1. **Given** the registry's served projects (the host registry's roots) and the routing legs of each (`pipeline.py resolve --directory <root>` with the shipped defaults when no story is live; the run's `routing.current.json` while one is), **when** `recover` runs (every tick) and whenever a run is claimed or ends, **then** the supervisor rebuilds an `agents` table in the queue file: one row per `(project, role)` for the roles `orchestrator`, `session`, `implementer`, `reviewer`, `consult`, `advisor`, `planner` (the legs of contract §5 mapped once, in one table in `apps/supervisor/src/registry.ts`), with `agent_id` `<project-id>/<role>`, `model`, `effort` and `advisor` from the resolved route, `persona` from a bindings file (`apps/supervisor/personas.json`, shipped: a display name per role; the sprites are EP-30's), `live_state` (Story 29.3; `offline` until then), `current_run` and `current_story` when the role has a live leg, and `jira_account` empty (EP-31's); the table is derived only: the plugin and onboarding are not changed, the registry is never edited by hand, and a project the host registry drops disappears on the next rebuild.

AC2. **Given** a consumer, **when** it reads `GET /agents` (bearer or session cookie) or `GET /agents?project=<id>`, **then** the answer lists the rows above with the time of the rebuild; an unknown project answers an empty list; the read-only status page gains an "Agents" section listing them per project; `bun test` pins the mapping from a resolved route, the rebuild on tick, claim and end, and the two routes; `apps/supervisor/README.md` documents the table and the routes.

There is no `orchestrator` leg and no `advisor` leg: `advisor` is a field of every leg (§5.1 "Advisor (0.1.21)"). The ruling, as `ROLE_LEGS` in `registry.ts`:

| role | source | model | effort | advisor |
|---|---|---|---|---|
| `orchestrator` | leg `supervise` (the post-hoc supervisor pass, `skills/tk-studio-launch/customize.toml:50`) | leg's | leg's | leg's |
| `session` | leg `session` | leg's | leg's | leg's |
| `implementer` | leg `implementer` | leg's | leg's (resolve already fills `inherited-session`) | leg's |
| `reviewer` | leg `reviewers` (the dev session's subagent reviewers; 29.3 maps "its reviewers" to `reading`) | leg's | leg's | leg's |

The legs `seam`, `review` and `triage` map to no role (the seven roles are closed by the story). A missing field is `null`, never invented. The table is the only place the mapping lives. Story 29.3's `office.ts` and Story 29.4's contract text read it, so keep it exported (`ROLE_LEGS`, `ROLES`).

**`apps/supervisor/src/registry.ts` (new):** no HTTP and no page.
- `rowsFor(projectId, route, persona, live)`: pure. `route` is `{<leg>: {model, effort?, advisor?}}`, either the `route` of `pipeline.py resolve` or the top-level legs of `routing.current.json`, which `pipeline.py:385` `current_payload` writes beside `story, written_at, consult_*, matched_rule, story_override, sources`. Returns seven rows with these fields:
  - `agent_id` `<projectId>/<role>`, plus `project` and `role`
  - `model`, `effort`, `advisor`
  - `persona`: the display name, or `null`
  - `live_state: "offline"`
  - `current_run`, `current_story`
  - `jira_account: ""`
- `resolveRoute(root, deps)`: `runUv(root, join(pluginRoot(env), "lib", "pipeline.py"), ["resolve", "--directory", root])`, parsed with `lastJsonObject` (`server.ts:340`, `:627`). `pluginRoot(env)` is the exported one in `env.ts:38`, not the private one in `server.ts:121`. The pattern to copy is `registryShow`, `server.ts:65`. `ok:false` or no JSON throws a named `RouteResolveFailed` (project id plus the refusal text).
- `liveRun(queue, projectId)`: the most recently created run of the project in `running`, `paused` or `external` whose `servedRoot(run)` (`queue.ts:745`) holds `.bmad-loop/routing.current.json`.
  - That file supplies the route, and `current_run = run.run_id`, `current_story = file.story` on every row of the project.
  - When there is no such run, the route comes from `pipeline.py resolve` and both fields are `null`.
  - A worktree removed by close-out or an `external` run has no served root, so it counts as no live leg.
  - An unreadable `routing.current.json` falls back to resolve. Name it in the rebuild's `problems[]`.
- `loadPersonas(path?)`: reads `apps/supervisor/personas.json`, resolved from `import.meta.dir`, the way `README` is located in the tests. A missing file or a missing role gives `persona: null`. Malformed JSON is a named `PersonasInvalid` in `problems[]` and every persona is `null`; it never fails the rebuild.
- `rebuildAgents(queue, deps)`, with `deps = {registry?: () => registryShow(), resolve?: resolveRoute, personas?: string, now?}`:
  - **Registry read fails** (throws, or `ok:false`): leave the table unchanged and return `{rebuilt: false, problem}`. A transient failure must not empty the table. "No registry" (the tick's inert case, `tick.ts:282`) is the same branch.
  - **Registry read succeeds:** build every project's rows, then replace the whole table in one `immediate()` transaction (`DELETE` then `INSERT`), with one `rebuilt_at`. That is how a dropped project disappears.
  - **A project whose resolve refuses** keeps its seven rows with `model`/`effort`/`advisor` `null`, so the ids stay stable. Its error goes in `problems[]`. Return `{rebuilt: true, rebuilt_at, projects, problems}`.
  - Never write `service_events` for a rebuild: it runs every tick, and that table is never pruned (29-1 residual).
- `readAgents(queue, project?)`: rows ordered by project, then by `ROLES` order, plus the `rebuilt_at` (`null` before the first rebuild).
- Projects come from `registryShow().projects` (`{<id>: {root, …}}`). Use the entry root (`entryRoot` at `server.ts:76`, or `registryRoot` at `planstatus.ts:86`). Do not use `writeStarterLocks`' job-checkout enumeration (`sandbox.ts:444`): the story says the host registry's roots.

## Risks and open decisions

- **Size:** ten files, band L. The new module and its tests are most of the diff. If the Files list grows beyond these (the cli.ts test injections excepted, see § Files), halt: the projection is 29.3's, the contract is 29.4's.
- **Ruling, not a Block If:** the role → leg table above. If the dev session finds a design document that contradicts it (an orchestrator leg, or an advisor model id), consult, and record a DRIFT `affects: 29-3, 29-4`. Never invent a leg in `pipeline.py`.
- **Cost:** a `pipeline.py resolve` subprocess per served project, on every tick and every claim and end. That is acceptable at today's one to three projects. Do not cache across rebuilds: the table must follow the routing as it changes.
- **Block If:** an AC appears to need a change to `pipeline.py`, `registry.py`, onboarding or the contract. Consult; never do it (AC1: "the plugin and onboarding are not changed").
- **Block If:** a GET path (the route or the page) can only be served by rebuilding. Consult: the page's no-write test pins reads as pure.
- `live_state` is `offline` on every row until 29.3. Do not derive any state here.
