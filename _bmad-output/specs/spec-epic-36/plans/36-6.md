## Intent

Three lib surfaces still decide by hand or by name: `plansync setup`'s `POST /workflows/update` keeps the legacy `from`/`to` transition keys and its new GLOBAL transitions carry no `id`, so the first live setup against the owner's site may still be refused (hole 92, DW-127; the DW-107 bundle of #290 already fixed the uppercase types, the v3 version and the To Do category); `launch.py check` writes `.bmad-loop/policy.toml` even when git tracks it, dirtying the tree the engine's preflight then refuses (DW-62), and its engine-gate clause cannot tell whether the engine sandbox was provisioned `WITH_GODOT` (DW-71); `engage.py scope` calls a project a game by a `gds-` name prefix, so confirming the plugin-shipped `gds-engine-godot-4` alone makes every `scope` refuse `GameDocsMissing` (DW-90). This story makes each decide by evidence: the v3 transition shape with ids, a refusal before the tracked write, a provisioning marker the launch check reads, and the installed-module manifest as the game-project evidence. AC1 to AC3 are lib and tests only. AC4 and AC5 change the supervisor (see the 36.5 entry under Risks).

## Acceptance Criteria

AC1. **Given** `plansync.py setup` against a simplified-workflow project **When** it updates the workflow **Then** the transitions copied from `GET /workflow/search` carry `INITIAL`/`GLOBAL`/`DIRECTED` types, the version comes from the v3 workflows search, the setup accepts any status in the To Do category where it asked for a literal `To Do`, the global transitions it adds (Blocked → Block Resolved, into To Do, into Blocked) carry ids in the `POST /workflows/update` payload and the legacy `from`/`to` keys are dropped (`jirabackend.py update_workflow`; DW-127, hole 92); the live call runs once by the operator through the consult log against the owner's site and the spec records the answer

AC2. **Given** `launch.py check` on a served project whose `.bmad-loop/policy.toml` is tracked, and an `engine.verify_commands` gate on a sandbox **When** `reconcile_verify_commands` would write the policy, and when the engine-gate clause reads the sandbox **Then** the write is refused or reported through `pipeline.unignored_writes` and the tree stays clean (`launch.py`; DW-62), and the clause reads whether the sandbox was provisioned `WITH_GODOT` from a record the pin writes (the tracked config or the sandbox's own marker) and warns on a gate without it (`launch.py engine_gate_clause`; DW-71)

AC3. **Given** a project whose working set confirms the plugin-shipped `gds-engine-godot-4` alone **When** `engage.py scope` decides `is_game_project` **Then** it reads the registry's evidence that the `gds` module is installed, not a `gds-` name prefix (`engage.py:797-799`), and the contract's CAP-15 rule follows (DW-90); the lib suite covers each with fakes; the contract (0.1.31, additive) names the rules; the entries close by this PR

AC4. **Given** a story the launch is about to run (`tk-studio-launch` for a `run-epic` job: the first story and every later one, a resume included) **When** the engine starts on it **Then** the launched path calls `plansync.py status --directory <owner root> --id ST-NNN --status in-progress` once (the verb the review and done phases use), recorded as a `plan-status` event with `phase: in-progress`, `ok` and `previous_status`, so the story's issue reads In Progress from the build's start instead of Backlog; a refusal or a blocked re-sync is one event and never stops the launch; the review phase at PR open and the done phase at the merge follow as now, a block's `Blocked - Awaiting User` wins while it stands, and the plan-status suite covers the third phase with a fake; the contract names it (hole 104, DW-146; added 2026-10-31, after this plan's bootstrap).

AC5. **Given** a `run-epic` job whose declaration names its rhythm (one story per run, or a stories-per-run figure; the shipped `run-epic.json` and the project instances carry it as a field, not prose) **When** the launch starts the engine **Then** the launched path arms the graceful stop itself from that figure (the `launch.py stop --graceful` the operator issued by hand after every Epic 35 launch), recorded as a `stop-armed` event with the figure and the engine id; a job with no rhythm declared runs to the epic's end and the launch check says so; a `run-epic` instance that declares one story per run never builds two stories in one run again; the launch suite covers the arming with a fake; the contract names the field and the event (hole 105, DW-147; added 2026-10-31, after this plan's bootstrap).

## Settled shape

1. DW-62 — the tracked-policy write: **refused**, never reported-and-written. `reconcile_verify_commands` guards only at the write (after the `if not added:` return): when `POLICY_REL` is in `pipeline.unignored_writes(root)` or `git ls-files --error-unmatch -- .bmad-loop/policy.toml` answers 0, it answers `refused()` with `policy: "refused"` and the row detail `refused: .bmad-loop/policy.toml is tracked (or not gitignored); add <n> command(s) from <source> by hand — fix it by hand`; nothing is written, `check` ends `blocked` on the gap, `git status --porcelain` stays clean. A tracked policy with nothing to add reads `unchanged`. Per driver-contract 0.1.28 (33.5: "a refusal is a gap the session never closes by hand") and `launch.py`'s own rule ("a named refusal, never a guess").
2. DW-71 — the provisioning record: **the sandbox's own marker**, written by the provisioning, read by the launch check. `tools/sbx-engine/provision-engine.sh`'s `WITH_GODOT` block writes `$HOME/.tk-studio/provisioned` inside the sandbox with one `key=value` line per option (`WITH_GODOT=<version>`, the date); `engine_gate_clause` reads it with one `sbx exec <sb> cat ~/.tk-studio/provisioned` per sandbox `sbx ls` lists as running (the supervisor config's `jobs.*.sandbox`), falling back to `test -x ~/.local/bin/godot` for a sandbox provisioned before the marker existed; the row reads `… sandbox <sb>: provisioned WITH_GODOT <ver>` or `warning: sandbox <sb> has no WITH_GODOT record; an engine.verify_commands gate there refuses`; `not running`/`sbx absent`/`daemon down` warn nothing. The story text's "a record the pin writes (the tracked config or the sandbox's own marker)" is read as the provisioning's marker: the pin runs on the host and writes only the per-user store, never the tracked tree (33.3, 33.5), and provisioning is per sandbox, not per project (`kb/engine-godot-4-pinned.md:65`). No supervisor change, so no serve restart. Appended to SPEC.md design notes.
3. AC1's live call — the operator step: the spec's `## Consult Log` carries the ask in the 35.4/35.7 form (`<date> — operator ask (AC1, tier ask, unverifiable-here): run uv run plugins/tk-studio/lib/plansync.py setup --directory <root> … against the owner's site; paste the POST /workflows/update status and body, and GET /workflows/search?expand=statuses,transitions for the project`), the criterion `unverifiable-here` until the evidence lands; a refusal of the payload shape by the site is a follow-up DW naming the site's answer, never a block of this story (the owner-steps fallback already exists).
4. DW-90 — the game-project rule: a game project is one whose tracked `working_set` holds `gds` or a `gds-` entry **and** whose `_bmad/_config/manifest.yaml` lists the `gds` module installed (`inventory.read_manifest_modules`); the plugin-shipped `gds-engine-godot-4` alone is not enough; an absent or unreadable manifest or config is not a game project (today's posture). The contract row :771 and the 0.1.31 paragraph name it; the SPEC's CAP-18 and the Epic 34 SPEC's CAP-15 origin are the same rule.

5. AC4 — the in-progress phase: **supervisor-side**, on the launched path (the launch inside the sandbox cannot write queue events); one call per story start, idempotent on a resume (a `plan-status` `in-progress` event already recorded for the story skips the call); the Jira category mapping needs nothing (`in-progress` → indeterminate exists).
6. AC5 — the rhythm field: `stop: {after_stories: 1}` on the job definition (beside `max_runs`, additive; `run-epic.json` ships `after_stories: 1`, `run-epic-36.json` carries it); the arming uses 36.3's tier-routed helper; the `stop-armed` event is recorded right after `engine-pid`; no field → no arming and one launch-check line.
