## Intent

A sweep's triage names each decision as a bare question (`launch.py triage_summary` and `sweep.ts parseTriage` keep only `{id, question}`), the engine skips it (`--no-prompt`), the PR lists it, and nothing asks the owner where he answers. On 2026-11-05 nineteen issues were posted to Jira by a scratch script (hole 112, DW-171), and five of them are still open (TKSTUDIO-220 to 224). This story gives the decisions a source and a sink. The source: the triage's options are lettered with a default on the studio side, and `track.py block --source sweep` posts one Task per related group from the sweep's close-out (the PR body names the keys). The sink: the sync-back tick ingests an answered issue at `Block Resolved` into the ledger (`decision:` lines through a ledger verb) and into the studio's record, which the engine's `bmad-loop decisions` is fed from. The tick then replies, and moves the issue to Done or re-blocks it. The studio inbox shows the items. Last, the plan-status promote leaves `Blocked - Awaiting User` once no block stands (EP-36 B1's remainder, the retrospective's B3, AI-4).

## Settled shape

Each shape is settled from the code and the design documents named. Its SPEC design-note bullet is in the planner's report (the coordinator appends them; this plan writes no other file).

1. **The decision shape (settles CAP-10's open question).** The stock skill already emits options and a recommendation, so the studio side letters them and forks nothing (AD-4). `triage_summary` (lib) and `parseTriage` (supervisor) project each decision as `{id, question, context, options: [{letter, text, key, effect}], default}`:
   - `letter` is `A`, `B`, `C`, … in the skill's option order.
   - `text` is the `label`, followed by ` — <intent or resolution>` when either is present, on one line (whitespace collapsed), clipped to 200.
   - `key` and `effect` are the skill's own (the engine verb takes `key`).
   - `default` is the letter of the option whose `key` equals `recommendation`, else `null`.
   - No options gives `options: []` and `default: null`.

   The `sweep-triage` ledger payload and `triage_reason` are unchanged (ids). The note in `recordTriage` carries the new shape (additive). e2e_run_sweep's fixture gets two options and asserts the letters and the default.
2. **The grouping rule.** Decisions are related, and go in one issue, when their normalised `question` and their normalised option list are equal. Normalising lowercases, collapses whitespace and removes every `DW-\d+` token. The option list is the sequence of `(label, effect)` plus the recommendation's index. Otherwise each decision gets its own issue. A group holds at most 30 ids and is chunked past that. Groups are ordered by their lowest DW number, ids inside a group by DW number. This is the hand posting's "batched only when related, as many tickets as it takes" (handoff :107), made deterministic.
3. **The issue form.**
   - Summary: `Decision: DW-87 — <question>` for one id, `Decisions: DW-12, DW-13 — <question>` for several. The question is the group's first, clipped so the summary stays within 255 characters; past 6 ids the list reads `DW-12, …, DW-17 +N`.
   - Type `Task`, label `tk-studio-decision`, `assignee {accountId: <planning.jira.owner_account_id>}` on the create.
   - Description (REST v2 plain text):
     ```
     Sweep <studio run id> (engine <engine run id>) needs <n> decision(s). Answer in one comment: one "<id>: <letter>" line per decision, "all: <letter>" for every decision here, or "default" to take each default.

     <id>: <question>
     <context>
     A) <text>
     B) <text>
     Default: <letter|none>
     ```
     The block above repeats per id, with a blank line between.
   - Then `_block_issue` moves the issue to `Blocked - Awaiting User` and posts the mention comment `[~accountid:<owner>] Blocked: <n> sweep decision(s) need your answer: <ids>` / `Resolves when: reply with one "<id>: <letter>" line per decision, "all: <letter>", or "default"`. This is the form `inbox.BLOCK_COMMENT_RE` reads.
4. **`track.py block --source sweep`.** The argv: `uv run track.py block --directory ROOT --source sweep --triage PATH [--triage PATH …] --run-id RID [--ask DW-N …] [--dry-run]`.
   - Exclusive with `--story`, `--engagement`, `--reason`, `--resolves` and `--kind`. Each mix is refused by name, exit 2, no call.
   - Later `--triage` files win by id (the `mergeTriages` rule).
   - An id already asked on a record issue whose `state` is `open`, or holding a recorded answer, is skipped (`skipped[]: "DW-n: already asked on KEY" | "DW-n: answered on KEY"`), unless `--ask DW-n` names it (a recorded answer that no longer matches the triage's options). A re-asked id's block gets the line `Earlier answer: <letter> (<KEY>) no longer matches these options`.
   - Result: `{ok, dry_run, source: "sweep", run_id, issues: [{issue, ids, created, transitioned, commented, skipped?, error?}], skipped[], notes, written}`, plus the AD-11 block.
   - No decisions gives `complete` with nothing posted. Refusals are `block_engagement`'s (binding, variables, owner, `IssueCreateRefused`) plus `TriageUnreadable` (a path absent or not a JSON object).
   - A temporary failure gives `partial`, `ok: false`, `retry: true`.
   - Dry run: no call to create, nothing written. One note per group, `dry run: would create "<summary>" (Task, tk-studio-decision, assigned to the owner) for <ids> and move it to 'Blocked - Awaiting User' with the mention comment`. `issues[]` entries are `{issue: null, ids, created: false, …}`, status `partial`.

6. **The answer grammar and the `default` rule.**
   - The ingest reads the owner's comments in `_bmad-output/tracking/<KEY>/comments.jsonl` (the last line per id; `author: "owner"`) created after the newest agent `Blocked:` comment. Lines are read in comment order, then line order, and a later line wins.
   - A line is trimmed, a leading `-`/`*` is stripped, and it is matched case-insensitively against: `^(DW-\d+)\s*[:=]\s*([A-Z])\s*[.!]?$` (an id answer), `^all\s*[:=]\s*([A-Z])\s*[.!]?$` (every id of the issue) and `^default\s*[.!]?$` (the default flag).
   - Precedence: an id's own line, then `all:`, then (only when a `default` line is present) the id's `default`.
   - A letter outside the id's options leaves the id open, named `DW-n: no option X`.
   - A line `DW-n: <letter> <more text>` is a qualified answer. It is not ingested; it is named `DW-n: qualified answer, not ingested` and the id stays open (the hand ingests' "A with one change" and "none of A/B/C" stay the operator's).
   - An id with a `default: null` under `default` stays open, named `DW-n: no default`.
7. **The `decision:` line and its verb.** The line is `decision: <letter> — <text> (<KEY>, <YYYY-MM-DD>)`, inserted directly after the entry's `status:` line. The verb is a new subcommand: `uv run plansync.py ledger-decide --directory ROOT --id DW-N --letter L --text TEXT --issue KEY [--date YYYY-MM-DD] [--dry-run]`.
   - Text: one line, clipped to 200.
   - Idempotent: the same line already on the entry gives `unchanged`, no write.
   - One atomic write. The status block ends the result: `{ok, ledger, id, line, decided: bool, unchanged: bool, written}`.
   - Refusals (`blocked`, exit 2): a bad id, letter, key or date; `LedgerDuplicateId`; `LedgerMissingId` (38.3's); no ledger.
   - The ingest calls `plansync.ledger_decide` in process ("through the ledger verb"), one call per answered id.
   - The entry's `status:` is never touched; the flips stay ledger-resolve's and the engine's.
8. **The engine answer (settles CAP-11's open question).** A non-interactive form exists: the verb's prompter reads stdin, and `--json` lists the pending set in order with each option's `key`. "An open sweep record" is a `run-sweep` queue run whose engine has ended and whose worktree still holds `.bmad-loop/runs/<engine id>/triage*.json`. That is the run at its close-out, the only time `pending_missed_decisions` can see it and nothing else writes the worktree's git.
   - At each sweep close-out site, before `postDecisions`, `answerDecisions(queue, run, summary, deps)` in sweep.ts reads the record's `answers` (at `run.root`) for the triage's decision ids. It matches each answer to the triage's options by `(effect, normalised label)`, else by `key` when that option's label is equal. A miss goes to `--ask`.
   - It runs `sbx exec <run.sandbox> sh -c '"$HOME/.local/bin/bmad-loop" decisions --json --project <vm>'`. Then, when the leading pending ids have matched answers, it runs `sbx exec <run.sandbox> sh -c 'printf "%s\n" <k1> <k2> … | "$HOME/.local/bin/bmad-loop" decisions --project <vm>'`. `<vm>` is `toVmPath(servedRoot(run))` with a POSIX tail. Keys are checked against `^[A-Za-z0-9_-]{1,16}$` before they go in the line, else the id is skipped.
   - The walk stops at the first pending id with no answer. EOF then ends the verb non-zero, which is expected. The outcome is judged by a second `--json` read: ids gone from pending are `answered`.
   - The engine writes its own `decision:` line and commits the ledger and its store on the run branch. That commit is in the sweep's PR.
   - One note per engine run: `sweep-decisions-answered {engine_run_id, answered: [ids], left: [ids], ok, error?}`. A failure never blocks the close-out.
   - Else (no open sweep record) the ingest's `answers` entry is the record the next sweep's close-out feeds the same way. The next triage re-surfaces the still-open id, and the close-out answers it instead of posting it again.
