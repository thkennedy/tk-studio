## Intent

The launch surface has three holes. A relaunch (stories already `done`, routing already applied) ended in prose with no status block and pointed at the retired ClaudeOS queue (hole 20, PROP-062). Bootstrap output dirtied the tree, so the readiness check refused the launch's own work and two launches needed a second pass (hole 10). The engine's `max_tokens_per_story` stayed at the template's 2,000,000 while every story measured 3.9M to 4.4M weighted (hole 4, PROP-033). The fix: the deterministic core carries the AD-11 block at the end of every result, so every skill path ends on the same shape. The skill commits its bootstrap output before `check`. `check` and `start` compare the policy limits with the budget bands, report mismatches, and never edit the policy. Band L, reason: core verbs, skill text, the conformance runner and manifest, a fixture, tests and the contract row, about 8 files and more than 300 changed lines.

## Acceptance Criteria

1. **Given** a first launch on an epic **When** the bootstrap writes `SPEC.md`, `stories.yaml` and the first plan **Then** the launch commits them on the run branch with one named commit message before its readiness check, so the dirty-tree refusal never fires on its own output, and the rule is stated once in the skill text (the Epic 20 and 22 launches needed a second pass; the Epic 24 and 25 launches committed theirs)
2. **Given** a relaunch on an epic with stories already `done` and routing already applied **When** the session ends **Then** its last output is the JSON status block exactly as on the fresh path, the watch hint names the supervisor's status page and the `status` verb and never ClaudeOS, and a conformance drive covers the relaunch case beside the fresh case
3. **Given** the project's `.bmad-loop/policy.toml` limits (`max_tokens_per_story`, wall-clock, review caps) and the budget bands in `.tk-studio/budget-bands.yaml` **When** `start` or `check` runs **Then** the launch result names every limit the bands exceed (band ceiling above the policy limit) as a `budget_mismatch` entry with both numbers, `check` ends `partial` naming them, and `start` refuses to start the engine on a mismatch unless the payload carries `allow_budget_mismatch: true`; the machine-local policy file is never edited by the skill
4. **Given** the lib suite and conformance **When** the story closes **Then** both are green, including the new drives, and the driver contract §2 launch row states the bootstrap commit, the relaunch block and the budget check (0.1.21, additive)

## Settled shape (planner rulings, 2026-10-15; the design documents constrain these, so they are not Block Ifs)

1. **The block comes from the core.** Every `launch.py` verb result (check, start, status, stop, and the `LaunchError` refusal) ends with the four AD-11 keys, in this order: `status`, `intent` (`"tk-studio-launch"`), `artifacts`, `reason`. This follows the Story 25.5 doctor precedent: one JSON object whose last keys are the block. The cases:
   - `check`: `complete` when ok with no mismatch; `partial` naming each `budget_mismatch`; `blocked` naming the gaps.
   - `start`: `complete` with `artifacts` = [`run_dir`, `spec_folder`]; `blocked` on a refusal, a mismatch, or an unacknowledged launch.
   - `status`: `complete`.
   - `stop`: `complete`, or `blocked` on a refusal.

   The skill's every path, fresh or relaunch, ends by printing the last core result's block as its final line. The skill adds to `artifacts` only the SPEC/plan files it wrote this session. That is the one rule, stated once.
2. **Budget comparison.**
   - `weighted_tokens` of the largest band is compared with `max_tokens_per_story`.
   - `review_cycles_max` of the largest band is compared with `max_review_cycles`.
   - A policy limit the bands carry no field for (the wall-clock `session_timeout_min`, `max_tokens_per_session`) is listed under `budget.not_compared` with the reason `no band field`. It is never a mismatch.

   Each mismatch is `{"limit": "<policy key>", "policy": <n>, "band": "<S|M|L>", "band_field": "<field>", "band_value": <n>}`.

   Both `check` and `start` carry `budget: {compared[], budget_mismatch[], not_compared[]}`. A mismatch is never a `gaps[]` entry, so the existing `ok` semantics hold.

   `start` refuses on a mismatch (exit 2, `blocked`) unless `--allow-budget-mismatch` is given. The payload's `allow_budget_mismatch: true` maps to that flag.

   A missing or unparseable `policy.toml` or `budget-bands.yaml` is a named `budget` check entry, not a crash and not a mismatch.
3. **Bootstrap commit.** The skill commits on the checkout's current branch (`loop/epic-<N>`) with exactly `loop(epic-<N>): SPEC, manifest and first-story plan from the launch bootstrap`. The commit stages only the files the bootstrap wrote (`SPEC.md`, `.memlog.md`, `stories.yaml`, `plans/<N>-<M>.md`, and any canonical plan files the transcription wrote). It happens after step 4 and before step 5's `check`. If nothing was written (a relaunch), there is no commit. The skill never commits anything else, and never pushes.
4. **Watch hint.** Attended and headless reports name the supervisor's status page and `launch.py status` (the `status` verb), plus `bmad-loop tui`. They never name ClaudeOS.
5. **Conformance drives.** `runner.py` extends `expect: "status-block"` to surface drives. This is additive under §8, and the judge is shared with `cli_drives`. A surface drive may declare `status` (the expected block status). Without it, any schema-valid status passes, with exit 0 or 2. Two new `tk-studio-launch` drives:
   - **Fresh:** `launch.py check --directory {sandbox} --spec _bmad-output/specs/spec-none` expects a `status-block` with status `blocked`.
   - **Relaunch:** `launch.py check` against a new fixture `contracts/conformance/fixtures/launch-relaunch/`. The fixture has `SPEC.md`, a `stories.yaml` with two entries, one `stories/<id>-*.md` with `status: done`, and `.bmad-loop/routing.current.json`. The drive expects a `status-block` with the intent `tk-studio-launch`. Its status depends on whether the drive box has `bmad-loop`, so the status is not declared.
