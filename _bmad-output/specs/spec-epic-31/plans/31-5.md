## Intent
When the loop cannot progress a story, the story's Jira issue, and each dependent story, moves to `Blocked - Awaiting User` with an agent comment that @mentions the owner, names the reason and says what resolves it. This is done by a new `tk-studio-track block` verb that the supervisor's paused-run pass calls (§6.9 items 1 and 2, §7.4). The sync-back then derives one inbox from those statuses into `_bmad-output/tracking/inbox.json`. The supervisor serves it at `GET /inbox` (contract 0.1.26, additive), and the office shows a persistent "!" on the desk whose work is blocked. Every Atlassian write goes through the planning adapter (`jirabackend`, AD-4). Nothing local is promoted except the status move and the comment that the verb exists to make (D9).

## Acceptance Criteria
- AC1: **Given** a story the loop cannot progress (a dev session's `blocked` end, a `paused` run awaiting a ruling, an engagement question) **When** the loop reports it **Then** the issue (and each dependent story, by the plan's links) moves to `Blocked - Awaiting User` with a comment that @mentions the owner and names the reason and what resolves it (a `tk-studio-track block` verb the supervisor's paused-run pass and the engine's escalation hook call)
- AC2: **Given** the sync-back **When** it reads the mentions **Then** it derives `inbox_item {issue, priority, blocked_since, reason_comment, state: open | resolved | validating}` for every issue in that status, sorted by priority then time, into `_bmad-output/tracking/inbox.json`; the supervisor serves it at `GET /inbox` (a supervisor surface the web consumes, contract 0.1.26 additive) and the office shows a persistent "!" bubble on the desk whose work is blocked, cleared when the status changes, never when a message arrives

## Settled shape
Each shape is appended to SPEC.md "Design notes" as one bullet.
1. **`tk-studio-track block`** (named placeholder rule).
   - Command: `track.py block --directory ROOT --story <entity id | N-M-slug> --reason TEXT --resolves TEXT [--source run|engagement] [--dry-run]`.
   - It resolves the story's entity and its `external.jira.key`, plus each dependent (entities whose `depends_on` names it).
   - For each issue already in `Blocked - Awaiting User`, the transition is skipped. Otherwise it calls `transition_to_name(BLOCKED_STATUS)`.
   - Then it posts one agent comment: `[~accountid:<owner>] Blocked: <reason>\nResolves when: <resolves>`. A dependent's comment adds `\nBlocked by: <issue key>`. The comment is skipped when the issue's newest agent comment in `tracking/<KEY>/comments.jsonl` has the same body.
   - Result: `{ok, dry_run, issues:[{issue, entity, role: story|dependent, transitioned, commented, skipped?}], notes[], written[]}`, with the §3 status block last.
   - Refusals, each `blocked` by name: no `planning.jira` binding; absent env (no call); no `owner_account_id` (a mention needs it); an entity that was never promoted (no `external.jira.key`); no transition reaching the status.
   - A dependent that fails while the story succeeded makes the run `partial`.
2. **`_bmad-output/tracking/inbox.json`** (named placeholder rule).
   - Shape: `{inbox_version: 1, generated_at, project_key, items:[{issue, entity?, title?, priority, blocked_since, reason_comment: {id, body, created} | null, state}]}`.
   - `state` comes from `external.jira.status` by name: `Blocked - Awaiting User` is `open` and `Block Resolved` is `resolved`. `validating` is reserved for 31.7, which writes it; 31.5 keeps an existing `validating` while the status is still `Block Resolved`.
   - `reason_comment` is the newest comment whose `author` is `agent` and whose `mentions` include `owner`. `blocked_since` is its `created`, else when the tick first saw the status.
   - `priority` is the Jira `priority.name` as pulled, else the canonical `priority` mapped P0 Highest, P1 High, P2 Medium, P3 Low, else `null`.
   - Sort by priority rank (Highest to Lowest, then `null`), then `blocked_since` ascending.
   - The file is rebuilt on each complete-read tick:
     - Issues returned by the search update their items.
     - An issue leaves the inbox when its status name leaves the two setup statuses.
     - Items for issues not returned are kept, because an unchanged `updated` means an unchanged status.
     - A local entity in a setup status that has no item is added from local data.
   - It is atomic and named in `written[]`. A dry-run, `rate-limited`, `error` or `blocked` tick leaves it untouched.
3. **`GET /inbox?project=<id>` and the office field** (optional entry).
   - The route answers `{ok:true, project, generated_at, items:[…]}`, read from the served project's `tracking/inbox.json` exactly as served. A missing file gives `items: []` with `generated_at: null`, never a 404 or an error.
   - Readable by bearer or cookie (`readRoute`). It is a §1 web-table row, 0.1.26 additive.
   - The office projection gives `OfficeAgent` an optional `blocked_issue: {issue, state} | null`. It is set when the agent's `current_story` (`N-M`) maps by `source: epics.md#story-N.M` to an entity whose issue has an `open` inbox item, and it is recomputed when the inbox file changes.
   - The web's "!" shows while `blocked_issue` is non-null. Comment and message events never touch it.
4. **The supervisor's call** (optional entry).
   - `awaitRuling` runs `track.py block --story <story_key> --reason <landing reason> --resolves "a ruling in the spec (<spec path>)"` for a project with a `planning.jira` binding. Without a binding it skips silently.
   - A `track-block` queue event per (story key, engine run id) records the result on `ok` or a by-name `blocked`. A transient failure (no JSON, a crash) is retried on the next pass.
   - The existing `awaiting-ruling` event and its notification are unchanged.

## Risks and open decisions
- **The engine's escalation hook does not exist.**
  - bmad-loop fires no hook on an escalation or a pause, and it is not this repo's to change.
  - Every escalation ends in a paused run, which the supervisor's paused-run pass sees, so that pass is the one caller.
  - Record a DRIFT line naming the absent hook. Do not add a hook to bmad-loop or to `.bmad-loop/plugins/`.
  - **Block If:** an escalation path is found that ends without a paused run.
- **The engagement question** (AC1's third trigger) has no caller yet. The engagement loop is EP-32, and 31.7 AC2 makes its questions issues. The verb takes `--source engagement` so the shape is fixed now; the call site is not built here.
- **Block If:** AC1 can be met only by a Jira write outside `jirabackend` (AD-4), or by promoting anything besides the status move and the block comment (D9).
- **Block If:** the inbox needs a second JQL search per tick. The 31-1 note asks for one paged search; Settled shape 2's merge is meant to avoid it.
- **Block If:** the Files list must grow past the list above. The plan-sync SKILL and `jobs/` stay untouched.
- Not Block Ifs: the four settled shapes; the ungraded `POST /issue/{key}/comment` and transitions-by-name request shapes (pin them in the fakes); and the absent `bun` (record it `unverifiable-here`).
- **Oversize.** About 1,200 to 1,500 new lines over about 25 files across lib, the supervisor and the web. That is past the L band, as 31.2 to 31.4 were, and the story is not split here. If review cycles run out, defer the web "!" residue rather than widening.
- **Order.** The story needs 31.2's binding (`owner_account_id`, `project_key`) and 31.4's tick and comment log. 31.6 reads `GET /inbox` and `blocked_issue`, and 31.7 writes `validating`.
