## Intent
The owner answers a blocked story from the desktop or the iPad without opening Jira (§6.9 items 2 to 4). The web gains an Inbox screen that lists the open items 31.5's `GET /inbox` serves. It also gains an Issue screen that shows one issue the way Jira would, with a reply box and a **Done** button. A reply or Done goes through a supervisor surface, `POST /inbox/{key}/reply`. The supervisor runs a new `tk-studio-track reply` verb on the host with the owner's host-only token. The verb posts the comment as the owner and moves the issue to `Block Resolved`, through the planning adapter (AD-4). The item leaves the list on the next sync-back, because 31.5 derives `Block Resolved` as `resolved`. Contract 0.1.26 stays additive (AD-2, AD-19).

## Acceptance Criteria
- AC1: **Given** `GET /inbox` and the tracked issues **When** the Inbox screen renders **Then** it lists open items sorted as served, each with the project, the issue key and title, the priority, how long it has waited and the reason's first line; the web's nav gains Inbox and Issue; the count sits on the nav item
- AC2: **Given** one item **When** the Issue screen opens **Then** it shows the issue Jira-like (status, the run and PR when the plan links one, the cost from the ledger when known, the comments in order with author and time), a reply box, and a **Done** button for a simple request; sending a reply, or Done (which writes "Done." as the owner), posts the comment through the supervisor (`POST /inbox/{key}/reply`, the owner's token, never the agent's) and moves the issue to `Block Resolved`; the item leaves the list on the next sync-back; vitest covers the list, the view and the two actions with a fixture

## Settled shape
Each shape below has its bullet appended to SPEC.md `## Design notes (settled shape, planner, 2026-10-24)`.

1. **The issue read: `GET /inbox?project=<id>&issue=<KEY>`.** This keeps the web on the two §1 inbox surfaces that SPEC Constraints name. Without `issue`, the answer is 31.5's, unchanged. With it, the answer is `{ok, project, generated_at, items, issue}`:
   - `items` holds the matching item, or nothing.
   - `issue` is `{key, entity, title, status, run, cost_usd, comments[]}`. `entity` is the plan entity id whose `external.jira.key` is `KEY`, or `null`. `status` is the entity's `external.jira.status`, else the item's state, else `null`. `run` is the story's latest run as `GET /board` composes it, or `null`. `cost_usd` is that run's ledger `job-run` cost (`payload.run_id` = the run's `studio_run_id`), or `null` when unmetered or absent.
   - `comments[]` comes from `_bmad-output/tracking/<KEY>/comments.jsonl`. Keep the last line per `id` (an edit appends one), in `created` order, each `{id, author, update_author?, body, created, updated}`.
   - A key not matching `^[A-Z][A-Z0-9]+-\d+$` is `400 BadIssue`. A key with no item, no entity and no comment log is `404 UnknownIssue`.
   - Any `GET /inbox` on a cookie session answers the session's CSRF token in the `X-CSRF-Token` response header. A bearer answer has none.
2. **`POST /inbox/{key}/reply`.**
   - Body: JSON `{project, body?: string, done?: true}`. Exactly one of a non-empty `body` (at most 32 KiB UTF-8) or `done: true` is allowed, else `400 SchemaError`. Done writes the body `Done.`.
   - Auth: the bearer, or a cookie session with `X-CSRF-Token`, else `403 CsrfRefused`.
   - The supervisor checks that `TK_STUDIO_ATLASSIAN_OWNER_EMAIL`, `TK_STUDIO_ATLASSIAN_OWNER_TOKEN` and `TK_ATLASSIAN_CLOUD_ID` are present, after the User-environment fill. When any is absent: `409 OwnerSeatMissing {missing: [names]}`, with no spawn.
   - It writes the body to a temp file (removed afterwards), then runs `uv run <plugin>/lib/track.py reply --directory <registry root> --issue <KEY> --body-file <tmp>`. The body never goes on the command line.
   - Answers: `ok` → `200 {ok, project, issue, commented, transitioned, status}`. `blocked` → `409 ReplyRefused {reason}`. `retry: true` → `503 ReplyRetry {reason}`. No JSON or a spawn failure → `500 ReplyFailed`. Unknown project → `404 UnknownProject`.
   - It writes no queue event: the item leaves on the next sync-back, and the web shows "sent; it leaves the Inbox on the next sync-back".
3. **`tk-studio-track reply`.**
   - `track.py reply --directory ROOT --issue <KEY> (--body-file PATH | --done) [--dry-run]`.
   - It posts the comment with the owner-seat client (`jirabackend`, gateway, `/rest/api/2`, plain text), then moves the issue by name to `Block Resolved` (`transition_to_name`). An issue already in `Block Resolved` skips the transition, named in `skipped[]`.
   - Refusals end `blocked`, by name: no `planning.jira` binding; an absent owner variable or cloud id (before any call, marker `no Atlassian call made`); no recorded `owner_account_id`; a created comment whose `author.accountId` is not the owner's (the wrong seat's token: named, and nothing moved); no transition reaching `Block Resolved` (the comment stays, `commented: true`).
   - A transient failure ends `partial` + `ok: false` + `retry: true` (the 31.5 precedent).
   - Result: `{ok, dry_run, issue, commented, comment_id, transitioned, status, notes[], skipped[], written[]}`, then the §3 block. No local file is written, and nothing else is promoted (D9).
4. **The web.**
   - `SCREENS` becomes `office, board, status, inbox, issue`.
   - The Inbox fetches `GET /inbox?project=<p>` for each served project (`projectsFrom` order). It keeps `state === "open"` items, in served order within each project, and concatenates the projects. Each row shows: project, key, title (else `—`), priority (else `—`), waited (now − `blocked_since`, as `5m`/`3h`/`2d`) and the first line of `reason_comment.body` (else `—`).
   - The nav count is that row count, refetched as the Board refetches (live-state key, focus and visibility). An empty inbox shows no count.
   - Choosing a row opens the Issue screen for `(project, key)`, remembered under `tk-studio.web.issue`. Without one, the Issue screen says "Choose an item in the Inbox".
   - The view shows: status, run state and PR link (`safeHref`), cost (`$0.00`, else "not metered"), and comments in order with author (`owner`/`agent`) and time. Below them, a reply box with Send (disabled when empty), and Done.
   - The model owns `postReply(project, key, {body} | {done: true}, csrf)`, which never throws and names the supervisor's `error`. The vitest fixture is one `inbox.json`-shaped answer plus one issue answer.

## Risks and open decisions
- **Block If:** the owner's token would have to reach the sandbox, or any surface would have to post as the owner with the agent's token.
- **Block If:** the reply needs an Atlassian write outside `jirabackend` (AD-4), or the supervisor would call Jira itself.
- **Block If:** the Issue view needs a supervisor surface besides `GET /inbox` (with `issue`) and `POST /inbox/{key}/reply` (SPEC Constraints, the web's surfaces).
- **Block If:** the Files list must grow past the list above.
- Not Block Ifs: the four settled shapes; the `/rest/api/2` reading of the 31-1 note; the ungraded owner-comment and transition shapes (pin them in the fakes); the released-roster red; a missing `node_modules/.bin` (use the direct entry files).
- **Oversize.** About 25 files across lib, the supervisor and the web, and about 1,200 new lines. That is past the L band, as 31.2 to 31.5 were, and the story is not split here. If review cycles run out, defer screen styling residue rather than widening.
- **Order.** The story depends on 31.5's `GET /inbox`, `inbox.json` v1 and `comments.jsonl` `update_author`. 31.7 reads the `Block Resolved` that this reply makes, and its owner check reads the changelog's accountId. The wrong-seat refusal (Settled shape 3) keeps that accountId the owner's.
