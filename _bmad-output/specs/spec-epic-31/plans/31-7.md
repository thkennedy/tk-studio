## Intent
When the owner's reply or Done moves an issue to `Block Resolved` (31.6), the loop must check that the reply really resolves the block before the story continues (§6.9 items 4 and 5). The supervisor sees the resolved item that the sync-back wrote. It then queues a shipped `validate-resolution` job on the host tier with the planner leg's model. The session first checks that the owner made the transition. It then reads the reason and the reply from local memory, and either tests what it had to be able to do or judges the answer. On a pass it moves the issue back to `To Do` or `In Progress` and writes any ruling into the paused story's spec, and the supervisor resumes the paused run. On a fail it re-blocks the issue with a follow-up comment, which puts it back in the Inbox. The loop's `escalate` rulings reach the same inbox through 31.5's paused-run pass.

## Acceptance Criteria
- AC1: **Given** an issue in `Block Resolved` **When** the sync-back sees it **Then** the supervisor queues a `validate-resolution` job for the project (host tier, the planner leg's model): the session reads the reason and the reply, and either tests the thing it had to be able to do (a command, a path, a sign-in) or judges whether the answer is enough; a pass moves the issue back to `To Do` or `In Progress` (the loop re-arms the story: the supervisor's paused run resumes with the ruling written into the spec, or the job's next tick re-runs it), a fail moves it to `Blocked - Awaiting User` with a follow-up comment that lands in the inbox again
- AC2: **Given** the engagement's questions and approvals and the loop's `escalate` rulings **When** they arise **Then** each is an issue with comments in the same project, so the owner has one inbox for everything; the supervisor's `awaiting-ruling` writes the block instead of a Telegram note alone, and a reply that carries a ruling is written into the spec by the validation session; the lib suite and `bun test` cover the queueing, the two outcomes and the ruling write with fakes

## Settled shape
Each shape below has its bullet appended to SPEC.md `## Design notes (settled shape, planner, 2026-10-24)`.

1. **`tk-studio-track validate`.** `track.py validate --directory ROOT --issue <KEY> (--check | --pass --to "To Do"|"In Progress" [--ruling-file PATH --spec PATH] | --fail --follow-up-file PATH) [--dry-run]`. It uses the agent seat only (`client_for`) and never the owner variables.
   - **Shared refusals**, each ending `blocked` by name: a bad key; no `planning.jira` binding; an absent agent variable (marker `no Atlassian call made`, before any call); no `owner_account_id`; an issue whose live status (`_current_status`) is not `Block Resolved`.
   - **`--check`:**
     - It reads the changelog (`issue_changelog`, `last_transition_into(…, RESOLVED_STATUS)`). `owner_resolved` is true only when that transition's `account_id` is non-empty and equals `owner_account_id`.
     - It reads, from local memory only:
       - `reason`: `inbox.reason_comment`.
       - `replies[]`: the `comments.jsonl` lines (last line per `id`) whose `author` and `update_author` are both `owner`, created after the newest agent comment.
     - It marks the inbox item `validating` (`inbox.mark_validating`, named in `written[]`).
     - Result: `{ok, dry_run, issue, entity, story, owner_resolved, transition: {id, created, account_id} | null, reason, replies[], notes[], written[]}`, then the §3 block. `owner_resolved: false` is a `complete` result, not a refusal; the session then takes the fail path.
   - **`--pass`:**
     - It moves the issue by name to `--to` (`transition_to_name`). No transition reaching the target is a refusal by name.
     - With `--ruling-file`, it writes the ruling into `--spec` first (shape 6).
     - It appends a `validation.jsonl` line (shape 3) with `outcome: pass`.
   - **`--fail`:**
     - It re-blocks through the `block` internals for the issue's entity. The reason is the follow-up text. The resolves text is `a reply in the Inbox that answers the follow-up`. This posts the `Blocked:` agent comment that `inbox.reason_comment` and the Inbox read.
     - It appends `outcome: fail`.
   - **A transient failure** ends `partial` + `ok: false` + `retry: true`, writes no line, and the session calls again.
2. **The changelog read** is `jirabackend.issue_changelog(client, key)` (paged) and the pure `last_transition_into(histories, name)`, beside `issue_comments`. It is read-only and used only by `validate --check`.
3. **`_bmad-output/tracking/<KEY>/validation.jsonl`.** One line per outcome: `{issue, outcome: pass | fail, at, transition_id, reply_ids[], to?, ruling?: <spec path>, follow_up_comment_id?}`. It is appended atomically and named in `written[]`. It is local memory, never promoted (D9), and it is the supervisor's evidence for the re-arm.
4. **The supervisor's resolution pass** (`apps/supervisor/src/resolution.ts`, `resolutionPass(queue, deps)`, run right after `closeOutPaused`).
   - **What it reads:** for each project with a `planning.jira` binding, its registry root's `inbox.json`, keeping the items with `state === "resolved"`.
   - **Queue key:** `(project, issue, reason_comment.id ?? blocked_since)`, which marks one block cycle and so one transition. It records a `validate-queued` service event per key and never queues a recorded key again.
   - **Paused-run lookup:** the paused run for an item is the one whose latest `track-block` since its latest `paused` names the issue with `role: story`.
   - **Enqueue:** the `validate-resolution` definition, resolved as `validate` resolves it, with `target.payload` = `{verb: "validate", project_root, issues: [{issue, story, paused_run, spec}]}`. `paused_run` is the queue run id or `null`; `spec` is `findSpec` in `servedRoot(run)` or `null`. Run options: `tier: "host"`, plus `model` and `effort` from the served project's `.bmad-loop/routing.current.json` `planner` leg when present (else the job's own routing). One live run per checkout (the idempotent mint), so a later item waits for the next pass.
   - **Re-arm:** after a `validate-resolution` run ends, for each payload issue whose newest `validation.jsonl` line is `pass` and whose `paused_run` is still `paused`, the pass calls `resumePaused` and records `validate-resumed`. A refusal is recorded, never thrown: `StoryLanded` is left to `closeOutLanded`, which relaunches a landed story. A `fail` line resumes nothing: the item returns as `open` on the next sync-back, and its new block comment makes a new key.
5. **The checkout lock.** `claim` does not wait on a **paused** holder when the claimant's `job_id` is `validate-resolution`: the validation exists to un-pause that holder. It still waits on a queued or running holder. The run works in its own worktree and writes only Jira, the registry root's tracking memory and the paused spec.
6. **The ruling write.** When the owner's reply carries a ruling (the block's resolves text names "a ruling in the spec"), `--pass --ruling-file` writes the ruling into the paused story's spec. The spec is the `spec_file` that `bmad-loop-resolve` edits: `findSpec`, `stories/<key>-*.md`. The SPEC Assumption's "the paused story's SPEC.md" is read as that file, because bmad-loop-resolve edits the epic SPEC.md only for sentinels.
   - Inside the spec's `<intent-contract>` block (else `<frozen-after-approval>`), just before its closing tag, it inserts `**Ruling (owner, <issue key> comment <id>, <date>):** <the reply verbatim>`.
   - It never changes `status:` (bmad-loop-resolve L169-171). An absent block or spec is a refusal by name.
   - The session judges whether the reply carries a ruling; the write is deterministic.
7. **The shipped job.** `plugins/tk-studio/jobs/validate-resolution.json`: `{id: "validate-resolution", target: {skill: "tk-studio-track", payload: {verb: "validate"}}, trigger: "one-shot", guards: {max_turns: 60, max_wall_clock_seconds: 1800}, stop: {on_status: ["blocked"]}, effort: "high"}`. There is no `model` (the planner leg is passed at enqueue), and it is shipped undeclared, as `atlassian-sync-back` is. The SKILL.md `validate` paragraph is the session procedure: `--check` each payload issue; `owner_resolved: false` → `--fail`; otherwise test the command, path or sign-in the reason names when it can be run on the host, else judge the replies. Pass → `--pass --to "In Progress"` (`To Do` when the run never started), with `--ruling-file` when the reply is a ruling. Fail → `--fail` with a follow-up that says what is still missing. End on the §3 block.

## Risks and open decisions
- **Block If:** the session would need the owner seat, or any Jira write outside `jirabackend` (AD-4).
- **Block If:** the validation must run while the paused run's checkout lock is held, and the narrow exemption (Settled shape 5) is not enough. For example, the run's own close-out or worktree prep would write the paused branch.
- **Block If:** `bmad-loop resolve --no-interactive --resume` refuses a resume unless bmad-loop-resolve's `resolution.json` marker exists. Today `POST /runs/{id}/resume` resumes without it.
- **Block If:** the Files list must grow past the list above, or a new skill folder (a released-roster entry) becomes necessary.
- **The engagement's questions and approvals** (AC2's first clause) have no caller: the engagement loop is EP-32 (a SPEC Non-goal). `track.py block --source engagement` (31.5) fixes the shape. Record a DRIFT line and build no call site. The loop's `escalate` rulings already become issues through 31.5's paused-run pass.
- **The validation run's close-out:** the run commits nothing in its worktree. If the queue's close-out would open a PR or fail on an empty branch, follow the research and evolve jobs (skill-target jobs that commit nothing) and record it.
- Not Block Ifs: the seven settled shapes; the ungraded changelog REST shape (pin it in the fakes); the released-roster red; a missing `node_modules/.bin`.
- **Oversize.** About 20 files across lib and the supervisor, and about 1,000 to 1,300 new lines. That is past the L band, as 31.2 to 31.6 were, and the story is not split here. Halt if the Files list grows past the band.
- **Order.** This story needs 31.5's `inbox.json` and `track-block`, and 31.6's owner transition (its wrong-seat refusal keeps the changelog's accountId the owner's). It is the epic's last story.
