## Intent
A new `plansync.py sync-back` verb pulls the project's Atlassian state into local memory, so that agents never query Atlassian live for context (§6.8 c and e, D9, AD-22). It covers each tracked issue's status (mapped onto the canonical enum, the Jira original kept under `external.jira`), its comments (an append-only log), its attachments as links, and every owner-authored Confluence page, mirrored read-only into `kb/confluence/`. A new shipped cron job, `atlassian-sync-back`, runs the verb every 10 minutes. The drift check gains a `tracking` plane. The second class (comments, attachments, owner pages) is backend-authoritative and append-only. Nothing local is promoted back, and entity fields other than status are untouched (AD-5).

## Acceptance Criteria
- AC1: **Given** a project set up and the shipped job `atlassian-sync-back` (cron, every 10 minutes by default; `durable`) **When** it runs **Then** it pulls each tracked issue's status (mapped onto the canonical enum per AD-6, the Jira original kept under `external.jira`), its comments (append-only into `_bmad-output/tracking/<key>/comments.jsonl`: `{issue, author: owner | agent, body, mentions[], created, source: jira}`), its attachments as links, and every owner-authored Confluence page into `kb/confluence/<slug>.md` with a provenance header (read-only sources: a local edit is overwritten and reported); nothing local is promoted back; the run's record names counts and the newest comment seen
- AC2: **Given** the sync-back **When** it is tested **Then** the lib suite covers the status mapping, the append-only comment log (a comment seen twice is written once), the attachment links, the page mirror and the overwrite report, with a fake REST; `tk-studio-activate`'s drift check gains a `tracking` plane that says when the last sync-back ran and whether the binding is reachable

## Settled shape
- **1. Tracking memory layout (named placeholder rule; SPEC.md bullet "CAP-7 — tracking memory layout").** The Jira key is the folder name.
  - `_bmad-output/tracking/<KEY>/comments.jsonl` holds one object per line: `{issue, id, author, body, mentions[], created, updated, source: "jira"}`. These are the AC's six keys plus the Jira comment `id` and `updated`, which de-duplication needs.
    - A line is appended only when its `(id, updated)` pair is new. A comment seen twice is written once. An edited comment appends a new line with the same `id`, and readers take the last line per `id`.
    - `body` is the v2 body, verbatim.
    - `author` is `owner` when `author.accountId` equals the recorded, non-empty `planning.jira.owner_account_id`, else `agent`. Those are the only two values (SPEC Constraints).
    - `mentions[]` lists each `[~accountid:<id>]` in the body, resolved `owner` / `agent` by the same rule, with any other account id kept raw.
  - `_bmad-output/tracking/<KEY>/attachments.jsonl` holds one object per line: `{issue, id, filename, mime, size, author, created, url, source: "jira"}`. `url` is the API's `content` link, verbatim. A line is appended only for a new `id`. Links only: no download, and never an upload.
  - `_bmad-output/tracking/sync-state.json` holds `{cursor, last_run: {at, status, case, counts, newest_comment}, rate_limit: {…}, pages: {<page_id>: {path, version, content_hash}}}`.
    - `cursor` is the largest issue `updated` seen. It is written only after every page of the tick has been read.
  - Every file the verb writes is named in `written[]`, so commit staging derives from the response (contract 0.1.13).
- **2. The owner-page mirror (named placeholder rule; SPEC.md bullet "CAP-7 — owner-page mirror").** `kb/confluence/<slug>.md` holds every page in `planning.confluence.space_id` whose `authorId` equals the owner's account id, excluding page ids in `.tk-studio/confluence-pages.json`.
  - The header is YAML frontmatter: `source: confluence`, `page_id`, `title`, `space_key`, `author: owner`, `version`, `url`, `synced_at`, `read_only: true`, and `content_hash: sha256:<hex>` over the body below the header. The body is the storage XHTML, verbatim (D9: "pulled back verbatim"), with no conversion.
  - `<slug>` is the lower-cased title with runs of non-alphanumerics replaced by `-`. On a collision the page id is appended (`<slug>-<page_id>`). The path is then kept per page id in `sync-state.json`, so a renamed page keeps its file.
  - A file whose body no longer matches its header hash is overwritten and named in `overwritten[]`. A page whose version and local hash are both unchanged is not rewritten.
  - A page that is gone, or is no longer the owner's, is left on disk and named in `notes[]`.
  - The mirror is not registered in `kb/index.md` and does not pass the promotion gate. AD-22 calls it a binding beside the kb, which settles SPEC Open Question 4 for 31.4. No `knowledge.confluence` key is written: the mirror reads `planning.confluence.space_id` and the fixed `kb/confluence/`. AD-22's named binding is a deferred entry.
- **3. Tracked issues and the cursor (named placeholder rule; SPEC.md bullet "CAP-7 — tracked issues and the cursor").**
  - The search is one paged `GET /rest/api/2/search/jql` per tick with `jql = project = "<planning.jira.project_key>" [AND updated >= -<n>m] ORDER BY updated ASC` and `fields = status,updated,comment,attachment`.
  - `<n>` is the minutes from the cursor to now, rounded up, plus 5. A relative bound is the form JQL reads without a time zone, so `zoneinfo`/tzdata is never needed on the Windows host. The first tick has no bound.
  - Status is applied only to canonical entities that carry `external.jira.key`. Comments and attachments are logged for every issue the search returns, because inbox issues (31.5, 31.7) need not be plan entities.
  - When an issue's `comment.total` exceeds the comments returned, that issue alone pages `GET /issue/{key}/comment`. This is overflow only, never a per-issue fetch.
  - The v2 `search/jql` and `nextPageToken` shapes are ungraded: pin them in the fake. A move to v3 is DRIFT affecting 31-6.
- **4. The `tracking` drift plane (named placeholder rule; SPEC.md bullet "CAP-8 — the tracking plane").** `{plane: "tracking", status, case, detail, last_run?, fix?}` reads `.tk-studio/config.yaml` and `_bmad-output/tracking/sync-state.json` only, with no network call (contract §6 "read-only", manifest `external_calls: false`). "Whether the binding is reachable" is the last tick's observed outcome. The `case` values:
  - `not-bound`: no `planning.jira` binding. Status `ok`; tracking is not set up.
  - `never-run`: bound, but no state file. Status `missing`; the fix is `plansync.py sync-back --directory <root>` and declaring the job.
  - `ok`: the last run is `complete` or `partial`, and is newer than 30 minutes (three ticks). Status `ok`.
  - `stale`: the last run is older than 30 minutes. Status `drift`.
  - `token-missing`: the last run named an absent variable. Status `drift`; the fix names it.
  - `unreachable`: the last run hit a connection error or 5xx on preflight. Status `drift`.
  - `deactivated`: the gateway answered preflight with 404 or 410. This classification is ungraded; pin it in the fake. Status `drift`; the fix is the owner's sign-in (kb §1 step 10).
  - `auth`: the last run hit the 401/403 split. Status `drift`; the fix is the split's own text.
- **5. The shipped job (optional entry; SPEC.md bullet "CAP-7 — the shipped job").** `plugins/tk-studio/jobs/atlassian-sync-back.json` contains:
  - `"target": {"core": ["lib/plansync.py", "sync-back", "--directory", "{project_root}"], "payload": {}}`
  - `"trigger": "cron"`, `"cadence": {"mode": "fixed", "schedule": "*/10 * * * *"}`, `"durable": true`
  - `"guards": {"max_wall_clock_seconds": 300}`, `"stop": {"on_status": ["blocked"]}`, `"effort": "low"`
  
  It ships undeclared, as `evolve-proposals` does: the project instance in `.tk-studio/config.yaml` `jobs` declares it and may override the schedule.
  - A core target, not a skill target, because a skill target is a model session every 10 minutes.
  - `execute_core` replaces the exact argument `{project_root}` in `target.core[1:]` with the submitting project's root. It takes the root from `submit` and `wake`. No other templating; a definition without the token runs exactly as today.
  - `_summarize_result` also lifts `status`, `counts` and `newest_comment`, so the run's `summary.json` (its record) names them.
  - `job.schema.json` describes the token, and the contract's §4 notes it, both additive.

## Risks and open decisions
- **Block If:** the AC can be met only by promoting a comment, attachment or page to Atlassian, by changing an entity field other than `status` (D9, AD-5), or by a write that bypasses the planning adapter (AD-4).
- **Block If:** the `tracking` plane needs a live call. That would break contract §6 "read-only" and the manifest's `external_calls: false`, which is an operator ruling.
- **Block If:** the `{project_root}` argument cannot be added without changing an existing job's behaviour or a required field of `job.schema.json`.
- **Block If:** the Files list must grow past the twenty above.
- Not Block Ifs:
  - The five settled shapes.
  - The ungraded request shapes: `search/jql`, `nextPageToken`, the comment overflow, `spaces/{id}/pages` with `authorId`, and the 404/410 deactivated reading. Pin them in the fakes.
  - The live tick (unverifiable here).
- **Refusals and partial runs.**
  - Absent Jira variables or no `planning.jira` binding: `blocked`, named, with no call.
  - Absent `TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN`: the Jira half runs, the mirror is skipped, and the run is `partial` with case `token-missing`.
  - No recorded `owner_account_id`: comments, attachments and the mirror are skipped by name, because an append-only log must never misattribute an author. Status still applies, and the run is `partial`.
  - A 429 after the retries, or an error between pages: the cursor is unchanged and the run is `partial`, naming `RateLimit-Reason`.
- **Working tree.** Each tick writes under `_bmad-output/tracking/`, `kb/confluence/` and the entity files. The verb names them in `written[]` and commits nothing. No shipped job commits today. Whether the instance's checkout commits them is the operator's call when the job is declared; it is not built here.
- `plan/index.md` and the projection follow at the next `sync`. Sync-back writes entity files only, and never runs promote.
- **Oversize.** About 1,300 to 1,600 new lines over 20 files: `syncback.py` about 400, the client changes about 150, the drift plane about 80, the job seam about 30, and the tests. It sits past the L band's spirit, as 31.2 and 31.3 did, and is not split here. The `invoke_dev_with` asks the session to halt `blocked` if Files grows. If review cycles run out, the residue is deferred, not widened.
- **Order.** Sync-back needs 31.2's binding (`planning.jira.project_key`, `owner_account_id`, `planning.confluence.space_id`) and 31.3's page index (optional; when it is absent, no page is excluded by id).
