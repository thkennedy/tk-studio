## Intent
This story has two halves, hole 59 and the 2026-10-26 tick.

1. **Engine end.** The engine-end sweep ends a resumed or relaunched run from its engine's own terminal status (`engineEndState`). Every status but `finished` maps to `partial`, so a graceful `stopped` after the story landed ends `partial` today. A first engine's graceful stop ends `complete`, because its end is the launch's recorded `end`. The sweep will read the engine journal: a `stopped` engine whose last story entry is a `story-done` ends `complete` with `reason: null`, exactly as a first engine does.
2. **The pacer.** Its passes are invisible, and a 30-minute tick was only seen afterwards. Each pacer step (tick, drain) will log its duration and exit code to 33.1's file, and the last ones will be served on `GET /status` as `pacer` and shown on the status page. A step over 10 minutes logs a warning naming the run it drove.

## Acceptance Criteria
- AC1: **Given** a run whose engine was resumed (`POST /runs/{id}/resume`) or relaunched by the paused-run pass and then ends `stopped` after a `story-done` for the story it was driving **When** the engine-end sweep runs **Then** the run ends `complete` exactly as a first engine's graceful stop does (`reason: null`, the PR not a draft), and `partial` is reserved for an engine that stopped before its story landed; `bun test` covers both paths on resumed and relaunched engines
- AC2: **Given** the pacer (`start.ps1`: tick, drain, sleep) **When** each pass runs **Then** its duration and exit code are logged (33.1's file) and the last ones are served in `GET /status` as `pacer {last_tick_ms, last_drain_ms, last_pass_at}` (contract 0.1.28, additive), a pass longer than 10 minutes is logged as a warning naming the pass and the run it was driving, and the status page shows the pacer line; the runbook's supervisor table gains the pacer's shape

## Settled shape
These rulings govern. No SPEC.md bullet is appended: SPEC.md is outside the gate's write surface, as 33-5's and 33-6's plans recorded.

1. **The graceful-stop rule** (`worktree.ts`):
   - Add an exported `storyLandedBeforeStop(journalDir): boolean`. It reads `<dir>/journal.jsonl`, skipping unparsable lines. A missing or unreadable file answers false.
   - The segment is the entries after the latest `run-start` or `run-resume` (the whole file when there is none).
   - It answers true when the segment's latest entry of kind `story-start` or `story-done` is a `story-done` with a non-empty `story_key`.
   - `engineEndState(status, storyDone = false)`: `finished` → `complete`; `stopped` with `storyDone` → `complete`; anything else → `partial`.
   - In `sweepEngines`, for a resumed or relaunched run only: when `st.detail.status === "stopped"`, compute `storyDone` from `join(servedRoot(run), ".bmad-loop", "runs", run.engine_run_id)` **before** `closeOut`. The end is `complete` with `reason: null`; otherwise it keeps today's state and reason (`resumed|relaunched engine ended 'stopped'`).
   - Unchanged: `interrupted`/`crashed` stay `partial`; a red host verify still overrides to `partial`; a killed relaunch keeps `launched.end`; a first engine is untouched.
   - The `ended` event's detail shape is unchanged.
2. **A pacer pass** (the tee, `log.ts`):
   - The argument grammar becomes `--tag <tick|drain> [--pass] -- <script> [args…]`. `--pass` is accepted only with `tick` or `drain`; any other use is the usage error, exit 2.
   - `start.ps1` `Invoke-PacerStep` alone passes `--pass`. Recover never does, so it is never counted.
   - Under `--pass` the tee measures the child's wall time with its injected clock, from spawn to `close`. Before its `stopped (…)` line it appends one line under its tag: `pass: <ms> ms, exit <code>`, where `<code>` is the code it exits with.
3. **The slow-pass warning:**
   - A pass whose `ms > SLOW_PASS_MS` (exported, `600_000`) also appends `warning: pass <tick|drain> took <ms> ms (over 10 min), driving <ids>`.
   - `<ids>` are the distinct queue run ids matched in the child's stdout and stderr lines by `/\bq-[A-Za-z0-9][A-Za-z0-9._-]*-\d{8}T\d{6}Z-[0-9a-f]{6}\b/g`, in first-seen order. At most 5 are named, then `+<n> more`; with none it reads `no run named`.
   - The same text goes once through the notifier (`notifier(env)`; `kind: "none"` sends nothing), clipped to `NOTICE_MAX_BYTES`. It is sent through an injectable `fetch` on the tee's io (default the global), awaited before the tee exits, and a failure is swallowed. This is the SPEC's "one line per pacer warning".
   - The line carries nothing but the step, the duration and run ids.
4. **The last pass, served:**
   - Under `--pass`, after the pass line, the tee writes `<TK_SUPERVISOR_WORK>/supervisor/pacer.json` = `{last_tick_ms, last_drain_ms, last_pass_at}`. It reads the current file (absent or invalid → all `null`), sets its tag's `last_<tag>_ms` and sets `last_pass_at` to the ISO time of the pass end.
   - The write goes to `pacer.json.tmp-<pid>`, then a rename. A failed write is swallowed, and the log line still stands. Nothing is written with `TK_SUPERVISOR_WORK` unset.
   - An exported `readPacer(env)` answers those three fields, each a number, an ISO string or `null`. It answers all `null` when the file is absent, unreadable or invalid, or the work folder is unset.
   - `GET /status` adds `pacer: readPacer(env)` beside `log`, always present (contract 0.1.28, additive). The JSON keys are exactly those three.
5. **The status page:** `PageData` gains `pacer?` (filled by `gatherPage` through `readPacer`). The "Supervisor log" section opens with one line: `pacer: last tick <n> ms · last drain <n> ms · last pass <ISO>`, each missing value shown as `-`, or `pacer: no pass recorded` when all three are `null`.
6. **The runbook row** (§4 table), item `Pacer`: (33.7) `start.ps1` runs tick, drain, then sleeps `-IntervalSeconds` (default 60). Each step runs under the log tee with `--pass` and logs `pass: <ms> ms, exit <code>`. A step over 10 min logs `warning: pass <step> took … driving <run ids>` and sends one notifier line. The last pass is in `<TK_SUPERVISOR_WORK>\supervisor\pacer.json` and on `GET /status` as `pacer {last_tick_ms, last_drain_ms, last_pass_at}`, and the status page shows its line.

## Risks and open decisions
- Band L, with these reasons:
  - 12 files across two independent halves.
  - About 120-180 lines of source and 250-350 lines of tests.
  - The docs carry one paragraph or row each.
  - It is within an L story's reach (33-6 landed at about 1000 lines), so it is not oversize. Halt if the Files list grows.
- The `story-done` reading is the engine journal's shape, which is upstream (bmad-loop). It is read only and never forked. A resumed engine that journals the re-armed story's landing under another kind is not recognised; its run ends `partial` as today, the safe failure.
- The run ids in the warning come from the step's own output, not the queue. A step that prints no run id is warned as `no run named`.
- Block If the engine's graceful stop reports a terminal status other than `stopped` (for example `finished`, which already ends `complete`). In that case hole 59 has another cause: record the observed status and halt rather than widening the rule.
- Block If the pacer data needs a queue table or a `service_events` kind (`queue.ts`), or a change to `tick.ts` or `cli.ts`. Both are outside Files.
- Block If `GET /status`'s JSON must change anything but adding `pacer`, because the JSON answer is pinned byte for byte for non-HTML clients.
