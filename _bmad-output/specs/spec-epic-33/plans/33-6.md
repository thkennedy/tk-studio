## Intent
A dev session renders its skill with `_bmad/scripts/render_skill.py` into `_bmad/render/<skill>/<slug>-<root hash>/<generation>/`. Inside the sandbox a freshly rendered snapshot can look half-written across the sbx mount, with ENOENT on files the manifest lists, while the host sees it complete (hole 65). The session then HALTs by design, writes a `blocked` spec, and bmad-loop pauses the run on a CRITICAL escalation. Today an operator removes the snapshot and resumes. This story teaches the supervisor's paused-run pass to recognise that one halt and to do the same thing once per story. It deletes the snapshot folder and the untracked `blocked` draft, resumes through `resumePaused`, records `auto-resume` and sends one notifier line. A second such pause on the same story is left for the operator. No upstream skill is forked.

## Acceptance Criteria
- AC1: **Given** a run paused on a CRITICAL escalation whose reason says the skill render failed and names the snapshot folder under `_bmad/render/` **When** the paused-run pass runs and the host sees that folder complete (every file the manifest names is present and non-empty) **Then** the pass removes the snapshot folder and the dev session's untracked `blocked` spec draft, resumes the run once (`POST /runs/{id}/resume`'s path), records `auto-resume {reason: stale-render-view, snapshot, attempt: 1}` and notifies one line; a second such pause on the same story is left for the operator with the reason naming the first attempt; the upstream skills are untouched (no fork)
- AC2: **Given** the pass **When** it is tested **Then** `bun test` covers the recognition (the reason text, the folder check), the single-attempt rule and the untouched other pauses with fixtures; the runbook's hole-65 row names the behaviour

## Settled shape
These rulings govern. No SPEC.md bullet is appended: SPEC.md is outside the gate's write surface, as 33-5's plan recorded.

1. **Recognition** (`staleRenderView(run, events)`, reads only). All of these must hold:
   - The latest `paused` event's `paused_stage` is `escalation`.
   - Its `paused_reason` contains `CRITICAL escalation from dev session`.
   - The reason contains one of the four renderer messages above, or `render_skill.py`.
   - The reason names exactly one distinct snapshot folder, matched as `_bmad/render/<skill>/<slug>/<generation>`. Each segment is `[A-Za-z0-9._-]+`, never `.` or `..`, and any separator is accepted. A path that runs on to a file (`…/<generation>/step-01.md`) is cut to the folder.
   - The folder resolves under `<servedRoot>/_bmad/render/` (`isWithin`, after `resolve`). The prefix before `_bmad/render/` is ignored, because the reason may carry the sandbox's path.
   - The paused story's spec (`findSpec` at the served root) has frontmatter `status: blocked` and is untracked: `git -C <servedRoot> ls-files --error-unmatch -- <relative spec>` exits non-zero (argv only).
   - Anything else is not this halt, and the pass behaves exactly as today.
   - This answers SPEC Open Question 3: the draft is the spec at the served root (the host side of the same mount), so no sandbox-side file is touched.
2. **The folder check** (`snapshotComplete(dir)`):
   - `manifest.json` parses to an object whose `outputs` is a non-empty object.
   - Every key of `outputs` is a relative path inside `dir` that is a regular file with size above 0.
   - Hashes are not compared; the AC asks only for present and non-empty. An incomplete folder on the host is not a stale view, so it is left for the operator as today.
3. **The single-attempt rule.** An attempt is an `auto-resume` event on the run whose `story_key` is this story and whose `attempt` is 1, under any engine run id and at any time.
   - **None:** the pass takes the lease, then:
     - removes the snapshot folder (`rmSync` recursive) and the draft spec;
     - calls `deps.resume`;
     - records `auto-resume {reason: "stale-render-view", snapshot, story_key, engine_run_id, attempt: 1, resumed, notify}` plus `error` when the resume refused;
     - sends one line.
     - `snapshot` is the folder relative to the served root, with `/` separators.
     - A removal that fails records nothing and resumes nothing; the next pass tries again.
     - A refused resume still counts as the attempt (`resumed: false`, `error` `"<code>: <detail>"`), and the run stays paused.
   - **One already:** the pass records once per pause (since the latest `paused`) `auto-resume {reason: "stale-render-view", snapshot, story_key, engine_run_id, attempt: 2, resumed: false, first_at: <the attempt-1 event's time>, notify}` and sends one line. It removes and resumes nothing. Then the existing 31.5 block logic runs unchanged for that pause.
   - Never a third event per pause, and never a second resume per story.
4. **The lines** (one each, flattened and clipped to `NOTICE_MAX_BYTES` as `claimRefusedLine` does; nothing but the run id, story key, snapshot path and time):
   - attempt 1, resumed: `supervisor: run <run_id> auto-resumed: story <key> halted on a stale render view of <snapshot> (attempt 1)`
   - attempt 1, refused: `supervisor: run <run_id> stays paused: auto-resume of story <key> after a stale render view of <snapshot> refused: <error>`
   - attempt 2: `supervisor: run <run_id> stays paused for the operator: story <key> halted on a stale render view of <snapshot> again after the auto-resume at <first_at>`
   - With no notifier, the event's `notify` is the same `{ok: false, skipped: "no notifier configured (TK_SUPERVISOR_NOTIFY is unset)"}` that `awaitRuling` records.
5. **The pass's return** stays `{closed, awaiting}`. An auto-resumed run is in neither list.

## Risks and open decisions
- Band L: 5 files, about 150-250 lines in `closeout.ts` plus about 300 lines of tests. The contract, README and runbook obligations push it past M. That is not oversize.
- The reason is the dev session's own prose. The recognition keys on the renderer's fixed messages and the folder path, never on wording the session chooses. A session that paraphrases the renderer's message without quoting it is not recognised, and its pause is left for the operator. That is the safe failure.
- Deleting files on the host is the only destructive step. It is bounded to one folder under `<servedRoot>/_bmad/render/` (gitignored) and one untracked spec, and only after the full recognition and the folder check pass.
- Block If bmad-loop's resume refuses a re-armed escalation whose spec was removed (the reading above says `rearm_escalation` tolerates it). Record the refusal text and halt rather than keeping the draft or editing its status.
- Block If the recognition needs a field that the `paused` event does not carry (for example the reason clipped before the path). Record what the event holds and halt; do not widen the engine status read in `worktree.ts`.
- Block If the Files list must grow, for example a `queue.ts` change for the event or an office/page change.
