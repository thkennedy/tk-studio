## Intent
A sandbox started outside the supervisor comes up without the Max login: a session's `sbx exec` on a stopped sandbox does this (hole 68). The pin's `sbx run -d --name` leaves a running sandbox as it is, so every claim is refused until an operator stops it. This story makes the pin notice that case. When the sandbox was already running and its login probe says not logged in, the pin stops and starts it once, probes again, records both probes, and only then lets the preflight judge. The readiness check warns about a running engine sandbox for which the supervisor recorded no pin.

## Acceptance Criteria
- AC1: **Given** a run on the sbx tier whose sandbox is already running when the pin runs **When** the pin's login probe (`sbx exec <sb> env -u ANTHROPIC_API_KEY claude auth status --json`) answers not logged in **Then** the pin stops and starts the sandbox once (`sbx stop`, `sbx run -d --name`), probes again, and only then runs the preflight; both attempts are recorded on the run (`pin-restart {probe_before, probe_after}`); a sandbox still logged out after the restart refuses the claim through 33.2's event naming the renewal; a sandbox the supervisor itself pinned in this pass is never restarted twice
- AC2: **Given** `tk-studio-launch check` (the readiness check) and the runbook **When** the engine sandbox is running with no supervisor pin recorded for it **Then** the check names it as a warning ("started outside the supervisor; the next pin restarts it"), and the runbook's hole-68 row stays the rule for sessions; `bun test` covers the restart, the single-restart rule and the warning with a fake `sbx`

## Settled shape
1. **The `pin-restart` event.** Its detail is `{sandbox, probe_before, probe_after, pass_at}`. Each probe is the `judgeAuthStatus` answer: `null` when the claude.ai login is present, else its gap text (`harness auth: Max login missing or expired (…)`). Never stdout, never a token. There is one per sandbox per refusal episode of the run (since its latest `claim-refusal-cleared`). A further restart in the same episode, which the guards normally prevent, patches that event in place (`probe_before`, `probe_after`, `pass_at`). This follows the in-place rule of `pin-failed` and `claim-refused`. Appended to SPEC.md.
2. **The restart guards** (the AC's "once" and "never restarted twice"; not a Block If). Restart only when all of these hold:
   - (a) the sandbox was running before this pin, per `sbx ls`;
   - (b) the probe answered not logged in;
   - (c) this pass has not restarted this sandbox yet (the per-pass set);
   - (d) this run's open episode has no `pin-restart` for this sandbox;
   - (e) no other run holds the sandbox `running`/`paused`/`external`, and no ended run's engine there is alive.

   When (c), (d) or (e) fails, there is no restart and no `pin-restart` event. The preflight refuses as 33-2 does, and `loginResolves` names the renewal. Guard (e) exists so that a live engine is never stopped (the SPEC's process rules; `releasePin`'s holder rule).
3. **The supervisor pin record.** The path is `<TK_STUDIO_HOME or ~/.tk-studio>/sandboxes/<sandbox>.pin` (a safe file name), holding the JSON `{sandbox, since, run_id, supervisor_pid}`. It is written on every `pinned` and removed when `pin-released` stopped the sandbox. The launch check reads its presence; it is advisory, like the starter lock. This follows the pattern of `plugins/tk-studio/contracts/driver-contract.md` §4 "Starter lock (0.1.23, Story 28.6)". It is recorded under contract 0.1.28 (Story 33.3, additive) and appended to SPEC.md.
4. **"`bun test` covers … the warning".** The warning is computed by the Python readiness check, so the lib suite (`test_launch.py`) covers the warning text and its cases with a fake sbx runner. `bun test` covers the pin record it reads: written on a pin, written after a restart, removed on release. Write the same reading into the spec's intent contract; it is not a deviation.
