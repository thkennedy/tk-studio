## Intent
Hole 52: a red host leg can be re-run today only by the hand recipe (cut a worktree, run `verify.host`, flip the PR). This story gives the supervisor one motion for it. `POST /runs/{id}/verify` (bearer only) and the cli verb `verify <run id>` cut a fresh worktree from the ended run's pushed branch tip and run the project's `verify.host` there exactly as the close-out does (`hostVerify`). The motion records a new `host-verify` event, removes the worktree and, on green, marks a draft PR ready. The run's terminal state never changes (SPEC Constraints: CAP-15 changes `host_verify` only).

## Acceptance Criteria
- AC1: **Given** an ended run with a pushed branch and a PR (`partial` with `host_verify: red`, or any ended run) **When** `POST /runs/{id}/verify` arrives (the bearer only) or the cli verb `verify <run id>` runs **Then** the supervisor cuts a fresh worktree from the branch's tip, runs the project's `verify.host` there exactly as the close-out does, records a new `host-verify` event with the result, removes the worktree, and on green marks a draft PR ready and ends the run's `host_verify` state `green` (the run's terminal state is unchanged; the plan pull-back sees the PR as before); a live run, an external run or a run with no branch is a 409 by name; a leg already running for the run is 409 `VerifyRunning`; contract 0.1.28 names the route
- AC2: **Given** the verb **When** it is tested **Then** `bun test` covers the worktree, the recorded event, the draft-to-ready flip and every refusal with fakes; the README's route table and the runbook's "when a host leg is red" steps name it

## Settled shape
These rulings govern. No SPEC.md bullet is appended, because SPEC.md is outside the gate's write surface (as 33-5's to 33-7's plans recorded).

1. **The module.** Add `apps/supervisor/src/hostleg.ts` (new). It imports from `worktree.ts`, `hostverify.ts` and `queue.ts`; none of them import it, so there is no cycle.
   - It exports `VerifyRefusal = "RunNotFound" | "ExternalRun" | "RunNotEnded" | "NoBranch" | "VerifyRunning" | "SchemaError" | "VerifyFailed"` and `class VerifyRefused extends Error {code}` (the `ResumeRefused` shape).
   - It exports `rerunHostLeg(queue, runId, opts: {by: "api" | "cli"}, deps: HostLegDeps): Promise<HostLegStarted>` and `HostLegDeps extends WorktreeDeps` (`self?: Owner`, `now?`).
2. **The refusals,** checked in this order before anything runs:
   - `RunNotFound`: no such run (404).
   - `ExternalRun`: the run is `external` (409).
   - `RunNotEnded`: the run is `queued`, `running` or `paused` (409; the "live run").
   - `NoBranch` (409) covers three cases. The run has no recorded `worktree`. `git ls-remote --heads origin refs/heads/supervisor/run-<id>` in `run.root` answers no line (a "no changes" end, or a branch never pushed). Or that call fails, with the detail naming it.
   - `VerifyRunning`: the lease is held by a live owner (409).
   - `VerifyFailed`: the work folder is unset, or the cut or materialise fails (500). A `VerifyFailed` after the lease releases it.
   - The tip SHA is the `ls-remote` answer's first field.
3. **The lease** (`queue.ts`, mirroring `takeEndedCloseOut`):
   - `takeVerifyLeg(runId, self): boolean`. In an immediate transaction it re-reads the run. It answers false unless the run is terminal. It answers false when the latest `host-verify-leg` event has a non-null `owner`, no `host-verify` and no `host-verify-leg` follow it, and `ownerLive(owner, self)`. Otherwise it appends `host-verify-leg {owner: ownerDetail(self), by}` and answers true.
   - `releaseVerifyLeg(runId, self)` appends `host-verify-leg {owner: null, released: ownerDetail(self)}`, only while the latest lease is `self`'s and no `host-verify` follows it.
   - The `host-verify` event the leg records closes the lease. A dead owner's lease is taken over.
   - The refusal is `VerifyRunning` when `takeVerifyLeg` answers false on a terminal run.
4. **The leg,** run by one async `runLeg`:
   - The path is `<run.worktree>.verify`: a sibling of the run's recorded worktree, so under `<TK_SUPERVISOR_WORK>/worktrees/<project>/`. A leftover at that path (a crashed earlier leg) is removed first: `git worktree remove --force` in `run.root`, then `rmSync` and `git worktree prune`.
   - Fetch with `git fetch origin +refs/heads/<branch>:refs/remotes/origin/<branch>`, then cut with `git worktree add --relative-paths --detach <path> <tip sha>`. The cut is detached, because the local run branch may still exist.
   - Then `materialise(run.root, servedRoot({worktree: path, prefix: run.prefix}), deps)`, as `prepareWorktree` does. The close-out's leg runs in a materialised worktree.
   - Then `hostVerify({...run, worktree: path}, guardS, deps)`, with the sweep's guard (Code Map).
   - Then the worktree is removed (`git worktree remove --force <path>`, else `rmSync`; best effort).
   - Then the PR. It is the latest canonical `detail.pr` on the run's `ended`, `closed_out` or `paused` events (`priorPr` covers the last two; check `ended` first), else `openPrUrl` of `gh pr list --head <branch> --state open --json url`.
   - On green with a PR, `gh pr view <pr> --json state,isDraft`. When the PR is `OPEN` and a draft, run `gh pr ready <pr>` (`pr_ready: "marked"`). Open and not a draft: `"already"`. Not open: `"not open"`. A failure: `"error: <clipped>"`. No PR: `pr: null`, nothing flipped.
   - Red or skipped: the PR is never touched (no `--undo`, no body edit).
   - The PR body is not regenerated. Its `## Host verify` section keeps the original result (see Risks).
   - Last, one `queue.note(runId, "host-verify", {...result, rerun: {by, head: <tip sha>, worktree: "removed" | "kept: <why>", pr: <url|null>, pr_ready?}})`. That is the AC's new event; it closes the lease.
   - The run's state, the `ended` event and `endEngine` are never touched.
   - A throw inside the leg records `host-verify {skipped: true, reason: "re-run failed: <clipped>", rerun: {...}}`, so the lease always closes. A cut or materialise failure releases the lease (`releaseVerifyLeg`), records no `host-verify`, and is `VerifyFailed`.
5. **The route.** `POST /runs/{id}/verify` is bearer only (never added to `cookieRoute`). The body is empty or `{}`; anything else is `400 SchemaError`, and unparsable JSON is `400 MalformedJson` (the resume route's handling).
   - `ApiDeps.verify?: (runId) => Promise<HostLegStarted>`, defaulting to `rerunHostLeg(queue, id, {by: "api"})`.
   - The refusals and the lease are synchronous with the request. Once the lease is taken, the leg runs in the background (`void`), as the resume's child does, because a leg can take the job's whole guard.
   - The answer is `202 {ok: true, run_id, state: <the unchanged terminal state>, verify: "started", head: <tip sha>}`. The result is the `host-verify` event on `GET /runs/{id}` and `/events`, and the board's `host_verify`.
   - Refusals map RunNotFound to 404, SchemaError to 400, VerifyFailed to 500, and everything else to 409, with `{ok: false, error: <code>, run_id, detail}` redacted.
   - `rerunHostLeg` therefore answers a started handle `{run_id, state, head, done: Promise<HostLegResult>}`, and the route does not await `done`.
6. **The verb.** `bun src/cli.ts verify <run id>`: exactly one argument, else the usage line and exit 2. It opens the queue, calls `rerunHostLeg(…, {by: "cli"})`, awaits `done` in the foreground, and prints one JSON object: `{ok: true, run_id, state, head, green, skipped?, reason?, pr, pr_ready?, worktree}`. The exit code is 0 green, 1 red or skipped, and 2 a refusal (`{ok: false, error: <code>, detail}`). `USAGE` gains `bun src/cli.ts verify <run id>`.
7. **The docs:**
   - README: a `POST /runs/{id}/verify` row after resume's, with the body, the 202, the refusals and the event. Also the cli verb wherever the README lists `recover`/`drain`.
   - Contract: a `**0.1.28 (Story 33.8, additive).**` paragraph after 33.7's, naming the route, the verb, the refusals, `host-verify` `rerun` and the `host-verify-leg` lease event. Also a header-list entry on :5. No version bump, and no surface-table row.
   - Runbook: a **When a host leg is red** paragraph after step 5 of the epic list (before **When a supervisor run pauses**). It reads: read the draft PR's `## Host verify`, fix it (a roster row, an environment fault) on the branch or the box, then `POST /runs/<id>/verify` or `bun src/cli.ts verify <id>` from `apps/supervisor`, and read the `host-verify` event. It replaces the hand recipe. The events table also gains a `host-verify-leg` row, and the `host-verify` row notes `rerun` (33.8).

## Risks and open decisions
- **Band L:**
  - 10 files: 2 new sources and tests, 4 modified sources and tests, 3 docs.
  - About 220-300 lines of source and 300-400 of tests.
  - One new module, two queue methods, one route and one verb.
  - Within an L story's reach, so not oversize. Halt if the Files list grows past it.
- The verb requires the run's recorded `tier` to be `sbx` for the leg to run. A host-tier run's re-run records `skipped: host-tier run …`, exactly as its close-out did; that is "exactly as the close-out does", not a gap.
- The config is read at the run's `base_ref` in the checkout (`verifyCommand`), as the close-out does. A fix to `verify.host` itself only counts once it is on that ref in the checkout. The runbook's steps say so.
- The PR body keeps its original `## Host verify` section. The re-run's result lives on the `host-verify` event and the board. Regenerating the body needs the launch's status block and the metered cost; that is out of scope, and a later story may add it.
- The route answers 202 and runs the leg in the serve process. If `serve` dies mid-leg, the lease's owner is dead (re-takeable), and the `.verify` folder is cleared by the next re-run.
- **Block If:**
  - The re-run must change the run's terminal state, its `ended` event, or `closeOut`/`sweepEngines` in `worktree.ts` (`worktree.ts` is read only here).
  - The derived `host_verify` (board, inbox, office) does not turn green from a later green `host-verify`, so a reader must change.
  - The route must be reachable by a cookie session.
  - A production file outside Files must change.
