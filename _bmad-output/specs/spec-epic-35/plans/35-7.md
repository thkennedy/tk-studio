## Intent

The deferred-work sweep runs only inside a bmad-loop sweep session, and no studio job starts one, so DW-46 to DW-65 and the retro's deferred findings (DW-85 to DW-87) have no path to a PR. Story 35.7 ships a `run-sweep` job type in `run-epic.json`'s shape. Its launch verb starts `bmad-loop sweep` detached in the supervisor run's own worktree, so every bundle commit lands on `supervisor/run-<id>` and never on main. The supervisor records the triage, runs the host leg once, and opens one close-out PR that lists the bundles, the blocked entries and the human decisions. When that PR merges, the merge pass flips the entries to `resolved … by #N`. Repo: tk-studio (`apps/supervisor`; `plugins/tk-studio` jobs, lib, skills and contracts).

## Acceptance Criteria

AC1. **Given** `plugins/tk-studio/jobs/run-sweep.json` (one-shot, guards, `stop.on_status`, effort, in `run-epic.json`'s shape) and a project instance naming it **When** `POST /jobs {project, job}` queues it **Then** the supervisor pins the sandbox and starts the engine's sweep session detached (the triage pass: `bmad-loop-sweep` reads `deferred-work.md` and returns the partition; `max_bundles` and the attempt caps from `.bmad-loop/policy.toml`), records the triage result in the run workspace and a `sweep-triage` event (the taxonomy extended additively), and the launch's status block names the bundles, the blocked entries and the human decisions

AC2. **Given** a validated triage **When** the bundles execute **Then** each bundle is one engine dev pass in the run's worktree followed by the host leg and the close-out's PR (one PR per bundle, or one per sweep with the bundles listed: the planner decides and the contract names it), the `blocked` and `human decision` entries are listed in the PR body and the inbox line, a merged PR flips its entries to `resolved … by #N` through the plan pull-back, and the sweep ends `complete | partial | blocked` with the status block and a `job-run` ledger line

AC3. **Given** tk-studio **When** the operator queues `run-sweep` once on the sandbox tier at the engine's request through the consult log **Then** one real sweep runs over the open ledger (its first targets: DW-46 to DW-65 and the consolidation entries DW-85 to DW-87; `max_bundles` bounds it), its PRs are merged on green by the operator, the ledger reads the closures; conformance drives the surface with a fake engine; the contract (0.1.30, additive) names the job type; the cost lands in the ledger

## Settled shape

These are the planner's rulings. They are binding, and the dev session does not reopen them. Each is recorded under SPEC.md's `## Design notes` (CAP-15, CAP-16).

1. **The job and the launch verb.**
   - `jobs/run-sweep.json` matches `run-epic.json` key for key. `target.skill: "tk-studio-launch"`, payload `{verb: "sweep"}` (an instance may add `max_bundles: <int ≥ 1>`), `trigger: one-shot`, `requires: {tier: "sbx"}`, guards `{max_turns: 80, max_wall_clock_seconds: 3600}`, `stop.on_status: ["blocked"]`, `effort: "high"`.
   - `launch.py sweep [--run-id <rid>] [--max-bundles <n>] [--triage-wait <s>]` does this:
     - It refuses before spawning:
       - the project has no `.bmad-loop/policy.toml` or no `deferred-work.md`, or the tree is dirty (`git status --porcelain`, the paths named): a `blocked` status block naming the gap, nothing spawned;
       - an existing run dir: refused as `start` does.
     - Then it spawns `bmad-loop sweep --project <root> --no-prompt --run-id <rid> [--max-bundles <n>]` detached (`spawn_detached`). It polls for `state.json` as `start` does.
     - Then it waits up to `--triage-wait` (default 1500 s, inside the job's 3600 s guard) for `<run dir>/triage.json`, or for the run to end or pause.
   - The status block keeps `intent: tk-studio-launch` and `artifacts: [".bmad-loop/runs/<rid>"]` (plus `.bmad-loop/runs/<rid>/triage.json` when read). The result carries `triage: {bundles: [{name, dw_ids}], blocked: [{id, blocker}], decisions: [{id, question}], already_resolved: [id], skip: [id]}` when read.
   - The `reason` is one line, `bundles: <name> (DW-a, DW-b); …; blocked: DW-x, …; decisions: DW-y, …`, with `none` for an empty list.
   - Status:
     - `complete` on a read triage, or when the wait elapses with the engine still running; the reason is then `triage still running`, and the supervisor's watch records the triage later.
     - `blocked` when the engine ended or paused before any `triage.json` (the triage escalated after `max_triage_attempts`).

2. **The `sweep-triage` event: two records, one per store.**
   - **(a) The ledger event.** `taxonomy.v1.json` gains `sweep-triage`. Its emitter is `lib/launch.py sweep` alone (AD-12), through `ledger.emit`, once per triage read. The payload is `{run_id (the engine run id), bundles: number, dw_ids: [string], blocked: [string], decisions: [string], already_resolved: [string], skip: [string]}`.
   - **(b) The queue event.** The supervisor's watch (`sweepEngines`), on a `run-sweep` run, the first time `<worktree>/.bmad-loop/runs/<engine id>/triage.json` exists:
     - It copies the file to the run workspace as `<studioHome>/projects/<key>/runs/<studio_run_id>/sweep/triage.json` (atomic).
     - It notes one `sweep-triage {engine_run_id, path, bundles: [{name, dw_ids}], blocked: [{id, blocker}], decisions: [{id, question}], already_resolved: [id], skip: [id]}`. It is idempotent: once per engine run, never re-noted.
     - An unparseable file is noted once, as `sweep-triage {engine_run_id, error: "<clipped>"}`.

3. **One PR per sweep, with the bundles listed.** This is the planner's choice, and the 35.7 contract paragraph names it.
   - Why: bmad-loop commits every bundle in place on the checked-out branch, which is the run's `supervisor/run-<id>`. One supervisor run is one branch and one PR (`priorPr`, adoption). One PR per bundle would need the engine's worktree isolation with its local merge suppressed, which bmad-loop 0.9.1 does not support.
   - So each bundle is one engine dev pass, in the run's worktree, committed on the run branch. The host leg runs **once**, at the engine's end, over all the bundles. Then the close-out opens one PR.
   - `prBody` for a sweep run gains a `## Sweep` section, before `## Host verify`, with three parts:
     - one line per bundle, `- <name> (DW-a, DW-b): landed | not landed — <why>`. A bundle has landed when the journal holds its bundle ledger-close kind (`sweep.py:1290`, the `kind` passed to it) for `dw-<name>`, else from the bundle's `tasks/dw-<name>/result.json`.
     - `### Blocked`: `- DW-x: <blocker>`, or `none`.
     - `### Human decisions`: `- DW-y: <question>`, or `none`, with a note that they were skipped unattended and that `bmad-loop decisions` answers them.
   - `noticeText`, for a sweep run, adds one line: `sweep: <landed>/<n> bundles; blocked: DW-x, …; decisions: DW-y, …`.

4. **The end state.**
   - `complete`: every triaged bundle landed (or there were zero bundles), and the host leg is green or skipped.
   - `partial`: at least one bundle landed and another did not, or the host leg is red or inconclusive.
   - `blocked`: no `triage.json` ever (escalated), or bundles > 0 and none landed.
   - An engine `paused` on a sweep run is closed out like an ended one, with the same three-way rule and the paused bundle `not landed — paused at <stage>`. It is never relaunched through `closeOutPaused` (no epic relaunch), and `endEngine` stops the engine as on an end.
   - The supervisor's `job-run` line is the existing `finishStudio` → `jobrun.py finish`, with `--total-cost-usd` from the sweep's `run.json` and the block's reason, so the cost lands in the ledger.

5. **The ledger flip after the merge (the plan pull-back).**
   - New lib verb: `plansync.py ledger-resolve --directory <owner root> --pr <owner/repo#N> --ids DW-a,DW-b [--date <YYYY-MM-DD>]`. It rewrites each named entry's `status:` line from the engine's `done <date>` form to `resolved <date> by <owner/repo>#N (sweep bundle dw-<name>; <the engine's resolution text, clipped>)`.
   - It is idempotent: an entry already `resolved … by #N` is unchanged, and a still-`open` entry (the owner checkout has not pulled the merge) is `pending`. It writes atomically and ends in the JSON status block `{ok, resolved: [...], pending: [...], unchanged: [...]}`.
   - The supervisor's merge pass gains a `ledgerPass` beside `stagePass`, with the same pattern. For each terminal `run-sweep` run whose PR is `MERGED`, under a `plan-lease {phase: "ledger"}`:
     - It calls the verb with the bundles' `dw_ids` that landed, plus the triage's `already_resolved` ids the engine closed.
     - Each attempt is one `ledger-resolve {pr, ids, resolved, pending, ok, settled?}` event.
     - `pending` retries on the next tick, bounded by `PLAN_RETRY_LIMIT`.
   - The supervisor never commits the ledger itself. The rewrite lands at the owner root exactly as the Stage Log rows do (CAP-17's design note).

6. **The conformance drive.**
   - `contracts/conformance/e2e_run_sweep.py` (new) is registered under the `tk-studio-launch` surface (headless-clean, `expect: json`). It runs in process with fakes:
     - `launch.sweep` against a fake substrate that writes `state.json` and a valid `triage.json` (two bundles, one blocked, one decision): the status block names all three;
     - a dirty tree: `blocked`;
     - `plansync.ledger-resolve` on a fixture ledger (`done` → `resolved … by #N`, then the call again is `unchanged`);
     - `lib/job.py` loads `run-sweep`;
     - `bun test test/sweep.test.ts -t "Story 35.7"` from `apps/supervisor`, as `e2e_vertical_slice.py` does.
