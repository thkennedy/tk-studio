# Epic 34: The Vertical-Slice Pack

## Why

A pain to solve. No run has ever imported the game or run its engine tests: the engine runs in a Linux sandbox that has no `godot`, and the host leg runs TUA's `verify.sh` without `TUA_ENGINE_GATE=1`, so "it builds" has stood in for "it plays" since the first run on The Universe Awaits (`C:\GitHub\the-universe-awaits`, Godot 4.7.2 Mono with its GoDotTest suite, served by the supervisor since Story 23.3). This epic ships Phase 3 of the design spec's build order (its EP-33; EP-34 in the plan because Epic 33 took the number): the engine gate on the host leg, a measured playable run, the `playable-verify` leg with a screenshot-only judge, pinned engine knowledge, one engine MCP per run, the asset-manifest ladder (greybox, CC0 mirror, capped generation) and the `run-vertical-slice` job that ends user flow F9 in a playable greybox slice with proof media and a measured cost. Sources in order of authority: the planning-pass brief's Phase 3, the research's §4 (build on others, own the gates; digests 01 and 02), user flow F9 and the feature ledger's Phase 3 row (`_bmad-output/planning-artifacts/design/studio-design-spec-2026-10-09/`), and the 3D tooling note. What exists today: TUA's `scripts/engine-gate.sh` (headless import, then the engine tests) and the `TUA_ENGINE_GATE=1` branch of its `scripts/verify.sh`; the supervisor's host leg (Stories 27.4, 33.4, 33.8), which runs a project's `verify.host` on the Windows host in the run's worktree before the PR, where Godot (`$env:GODOT`, `godot` on PATH) and Blender 5.2 live; the engagement loop (EP-32), for which a game project is only a project whose working set carries the GDS skills. TUA is the reference project throughout; nothing here changes TUA's `main` except through TUA's own run PRs.

## Capabilities

- **CAP-1** (34.1)
  - **intent:** The host leg runs a project's `verify.engine` (one command line, declared beside `verify.host`, additive; TUA's is `bash scripts/engine-gate.sh`) after `verify.host` is green, in the worktree, with the folder of `$env:GODOT` prepended to PATH and the project's own flags left to the project, on the close-out and on 33.8's `verify`.
  - **success:** The `host-verify` event carries `engine: green | red | skipped (no verify.engine)` with the exit code and the log tail; `red` ends the run `partial` with `host_verify: red` exactly as a red `verify.host` does; `bun test` covers the ordering, the PATH composition, the event and both verdicts with a fake engine binary.
- **CAP-2** (34.1)
  - **intent:** The box can prove the engine is reachable, and the gate is on the contract and proved on TUA.

- **CAP-3** (34.2)
  - **intent:** The operator has one proven way to run the game on the agent PC for a bounded number of ticks under a seeded, scripted scenario and get frames and a pass or fail back: `plugins/tk-studio/lib/playable.py run --directory <project> --scenario <file> --seed <n> --ticks <t> --out <dir>` starts the game with a `PlayableHarness` autoload (C#, shipped by the plugin as a template the project copies in; TUA carries it under `game/src/Debug`) that reads the scenario (JSON: named inputs per tick; per-tick invariants such as "the player node exists", "no error line in the log", "the frame time stays under the budget"), drives the inputs deterministically from the seed, captures a frame from the active camera every k ticks, and quits 0 when every invariant held or 1 naming the first that failed.
  - **success:** The run writes `<out>/report.json`, `<out>/frames/*.png` and `<out>/log.txt`, is killed by a wall clock on overrun, ends in a status block (AD-11); the lib suite covers `playable.py` with a fake engine binary (the argv, the scenario parsing, the invariant verdicts, the wall clock); the harness depends on nothing in the studio, so a project can run it alone.
- **CAP-4** (34.2)

- **CAP-5** (34.3)

  - **success:** The judge answers the rubric (the scene loaded; the player is visible and framed; no missing-texture magenta and no error overlay; the HUD reads; the scenario's named moments appear in the frames they name) with `verdict: pass | fail` and `findings[]` each naming a frame and a rubric line, and ends in a status block; the `host-verify` event carries `playable: pass | fail | skipped` and the findings.

## Constraints

- Where things run: every `claude` session (an engine) runs only in the project's Docker Sandbox, never with bypass on the host; the host leg runs deterministic scripts and the engine binaries (`godot`, `blender`), never a model; the judge that looks at frames is a routed leg on the sandbox tier over the mounted worktree and never sees code or the spec; no 3D generation runs natively on the host (the research's Windows rule); the engine never runs on the host: where a story's proof needs the host (Godot, Blender, the display session, an MCP install, a TUA run) the engine asks through the spec's consult log and the operator session does that step on the box and answers with the evidence.
- Boundaries: GDS stays at the pin and `gds-game-architecture/engine-mcps.yaml` stays upstream-owned (AD-1); one engine MCP per run, paired with a skill that pins the engine version, and `.mcp.json` written only on confirmation by `recommend.py record --mcp`; secrets reach a worker by name only (`-e`, a User environment variable), never a file; a placeholder is kept until its replacement passes the same gates (`facts` and visual); TUA's `main` changes only through TUA's own run PRs.
- Surface rules: every surface change is additive on the contract (0.1.29 and up), ends in a status block (AD-11), is covered by conformance (AD-19) and lands its cost in the ledger (the `playable-verify` leg and every generator call as their own lines); spikes come first where the research's claims are untested on the box (34.2 the playable run, 34.5 the MCP comparison), as EP-30 did with the renderer.
- Repo and cadence: tk-studio (`apps/supervisor` host leg and pin, `plugins/tk-studio/lib` `playable.py` and `assets.py`, the contracts and conformance, `plugins/tk-studio/jobs`, the skills `tk-studio-playable-judge` and `gds-engine-godot-4`, `tools/installer/cli` doctor, `kb/` and the runbook); one story per run with a graceful stop after each, as EP-32 and EP-33 ran; a story proved on TUA records its proof in `kb/` as Story 23.3 did; a unit is a whole story.
- Inherited from EP-33: the operator overlay `.bmad-loop/policy.toml` stays gitignored and `engine.verify_commands` is reconciled from the tracked source by the readiness check; `bun` is not on the launch host's PATH, so a dev session runs `bun test` in the engine sandbox or records the gate `unverifiable-here` with the attended command; every `sbx`, Atlassian, engine binary, Blender, generator, clock and judge in a test is a fake, no live call; the loop never pushes, tags or runs the release motion.

## Non-goals

- Any change to TUA's `main` outside TUA's own run PRs.
- A fork of GDS or of its engine catalogue.
- Native 3D generation on the host; a second generator beyond the capped Meshy rung.
- Exposing the engine MCP's scene-editing tools to the dev session.
- A model on the host leg; a judge that reads code or the spec.
- The tooling note's Unity, Unreal, web-3D, Gaussian-splat and USD rows (parked: outside the Godot-first ruling, the mesh ladder and the 2D office).
- Video capture beyond frames and a contact sheet.
- Breaking a story into sub-tasks; a non-additive contract change.

## Success signal

- On the agent PC a TUA story that breaks a scene or an engine test goes red on the host leg before its PR opens; one `POST /jobs` (or one chat message) on TUA ends in a merged PR with a playable greybox scene, the frames in the PR, the slice's verdicts in the closeout report, a `job-run` ledger line with the cost, conformance green at 0.1.29 or later and the three skills' eval cases above threshold; the feature ledger's Phase 3 row reads built.
