## Intent
A dev session on a game project works from model priors about the engine. It guesses APIs that changed, hand-edits serialised scenes, and runs a bare `godot` that does not exist on the box. This story ships a read-only engine-knowledge skill, `gds-engine-godot-4`, inside the tk-studio plugin, together with a small deterministic core that reads the project's pinned engine version and checks it against the skill's supported range. When detection is confident the project is Godot, onboarding proposes the skill with evidence and records it only on confirmation. An out-of-range pin warns and never mismatches silently. The skill reaches every dev session through the existing skills mount, which mounts the whole plugin. The launch check's `verify commands` row also says where the engine gate runs: in the sandbox (`engine.verify_commands`, 33.5) or on the host leg (`verify.engine`, 34.1).

## Acceptance Criteria
- **AC1** — **Given** the `game-godot` detect profile **When** `tk-studio-onboard` proposes a working set for a project it detects as Godot **Then** the proposal carries, with its evidence, the plugin-shipped engine skill `gds-engine-godot-4` (read-only knowledge: the pinned version read from `project.godot`'s `config/features` and `global.json`'s SDK, the headless flags, the C# and GoDotTest conventions, the rule that `.tscn` and `.tres` files are written only the way the editor writes them, the import-cache rule, the `$env:GODOT` rule on the box) and records it in `working_set.<role>` only on confirmation; a project whose pinned version falls outside the skill's supported range gets a warning, never a silent mismatch; `recommend.py`'s tests cover the suggestion and the version check
- **AC2** — **Given** a run on a game project **When** the launch materialises the worktree **Then** the engine skill reaches the dev session the way the studio's other skills do (the skills mount), and `engine.verify_commands` (33.5) carries the project's engine gate when the sandbox can run it and names the host leg (34.1) when it cannot; the roster row, the README row and the kb row exist; a `claude plugin eval` case checks the skill answers the three pinned facts
- **AC3** — **Given** GDS's own engine catalogue (`gds-game-architecture/engine-mcps.yaml`, upstream-owned, AD-1) **When** the skill is written **Then** it cites the catalogue and never forks it

## Settled shape
1. **The skill folder.** `plugins/tk-studio/skills/gds-engine-godot-4/` holds `SKILL.md` (frontmatter `name: gds-engine-godot-4`, read-only knowledge, a `description` naming Godot 4 C#/GoDotTest projects) and `customize.toml` (peer shape). It also holds `pin.json`, which is the skill's supported range as data: `{"engine": "godot", "supported": {"min": "4.7", "below": "4.8"}, "tested": "4.7.2"}`. Widening the range is a data edit made after the knowledge has been checked against the new minor. The SKILL.md sections:
   - the pinned facts: run `engine_pin.py check` first, and answer from its output;
   - the headless flags;
   - the C# and GoDotTest conventions;
   - `.tscn`/`.tres` are written only the way the editor writes them (never hand-edit the serialised text; change scenes through the editor, the engine MCP or code that instances at runtime);
   - the import-cache rule (`.godot/` is generated and never committed or hand-edited; re-import headless after an asset change);
   - the box rule (`& $env:GODOT …` on the host; a bare `godot` only in a `WITH_GODOT` sandbox);
   - where the engine gate runs (Settled shape 4);
   - the catalogue citation (AC3).

   It also carries the AD-11 status-block line with `"intent": "gds-engine-godot-4"` and the sentence "If the deterministic core is unrunnable".
2. **The core `lib/engine_pin.py`** (stdlib, `uv run`, atomic writes not needed because it is read-only). The verb is `check --directory <project> [--skill gds-engine-godot-4]`.
   - Reads:
     - `project.godot` `[application]` `config/features=PackedStringArray(...)`: the first element matching `^\d+\.\d+$` is `features_version`.
     - `global.json` `msbuild-sdks."Godot.NET.Sdk"`, as `godot_net_sdk`.
     - `global.json` `sdk.version`, as `dotnet_sdk`. It is reported, never range-checked.
     - `pin.json` from `<plugin>/skills/<skill>/`.
   - `pinned`: `godot_net_sdk` when present, else `features_version`.
   - Warnings, each a sentence naming both values and the file:
     - `pinned` is outside `[min, below)` (numeric dotted compare);
     - the major.minor of `features_version` and `godot_net_sdk` disagree;
     - neither is readable (`pinned version unreadable`).
   - Output: JSON `{engine, features_version, godot_net_sdk, dotnet_sdk, pinned, supported, in_range, warnings[]}` then the AD-11 block with `intent: gds-engine-godot-4`, status `complete` (warnings allowed, exit 0).
   - Refusals, `blocked`, exit 2:
     - `no project.godot`;
     - `unknown skill` (no `pin.json`);
     - `malformed global.json` (JSON error; an absent global.json is not a refusal).
   - `recommend.py` imports its pure function (`read_pin(root) -> dict` and `check(root, skill) -> dict`). It never spawns the core.
3. **The profile and the proposal.**
   - `game-godot.json` gains `"suggests_skills": ["gds-engine-godot-4"]`, optional and absent on every other profile.
   - `detect.py` passes it through on the candidate (default `[]`). That is additive output on the `tk-studio-detect` surface; name it in the 0.1.29 sentence.
   - When the outcome is confident, `propose` adds each name as `kind: "skill"`.
     - `status` is `"installed"` when `<plugin>/skills/<name>/SKILL.md` exists, else `None`. The unavailable note then covers skills as well as modules.
     - The evidence is `detection: detected game-godot (score …): …` plus `engine-pin: pinned <v> from <file>; supported <min>..<below>`.
     - When `check` returns warnings, the entry gains `"warnings": [...]` and every warning is also appended to the proposal's `notes`, prefixed `gds-engine-godot-4: `. The skill is still proposed: the operator decides, and the warning is what makes the mismatch visible.
   - `record` is unchanged: only a confirmed set lands in `working_set.<role>`.
4. **Where the engine gate runs (the launch check's `verify commands` row).** The rule is constrained by driver-contract §1 0.1.28/0.1.29: `engine.verify_commands` is the in-sandbox list and `verify.engine` is the host leg's single command, two keys never merged. When the tracked config has a non-empty `verify.engine` string, the row's detail gains one clause:
   - `engine gate: sandbox (engine.verify_commands)` when an `engine.verify_commands` entry equals `verify.engine` once stripped;
   - `engine gate: host leg (verify.engine, Story 34.1)` otherwise.

   When there is no `verify.engine` but some `working_set.<role>` carries `gds-engine-godot-4`, the row warns: `engine gate: none (set verify.engine for the host leg, or add the gate to engine.verify_commands only in a WITH_GODOT sandbox)`. The row's status never goes red for this. The skill and the kb row state the same rule: the gate goes in `engine.verify_commands` only when the sandbox was provisioned `WITH_GODOT`, and otherwise in `verify.engine`.
5. **The eval case.** It lives in `plugins/tk-studio/evals/gds-engine-godot-4-pinned-facts/` and is scaffolded with `claude plugin eval init --bare gds-engine-godot-4-pinned-facts` when `claude` is available, else written as `prompt.md`.

## Risks and open decisions
- **Oversize.** The Files list has 23 entries, past band L (budget-bands: L is "larger, with a stated reason"). The reason is that a new conformance surface carries a fixed tail: roster, manifest, contract, `SURFACE_CORES` and the README/kb rows. Do not split it here. Halt if the Files list grows past the list above.
- **The skill's name breaks the `tk-studio-*` surface convention**, because the AC names it `gds-engine-godot-4`. The runner, the roster drift check and the supervisor's discovery all take every `skills/*` folder (verified), and §1's sentence is extended additively (Settled shape 6). `evolve.py:226`'s `tk-studio-[a-z]…` surface regex will not attribute observations to this skill, which is acceptable. **Block If:** any gate rejects a non-`tk-studio-` skill folder and the only fix is to rename the skill or change a gate outside Files.
- **Orchestrator routing shows the recorded skill as `missing`** (`orchestrate.py:118-124`), because inventory has no plugin-skill plane. The mount does not depend on it. Do not widen inventory in this story: record a DRIFT-free deferral (class a: the routing display of a criterion's artifact) for a later story.
- **Block If:** `claude plugin eval init --bare` produces a case format whose expectations cannot name the three facts, and `prompt.md` is rejected too.
- **Block If:** the launch check's `verify commands` row cannot carry the clause without changing its status-block shape or a §2 field that is not additive.
- The supported range `4.7 … <4.8` is deliberately narrow: a 4.6 or 4.8 project warns. That is the "never a silent mismatch" side of the trade-off, and it is not a Block If.
- The README's missing `tk-studio-playable-judge` row (34.3) stays out of scope. Note it in the Auto Run Result as an observed gap.
