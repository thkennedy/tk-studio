## Intent
34.3's `playable-verify` leg needs one proven way to run the game on the agent PC: bounded ticks, a seeded and scripted input scenario, and frames plus a pass or fail coming back. This story writes that tool. `playable.py run` starts `$GODOT` with a `PlayableHarness` C# autoload, which the plugin ships as a template the project copies in. The story also writes the kb record of the three rendering paths, measured on the host by the operator session at the engine's consult-log request, with the ruling that names the path 34.3 uses. `tk-studio-launch check` gains an advisory warning when that path's precondition is missing. The engine never runs on the host. The harness copy-in to TUA (`game/src/Debug`) and TUA's scenario land through a TUA PR or the operator's step, never through this run (SPEC Assumptions).

## Acceptance Criteria
- AC1: **Given** TUA on the box (Godot 4.7.2 Mono, the logged-in session's display) **When** `plugins/tk-studio/lib/playable.py run --directory <project> --scenario <file> --seed <n> --ticks <t> --out <dir>` runs on the host **Then** it starts the game with a `PlayableHarness` autoload (C#, shipped by the plugin as a template the project copies in; TUA carries it under `game/src/Debug`) that reads the scenario (JSON: named inputs per tick; invariants per tick such as "the player node exists", "no error line in the log", "the frame time stays under the budget"), drives the inputs deterministically from the seed, captures a frame from the active camera every k ticks, and quits 0 when every invariant held or 1 naming the first that failed; the run writes `<out>/report.json`, `<out>/frames/*.png` and `<out>/log.txt`, is bounded by a wall clock that kills an overrun, and ends in a status block (AD-11)
- AC2: **Given** the three rendering paths (the session's display, windowed; Movie Maker frames through `--write-movie`; `--headless`, which renders nothing) **When** the spike measures them on the box (the operator session runs the measurements on the host at the engine's request through the consult log, with the harness and `playable.py` the engine wrote) **Then** `kb/playable-verify-on-the-box.md` records which path produced frames, the time per tick and the pixel evidence, and names the one 34.3 uses (the story's ruling, in its consult log); `tk-studio-launch check` warns when that path's precondition is missing (no display session, no `$env:GODOT`)
- AC3: **Given** the lib suite **When** it runs **Then** `playable.py` is covered with a fake engine binary (the argv, the scenario parsing, the invariant verdicts, the wall clock); the harness depends on nothing in the studio, so a project can run it alone

## Code Map
- **`plugins/tk-studio/lib/playable.py` (new): the host-side runner.** It is stdlib only (NFR9; `test_installer_bootstrap` and `test_utf8_guard` sweep `lib/*.py`), so `main()` must call `sys.stdout.reconfigure(encoding="utf-8")` (the `test_utf8_guard.py` static sweep). Verb: `run` only. Shape:
  - Engine binary: `--godot <path>`, else `GODOT` from the environment, stripped. It must be an absolute path to a file. Never a bare `godot`: the box's exe is `Godot_v4.7.2-stable_mono_win64_console.exe` (34-1 finding, runbook §2 :155-172, replan entry closed into this plan). Unset, non-absolute or missing is a refusal (`blocked`, exit 2) naming it, worded the way the doctor's `engine` row is (`tools/installer/cli/tk_studio_cli/doctor.py` `check_engine` :1076).
  - Project: `--directory` holds `project.godot`, or exactly one `<directory>/*/project.godot` exists (TUA: `game/`, runbook :513 `--path game`). Anything else is a refusal naming what was found.
  - Scenario: parsed and validated before anything starts (Settled shape 1). A bad scenario is a refusal naming the field. Seed and ticks are non-negative ints and ticks > 0, else a refusal.
  - argv: `[GODOT, "--path", <godot dir>, <mode flags>, "--", "--playable-scenario=<abs>", "--playable-seed=<n>", "--playable-ticks=<t>", "--playable-out=<abs out>"]` (Settled shape 3). Mode flags come from `--mode display|movie|headless`, default `display` until the ruling: `display` adds `--windowed --fixed-fps 60`, `movie` adds `--write-movie <out>/frames/movie.png --fixed-fps 60`, `headless` adds `--headless --fixed-fps 60`. If the ruling picks another path, change the default in this story and record it in the consult log.
  - Output: `<out>/` is created. stdout and stderr go to `<out>/log.txt` as they arrive (never into the project tree). Godot's `--log-file` may be added if the measurement shows stdout loses lines; record that in the kb record.
  - Wall clock: `--wall-clock <s>`, default 120. Use `subprocess.Popen(..., stdin=DEVNULL)` and wait with a timeout. On overrun: `kill()`, then `wait()`, then verdict `fail` with `failed: {invariant: "wall-clock", detail: "<s>s exceeded"}`. The precedent is `launch.py` `run_cli` :141-150 (timeout, DEVNULL, utf-8 with `errors="replace"`) and `sandbox_login.py` `Deadline` :196. Put the spawn in a module-level `run_engine(argv, *, cwd, log_path, timeout_s)` returning `(exit|None, timed_out, duration_ms)`, so tests can inject it (as `launch.run_cli` / `launch.run_sbx` are injected in `tests/test_launch.py`).
  - Report: read `<out>/report.json` as the harness wrote it, merge `run` (Settled shape 2) and write it back atomically (tmp then `os.replace`, as `launch._write_atomic` :475). No report from the harness (a crash or the wall clock) means `playable.py` writes one itself with `verdict: fail`, `failed: {invariant: "harness", detail: "no report.json (exit <n>)"}` or the wall-clock failure. A harness pass with exit ≠ 0, or exit 0 with a `fail` report, is a fail naming the mismatch. Scan `log.txt` for `ERROR:` / `SCRIPT ERROR:` lines into `log_errors[]` (first 20). An error line under a harness pass with a `no_error_log` invariant is a fail.
  - Status block: the last keys are `status` (`complete` on pass, `partial` on fail, `blocked` on refusal), `intent: "playable"`, `artifacts` (`report.json`, `log.txt`, the frames folder; out-relative), `reason` (the first failure or the refusal). Use the same key order as `launch.with_block` :569-574. Exit 0 pass, 1 fail, 2 refusal or bad invocation (the story's "quits 0 … or 1").
- **`plugins/tk-studio/lib/godot/PlayableHarness.cs` (new): the template.** The sibling-folder precedent is 34.6's `plugins/tk-studio/lib/blender/greybox.py`. It is Godot 4 C#, `public partial class PlayableHarness : Node`, and depends on nothing in the studio (AC3). Behaviour:
  - It is inert unless `OS.GetCmdlineUserArgs()` carries `--playable-scenario=`. A project can keep it registered as an autoload and play normally.
  - It reads the scenario JSON (`System.Text.Json` or Godot `Json`) and seeds `RandomNumberGenerator` and `GD.Seed` from `--playable-seed`.
  - In `_PhysicsProcess` it counts ticks and applies that tick's inputs through `Input.ParseInputEvent(new InputEventAction { Action, Pressed, Strength })`. A seeded `random_inputs` block draws from the RNG only.
  - It evaluates the invariants each tick (`node_exists` through `GetTree().Root.GetNodeOrNull`, `frame_time_under` against the scenario's budget using `Performance.GetMonitor(Performance.Monitor.TimeProcess)`, `no_error_log` through a custom `Logger` registered with `OS.AddLogger`; confirm the API on 4.7.2 during the measurement and record it).
  - Every `capture_every` ticks it saves `GetViewport().GetTexture().GetImage()` to `<out>/frames/<tick:D6>.png` (skipped in `movie` mode, where Movie Maker writes the frames).
  - It writes `<out>/report.json` (Settled shape 2) and calls `GetTree().Quit(0|1)`.
  - A header comment names the copy-in: copy to `<project>/src/Debug/PlayableHarness.cs` (TUA: `game/src/Debug`) and register `[autoload] PlayableHarness="*res://src/Debug/PlayableHarness.cs"`.
  - The lib suite cannot compile it. Its test asserts only that the file exists and that its text names the user args, the report keys and the inertness check (keep the names in one place: `playable.py` constants that the test greps for in the `.cs`).
- **`plugins/tk-studio/lib/godot/scenario.example.json` (new):** a minimal valid scenario that the lib test parses through `playable.py`'s validator, so the documented shape cannot drift.
- **`plugins/tk-studio/lib/tests/test_playable.py` (new): AC3.**

  - The real wall-clock test calls `run_engine` directly with `[sys.executable, "-c", "import time; time.sleep(30)"]` and `timeout_s=1`, asserting the kill, `timed_out` and duration < 10 s.
  - Cases: the argv per mode; the refusals (`GODOT` unset, relative, missing; no `project.godot`; two candidates; a bad scenario per field); a harness pass gives exit 0 and `complete`; a harness fail gives exit 1 naming the invariant and tick; no report gives fail `harness`; the wall clock gives fail `wall-clock`; exit/verdict mismatches; the `log_errors` scan; the status-block key order; out-relative artifacts; and the template text checks above.
