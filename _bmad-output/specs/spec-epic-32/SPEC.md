# Epic 32: The Engagement Loop v1

## Why

A vision to realize, and the build order's next step after EP-31. The design spec's §6.4, §7.1 and user flow F2 make hiring the studio one record with a state, moved only by typed inputs, talked to through the supervisor's own chat route (D2: Hermes is out; the planner leg is a `claude -p` session with the plugin whose memory is the project's plan, kb and synced Confluence pages), scoped on an editable Confluence page, quoted from the meter's own history as a 50/85/95 band with a hard cap (D4: tokens as the figure, dollars as the shadow), approved by one verb that fixes the autonomy level, run by the loop as today, and closed by a report that says done, not done and why. The evidence is the research record's B5 (`research/studio-front-end-and-repo-structure-2026-10-09/research.md` §9): every surveyed product gates on a plan and none quotes before running or reports partial delivery; its template (states, not prompts) is adopted as written, Jules's enum renamed to §7.1's. What exists today: F2's steps 5 and 6 as `POST /jobs` plus the loop, the inbox and the two statuses (EP-31), the Confluence publish and the sync-back (31.3, 31.4), the board's hand-written budget band. The engagement record is canonical in the served project's `_bmad-output/engagements/<id>/` (AD-5, like the plan); the supervisor holds the state machine and serves the API; the Confluence pages and the Jira comments stay backend-authoritative and append-only (D9, AD-22); the planner session never holds a bearer and never moves the state: it writes files through the new `tk-studio-engage` surface and proposes inputs the owner sends. Every surface is additive on contract 0.1.27. Planned 2026-10-25 after EP-31 landed. Attended: Tim's owner seat (`TK_STUDIO_ATLASSIAN_OWNER_EMAIL`, `TK_STUDIO_ATLASSIAN_OWNER_TOKEN`) must be set on the box before 32.3's reply path is exercised live; the first live engagement (on the-universe-awaits or on tk-studio itself) is an attended acceptance after 32.8, recorded in `kb/`. Sizing: Epic-21-sized or larger (§10); one story per run with a graceful stop after each, as EP-31 ran. Repo: tk-studio (`apps/supervisor`, `apps/studio-web`, `plugins/tk-studio/lib` and skills, the contract, `kb/`); eight stories, 32.1 laying the record and its table first.

## Capabilities

- **CAP-1** (32.1)
  - **intent:** A request creates one engagement record the owner can read and trust.
  - **success:** Given a registered project and a request in plain language, `POST /engagements {project, request}` (the bearer, or a session cookie with `X-CSRF-Token`, else 403 CsrfRefused) writes `_bmad-output/engagements/<id>/engagement.yaml` in the served project's root (the id `ENG-NNN` from the plan counter's new `engagement` series; `shape_version: 1`; the §7.1 fields `id, project, state, request, questions[], assumptions[], scope_page, quote, autonomy, approved_at, closeout`, plus `created`, `updated`, `spend {planning_usd, runs_usd}` and `inputs[]`, the typed-input log) in state `intake`, appends a queue event `engagement {id, project, state, from: null}`, and answers 200 `{ok, engagement}`; `GET /engagements?project=<id>` lists the project's engagements newest first and `GET /engagements/{id}` reads one with its chat pointer (32.2); a cookie session reads both; an unregistered project is 404 UnknownProject; contract 0.1.27 (additive) names the routes.
- **CAP-2** (32.1)
  - **intent:** Only a typed input moves the state, and every transition is one row of one tested table.
  - **success:** Given the states `intake → awaiting-answers → scoping → quoted → approved → in-progress → delivered` with the side exits `paused`, `failed`, `partial`, `cancelled`, `POST /engagements/{id}/input {verb, …}` with one of `answer`, `go`, `revise`, `question`, `approve`, `cancel` (each with its typed payload, checked by schema) applies exactly the transitions of one exported table in `apps/supervisor/src/engagement.ts` (written into the contract's §7.1 row and tested row by row); any other body is 400 SchemaError, a verb illegal in the current state 409 IllegalInput `{state, verb}`, a terminal state 409 EngagementClosed; nothing else moves `state`: not a chat message, not the planner, not a timer; every applied input is appended to `inputs[]` with its time and its source (`bearer` | `cookie` | `planner` for 32.3's one exception) and emits an `engagement` event carrying `from`; `bun test` covers every row and every refusal.
- **CAP-3** (32.1)
  - **intent:** The office and the board show every engagement and which ones need the owner.
  - **success:** `GET /office` and the stream's snapshot carry `engagements[] {id, project, state, title (the request's first line, 80 characters), needs_you}` (0.1.27, additive) and the hub emits `office.engagement {id, state, from}` deltas on each change; `GET /board`'s Needs-you column lists the project's engagements in `awaiting-answers` and `quoted` as items `{engagement, state, title}`; the office projection's and the board's tests cover the rows.
- **CAP-4** (32.2)
  - **intent:** The owner talks to the studio about an engagement from the web and the planner leg answers from the project's memory.
  - **success:** Given a non-terminal engagement, `POST /chat/{engagement} {message}` (the bearer or a cookie with `X-CSRF-Token`; the body at most 32 KiB UTF-8) appends `{seq, at, author: owner, body}` to `_bmad-output/engagements/<id>/chat.jsonl` and queues one run of the shipped job `engagement-chat` (one-shot; host tier; the planner leg's model and effort from the project's routing, passed at enqueue as `validate-resolution`'s are; payload `{engagement, seq}`; `guards.max_turns` 80, `max_wall_clock_seconds` 1800): a `claude -p` session on the host in the served project's root with the plugin, driven by the new contract surface `tk-studio-engage` (`lib/engage.py`), which reads the record, the chat so far, the plan under `_bmad-output/planning-artifacts/`, `kb/` and `kb/confluence/` and writes the reply with `engage.py reply` as `{seq, at, author: planner, body, run_id, proposals[]}`; the run's `job-run` event carries the cost and `spend.planning_usd` sums it (scoping is metered; the quote says so); the answer is 200 `{ok, engagement, seq, run_id}`; a message sent while a chat run is live is queued behind it on the checkout lock, never refused; a terminal engagement is 409 EngagementClosed.
- **CAP-5** (32.2)
  - **intent:** The chat is readable live and the planner's proposals are buttons the owner presses, never actions the planner takes.
  - **success:** `GET /chat/{engagement}?since=<seq>` (JSON, or `Accept: text/event-stream` with the office stream's id, replay and heartbeat conventions) returns the lines after `seq` and the planner's reply reaches an open stream without a reload; a `proposals[]` entry is `{verb, payload, label}` (an input the planner suggests, which the web renders as a button and the owner sends through 32.1: the planner has no bearer and no CSRF token and moves nothing); the chat session's environment is a worker's (`buildWorkerEnv`: every `TK_SUPERVISOR_*` secret and the owner seat stripped); `bun test` covers the append, the queueing behind a live run, the stream and the refusals with a fake planner; the lib suite covers `engage.py reply` (the memory it assembles, the reply line, the proposal shape) with a fixture project.
- **CAP-6** (32.3)
  - **intent:** At most three multiple-choice questions with defaults wait on the owner loudly, in the inbox.
  - **success:** Given an engagement in `intake` whose planner turn finds gaps a default cannot cover, `engage.py questions` (at most three, each `{id, text, options[] with exactly one default, impact}`; a fourth is refused by name) fills `questions[]`, the state moves `intake → awaiting-answers` by a `question` input the supervisor applies on the planner's behalf from the written file (the one exception to "the owner sends every input", recorded with source `planner` and the run id), one Jira issue per engagement (`ENG-NNN: questions`, issue type Task, in the project's Jira project) is created or updated through the planning adapter and moved to `Blocked - Awaiting User` with the questions as a comment that @mentions the owner (31.5's `track.py block` path, extended with `--engagement`), the sync-back's inbox lists it (the item carries `engagement: ENG-NNN`), and the office shows the "!" bubble on the planner's desk.
- **CAP-7** (32.3)
  - **intent:** Answers arrive from Jira or the cards, and an absent owner leaves stated assumptions, never a stall.
  - **success:** Given the owner's reply on the issue (31.6's Issue screen, Jira itself) or the Chat screen's answer cards, when the sync-back pulls the comment or `POST /engagements/{id}/input {verb: answer, answers: {<id>: <option>}}` arrives, the answers land in `questions[].answer` (a comment is parsed as `<id>: <option>` lines, a free-text answer is kept verbatim for the planner to judge), the issue moves to `Block Resolved` and on to `Done` (no validation leg for a question), and the state moves `awaiting-answers → scoping` once every question has an answer; `go` with questions open converts each unanswered question into its default as a stated assumption in `assumptions[]` (named on the scope page) and moves on; nothing moves on a timer; the lib suite and `bun test` cover the cap, the issue and the inbox item, the two answer paths and the assumptions with fake Atlassian REST.
- **CAP-8** (32.4)
  - **intent:** The scope of work is a Confluence page with deliverables, acceptance signals, exclusions and dated dependencies fixed before any run.
  - **success:** Given `scoping`, `engage.py scope` from the turn's `scope.md` (the sections, in order: goal; deliverables, each with its acceptance signal; exclusions; what the studio needs from the owner, each dependency dated; milestones; proposed epics and stories in `epics.md`'s story shape) has 31.3's publish put the page in the engagement's Confluence folder (`Engagements/ENG-NNN/Scope of Work`; provenance footer; skipped by content hash when unchanged) and records `scope_page {id, url, version}`; the proposed epics and stories are not plan entities yet (nothing under `plan/` before approval); a scope with a deliverable lacking an acceptance signal is refused by name.
- **CAP-9** (32.4)
  - **intent:** The owner edits the scope where they read everything else, and a revision replaces it wholesale.
  - **success:** When the owner edits the page in Confluence (mirrored by the next sync-back, 31.4, `kb/confluence/`) or sends `revise` with a body from the Chat screen, the revision replaces `scope.md` wholesale (the page is authoritative while `scoping`, D9; a `revise` body becomes the new page); a `revise` in `quoted` returns the state to `scoping` and voids the quote; the planner's next turn reads the new scope; the lib suite covers the round trip (Markdown to storage format to mirrored Markdown keeps every section), the replace rule and the refusal with a fake Confluence REST.
- **CAP-10** (32.5)
  - **intent:** The quote is a 50/85/95 band from the studio's own history with a hard cap, never a bare number.
  - **success:** Given the meter's per-story records (this story makes the payload structured and additive: `kind: meter`, `story_key`, `epic`, `usd`, `tokens {input, output, cache_read, cache_write}` per leg and the route, written to `transcripts/<key>/observation.json` and harvested to the host ledger as before) and the scope's proposed stories, `engage.py quote` (the planner's turn after the scope, or by hand) computes, for this project and story kind, a seeded bootstrap (10,000 resamples of per-story tokens over the proposed story count) 50/85/95 band in tokens, shown as plan-window share (`~/.tk-studio/config.yaml`'s `plan.window_tokens`, else "share unknown") with the list-price dollar shadow (`prices.json`), the cap (`cap = p95 + one story at p85`) and what happens at the cap (the run pauses `partial`, the engagement's issue blocks with the figures, the owner decides), the route and the autonomy levels on offer (32.6), and whether scoping was billable (the planning spend so far); a history under eight landed stories says "thin history" and widens the band from §10's sizing by analogy; `quote {band50, band85, band95, cap, basis, computed_at}` lands in the record, the state moves `scoping → quoted`, and `.tk-studio/budget-bands.yaml` gains `epics.<proposed EP>.usd_estimate` from the 85th so the board draws the band against spend once the epics exist.
- **CAP-11** (32.5)
  - **intent:** The quote is pinned by tests and visible on the record and the board.
  - **success:** The lib suite covers the resampling (seeded, exact), the thin-history rule, the share, the cap and the voiding on `revise` with fixtures; `GET /engagements/{id}` carries the quote and `GET /board`'s `band_usd` follows it; `kb/quote-band.md` records the method and its first figures.
- **CAP-12** (32.6)
  - **intent:** One verb approves with the autonomy chosen at that moment, and approval alone creates the plan, publishes it and starts the work.
  - **success:** Given `quoted`, `POST /engagements/{id}/input {verb: approve, autonomy: ask | steady | full, base_ref?}` (the bearer or a cookie with `X-CSRF-Token`; nothing else approves: no chat line, no planner proposal, no timer) has the supervisor run on the host in the served root: the scope's proposed epics and stories appended to `epics.md` as `## Epic N` sections carrying `engagement: ENG-NNN`, `plansync normalize` (the EP- and ST- entities, the index, the backlog mirrors), `plansync sync` (the promote to Jira with the design pages' links), the engagement's `run-epic-N` job declared under `.tk-studio/jobs/` and in `.tk-studio/config.yaml`'s `jobs` (the project's default worker placement), one commit on a branch `engagement/ENG-NNN` opened as a PR (main is protected; the run cuts from `base_ref` when given, else from main once the PR merges, the supervisor queuing it on the merge as the plan pull-back watches today); `autonomy` and `approved_at` are recorded, the state moves `quoted → approved`, and `approved → in-progress` on the first run's `launched` event; `ask` = a graceful stop after every story and a `question` to the owner before the next, `steady` = one story per run, resubmitted by the supervisor on each merge, `full` = the epic end to end.
- **CAP-13** (32.6)
  - **intent:** Spend is drawn against the band and the cap pauses the work for the owner's decision.
  - **success:** In `in-progress`, as runs end, `spend.runs_usd` sums the engagement's runs' `job-run` costs and the board draws the band against it; at the cap the supervisor stops the live run with a graceful stop, marks the engagement `partial`, blocks its issue (the inbox) with the figures, and waits for `go` (`{cap}` raises it by the owner's figure, back to `in-progress`) or `cancel`; `bun test` covers the approve path with a fake adapter (what is written, the PR, the job, the three autonomy levels, the cap) and every refusal.
- **CAP-14** (32.7)
  - **intent:** Intake, questions, scope, quote and approval happen from the desktop or the iPad without a terminal.
  - **success:** Given `GET /engagements`, `GET /chat/{id}` and the typed inputs, the Chat screen lists the project's engagements by state with the open one's transcript (owner and planner lines, the planner's run cost on hover), a message box (`POST /chat/{id}`), the state as a stepper (`intake … delivered`, the side exits marked), the questions as cards with their options and defaults (an answer sends `answer`), the scope page's link and a **Revise** box (sends `revise`), the quote as the band (50/85/95 as share and dollars, the cap, the autonomy levels) and an **Approve** control with the autonomy choice (sends `approve`), **Go** and **Cancel** where the table allows them, and a planner `proposals[]` entry as a button sending exactly that input; a **New engagement** form (`POST /engagements`); the nav gains Chat, and an engagement in `awaiting-answers` or `quoted` puts a count on it; the web sends the CSRF token as the inbox reply does; the stream keeps the transcript live and the watchdog on `visibilitychange` reconnects it on the iPad; vitest covers the stepper, the cards, the quote, each action and the refusals' rendering with a fixture; the studio-web gate stays green.
- **CAP-15** (32.8)
  - **intent:** Delivery says done, not done and why, with the cost per story, on evidence.
  - **success:** Given `in-progress` and the engagement's last run ending (`complete`, `partial`, `failed`, `cancelled`), the supervisor's engagement pass (at the `finally` sites, as the resolution pass does) writes `_bmad-output/engagements/<id>/closeout.md`: each deliverable's acceptance signal checked against the landed stories' specs and PRs (done / not done / why), the PRs, a per-story cost table from the meter's records and the runs' `job-run` events, the planning spend, the quote against the actual, and every side exit with its reason; publishes it as `Engagements/ENG-NNN/Closeout` beside the scope; sets `closeout` and the state `delivered` (every deliverable done) or leaves `partial` / `failed` with the report; moves the engagement's Jira issue to `Done`; the notifier sends one line with the link.
- **CAP-16** (32.8)
  - **intent:** Mid-run input is a typed verb on the live engagement, and a change after delivery is a new engagement with its own quote.
  - **success:** On a live engagement `question` (the owner asks; the planner's next turn answers; no state change), `revise` (back to `scoping` with the quote voided; a run in flight finishes its story through a graceful stop) or `go` (past a cap or past open questions) applies as 32.1's table says; after `delivered` a change is a new engagement (`POST /engagements {project, request, follows: ENG-NNN}`) with its own quote; `bun test` covers the closeout's composition and the three mid-run inputs with fakes; the lib suite covers the report's rendering and `engage.py closeout`; the contract's §2 names `tk-studio-engage` and its verbs (`reply`, `questions`, `scope`, `quote`, `closeout`; 0.1.27 additive) and §7.1 the state table; `kb/engagement-loop.md` describes the loop as built, for the attended first engagement and for EP-33.

## Assumptions

- One contract bump, 0.1.27, carries the epic's additive changes under one entry (the engagement, chat, office and board surfaces in §1 "Supervisor surfaces the web consumes"; `tk-studio-engage` and its verbs in §2; the `engagement-chat` job type in §4; the state table in a §7.1 row), extending as EP-31 did at 0.1.26; 32.1 opens the entry.
- The "plan counter's new `engagement` series" is `next.engagement` in `.tk-studio/plan-counter.yaml`, read and written atomically by the supervisor with its `js-yaml` dependency, every other key preserved; `plansync.py`'s `load_counter` accepts the extra key (it checks `epic`, `story` and `task` only) and `save_counter` writes the whole mapping back, so the two writers never clash on shape.
- The "queue event `engagement`" is a supervisor-scope service event (`queue.serviceEvent("engagement", {id, project, state, from, …})`): an engagement has no queue run, and service events are the queue's run-less kind (Story 27.5); the office hub reads the records from each served root as it reads `inbox.json`, so `engagements[]` and `office.engagement` follow the files, never the event alone.
- The engagement record files follow `_bmad-output/tracking/`'s precedent from EP-31: written by the supervisor into the registry's served root (the main checkout), untracked and uncommitted by the supervisor; the engine runs in a worktree cut from a ref, so these files never dirty an engine checkout. `bun` is not on the launch host's PATH, so dev sessions run `bun test` and vitest in the engine sandbox (`WITH_BUN=1`) and record the gate `unverifiable-here` with the attended command when the sandbox lacks it (EP-29 to EP-31 precedent).
- The shipped job `engagement-chat` ships under `plugins/tk-studio/jobs/` beside `validate-resolution` (trigger one-shot, a skill target on `tk-studio-engage` with `payload.verb: reply`, no `model`: the planner leg passed at enqueue), shipped undeclared and declared per project as `validate-resolution` is; the engagement's `run-epic-N` job (32.6) is the existing `run-epic` type declared under `.tk-studio/jobs/<id>.json`.

## Open Questions

- `scoping → quoted`: 32.1 names source `planner` as 32.3's one exception (the `question` input), yet 32.5 says the state moves `scoping → quoted` when `engage.py quote` lands the quote. Which typed input moves it: the owner's `go` in `scoping` once a quote is present (the planner proposes it as a `proposals[]` button), or a second planner-source exception the supervisor applies from the written quote? The 32.1 plan reads it as the owner's `go` (README §7.1 "only a typed input moves the state"; F2 step 5 "leaving planning is an explicit exit"); the operator may rule otherwise before 32.5.
- `approved → in-progress` "on the first run's `launched` event", `in-progress → partial` at the cap, and the run-end rows (`delivered` | `partial` | `failed`) are moved by supervisor-observed events, not typed inputs. The 32.1 plan records them as event rows of the same table with source `supervisor` in `inputs[]` (verbs `launched`, `cap`, `run-ended`), applied by an exported function 32.6 and 32.8 call; is a distinct `inputs[]` source value acceptable, or should these land in a separate `transitions[]` log?
