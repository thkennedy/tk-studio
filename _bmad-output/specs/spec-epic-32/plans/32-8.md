## Intent
After 32.6 an approved engagement runs, but nothing says when it is finished. A run that ends on its own (the epic done, failed or cancelled) leaves the record `in-progress`, with no report and the Jira issue open. This story adds the closing step: the supervisor's engagement pass, at the `finally` sites, sees the engagement's last run end and runs `engage.py closeout` on the host. That writes and publishes the report (done / not done / why, the PRs, the cost per story, the planning spend, the quote against the actual, the side exits). The pass then moves the state through 32.1's `run-ended` rows, moves the issue to `Done` and sends one notifier line. Three mid-run inputs complete what the table already allows: `question` changes no state, `revise` now stops a live run gracefully, and `go` passes a cap or open questions. After `delivered`, a change is a new engagement (`follows`) with its own quote. The contract, the skill and `kb/engagement-loop.md` describe the loop as built (F2 steps 7 to 9; B5 items 7 to 9).

## Acceptance Criteria
- AC1: **Given** `in-progress` and the engagement's last run ending (`complete`, `partial`, `failed`, `cancelled`) **When** the supervisor's engagement pass runs (at the `finally` sites, as the resolution pass does) **Then** it writes `_bmad-output/engagements/<id>/closeout.md`: each deliverable's acceptance signal checked against the landed stories' specs and PRs (done / not done / why), the PRs, a per-story cost table from the meter's records and the runs' `job-run` events, the planning spend, the quote against the actual, and every side exit with its reason; publishes it as `Engagements/ENG-NNN/Closeout` beside the scope; sets `closeout` and the state `delivered` (every deliverable done) or leaves `partial` / `failed` with the report; moves the engagement's Jira issue to `Done`; the notifier sends one line with the link
- AC2: **Given** a live engagement **When** `question` (the owner asks; the planner's next turn answers; no state change), `revise` (back to `scoping` with the quote voided; a run in flight finishes its story through a graceful stop) or `go` (past a cap or past open questions) arrives **Then** it applies as 32.1's table says; after `delivered` a change is a new engagement (`POST /engagements {project, request, follows: ENG-NNN}`) with its own quote; `bun test` covers the closeout's composition and the three mid-run inputs with fakes; the lib suite covers the report's rendering and `engage.py closeout`; the contract's §2 names `tk-studio-engage` and its verbs (`reply`, `questions`, `scope`, `quote`, `closeout`; 0.1.27 additive) and §7.1 the state table; `kb/engagement-loop.md` describes the loop as built, for the attended first engagement and for EP-33

## Settled shape
SPEC.md was not appended: the gate session's write surface excludes it. The dev session records each shape in its spec's Design Notes.
1. **CAP-15: the engagement's last run** (`named placeholder rule`, per the 32-6 replan and `approve.ts` step 7). The pass looks at a record in `in-progress` or `partial`. The candidate is its newest linked run over every approve cycle (`linksOf` without `since`). That run must be terminal, with no `after_run` resubmit naming it. No `ok` steady stop may still be awaiting its PR's merge (step 7 would resubmit it), and no ask pause or cap block may be owed. The closeout is written once per last run: an `engagement-closeout` service event names that run's `run_id`, and an event naming it means done. A later `go {cap}` from `partial` gives a new last run, so a new closeout replaces the file and the page.
2. **CAP-15: the composition, supervisor → lib** (`named placeholder rule`). The supervisor writes a JSON input file and runs `engage.py closeout --directory <served root> --engagement <id> --input-file <path>` through `uvRunner` (timeout 300), on the host, as the scope pass runs `scope --revise-at`. The input is:
   `{run_id, outcome_hint, runs: [{run_id, job, state, studio_run_id, cost_usd, pr}], stories: [{key, run_id, spec_status, pr, pr_state}], epics: [{job, queued: bool}], side_exits: [{at, to, verb, reason}], spend {planning_usd, runs_usd}, quote}`.
   - `stories` are the landed keys (`landedStory` and the `close-out` events per linked run). `spec_status` is the spec frontmatter `status` from `findSpec(run.worktree ?? root, key)`. `pr_state` comes from `gh pr view --json state` (null when gh fails).
   - `epics` are the jobs the approve pass declared (`engagement-approve` step `job` detail) against the ones queued.
   - `side_exits` are the record's `inputs[]` lines whose `to` is `paused`, `partial`, `failed` or `cancelled`, with `detail.reason`, a payload `reason` or the verb.
   - `bun test` covers this composition with fakes.
3. **CAP-15: a deliverable's verdict** (`named placeholder rule`, per `user-flows.md` F2 step 7: "the PR is the deliverable object; the acceptance signals fixed at scope time are the checklist"). The deliverables are `scope.md`'s `## Deliverables` `### <title>` items, with their signal (`SIGNAL_RE`, else the substring fallback). A deliverable's stories are the proposed stories in `## Proposed epics and stories` whose title or body names the deliverable's title (case-insensitive). When none names it, they are every story of the engagement.
   - `done` when each of those stories landed (`spec_status: done`) and its PR is `MERGED`.
   - Otherwise `not done` with the why, in this order: `no acceptance signal`, `epic not run` (its epic's job never queued), `story <key> not landed`, `PR <url> not merged`.
   - The report prints the signal as the checklist line and the PRs as its evidence. Judging the signal's text against the code is not mechanical; that is the attended first engagement's human read.
4. **CAP-15: the outcome** (`named placeholder rule`). Every deliverable done → `run-ended {outcome: delivered}`. Otherwise, the last run's queue state `blocked` → `failed`. Otherwise (`complete`, `partial` or `cancelled` with a deliverable not done) → `partial`. The queue's terminal states are `complete | partial | blocked | cancelled` (`queue.ts:63`), so the story's "failed" is a `blocked` run. The supervisor applies the row through `applyEvent` (`detail {outcome, run_id, closeout: <path>}`) in a fresh read. `partial → partial` is a row, so a repeat closeout is legal.
5. **CAP-15: the report, the page and the record** (`named placeholder rule`, per CAP-8's scope page rule).
   - `closeout.md` holds the `##` sections `Outcome`, `Deliverables` (each `### <title>` with `Acceptance signal:`, `Verdict: done | not done — <why>` and its PRs), `Pull requests`, `Cost per story` (a table `story | run | tokens | usd`, from the meter records by `story_key` with the `job-run` `cost_usd` per run, `—` when a figure is unmetered), `Spend` (`planning_usd`, `runs_usd`, total), `Quote against actual` (`band50`/`band85`/`band95` usd, the cap, the actual total and which band it fell in), and `Side exits`. It is written atomically.
   - The page is `ENG-NNN: Closeout` in the `ENG-NNN` child folder under `Engagements` (the scope's folder). Its body is `mdstorage.convert` plus `page_footer` (source `_bmad-output/engagements/ENG-NNN/closeout.md`), skipped when the footer hash and version match.
   - The record gets `closeout {path, page {id, url, version} | null, outcome, done: n, not_done: n, run_id, at}`, merged alone into a fresh read. A project with no Confluence binding writes the file with `page: null` and a note, not a refusal.
   - The result is `{status, engagement, outcome, page, written[]}`. The refusals are `NoScope`, `EngagementRecordUnreadable` and `CloseoutInputInvalid`; a transient failure carries `retry: true`.
6. **CAP-16: `revise` mid-run** (`named placeholder rule`, per the 32-6 replan "reuse launchStopGraceful as the cap does"). `runStep` step 4 also covers state `scoping` while any linked run of any cycle is live. Each live engine is stopped gracefully with reason `revise`, and a still-queued one is cancelled (`cancelQueued` with reason `revise`), once per engine as the cap's stops are. The engine finishes its current story and stops. There is no resubmit: a re-approval starts a new cycle. Neither the closeout pass nor `run-ended` runs for a record in `scoping`.
7. **CAP-16: `follows`** (`named placeholder rule`, per CAP-1's deferred entry, 32.1 plan Settled shape 5).
   - `POST /engagements` accepts `follows?: string` matching `ENGAGEMENT_ID_RE`. Anything else is 400 SchemaError.
   - It must name a record in the same served project: else 404 `UnknownEngagement {engagement}`. That record must be `delivered`: else 409 `FollowsNotDelivered {engagement, state}`.
   - The new record carries `follows: "ENG-NNN"` (an optional field, present only when given), starts in `intake` and gets its own quote by the normal flow. The previous record is never touched.
   - The contract's 0.1.27 clause names the field and both refusals.
8. **CAP-16: `question`** (`named placeholder rule`). The table's self-loop applies and logs `{verb: question, payload {text}, source}` with no state change and no pass. "The planner's next turn answers": the `tk-studio-engage` reply step reads the record's newest owner `question` line newer than the planner's last chat line and answers it in that reply. No turn is minted and no chat-line field is added.
9. **The contract** (`named placeholder rule`). Add one `0.1.27 (Story 32.8) adds to this same entry …` clause after 32.7's, with no `**0.1.28**`. Append "Story 32.8" to the Story/rulings row in 32.7's shape. Add `closeout` to the §2 `tk-studio-engage` row. The state table subsection stays as it is. Add one 32.8 pin.

## Risks and open decisions
- **Oversize.** The plan lists 16 files, past band L (`budget-bands.yaml`). The reason is that the story spans the supervisor pass, the lib verb, the routes, the contract and the kb. Halt blocked if the Files list must grow.
- **Served root after merge (DW-46).** The served root is not pulled after a PR merges, so a landed spec may exist only in the run's worktree. `findSpec(run.worktree ?? root, key)` covers a kept worktree, and an archived one reads as `spec_status: null`, so the report shows "not landed". Record any such case; never pull the served root here.
- **Only the first epic is queued (32.6).** A multi-epic scope reports the later epics' deliverables "not done — epic not run" until EP-33 queues them. That is expected, not a defect.
- **No shared `engagement.yaml` lock.** Every write is a fresh read with merge-only fields: `closeout` in the lib, the state through `applyEvent` in `writeFresh`.
- **Signal judgement.** Settled shape 3 is mechanical (the stories landed and the PRs merged). Whether the signal holds in substance is the attended first engagement's human read, recorded in `kb/engagement-loop.md`.
- **A cancelled engagement** (the owner's `cancel`, terminal) gets no closeout. `applyEvent` refuses a terminal record, and AC1 is given `in-progress`. A report for it is EP-33's call.
- **Live Atlassian, `gh` and the notifier** are fakes in every test (`unverifiable-here` until the attended first engagement).
- **Block If** a `TRANSITIONS` row must change (a `run-ended` from `paused`, say). HALT: that is a §7.1 change needing `bmad-correct-course`.
- **Block If** the closeout needs a field on the chat line, a new route, or a contract version beyond 0.1.27. HALT, naming it.
