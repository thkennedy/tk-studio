## Intent
The owner talks to the studio about one engagement through the supervisor's own chat route (design spec §6.4, D2). The route appends the owner's line to the engagement's `chat.jsonl` and queues a one-shot host-tier `engagement-chat` run. That run is a `claude -p` session of the planner leg driven by the new plugin surface `tk-studio-engage`. The session reads the record, the chat, the plan, `kb/` and `kb/confluence/`, and writes its reply with `engage.py reply`. The reply may carry `proposals[]` (buttons the owner presses later through 32.1's inputs); the planner itself moves nothing. The chat is readable as JSON or as a live stream with the office stream's conventions, and scoping is metered into `spend.planning_usd`.

## Acceptance Criteria
- AC1: **Given** an engagement that is not terminal **When** `POST /chat/{engagement} {message}` arrives (the bearer or a cookie with `X-CSRF-Token`; the body at most 32 KiB UTF-8) **Then** the message is appended to `_bmad-output/engagements/<id>/chat.jsonl` as `{seq, at, author: owner, body}` and the supervisor queues one run of the shipped job `engagement-chat` (one-shot; host tier; the planner leg's model and effort from the project's routing, passed at enqueue as `validate-resolution`'s are; payload `{engagement, seq}`; `guards.max_turns` 80, `max_wall_clock_seconds` 1800): a `claude -p` session on the host in the served project's root with the plugin, driven by the new contract surface `tk-studio-engage` (`lib/engage.py`), which reads the record, the chat so far, the plan under `_bmad-output/planning-artifacts/`, `kb/` and `kb/confluence/` and writes the reply with `engage.py reply` as `{seq, at, author: planner, body, run_id, proposals[]}`; the run's `job-run` event carries the cost like any run and the record's `spend.planning_usd` sums it (scoping is metered; the quote says so, 32.5); the answer is 200 `{ok, engagement, seq, run_id}`; a message sent while a chat run is live is queued behind it on the checkout lock, never refused; a terminal engagement is 409 EngagementClosed
- AC2: **Given** the chat **When** `GET /chat/{engagement}?since=<seq>` is read (JSON, or `Accept: text/event-stream` with the office stream's id, replay and heartbeat conventions) **Then** the lines after `seq` are returned and the planner's reply reaches an open stream without a reload; a `proposals[]` entry is `{verb, payload, label}` (an input the planner suggests, which the web renders as a button and the owner sends through 32.1: the planner itself has no bearer and no CSRF token and moves nothing); the chat session's environment is a worker's (`buildWorkerEnv`: every `TK_SUPERVISOR_*` secret and the owner seat stripped); `bun test` covers the append, the queueing behind a live run, the stream and the refusals with a fake planner; the lib suite covers `engage.py reply` (the memory it assembles, the reply line, the proposal shape) with a fixture project

## Settled shape
1. CAP-4 — the record's serialization (every later `engage.py` verb reads it): `named placeholder rule`. `writeEngagement` (and the counter mint's record write) serializes `engagement.yaml` as JSON text (`JSON.stringify(record, null, 2) + "\n"`), which is a YAML 1.2 document, so `readEngagement`'s js-yaml load is unchanged. Stdlib cores read it with `json`; a record that is not JSON is `blocked` `EngagementRecordUnreadable` in `engage.py`. The plan counter stays block YAML (plansync's miniyaml reads it). Per `driver-contract.md` (stdlib-only cores) and `plugins/tk-studio/lib/miniyaml.py` (the subset refuses lists of mappings). SPEC.md bullet appended.
2. CAP-4 — the chat run's queueing and payload (32.3 and 32.8 queue further turns; 32.6 and 32.8 read the costs): `named placeholder rule`.
   - `queue.enqueue` takes an opt-in `stack: true` that mints even while a run of the same (job, checkout) is live. The new run waits on the checkout lock in `claim`; it is never refused or adopted.
   - The run's payload is stored per run as the `enqueued` event's `detail.payload`, `{engagement, project, seq}`. The run-start overlay (`withStoredPayload`/`withQueuedPayload`, generalised) delivers it plus the driven run's own `run_id`.
   - A `chat-queued` service event `{engagement, project, seq, run_id, model, effort}` follows each mint.
   - Per `_bmad-output/planning-artifacts/epics.md` Story 32.2 AC1 ("queued behind it on the checkout lock, never refused") and `apps/supervisor/src/queue.ts` `enqueue`/`claim`.
   - SPEC.md bullet appended.
3. CAP-4 — `chat.jsonl` (32.3, 32.7 and 32.8 read and write it): `named placeholder rule`. One JSON object per line. Owner lines are `{seq, at, author: "owner", body}`; planner lines are `{seq, at, author: "planner", body, run_id, proposals[]}`. `seq` is an int that grows by 1 from 1 and is unique per file. Both writers (the supervisor and `engage.py`) take `chat.lock` (exclusive create in the engagement directory, stale after 30 s), re-read the last `seq` inside it, and append one line. A body is at most 32 KiB UTF-8. Per Story 32.2 AC1-AC2 and 32.1 Settled shape 1 (`chatPointer.last_seq`). SPEC.md bullet appended.
4. CAP-5 — a proposal (32.7 renders it): `named placeholder rule`. `{verb, payload, label}`, where `verb` is one of 32.1's six input verbs, `payload` is that verb's typed payload as 32.1 Settled shape 3 defines it (checked in `engage.py` with the same rules; an invalid one is `blocked` `ProposalInvalid` naming the index), and `label` is a non-empty string of at most 80 characters. A proposal is never applied by anyone but the owner sending it. Per Story 32.2 AC2 and 32.7 AC1. SPEC.md bullet appended.
5. CAP-4 — `spend.planning_usd`: `named placeholder rule`. At each `finally` site a chat-spend pass sums the ledger `job-run` `total_cost_usd` over every run named by the engagement's `chat-queued` events (a run without a `job-run` line yet counts 0, a later pass corrects it) and rewrites the record atomically when the sum changed. The pass emits no `engagement` event (the state does not move). Per Story 32.2 AC1 and Story 32.5 AC1 ("whether scoping was billable"). SPEC.md bullet appended.

  - `engage.py`'s memory is an index, not a dump.
  - The three released-roster guard failures (Verify 1).
  - The record files stay untracked in the served root (SPEC Open Question 3).
