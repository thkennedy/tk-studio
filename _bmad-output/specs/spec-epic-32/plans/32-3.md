## Intent
When the planner's turn finds gaps that a default cannot cover, it asks at most three multiple-choice questions, each with a default. The supervisor applies them from the file the planner wrote, which moves the state `intake → awaiting-answers` (32.1's event row `questions`, source `planner`). It then blocks one Jira issue per engagement, so the questions land in the owner's inbox and the office shows the "!" bubble. The owner can answer from Jira, from the Issue screen, or from the Chat screen's cards. Answers land in `questions[]`. Once every question is answered, the state moves to `scoping` and the issue goes to `Done`. A `go` turns the open questions' defaults into stated assumptions. Nothing moves on a timer (F2 step 2; B5 item 2).

## Acceptance Criteria
- AC1: **Given** an engagement in `intake` whose planner turn finds gaps a default cannot cover **When** the planner writes `engage.py questions` (at most three, each `{id, text, options[] with exactly one default, impact}`; a fourth is refused by name) **Then** `questions[]` fills, the state moves `intake → awaiting-answers` by a `question` input the supervisor applies on the planner's behalf from the written file (the one exception to "the owner sends every input", recorded with source `planner` and the run id), one Jira issue per engagement (`ENG-NNN: questions`, issue type Task, in the project's Jira project) is created or updated through the planning adapter and moved to `Blocked - Awaiting User` with the questions as a comment that @mentions the owner (31.5's `track.py block` path, extended with `--engagement`), the sync-back's inbox lists it (the item carries `engagement: ENG-NNN`), and the office shows the "!" bubble on the planner's desk
- AC2: **Given** the owner's reply on the issue (31.6's Issue screen, Jira itself) or the Chat screen's answer cards **When** the sync-back pulls the comment, or `POST /engagements/{id}/input {verb: answer, answers: {<id>: <option>}}` arrives **Then** the answers land in `questions[].answer` (a comment is parsed as `<id>: <option>` lines, a free-text answer is kept verbatim for the planner to judge), the issue moves to `Block Resolved` and on to `Done` (no validation leg for a question: the planner's next turn judges the answer), and the state moves `awaiting-answers → scoping` once every question has an answer; `go` with questions open converts each unanswered question into its default as a stated assumption in `assumptions[]` (named on the scope page) and moves on; nothing moves on a timer; the lib suite and `bun test` cover the cap, the issue and the inbox item, the two answer paths and the assumptions with fake Atlassian REST

## Settled shape
1. CAP-6 — `questions.json`, which the planner writes and the supervisor applies: `named placeholder rule`. The file is `_bmad-output/engagements/<id>/questions.json` = `{run_id, at, questions: [{id, text, options: [{label, default?: true}], impact}]}`.
   - 1 to 3 questions.
   - `id` matches `^[a-z0-9][a-z0-9-]{0,15}$` and is unique.
   - `text` and `impact` are non-empty strings.
   - 2 to 6 options, each `label` non-empty and unique, and exactly one option with `default: true`.
   - `engage.py questions` writes it atomically. The supervisor applies it once per `run_id` through `applyEvent` event `questions`.

   Per Story 32.3 AC1 and 32.1's `defaultOf` (`engagement.ts:240`). SPEC.md bullet appended.
2. CAP-6 — the engagement's Jira issue and its comment: `named placeholder rule`.
   - One issue per engagement, found by the exact summary `ENG-NNN: questions` in `planning.jira.project_key` (issue type `Task`, label `tk-studio-engagement`) and created when absent. No local file is written.
   - The block comment is `[~accountid:<owner>] Blocked: ENG-NNN needs <n> answer(s)`, then `Resolves when: reply with one "<id>: <option>" line per question`, then one block per open question: `<id>: <text>` (`Impact: <impact>`), followed by its options as `- <label>`, with ` (default)` on the default.
   - `track.py close` moves the issue to `Block Resolved`, then to `Done`.

   Per Story 32.3 AC1-AC2, `track.py` 31.5 comment rule and `inbox.py` `BLOCK_COMMENT_RE`. SPEC.md bullet appended.
3. CAP-6 — the inbox item's engagement and the planner's "!": `optional entry`.
   - An `inbox.json` item whose summary is `ENG-NNN: questions` carries `engagement: "ENG-NNN"`.
   - The office's `planner` agent row gets `blocked_issue {issue, state}` from the first `open` item that carries `engagement`, with or without a run.
   - The resolution pass never queues `validate-resolution` for such an item.

   Per `driver-contract.md` §1 (`blocked_issue`, the "!" follows it alone) and the design spec README "a persistent "!" bubble on the desk whose work is blocked". This settles SPEC Open Question 4. SPEC.md bullet appended.
4. CAP-6 — a Jira comment read as answers: `named placeholder rule`.
   - Each line of an owner comment after the newest agent comment that matches `^\s*([a-z0-9][a-z0-9-]{0,15})\s*:\s*(.+?)\s*$`, with a known open question id, is an answer.
   - The value is the option `label` when it equals one, case-insensitively and trimmed. Otherwise it is the text verbatim (for the planner to judge).
   - It is applied as `answer` with source `supervisor`, once per comment id.
   - Unparsed lines are ignored. A comment with no parsed line, or with questions still open, re-blocks the issue with the remaining questions.
   - A chat-card answer (`POST /engagements/{id}/input`) stays source `bearer`/`cookie`.

   Per Story 32.3 AC2 and 32.1's `InputSource` (`engagement.ts:43`). SPEC.md bullet appended.
