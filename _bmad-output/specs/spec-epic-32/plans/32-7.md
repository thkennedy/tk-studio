## Intent
Every engagement surface exists on the supervisor (32.1–32.6): the record and its typed inputs, the chat route and its stream, the questions, the scope page, the quote and approval. The web has none of it, so today an engagement is only reachable from a terminal. This story adds the Chat screen to the studio web (React DOM, a sixth screen in the switch). It lists the engagements, shows the open one's transcript live, and sends each typed input the table allows. The nav carries a count of the engagements that need the owner (§6.3 Chat; F2).

## Acceptance Criteria
- AC1: **Given** `GET /engagements`, `GET /chat/{id}` and the typed inputs **When** the Chat screen renders **Then** it lists the project's engagements by state with the open one's transcript (owner and planner lines, the planner's run cost on hover), a message box (`POST /chat/{id}`), the state as a stepper (`intake … delivered`, the side exits marked), the questions as cards with their options and defaults (an answer sends `answer`), the scope page's link and a **Revise** box (sends `revise`), the quote as the band (50/85/95 as share and dollars, the cap, the autonomy levels) and an **Approve** control with the autonomy choice (sends `approve`), **Go** and **Cancel** where the table allows them, and a planner `proposals[]` entry as a button sending exactly that input; a **New engagement** form (`POST /engagements`); the nav gains Chat, and an engagement in `awaiting-answers` or `quoted` puts a count on it; the web sends the CSRF token as the inbox reply does; the stream keeps the transcript live and the watchdog on `visibilitychange` reconnects it on the iPad
- AC2: **Given** the screen **When** it is tested **Then** vitest covers the stepper, the cards, the quote, each action and the refusals' rendering with a fixture; the studio-web gate stays green

## Settled shape
SPEC.md was not appended: the gate session's write surface excludes it. The dev session records each of these shapes in its spec.
1. **CAP-14, the planner's run cost on hover** (`optional entry`). `GET /runs/{id}` gains `cost_usd: number | null`. The value is the ledger `job-run` `total_cost_usd` for the run's `studio_run_id` (`inbox.ts runCost`), and null while there is no studio run id or no metered line. The change is one `0.1.27 (Story 32.7) adds to this same entry …` clause after 32.6's, with no `**0.1.28**`, plus a 32.7 pin. The web fetches it lazily: once per planner line's `run_id`, on the first hover or focus, cached per run, and `not metered` when null (the Issue screen's `costText`). No field is added to the chat line (32-2 replan).
2. **The engagement's served project and CSRF** (`named placeholder rule`). Every engagement read and post carries `?project=<id>`. The CSRF token is the `GET /inbox?project=<id>` answer's `X-CSRF-Token` for that project, read again when the project changes. With no token, every send is disabled (`canAct`).
3. **The actions per state** (`named placeholder rule`). `chat/model.ts` exports `ACTIONS: Record<state, verb[]>`, mirrored from `TRANSITIONS`' verb cells (event rows excluded). Its tests pin the cells exactly: `go` in intake, awaiting-answers, scoping and partial (with `{cap}` in partial); `revise` in scoping, quoted, approved, in-progress, paused and partial; `approve` in quoted; `answer` in awaiting-answers; `cancel` and `question` in every open state; nothing in a terminal state. A button outside its cell is never rendered, and a proposal whose verb is outside the cell renders disabled, naming the state. A 409 `IllegalInput` renders `{state, verb}`.
4. **The stepper** (`named placeholder rule`). The main path is `intake → awaiting-answers → scoping → quoted → approved → in-progress → delivered`. The side exits `paused`, `partial`, `failed` and `cancelled` are marked against the step they left. That step is the newest `inputs[]` line's `from` when its `to` is the side exit, else the closest main step.
5. **The nav count** (`named placeholder rule`). The count is the number of office `engagements[]` rows (snapshot + `office.engagement` deltas) whose `state` is `awaiting-answers` or `quoted`, across projects. Null shows no count, as the Inbox does.
6. **The remembered engagement** (`named placeholder rule`). `tk-studio.web.chat` = `{project, id}`, as `rememberedIssue`.
7. **Approval copy** (32-6 replan). The Approve control sends `{verb: approve, autonomy, base_ref?}` (`base_ref` only when the field is non-blank). `approved` reads "approved; the run starts when the plan PR merges". No PR link is shown, because the record carries none. `partial` shows `runs_usd` against `quote.cap`, with **Go** taking a positive `{cap}` figure (it replaces the cap). `paused` says "reply `continue` on the engagement's Jira issue", since there is no web verb for it.

## Risks and open decisions
