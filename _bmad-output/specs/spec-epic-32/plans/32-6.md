## Intent
In `quoted`, the owner's one `approve {autonomy, base_ref?}` already moves the record to `approved` (32.1's `record-approval`). Nothing yet does what approval means. This story builds the supervisor's approve pass on the host in the served root:
- append the scope's proposed epics and stories to `epics.md`
- run `plansync normalize` and `sync`
- declare the `run-epic-N` job
- open one commit on `engagement/ENG-NNN` as a PR
- queue the first run

It also wires the run-driven rows (`launched`, `cap`, and `run-paused`/`run-resumed` for `ask`), sums `spend.runs_usd`, and pauses the work at the cap for the owner's decision (F2 step 5; B5 item 5; CAP-12, CAP-13).

## Acceptance Criteria
- AC1: **Given** `quoted` **When** `POST /engagements/{id}/input {verb: approve, autonomy: ask | steady | full, base_ref?}` arrives (the bearer or a cookie with `X-CSRF-Token`; nothing else approves: no chat line, no planner proposal, no timer) **Then** the supervisor runs on the host in the served root: the scope's proposed epics and stories appended to `epics.md` as `## Epic N` sections carrying `engagement: ENG-NNN`, `plansync normalize` (the EP- and ST- entities, the index, the backlog mirrors), `plansync sync` (the promote to Jira with the design pages' links), the engagement's `run-epic-N` job declared under `.tk-studio/jobs/` and in `.tk-studio/config.yaml`'s `jobs` (the placement from the project's default worker placement), one commit on a branch `engagement/ENG-NNN` opened as a PR (main is protected: the plan change is reviewed like any change; the run cuts from `base_ref` when given, else from main once the PR merges, the supervisor queuing it on the merge as the plan pull-back watches today); `autonomy` and `approved_at` are recorded, the state moves `quoted → approved`, and `approved → in-progress` on the first run's `launched` event; `ask` = a graceful stop after every story and a `question` to the owner before the next, `steady` = one story per run, resubmitted by the supervisor on each merge, `full` = the epic end to end
- AC2: **Given** `in-progress` **When** runs end **Then** `spend.runs_usd` sums the engagement's runs' `job-run` costs and the board draws the band against it; at the cap the supervisor stops the live run with a graceful stop, marks the engagement `partial`, blocks its issue (the inbox) with the figures, and waits for `go` (`{cap}` raises it by the owner's figure, back to `in-progress`) or `cancel`; `bun test` covers the approve path with a fake adapter (what is written, the PR, the job, the three autonomy levels, the cap) and every refusal

5. **CAP-12, the job's placement** (`named placeholder rule`).
   - The approve pass declares the job in the repo only (the job file plus the `jobs:` id). It never writes `TK_SUPERVISOR_CONFIG`, which is outside the repo and which the supervisor never writes.
   - At enqueue, placement resolves as for any job (`jobPlacement`). When the config has no `<project>/run-epic-N` entry, "the project's default worker placement" is the placement of the project's highest-numbered `run-epic-*` entry in that config, else the host tier.    - Per Story 32.6 AC1 and `config.ts jobOptions`. SPEC.md bullet: not appended (as 1).
6. **CAP-13, spend, the band and the cap** (`named placeholder rule`).
   - **`spend.runs_usd`:** an `engagementRunSpendPass` beside `chatSpendPass`, at the same three `finally` sites with the same mapping. It sums `job-run` `total_cost_usd` over the runs named by `engagement-run-queued`, merges only `spend.runs_usd` into a fresh read, and never throws.
   - **The band:** at step `job` the pass re-keys `budget-bands.yaml` (32-5 replan). The predicted `basis.epics[].ep_id` usd moves to the minted EP id in `epic_bands_text`'s byte shape, which a lib test literal pins. A `null` `ep_id` writes no band and is named in the step's detail.
   - **The cap:** when `spend.runs_usd >= quote.cap` on an `in-progress` record:
     - call `launchStopGraceful` on the live linked run
     - `applyEvent(cap)` → `partial`
     - block the engagement's one issue with the figures (`runs_usd`, `cap`, `band85.usd`, `band95.usd`, and "reply with `go {cap}` from the web or the API, or `cancel`")
     - send one notifier line.
   - **After the cap:** `partial + go {cap}` (`raise-cap`) is the owner's existing input. The approve hook then resubmits the job. `cancel` stops the live run gracefully.
   - **The block:** `track.py block --engagement` gains `--kind questions|cap|ask` (default `questions`, today's behaviour). `cap` and `ask` need no open questions, and their comment keeps the 31.5 prefix `[~accountid:<owner>] Blocked: ENG-NNN …`. The `engagement-issue {action: blocked}` event carries `kind`, and `questions.ts closeStep` closes only a `questions` block.
   - Per Story 32.6 AC2, SPEC CAP-6 note "the engagement's Jira issue", and `engagement.ts raise-cap`. SPEC.md bullet: not appended (as 1).
