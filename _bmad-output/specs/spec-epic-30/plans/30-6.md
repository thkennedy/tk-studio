## Intent
The web becomes the home. A signed-in `GET /` answers the built web's `index.html`, the Office opens by default, and the last screen is remembered per browser. The read-only page moves to `GET /status`, stays the no-JavaScript fallback, and is linked from a new Status screen. That screen shows the queue, the live runs, the agents and the office section from what the web already reads, and refreshes from the store. Contract §1, runbook §4, the supervisor README and the status page's tests follow the new address (§6.3; AD-2: supervisor surfaces only).

## Acceptance Criteria
- AC1: **Given** the web built and the account signed in **When** `GET /` is requested with a session **Then** the supervisor answers the web's `index.html` (the Office screen opens by default; the last screen is remembered per browser) and the read-only page moves to `GET /status`, linked from the web's Status screen and answered without JavaScript as today; with no session, `GET /` is the sign-in page; the bearer API and every `/jobs`, `/runs`, `/agents`, `/office` and `/board` route are unchanged
- AC2: **Given** the Status screen **When** it renders **Then** it shows the queue's counts and live runs, the agents, the office section, the ledger's last events and the supervisor's version, each from the surfaces the web already reads (no new surface), and refreshes from the store rather than polling
- AC3: **Given** the move of the home **When** the story closes **Then** the contract's §1 names `GET /status` as the read-only page's address and `GET /board` among the web surfaces (0.1.25, additive), the runbook §4 and the supervisor README say the web is the home and how to build it, and the status page's tests and the conformance suite's status drive follow the new address

## Settled shape
Planner rulings on the route and the per-browser memory. No design document constrains them beyond the AC. They are not appended to SPEC.md, because the gate's write surface excludes it (the 30-4/30-5 precedent).
- **`GET /status` by content negotiation.** AC1 asks for the page at `/status` and for the bearer API to be unchanged, and the bearer API already answers JSON there. So:
  - A `GET /status` whose `Accept` names `text/html` (a browser navigation) answers the page (`page(csrf)`, as `/` does today).
  - Any other `Accept` (curl's `*/*`, none, `application/json`) answers today's JSON, byte for byte. This holds for bearer and cookie alike.
  - With no session, an HTML `GET /status` answers the sign-in page with `next=/status`; a non-HTML one stays 401 JSON.
  - Answers vary on `Accept`, so add `vary: Accept` to both answers on `/status`.
- **`GET /`.** With a session (cookie or bearer) and the web built, it answers `index.html` exactly as `GET /app` does. With no built web, it answers the read-only page as today, with its "not built" note, so the home is never a 503. With no session, it is the sign-in page, unchanged.
- **The remembered screen.** Key `tk-studio.web.screen`, values `office` | `board` | `status`. Absent, unknown or storage throws → `office`. Storage is injectable, modelled on `rememberedProject`.
- **The Status screen's link** is the absolute `/status`, a plain `<a>` (the `<base href="/app/">` makes a relative link wrong).
