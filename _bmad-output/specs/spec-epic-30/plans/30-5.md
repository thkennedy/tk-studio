## Intent
The supervisor gains `GET /board?project=<id>` (AD-2, a supervisor surface). It reads the served project's plan directory (epics and stories with canonical statuses), the queue's runs (each story's latest run with its state, PR and host-verify outcome), the open deferred-work entries that name a story, and the ledger's metered `job-run` spend per epic against an optional per-epic band in `.tk-studio/budget-bands.yaml`. The web gains a Board screen built from that answer: phased bars per epic, a findings count, a spend bar, and a Needs-you / Working / Done triage of the project's runs. Contract §1 names `/board` by appending to 30.4's existing 0.1.25 entry, with no second bump.

## Acceptance Criteria
- AC1: **Given** the plan directory of a served project (`_bmad-output/planning-artifacts/plan/`, the index and the entities) and the queue's runs and PRs **When** a consumer reads `GET /board?project=<id>` (a new supervisor surface, AD-2, named in the contract's §1 web surfaces at 0.1.25) **Then** the answer lists the epics with their stories and canonical statuses, each story's latest run (state, PR, host-verify outcome) when one exists, the open deferred-work entries that name the story (the findings), and per epic the metered spend from the ledger's `job-run` events against the epic's band when `.tk-studio/budget-bands.yaml` names one; the answer is cached per plan-directory mtime and rebuilt on change; a project with no plan directory answers an empty board with the reason
- AC2: **Given** the board **When** the Board screen renders **Then** epics are rows of phased bars whose segments are their stories coloured by status, the findings count drains as entries close, the spend bar sits against the band, and three columns triage every live run: Needs-you (paused, awaiting a ruling, a red host leg), Working (running), Done (ended today); each item links to the run's PR and names the ruling it waits for when there is one
- AC3: **Given** the screen **When** it is tested **Then** `bun test` covers the board surface from a fixture plan directory and queue (statuses, findings, spend, the cache), and vitest covers the rows, the columns and the links from a fixture answer

## Settled shape
- **30.5 — the per-epic band: optional entry**, per SPEC Assumptions ("an optional per-epic entry in `.tk-studio/budget-bands.yaml` whose shape the planner settles for 30.5; absent, the spend bar shows the spend alone") and the design spec README §6.3 / §7.1 (the quote band is EP-32's, so this is a plain figure).
  - The shape is a top-level block mapping keyed by the plan's epic id, `epics:` → `EP-030:` → `usd_estimate: <number>`, the same field name as the story bands.
  - Absent, malformed or non-positive, the band is `null`.
  - The dev session documents the shape in the supervisor README and adds no entry to the tracked yaml: the figure is the operator's.
  - Not appended to SPEC.md, because the gate session's write surface excludes it (the 30-4 plan's precedent).
- **The answer (settled here so 30.6 and the web share one shape):**
  - `{ok: true, project, built_at, plan: {reason?}, epics: [{id, title, status, band_usd: number|null, spend_usd: number, findings: number, stories: [{id, key: "N.M", title, status, findings: [{id: "DW-NN", title, severity}], run: {run_id, state, pr: string|null, host_verify: "green"|"red"|"skipped"|null, ended_at: string|null} | null}]}], triage: {needs_you: [item], working: [item], done: [item]}}`
  - Each triage item is `{run_id, state, story_key: string|null, pr: string|null, ruling: string|null}`.
  - A project with no plan directory answers `epics: []` and `plan.reason` naming the missing path. `triage` is still filled from the queue.
  - A missing `project` parameter answers 400 `ProjectRequired`. A project not in the registry answers 404 `UnknownProject`.
- **The triage rule:**
  - Every live run of the project goes in exactly one column.
  - Needs-you: `paused`, or the latest ruling event is `awaiting-ruling`, or the latest `host-verify` is red. `ruling` is the awaiting reason, else the pause reason.
  - Working: the other live runs (`running`, `queued`, `external`).
  - Done: terminal runs whose `ended_at` falls on the supervisor host's local day (SPEC Assumptions), from an injected `now`. A terminal run ended today with a red host leg goes in Needs-you instead.
- **The cache:**
  - The plan part is cached on a signature of the plan directory's `mtimeMs` plus each entity's `(mtimeMs, size)`. That is a superset of "per plan-directory mtime", because an in-place edit does not move a directory's mtime.
  - The findings are cached on the deferred-work file's `(size, mtimeMs)` and the spend on the ledger's. Runs and triage are composed on every request.

## Risks and open decisions
- **oversize.** This plan has thirteen Files entries plus a fixture folder, against L's "larger, with a stated reason". The reason is that the AC spans a supervisor surface, a contract append and a web screen. Halt `blocked` if the Files list grows past these thirteen entries and the fixture folder.
- **No second bump.** 0.1.25 is 30.4's entry. Appending to it is a score-2 DRIFT only if the 30.4 text must be reworded, which it must not be.
- **No new web surface beyond `/board`.** The web never reads `GET /runs/{id}` or `GET /jobs`, and the triage data comes from the `/board` answer.
- **The spend's attribution.** `job-run` carries no epic field, only `job_id`. A run whose job id is not `run-epic-N` counts toward no epic. Record such a run's spend under the answer's top level only if a test pins it; never guess an epic.
- **Plan-owner transcription.** `planOwner` (planstatus.ts:138) can resolve another registry project's plan for a transcribed `epics.md`. The board reads the served project's own plan directory, as AC1 says. Leave the transcribed case as the "no plan directory" answer, and record a DRIFT if a test demands otherwise.
- **The sandbox refuses symlinks**, so verify bun in a /tmp copy. The host leg is binding. A new web dependency (none expected) regenerates `bun.lock`.
- **unverifiable-here.** The attended look of the bars, the columns and the links on a desktop and the iPad, and a live board against the box's real plan, queue and ledger.
