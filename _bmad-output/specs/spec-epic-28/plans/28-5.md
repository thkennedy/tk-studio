## Intent

The supervisor identifies a checkout by its project root (`checkoutKey`, `queue.ts:125`). Two runs therefore never wait on each other: one on `apps/supervisor`, one on the repository root, though they are one git checkout. A run of a nested project also cuts a worktree of the whole repository and serves its top level (DW-25). The approach has two parts:

- Resolve the root's git top-level and prefix once per submission and record both on the run.
- Key only the lock by the top-level. Serve `<worktree>/<prefix>` wherever the run acts as the project, and keep the worktree top level for the git motions.

This is TypeScript under `apps/supervisor/src`, plus runbook §4 and the root deferred-work ledger (CAP-16, both correct-courses of 2026-10-17).

## Acceptance Criteria

AC1. **Given** a project whose registered root is nested inside a git checkout (`apps/supervisor` under `C:\GitHub\tk-studio`) **When** a run is enqueued, claimed, or looked up as live (`checkoutKey`, `enqueue`, the locks table, the live-run and lock lookups in `queue.ts` and `cli.ts`, the sandbox probe in `sandbox.ts`) **Then** the lock's key is the canonical, case-folded git top-level of the root (`git rev-parse --show-toplevel`, resolved once per submission and recorded on the run), never the project root itself; a root that is not inside a git checkout keys by itself, as today; the lock row and the status page still name the project root that holds it

AC2. **Given** a queued run for the nested project and a queued run for the repository root **When** `drain` or a tick claims one **Then** the other waits on the same lock (`holder` names the first run) and the two never run at once; `bun test` from `apps/supervisor` pins it with a nested fixture, the case-folded spelling included on win32

AC3. **Given** a project whose registered root sits below its git top-level (`apps/supervisor`) and a run the supervisor prepares for it **When** the worktree is cut and the run is invoked (`prepareWorktree` and the invocation root in `apps/supervisor/src/worktree.ts` and `cli.ts`; DW-25) **Then** the root the run serves is `<worktree>/<prefix>` with the prefix from `git rev-parse --show-prefix` of the project root (the worker's cwd, `payload.directory`, the sbx VM path, the `verify.host` read at the run's base), never the worktree's top level; a project at its git top-level is unchanged; `bun test` from `apps/supervisor` pins both cases

AC4. **Given** runbook §4 and the deferred-work ledger **When** the story closes **Then** §4's lock row says the lock is per git checkout and names the served subpath; DW-25 is closed; and 28.3's AC2 (the serialisation) and AC3's live clause (the project served) are satisfied by reference to this story *(widened by the second correct-course of 2026-10-17)*

**The ruling that shapes the change (planner): the lock key is not the job identity.** `runs.checkout` and `jobs.checkout` are also the job's identity. Consider `jobs` PK `(job_id, checkout)` (`queue.ts:584-588`), the unique index `runs_one_live (job_id, checkout)` (`:600`), and `enqueue`'s adopt-the-live-run lookup (`:1019-1027`). If `checkout` became the git top-level, a `studio-health` run for `apps/supervisor` and one for the repository root would be the same job. The second would be adopted, not left waiting, which breaks AC2's "the other waits … `holder` names the first run". So:

- Keep `checkout` as the project-root key.
- Add a run column for the lock key: name it, for example `lock_checkout` (canonical, case-folded top-level, or the root's own key when not in git).
- Add a run column for the prefix (`git rev-parse --show-prefix`, `""` at the top).
- Point every `locks` read and write at the run's lock key. AC1's "recorded on the run" is these columns.

## Risks and open decisions

- **Oversize.** 13 files, 7 of them source, is past band L. Per the bands, more than L goes to `bmad-correct-course`, which is the operator's call and is not split here. The dev session halts if the Files list grows past this list.
- **Block If: the lock key and the job identity cannot be separated without changing `jobs`/`runs_one_live`.** Say the dev finds the new column cannot carry the lock without changing the job identity key. Do not re-key `checkout`, because that makes the nested and root runs of one job adopt each other, against AC2. HALT and consult.
- **Block If: a driver-contract or conformance-schema surface changes.** The run columns are supervisor-internal queue state, and `/status` adds no field the contract pins. If the status payload has to change shape, that is a contract change (AD-19), so HALT.
- **Migration of live rows.** Rows minted before the column exists have a null lock key. Their lock sites fall back to `checkout`, which is the old behaviour. Pin the fallback with one test so that an upgrade with a held lock never orphans it.
- **The resume and engine-end paths are the easy misses.** `cli.ts:1701`, `sweepEngines`, `closeout.ts` and `lookupEnginePid` each read `run.worktree` as the project. Miss one and a nested run silently reads the outer `.bmad-loop`. The AC3 tests should cover the sweep, not only the first invocation.
- **The `git` read at submission is a new process on the submit path.** Bound it (short timeout, argv only). A failure keys by the root, never refuses the submission.
