## Intent

The sandbox's Claude login is the one monthly chore that blocks every sandbox run, and today it fails silently: hole 69's only signal is a console claim refusal, and the renewal is a terminal exchange inside the sandbox (`sbx run`, `/login`, `/exit`; TKSTUDIO-233 is the current reminder). This story gives the login a clock and a renewal button. In order:

- **The read.** `GET /sandbox/login` runs the Max-login preflight's own probe plus one `cat` of the sandbox's credential file. It answers the login's two expiries and a state (`ok`, `expiring` at three days or fewer, `expired`, `unknown`).
- **The renewal.** `POST /sandbox/login/start` and `POST /sandbox/login/code` drive the installed `claude auth login` in a detached tmux session inside the sandbox. A ten-minute `sandbox-login` lease keeps the claim gate off that sandbox while it runs. The code reaches the login through tmux's stdin buffer and never travels on an argument.
- **The card.** The Settings screen's Sandbox login card shows the clock and does the two-step renewal: Open sign-in, then paste the code.
- **The Task.** The drain pass mints one `tk-studio-owner` Jira Task, three days out, keyed by the expiry. The pass that reads the renewal moves it to `Done`.

The contract grows additively at 0.1.35 (Story 39.1 opens the bump). The runbook's hole-69 row reads fixed, and TKSTUDIO-233 is recorded there as the last manual renewal.

### CAP-5's open question, settled on this host's `claude` 2.1.319 (read-only; no login was run)

`claude auth login` **is a non-interactive CLI subcommand**, not only the REPL's `/login`:
- `claude auth --help` lists `login [options]`, `logout` and `status [options]`.
- `claude auth login --help` takes `--claudeai` (the subscription, the default), `--console`, `--email <email>` and `--sso`.

Read from the binary's bundled source:
- **It reads the code on stdin.** A `readline` reads `process.stdin`. Each line is `trim().split("#")` into `code#state`, then passed to `handleManualAuthCodeInput`.
- **A line without the `#` part.** It writes `Invalid code. Please make sure the full code was copied.` to stderr. The process **keeps waiting** for another line.
- **The URL it prints is the manual-redirect one.** `isManual: true`, `redirect_uri=https://platform.claude.com/oauth/code/callback`. That page shows the code to paste. The URL is printed in one of two forms:
  - with the localhost callback listener up: `Opening browser to sign in…` / `If the browser didn't open, visit: <url>` / `Paste code here if prompted > `;
  - without the listener: `The browser can't return the sign-in to Claude Code automatically. After you sign in, paste the code shown.` / `Sign in at: <url>` / `Paste code here > `.
- **The authorize base is `https://claude.com/cai/oauth/authorize`** (`CLAUDE_AI_AUTHORIZE_URL`), **not** the AC's `https://claude.ai/oauth/authorize`. The pane pattern matches both (Settled shape 4).
- **A code the token exchange refuses ends the process.** It prints `Login failed: That code wasn't accepted. It may be incomplete, expired, already used, or from an earlier sign-in attempt. Sign in again to get a new code.` and exits 1 (`AuthCodeRefusedError`).
- **Success** prints `Login successful.` and exits 0.
- **stdin closed before a code** exits 130 (`PasteInputClosedError`).

The repo grep (`kb/`, `plugins/`, `apps/supervisor`) finds no `claude auth login` caller. `setup-token` appears only at `driver-contract.md:738` (harness auth). The runbook's hole-69 row (`kb/agent-pc-setup-runbook.md:1616`) names the REPL form. The CLI form is the one this story drives; the REPL form stays the runbook's manual fallback.

tmux behaviour was checked on this host (tmux 3.6, a private `-L` socket, no claude involved):
- `new-session -d -s <name> -x … -y … <argv…> \; set-option -t =<name>: remain-on-exit on` keeps a dead pane readable.
- `capture-pane -p -J -S - -t =<name>:` returns joined wrapped lines from the history's start. Without `-S -`, a dead pane's last output was lost.
- `display-message -p -t =<name>: '#{pane_dead} #{pane_dead_status}'` gives the exit status.
- `load-buffer -b <buf> -` reads stdin.
- `paste-buffer -d -b <buf> -t =<name>:` then `send-keys -t =<name>: Enter` delivers one line to a `read`.

`sbx exec -i` (stdin kept open, docker's `-i`) is the one piece not checked here. `kb/offline-install-runbook.md:536` shows `sbx exec -it`. It is `unverifiable-here` and a Block If (Risks).

## Settled shape

Each item below is the planner's ruling. The SPEC design-note bullets are listed in the return. None of them is a Block If.

### 1. Which sandbox (CAP-4, CAP-5)

**The rule.** `?sandbox=<name>` on `GET`, or `{sandbox}` in `POST /sandbox/login/start`. When the name is absent, the sandbox is the one distinct `jobs.*.sandbox` of `TK_SUPERVISOR_CONFIG` (`configuredSandboxes(cfg, project?)`, new in `sandbox.ts`). `?project=<id>` narrows the candidates to the `jobs."<id>/…"` entries, which is "the project's placement".

**The refusals:**
- no candidate, or several: 400 `SandboxRequired {candidates}`;
- a name outside the config's sandboxes: 404 `UnknownSandbox {sandbox}`. Nothing is ever `sbx exec`ed into an unconfigured name;
- a name not matching `^[A-Za-z0-9][A-Za-z0-9_.-]{0,62}$`: 400 `SchemaError`.

### 2. The read and its answer (CAP-4)

`readSandboxLogin(sb, deps, nowMs)` in `sandbox.ts`. The calls, in order, each with `timeoutS` 30:

1. `sbx ls` through `sandboxRunning`. When the sandbox is not listed as running, there is no `exec`: the answer is `state: "unknown"`, `reason: "sandbox stopped"`. Its other fields come from the latest `sandbox-login-check` event for that sandbox (shape 7), with `checked_at` that event's `at`; with no such event they are null. Nothing is started.
2. The probe: the preflight's argv (`server.ts:852-862`), judged by `judgeAuthStatus`.
3. `["exec", sb, "cat", "/home/agent/.claude/.credentials.json"]`. The path is a string constant (`SANDBOX_CREDENTIALS`), never a `join`. Its stdout is parsed in memory. Only `claudeAiOauth.expiresAt` and `claudeAiOauth.refreshTokenExpiresAt` (numbers, ms) are kept. The parsed object and the raw stdout are dropped and never clipped into a reason, an event or a log.

The precedence is fixed, and the first that applies wins:

| # | Case | `state` | `reason` |
|---|---|---|---|
| 1 | probe spawn threw, exited non-zero, or unparseable | `unknown` | `the login probe failed: <exit N \| unparseable \| spawn error message>` |
| 2 | `loggedIn !== true` | `expired` | none |
| 3 | `authMethod !== "claude.ai"` | `unknown` | `logged in with '<method>', not the claude.ai subscription (the preflight refuses it)` |
| 4 | the `cat` exited non-zero, or the JSON or `refreshTokenExpiresAt` is missing or non-numeric | `unknown` | `the credentials file was not read: <exit N \| unparseable \| no refreshTokenExpiresAt>` |
| 5 | `refresh <= now` | `expired` | none |
| 6 | `refresh - now <= 3 × 86 400 000` | `expiring` | none |
| 7 | otherwise | `ok` | none |

**The answer** (200 always, even for `unknown`):

`{ok: true, sandbox, logged_in: bool|null, auth_method: str|null, subscription_type: str|null, access_expires_at: ISO|null, refresh_expires_at: ISO|null, days_left: int|null, state, checked_at: ISO[, reason]}`

- The expiries are `new Date(ms).toISOString()`.
- `days_left = max(0, floor((refresh - now) / 86 400 000))`.
- `reason` is present only on `unknown`.
- `ok` is the API's envelope. No other key is ever added: no token, no email, no org, no lease, no holder (the SPEC Constraint "GET /sandbox/login answers only its named fields").
- On a cookie session the answer carries `X-CSRF-Token`, as `/inbox` does.
- **GET never writes an event.**

### 3. The routes, the refusal names and the HTTP codes (CAP-4, CAP-5)

These sit beside the existing routes in `route()`, with the cookie allow-lists widened.

**`GET /sandbox/login`** (cookie or bearer):
- 200 as in shape 2;
- 400 `SandboxRequired`, `SchemaError`;
- 404 `UnknownSandbox`;
- 405 for other methods.

**`POST /sandbox/login/start {sandbox?}`** (cookie + CSRF, or bearer). The body is a JSON object with only `sandbox`.

| Code | Answer |
|---|---|
| 200 | `{ok: true, login_id, url, started_at, expires_at}` |
| 400 | `MalformedJson`, `SchemaError`, `SandboxRequired` |
| 403 | `CsrfRefused` |
| 404 | `UnknownSandbox` |
| 409 | `LoginWhileLive {sandbox, run_id, state}`: the first holder from `sandboxHolders(queue, sb, "", RESTART_BLOCKING_STATES)`, or a run with `verifyLegLive` on that sandbox |
| 409 | `LoginInProgress {sandbox, login_id, started_at, expires_at}`: an open lease |
| 409 | `SandboxStopped {sandbox}`: not listed running. No supervisor command starts a sandbox (SPEC Non-goals) |
| 500 | `LoginStartFailed {sandbox, last_line}` |

**`POST /sandbox/login/code {login_id, code}`** (cookie + CSRF, or bearer). Only those two keys are allowed. `login_id` matches `^[0-9a-f]{12}$`. `code`, trimmed, matches `^[A-Za-z0-9._~-]{1,256}#[A-Za-z0-9._~-]{1,256}$` (the CLI's `code#state`). Anything else is 400 `SchemaError` with the detail `the code is the whole text claude.ai shows after you approve (it contains a #)`. The pane is untouched, and it is no try.

| Code | Answer |
|---|---|
| 200 | the re-run read: exactly shape 2's body |
| 400 | `MalformedJson`, `SchemaError` |
| 403 | `CsrfRefused` |
| 404 | `UnknownLogin {login_id}`: no such lease |
| 409 | `LoginExpired {login_id}`: past its `deadline`. The lease is closed `expired` and the session killed |
| 409 | `LoginClosed {login_id, result}`: the lease is already closed |
| 409 | `LoginInProgress {login_id}`: another code for this login is in flight in this process |
| 409 | `CodeRefused {login_id, last_line, tries_left, url?}` |
| 500 | `LoginFailed {login_id, last_line}` |

### 4. The exchange (CAP-5): the open question's answer, as argv

Every call goes through `sbx`, argv only. Here `S` is `tk-login-<login_id>` and `T` is `=tk-login-<login_id>:`. The `login_id` is 6 random bytes in hex.

**Start.**
1. `["exec", sb, "tmux", "new-session", "-d", "-s", S, "-x", "1000", "-y", "50", "env", "-u", "ANTHROPIC_API_KEY", "claude", "auth", "login", "--claudeai", ";", "set-option", "-t", T, "remain-on-exit", "on"]`.
2. Every `pollMs` (default 1000), `["exec", sb, "tmux", "capture-pane", "-p", "-J", "-S", "-", "-t", T]`, until the **last** match of `/https:\/\/(?:claude\.ai|claude\.com\/cai)\/oauth\/authorize\?[^\s"'<>]+/g` that carries both `code_challenge=` and `state=`.
3. The wait is bounded at `urlWaitMs` (default 30 000).
4. On a timeout or a dead pane: `["exec", sb, "tmux", "kill-session", "-t", "=" + S]`, close the lease `failed`, and answer 500 `LoginStartFailed` with the last line.

**The code.**
1. `["exec", "-i", sb, "tmux", "load-buffer", "-b", S, "-"]`, with `input: <code>` (no newline) through `runProcess`'s stdin. `SandboxDeps.run` gains an optional `input` in its opts and `call` passes it through.
2. `["exec", sb, "tmux", "paste-buffer", "-d", "-b", S, "-t", T]`. The `-d` drops the buffer.
3. `["exec", sb, "tmux", "send-keys", "-t", T, "Enter"]`.
4. Poll `["exec", sb, "tmux", "display-message", "-p", "-t", T, "#{pane_dead} #{pane_dead_status}"]` and the capture, bounded at `codeWaitMs` (default 60 000).

**The outcome:**

| Pane | Status | Result |
|---|---|---|
| dead | 0 | Kill the session, close the lease `renewed`, re-run the read, answer 200 |
| dead | non-zero | Refused. On the first refusal: `clear-history -t T`, then `respawn-pane -k -t T env -u ANTHROPIC_API_KEY claude auth login --claudeai`, await a new URL whose `state=` differs (same bound), answer `CodeRefused {tries_left: 1, url: <new>}`. The old code is bound to the old PKCE verifier: the CLI's own words, "Sign in again". On the second refusal: kill, close `refused`, answer `CodeRefused {tries_left: 0}` |
| alive | — | A new `Invalid code.` line after the paste: refused. On the first, `CodeRefused {tries_left: 1}`, the same URL, the pane still waiting. On the second, kill, close `refused`, `tries_left: 0` |
| alive | — | Bound reached with no outcome: kill, close `failed`, answer 500 `LoginFailed` |

The tries are kept in the API closure's `Map<login_id, number>`. A serve restart resets them, which is harmless.

**The login state is the lease plus the session name, never memory.** A restarted serve still drives an open login.

**`last_line`.** The last non-blank captured line, with:
- ANSI stripped;
- every `https://…` replaced by `[sign-in URL]`;
- every line containing the code, either half of it, or starting `Paste code here` skipped;
- clipped to 300 characters.

**The URL** is in the 200 answer only. It is never in an event, a refusal, a `last_line` or a log.

### 5. The lease and the event: one kind, `sandbox-login` (CAP-5)

Both are service events of the kind `sandbox-login`.

**The opening event** (`Queue.takeSandboxLogin`, atomic `.immediate()`):

`{sandbox, login_id, owner: {pid, host, nonce, start?}, by: "owner", started_at, deadline}`

- `owner` is the serve process, in `ownerDetail`'s shape.
- `deadline` is `started_at + 600 s` and is the answer's `expires_at`.
- The take is refused when an open lease on that sandbox exists with its `deadline` ahead.

**The closing event** (`Queue.closeSandboxLogin`, idempotent: no second close for a `login_id`):

`{sandbox, login_id, result: "renewed"|"refused"|"failed"|"expired", by: "owner", started_at, ended_at[, closed_by: "drain"]}`

- This is the AC's service event `sandbox-login {login_id, result, by: owner, started_at, ended_at}`, plus `sandbox` (the gate is per sandbox) and, when the drain closed it, `closed_by`.
- Neither event carries a URL or a code.

**Reading the lease.**
- **Open** means an opening event with no closing event for its `login_id`.
- **Live** means open with its `deadline` ahead.
- `Queue.openSandboxLogin(sb, nowMs)` answers the live lease or null. `Queue.sandboxLogin(login_id)` answers `{open, closed}`. `Queue.staleSandboxLogins(nowMs)` answers the open leases past their deadline.
- The refusals before a lease (`LoginWhileLive`, `LoginInProgress`, `SandboxStopped`, the 400s and 404s) write nothing.
- A `LoginStartFailed` writes the opening event, then its `failed` close.

### 6. Who honours the lease (CAP-5, "as the host-verify-leg lease")

- **`claimGate`.** Its first step, on sbx and before the pin, is a live lease on `options.sandbox`. When there is one, `recordedRefusal` with:
  - `key: "sandbox-login:<sb>"`;
  - `reason: "sandbox <sb>: a Claude login renewal is in progress (login <id>, until <deadline>)"`;
  - `resolves: "send the code on the Settings page (/app/settings), or let the lease run out at <deadline>; the next drain pass claims the run"`.

  The run stays `queued`, as every claim refusal does.
- **`pinWithRestart`.** With a live lease on `sb` it never stops or starts the sandbox: it pins plainly. This is the `peerLegLive` precedent (`hostverify.ts:830-851`).
- **`releasePin`.** With a live lease on `sb` it does not `sbx stop`. It notes `pin-kept {sandbox, held_by: ["sandbox-login:<id>"]}` once per episode and answers `kept`.
- **`drainQueue`.** First, before its `for` loop, `expireSandboxLogins(queue, sbxDeps(opts.worktree), Date.now())`: for each stale lease, `tmux kill-session -t =tk-login-<id>` (best effort, only when `sandboxRunning`), then close it `expired` with `closed_by: "drain"`.
- The API's code route closes an overdue lease itself: `LoginExpired`.

### 7. The Task pass and its check event (CAP-7)

`sandboxLoginPass(queue, deps)` in `hygiene.ts` runs per configured sandbox from `drainQueue`'s `finally`. It runs only with injected deps under `bun test`. It never throws.

**The check event:** `sandbox-login-check {sandbox, state, refresh_expires_at, days_left, derived?: true, task?: KEY|null, task_error?, closed?: [KEY]}`. It carries no token.

**What the pass reads:**
- **(a) Read the sandbox** with shape 2's read when it is listed running and one of these holds:
  - there is no check yet;
  - the last check is older than 6 h (its state `ok`);
  - the last check is older than 1 h (any other state);
  - a `sandbox-login` closed `renewed` after it.
- **(b) Otherwise derive.** When the last check has a `refresh_expires_at` and no renewal followed it, the state comes from the clock alone (`derived: true`), with no `exec`. A logged-out `expired` stays `expired`. This is "the login has a clock": the Task does not wait for a run to start the sandbox.
- **(c)** Nothing to read and nothing to derive: return.

**What the pass does:**
- **Mint.** On `expiring` or `expired` with a known `refresh_expires_at` R, and no check event for R carrying a `task` key:
  - `uv run track.py block --directory <root> --source owner --task sandbox-login --sandbox <sb> --expires <R> --url <origin>/app/settings` (timeout 120);
  - record a check with `task` (or `task: null` and `task_error`).
  - The verb itself finds an open Task for R and does not mint a second.
- **Close.** On `ok` after a check that carried a `task` for another R with no `closed`:
  - `track.py close --directory <root> --source owner --task sandbox-login --sandbox <sb> --expires <R>`;
  - record the check with `closed`.
- **Otherwise** a read records a plain check, and a derivation records nothing.
- **`<root>`** is the first project, in config order, whose `jobs.<project>/…` names the sandbox, whose registry root (`registryShow()`) exists and is `jiraBound`. With none, the check records `task_skipped: "no bound project places on <sb>"`.

**The console line.** The claim-refusal line of hole 69 (`max-login`, `loginResolves` `cli.ts:1351-1354`) is unchanged: "keeps its line".

### 8. The Task's form (CAP-7)

The key is the expiry.
- **Type.** A `Task`, labels `["tk-studio-owner", "tk-studio-sandbox-login"]`, assignee `{accountId: owner}` (`_agent_seat`).
- **Summary.** `Renew the sandbox's Claude login before <YYYY-MM-DD HH:MM>Z`: R in UTC, floored to the minute, e.g. `before 2026-11-24 10:00Z`.
- **Description** (plain text, as `sweepdecisions._create_issue` sends it):

  ```
  The sandbox <sb>'s Claude login (the subscription's claude.ai grant) ends <R ISO>. Once it lapses, every run on the sandbox waits for a renewal.

  1. Open <url> and press Renew, then Open sign-in: approve on any device that holds your claude.ai session.
  2. Paste the code claude.ai shows into "Paste the code claude.ai shows after you approve" and press Send.

  The studio moves this Task to Done when it reads the renewed login.
  Key: sandbox-login <sb> <R ISO>
  ```
- **The block.** Then `_block_issue` to `Blocked - Awaiting User`, with `comment_body(owner, "the sandbox <sb>'s Claude login expires <date>" | "… expired <date>", "renew it on <url> (Renew, Open sign-in, paste the code, Send)")`.
- **The find.** JQL `project = "<KEY>" AND labels = "tk-studio-sandbox-login" AND statusCategory != Done`, then the exact summary in code, the lowest key winning.
- **The close.** Every open hit whose summary is not R's gets `unblock_comment("renewed: the login is valid until <date>")` once, then `Block Resolved` (optional, as `close_engagement`) and `Done` by name.

### 9. The `track.py` form (CAP-7)

`block` and `close` take `--source owner --task sandbox-login --sandbox SB --expires ISO` and, on `block` only, `--url URL`.

**The refusals.** `--source owner` is exclusive with `--story`, `--engagement`, `--reason`, `--resolves`, `--kind`, `--triage`, `--run-id` and `--ask` (a refusal by name, exit 2, no call). Also refused before any call:
- `UnknownTask` (any `--task` but `sandbox-login`);
- `SandboxInvalid` (shape 1's regex);
- `ExpiresInvalid` (not ISO-8601 with `Z` or an offset);
- `UrlInvalid` (not `http(s)://…/app/settings`);
- the `_agent_seat` gaps.

**`close`.** Its `--engagement` stops being `required=` in argparse and is checked in code: neither `--engagement` nor `--source owner` gives a JSON refusal, exit 2.

**The result.** `{ok, dry_run, source: "owner", task, sandbox, expires, issues: [{issue, created, transitioned, commented, moved?, skipped?, error?}], skipped[], notes, written: []}` and the §3 block.
- A 400 on the create is `IssueCreateRefused`.
- A transient failure is `partial`, `ok: false`, `retry: true`.
- A dry run creates and moves nothing and names what it would do.
