## Intent

The model and effort of every leg, the bands, the default autonomy and the per-band follow-up cap live in four files today. Only an operator at a terminal edits them: `.bmad-loop/routing.toml`, `.tk-studio/budget-bands.yaml`, the gitignored `.bmad-loop/policy.toml` and the shipped `customize.toml`. The web shows the route read-only, through `GET /agents`. This story gives the owner a Settings section that reads and writes them, keeping the existing rules:
- **D9:** the web requests and the supervisor runs a studio verb on the host. That verb is a new pair, `pipeline.py settings` and `settings-write`. The supervisor never touches the files itself.
- **AD-14:** routing owns model and effort.
- Every change is recorded as a `settings-changed` service event.
- The page shows the route the next run resolves, and says so when a run is live.

The presentation toggles (movement, sound, HUD detail) stay in the browser.

## Settled shape

1. **The verbs (CAP-24, SPEC design note).** `pipeline.py` gains two verbs. Neither touches the managed policy block, the profile, `[limits] max_followup_reviews` or `customize.toml`.
   ```
   uv run pipeline.py settings       --directory DIR
   uv run pipeline.py settings-write --directory DIR [--leg <leg>.<model|effort|advisor>=<v>]... \
       [--band <band>.<usd_estimate|followup_reviews_max>=<v>]... [--by-band <band>=<int>]... \
       [--autonomy=<ask|steady|full>] [--dry-run]
   ```
   - An empty value (`--leg review.effort=`, `--by-band M=`, `--autonomy=`) unsets the field: the leg falls back to the shipped value, the band to `[limits] max_followup_reviews`, the autonomy to `steady`.
   - `settings` writes nothing.
   - `settings-write` validates **every** value before writing **any** file. Then it computes each new text in memory and verifies each one by re-parsing (tomllib for TOML, `miniyaml.loads` for YAML) against the expected data. It writes `routing.toml`, then `budget-bands.yaml`, then `policy.toml`, each with an atomic `os.replace`, then re-resolves `routing.current.json` (`write_current(root, resolve(root, None))`, story `null`).
   - A failure mid-way restores the originals already written.
   - Exit codes: 0 when answered; 2 on a refusal.
   - `--dry-run` answers the diff and writes nothing.
   - **Text edits, keeping comments, alignment and each file's own newline:**
     - **`[defaults]`:** only the edited leg's one-line inline table is rebuilt. Keys keep their order, new keys are appended in `FIELDS` order, strings are rendered with `json.dumps`, and the trailer after the closing `}` (a comment) is kept. A leg absent from the table gets a line at the end of `[defaults]`, aligned to the existing `=` column. A missing `[defaults]` header is appended. A leg written as a `[defaults.<leg>]` sub-table or as dotted keys is `SettingsUnwritable`.
     - **`budget-bands.yaml`:** the band's `<field>: <value>` line under `bands:` → `<band>:` is rewritten, or inserted after the band's last field line. `usd_estimate` is rounded to cents and written without trailing zeros (`9`, `8.5`, `9.25`).
     - **`policy.toml`:** the `<band> = { max_followup_reviews = N }` line under `[limits.by_band]` is rewritten, keeping other keys and the comment, or inserted after the header. A missing header is created at the end of the `[limits]` table, before the next header line, or before the managed `BEGIN` block. A missing `policy.toml` with a by-band value is `SettingsUnwritable: policy missing: .bmad-loop/policy.toml (bmad-loop init creates it; never invented here)`.
     - **`[approval]`:** one line `autonomy = "<level>"`. The table is appended when absent; unsetting removes the line.
   - Write answer: `{ok: true, changed, dry_run, diff: [{field, from, to}], writes: {routing, bands, policy, current}` (`written|unchanged`)`, warnings[], pending_commit[], settings: <the read answer after the write>}`.
     - `field` is `legs.<leg>.<model|effort|advisor>`, `bands.<band>.<usd_estimate|followup_reviews_max>`, `by_band.<band>` or `autonomy`; `null` means unset.
     - Values equal to the current ones give `changed: false` and touch no file, not even `routing.current.json`.
   - `pending_commit[]` comes from `git status --porcelain --untracked-files=no -- .bmad-loop/routing.toml .tk-studio/budget-bands.yaml` (`text=True, encoding="utf-8"`, 30 s). It is `[]` with no git or no repository.
   - `check` also validates `[approval] autonomy`.
   - The docstring's verb list and exit codes name both verbs.
   - `kb/execution-pipeline-model-routing.md` and contract §5.1 list them.

3. **The read answer (CAP-24, SPEC design note).** `pipeline.py settings` answers `{ok: true, routing, legs[], overrides, bands[], by_band, autonomy, accepted, pending_commit[], warnings[]}`:
   - **`legs[]`:** in `LEGS` order, `{leg, configured, shipped, resolved, source}`.
     - `configured`, `shipped` and `resolved` are each `{model, effort, advisor}`, with `null` for absent. `configured` is the project's `[defaults]` entry, `shipped` the `[pipeline.legs]` entry, `resolved` from `resolve(root, None)`.
     - `source` is `{model, effort, advisor}`, each `shipped-default | project-default | inherited-session | null`. These map from resolve's `resource-default`/`project-defaults`/`inherited-session`; resolve's own labels are unchanged.
   - **`overrides`:** `{rules: [<match>…], stories: [<key>…]}`, read-only. A story they match resolves those first.
   - **`bands[]`:** in file order, `{band, usd_estimate, followup_reviews_max, policy_cap, policy_key}`.
     - `policy_cap` is the effective follow-up cap: `[limits.by_band] <band>`, keyed `limits.by_band.<band>.max_followup_reviews`, else `[limits] max_followup_reviews`, keyed `limits.max_followup_reviews`. It is `null` without a policy.
     - The AC's "bands … with cap" is `followup_reviews_max`, the band's own cap (38.7).
   - **`by_band`:** `{<band>: <int>}`.
   - **`autonomy`:** `{default, source}`.
   - **`accepted`:** `{models: sorted(MODELS), efforts: ["low","medium","high"], advisors: ["opus","fable","off"], autonomy: ["ask","steady","full"]}`.
   - **`warnings[]`** (never a refusal):
     - `band <B> followup_reviews_max <n> exceeds its policy cap <m> (<policy_key>): launch.py check names a budget_mismatch`;
     - `policy missing: .bmad-loop/policy.toml`;
     - `budget-bands missing: .tk-studio/budget-bands.yaml`.
   - **`GET /settings/routing?project=<id>`** (bearer or cookie) answers `200 {ok: true, project, …the verb's answer…, live_run, note, read_at}`. A cookie answer carries `X-CSRF-Token`, as `GET /inbox` does. The errors:
     - `400 ProjectRequired`;
     - `404 UnknownProject`;
     - `500 SettingsRootMissing {project, detail}` (no registry root, or a root not on disk);
     - `500 SettingsReadFailed {detail}` (no JSON, or `ok: false`).

4. **The write route (CAP-24, SPEC design note).** `PUT /settings/routing` (bearer, or cookie with `X-CSRF-Token`, else `403 CsrfRefused` and no verb run).
   - **The body** is `{project, legs?: {<leg>: {model?, effort?, advisor?: string|null}}, bands?: {<band>: {usd_estimate?, followup_reviews_max?: number}}, by_band?: {<band>: number|null}, autonomy?: string|null}`, with at least one of the four.
     - The shape is checked in `settings.ts checkSettingsBody`: a non-object, a missing project, an unknown key, a wrong type (a boolean counts as one) or an empty subset is `400 SchemaError {detail}`. Non-JSON is `400 MalformedJson`.
     - Every value judgement is the verb's.
   - **The supervisor** turns the body into `settings-write` argv (`settingsArgs`). Numbers go through `String(n)`, `null` becomes the empty value, and autonomy is always the `--autonomy=<v>` form. It runs the verb on the served root (the registry root, the host's project checkout; never a run's worktree), serialized per project by a promise chain (`inbox.ts` `replyChains`).
   - **On `ok: true`:** when `changed`, it records the event (shape 6). It answers `200 {ok: true, project, changed, diff, warnings, pending_commit, resolved: {<leg>: {model, effort, advisor}}, settings: <the read shape>, event: {kind: "settings-changed", at} | null, live_run, note}`. `resolved` is "the new resolved route".
   - **The verb's refusals:**
     - `SettingsValueRefused`: `400 {error: "SettingsValueRefused", refused}`;
     - `SettingsUnwritable`: `409 {error: "SettingsUnwritable", detail}`;
     - no JSON or a spawn failure: `500 SettingsWriteFailed {detail}`.

     None of these records an event.
   - Wrong methods answer `405 Allow: GET, PUT`.

5. **`SettingsValueRefused` (CAP-24, SPEC design note).** The verb answers `{ok: false, error: "SettingsValueRefused", refused: [{field, value, reason}]}`, exit 2, every bad value listed and no file written. The reasons:
   - `unknown model id (accepted: <sorted MODELS, ", ">)`
   - `effort outside routing's set (low, medium, high)`
   - `advisor outside (opus, fable, off)`
   - the pairing text of `_pairing_problems` (on the would-be `[defaults]` and the effective route)
   - `a cap below one` (an integer < 1 for `followup_reviews_max` or `--by-band`)
   - `not an integer`
   - `not a positive number` (`usd_estimate` ≤ 0 after rounding, or NaN)
   - `unknown leg (legs: <LEGS>)`
   - `unknown band (bands: <the file's bands>)`
   - `unknown autonomy (ask, steady, full)`

   `SettingsUnwritable {detail}` is the verb's other refusal: a form it cannot edit as a line, a missing policy, or a re-read that did not verify (`the write did not verify; the originals are restored`).

6. **The event (CAP-24, SPEC design note).** `settings-changed {project, actor: "owner", source: "cookie"|"bearer", diff: [{field, from, to}], files: [<root-relative paths written>], live_run: <run_id>|null}`.
   - It goes through `queue.serviceEvent` once per applied write that changed something.
   - It is never recorded for a refusal, a dry run or `changed: false`.
   - No value in it is a secret.

7. **The live-run note and the write's reach (CAP-24, SPEC design note).**
   - `live_run` is the project's newest run in `running | paused | external`: `LIVE_STATES` from `registry.ts:82`, exported. It is `{run_id, state}`, or `null`.
   - `note` is `"A run is live: changes apply to the next run"` when `live_run` is set, else `null`. GET and PUT both answer it.
   - The verb writes only in the served checkout. A live run's worktree copy of `policy.toml` and `routing.current.json` is never touched, which is why the change "applies to the next run":
     - The next worktree copies the checkout's `[limits.by_band]` (`COPIED_RUNTIME`).
     - Host-tier planner runs and quotes read the checkout's re-resolved `routing.current.json` at once.
     - The tracked `routing.toml`/`budget-bands.yaml` reach a run's worktree only once committed (Block If 1). `pending_commit[]` names them while they are not, and the page says so.
