## Intent

The owner can talk to one engagement in the page today, but not to the studio itself. He still gives the studio its instructions through the Claude Code app (addendum §0, §2 "Studio chat interface"). This story adds a studio-wide chat at `/app/chat`, in four parts:

- **The job.** A shipped one-shot `studio-chat` job (the `engagement-chat` pattern) runs the `tk-studio-orchestrator` core headless for one owner line. It answers from the reads the pages use and writes one reply with `proposals[]`.
- **The routes.** `POST /chat` and `GET /chat`, beside the engagement chat's `/chat/{id}`. They append the line, queue the run behind any running reply, and stream the reply text as `chat-delta` frames, tapped from the worker's `stream-json` stdout.
- **The screen.** The Chat screen's studio conversation shows the streaming reply with a cursor, an honest pending label, and each proposal as a button that sends a request the supervisor already knows.
- **The identity.** A lib test proves the job's entry and the skill's documented command resolve the same routing payload (AD-11).

   - **The AC's `stop {max_runs: 1}` is not carried** (correction 1). A one-shot, one run per line, is already the job's shape. `until` is the stop condition the schema requires, as for `engagement-chat`.
   - No `model` or `effort`: the planner leg is passed at enqueue (AD-14).
   - No schema field for the output format: the supervisor keys `stream-json` on the id (shape 6), as it keys `stack` on `engagement-chat`.

2. **The record `_bmad-output/tracking/studio-chat.jsonl`** at the served registry root, untracked (per SPEC Assumptions; addendum §3.8). It holds one JSON object per line. `seq` grows by 1 from 1 and is unique per file. Writers take `_bmad-output/tracking/studio-chat.lock` (exclusive create, stale after 30 s, 5 s wait, then `ChatBusy`), re-read the last `seq` inside it, and rewrite the file atomically. The same lock rules apply in TypeScript and Python. The record kinds:
   - **owner line:** `{seq, at, author: "owner", body}`. `body` is 1 to 4,000 characters (code points), not blank.
   - **press line:** `{seq, at, author: "owner", body: "pressed: <label>", pressed: {seq, index, kind}}`. It names the reply's `seq`, the proposal's 0-based `index` and its `kind`. It queues nothing.
   - **reply:** `{seq, at, author: "planner", body, run_id, reply_to, proposals[]}`.
     - `run_id` is the queue run id (as the engagement chat).
     - `reply_to` is the owner line's `seq`. At most one reply per `reply_to`.
     - `body` is at most 32 KiB UTF-8.
   - **failure reply** (the supervisor's, shape 9): `{seq, at, author: "planner", body: "No reply: the run ended <state>: <reason, one line, at most 200 characters>", run_id, reply_to, proposals: [], failed: true}`.
   - `author` stays `planner`, so the engagement chat's `event: chat` frame and the web's `isLine` read it unchanged.
   - A **pending turn** is an owner line with no `pressed` and no reply whose `reply_to` is its `seq`.

3. **The proposal kinds** (`proposals[]`, at most 6, each an object with `kind` and `label` plus its own fields, no other field; `label` 1 to 80 characters). Per addendum §3.8 and §3.2 F-C:
   - `queue {kind, label, project, job}`: `project` non-empty; `job` matches `^[a-z][a-z0-9-]*$`.
   - `answer {kind, label, id, letter, note, issue}`:
     - `id` is the question's id as its item asks it (`DW-87` on a decision Task, a question id on an `ENG-NNN: questions` item), matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`;
     - `letter` matches `^[A-Z]$`;
     - `note` is a string, possibly empty, at most 2,000 characters;
     - `issue` is the inbox item's key, matching `^[A-Z][A-Z0-9]+-\d+$`. It is additive to the AC's three fields: the route's `{key}` needs it.
   - `open {kind, label, route}`: `route` matches `^/app(/[A-Za-z0-9._~%-]+)*$`.
   - `engagement {kind, label, title}`: `title` non-empty, at most 32 KiB UTF-8 (`POST /engagements`' `request` rule).
   - `stop-after-story {kind, label}` and `open-studio {kind, label}` are **refused by name until 39.7**.
     - `studiochat.py reply` refuses `ProposalNotYet: <kind> lands in Story 39.7`, and nothing is written. The session drops the proposal and says in the body that the action arrives with 39.7.
     - The supervisor's press path refuses the same name (409 `ProposalNotYet`).
     - The web renders either kind disabled with the note "Not built yet: Story 39.7" (a record written by hand).
     - 39.7 lifts the refusal.

4. **The press mapping** (the web's `proposalAction`, pinned in `model.test.ts`):
   - `queue` → `POST /jobs {project, job, proposal: {chat, seq, index}}` with `X-CSRF-Token`. `chat` is the project whose studio chat holds the reply. See shape 11.
   - `answer` → `POST /inbox/{issue}/reply {project, body}`. The body is `"<id>: <letter>"`, plus `"\n" + note.trim()` when the note is not blank. The note always sits on its own line, never on the answer line: a trailing text is a qualified answer and is never ingested (`sweepdecisions.py:112`).
   - `open` → the 39.1 router's navigation to `route`.
   - `engagement` → `POST /engagements?project=<project>` with `{project, request: title}` (`postEngagement`).
   - On a 2xx (for `open`, before navigating), the web posts `POST /chat {project, pressed: {seq, index}}`. The supervisor writes the press line, with `body` `pressed: <label>` taken from the record.
   - A proposal named by a press line renders disabled ("Pressed").

5. **`POST /chat` and `GET /chat`** (`api.ts`, beside `/chat/{id}`). Both take cookie + CSRF or the bearer (per SPEC Constraints, surface rules).
   - **`POST /chat`.** The body is exactly one of:
     - `{project, text}`, where `text` is a non-blank string of at most 4,000 characters (code points);
     - `{project, pressed: {seq, index}}`.
   - **`POST /chat` refusals:**
     - `400 MalformedJson`;
     - `400 SchemaError` (an unknown field, both or neither of `text`/`pressed`, a blank text);
     - `400 LineTooLong {limit: 4000, length}`: the AC's refusal by name;
     - `404 UnknownProject`;
     - `404 UnknownProposal` (a press naming no reply or index);
     - `409 ProposalNotYet {kind}`;
     - `500 ChatJobUnresolved`;
     - `500 ChatQueueFailed` (the line removed again, as 32.2 does);
     - `503 ChatBusy`;
     - `403 CsrfRefused` (a cookie without the token).
   - **A line's answer** is `200 {ok, project, seq, run_id, behind, note}`:
     - `behind` is `{seq, run_id}` of the pending turn just ahead, else `null`;
     - `note` is `"Queued behind the reply to '<excerpt>'"`, else `null`.
     - `<excerpt>` is that line's body with whitespace runs collapsed to one space and trimmed. When longer than 40 code points it is cut to 40 and `…` is appended.
   - **A press's answer** is `200 {ok, project, seq, run_id: null, behind: null, note: null}`.
   - **`GET /chat?project=<id>[&since=<seq>]`:**
     - JSON is `{ok, project, since, last_seq, lines}`. `400 ProjectRequired`, `404 UnknownProject`, and a bad `since` is `400 SchemaError`, as 32.2.
     - With `Accept: text/event-stream`: `retry: 5000`, then the `id: <seq>` / `event: chat` frames (replay after `since` or a numeric `Last-Event-ID`, then each new line), the `chat-delta` frames (shape 6), and `: heartbeat` every `heartbeatMs`.
     - It is a fourth handler `studioChatSse`, never factored with `sse()`, `officeSse()` or `chatSse()` (the 32.7 rule).
   - **`chat-queued`** is the same kind as 32.2, with detail `{chat: "studio", project, seq, run_id, model, effort, behind}` (`behind` the run id ahead, or `null`). It has no `engagement` key, so every engagement reader skips it (Code Map).
   - Inside the lock, with no await between, the order is: append the line, write the reads file (shape 12), mint, record `chat-queued`. A failed mint or event drops the line and the reads file and answers `500 ChatQueueFailed`.

6. **The stream** (per addendum §4 choice 4: "streaming is of the reply text").
   - **The worker.** For job id `studio-chat` only, the worker's argv is `-p <prompt> --output-format stream-json --verbose --include-partial-messages --permission-mode <mode> [--settings …] [--model …] [--effort …] [--session-id|--resume …]`. Every other job keeps `--output-format json`.
   - **The tap** (`studioChatTap(root, runId)` → `{write(chunk), close()}`):
     - It buffers stdout into lines and parses each line as JSON.
     - It keeps only `{"type": "stream_event", "parent_tool_use_id": null, "event": {"type": "content_block_delta", "delta": {"type": "text_delta", "text": …}}}`. Thinking, tool input, sub-agent deltas, and the whole `assistant`/`user`/`result` messages are ignored.
     - It appends each kept `text` to an accumulator.
     - The streamed reply is the accumulator's text after the first `<reply>` marker, up to `</reply>` or the end. A trailing partial prefix of `</reply>` is held back.
     - It writes `_bmad-output/tracking/studio-chat-stream/<run_id>.txt` (UTF-8, atomic) whenever the reply grew, at most every 250 ms, with a final flush in `close()`.
     - A tap error is swallowed and never reaches the worker.
   - **The frame:** `event: chat-delta\ndata: {"run_id": "<id>", "reply_to": <seq>, "from": <code-unit offset>, "text": "<new text>"}\n\n`.
     - It has no `id:` line, so `Last-Event-ID` stays the chat `seq`.
     - Per connection, the stream sends a running studio-chat run's text from the length it last sent. After a reconnect that starts at 0.
     - The stream stops sending for a run once its reply line has been sent as `event: chat`, or once the run is terminal.
     - The live runs come from `queue.serviceEvents("chat-queued")` with `chat: "studio"` and this `project`, and from the queue state `running`.
   - **The web's assembly** (`applyDelta`) is `text.slice(0, from) + delta.text` when `from <= text.length`. A `from` past the end is ignored.
   - The record is authoritative: an `event: chat` reply with `reply_to` R drops R's streaming text.

7. **The lane and the quiet** (per addendum §3.1 (7) and §3.2 F-C: "what is running" costs a read, not a plan).
   - **The lane.** `mintStudioTurn` enqueues with `lockCheckout: "<resolved lockCheckout ?? root>#studio-chat"`. The turns serialize on their own lane: the second line's run waits on the first, oldest first, and never on an engine or epic lock.
   - **The queue.**
     - `STUDIO_CHAT_JOB = "studio-chat"` sits beside `ENGAGEMENT_CHAT_JOB`.
     - `stack` applies to both.
     - `LIVE_INDEX` excludes both: `job_id NOT IN ('engagement-chat','studio-chat')`.
     - `widenLiveIndex` recreates an index whose SQL lacks `'studio-chat'`.
   - **The quiet.**
     - A drained studio-chat run waiting on its lane records no `claim-refused` and sends no notifier line (`cli.ts:1610`: skip `recordedRefusal` when `run.job_id === STUDIO_CHAT_JOB`). The page shows the position.
     - Its end records `notify-skipped {why: "a studio-chat turn answers in the page (Story 39.3)"}` in `notifyEnd` and sends no line. The transcript copy is unchanged.

8. **The session** (the `studio-reply` verb, `tk-studio-engage` SKILL.md; per AD-11 and the orchestrator SKILL's flow). The payload is `{verb: "studio-reply", project, project_root, seq, run_id}`.
   - **Step 1: read the context.** Run `uv run "${CLAUDE_PLUGIN_ROOT}/lib/studiochat.py" context --directory <project_root> --seq <seq>`. It is read-only and answers `{ok, dry_run, mode: "context", seq, line, chat[], reads, routing, voice, shell?, not_yet[], notes[], written[]}` plus the status block:
     - `line` is the owner line;
     - `chat[]` is the last 40 lines;
     - `reads` is the reads file (shape 12), or `null` with a note;

     - `shell` is `orchestrate.load_shell()`, present only when `voice` is `council`;
