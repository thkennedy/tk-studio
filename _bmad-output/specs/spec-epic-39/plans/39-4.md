## Intent

The owner cannot see where a story stands or what it cost without Jira or the repository. The web has a row board (`GET /board`) and no page for one story, and nothing serves a story's Stage Log (addendum §2, the Kanban row; §3.2 F-D). This story:
- adds `GET /stories/{id}?project=`: one story composed from the plan store, its specs' Stage Log tables (with `stage-posts.json`), the queue and `board.ts`'s parts, cached on file stamps as the board is;
- adds `POST /stories/{id}/status`: the one owner-writable transition, `draft → ready`, applied by the supervisor through `plansync.py status` on the host and recorded as a `plan-status` service event with `actor: "owner"` (D9);
- turns the Board screen's default into a kanban (one column per canonical status, a card per story) beside today's row view, with one allowed drag;
- adds a story page at `/app/story/<id>`.

The kanban writes one transition and reads the rest; the loop owns every other column (addendum §4 choice 3). Contract 0.1.35 gains this story's paragraph (additive).

## Acceptance Criteria

AC1. **Given** the plan store (`_bmad-output/planning-artifacts/plan/ST-*.md`, canonical statuses `draft, ready, in-progress, blocked, review, done, dropped`), the Stage Log tables in the story specs and `_bmad-output/tracking/stage-posts.json` (`plansync.py stage`, `stage-post`)
**When** Story 39.4 lands
**Then** `GET /stories/{id}?project=` (cookie or bearer) answers one story: its frontmatter (id, title, status, parent, band, `external.jira.key`), its plan text, its Stage Log rows (stage, start, stop, model, tokens, cost) read from the spec on the host, its runs (from the queue, with state, PR and cost), its findings and PR from `board.ts`'s composition; a missing story is a named 404; the composition is cached on file mtimes as `GET /board` is; the contract names the route (0.1.35, additive); `board.test.ts` or a new `stories.test.ts` covers the composition and the 404.

AC2. **Given** the Board screen (`apps/studio-web/src/board/*`)
**When** `/app/board/<project>` is opened
**Then** it offers the kanban view (default) beside today's row view: one column per canonical status, a card per story with the epic badge, id and title, band, Jira key, PR number, cost and the current stage (from `office.progress`), "Needs you" marked; a card opens `/app/story/<id>`; a card dragged from `draft` to `ready` sends `POST /stories/{id}/status {status: "ready"}` and shows the hint "Requests plansync status ready; the loop owns every other column"; any other drag is refused in the page with the reason.

AC3. **Given** `POST /stories/{id}/status` (cookie + CSRF, or bearer)
**When** the body asks `ready` for a `draft` story
**Then** the supervisor runs `plansync.py status` on the host for that id (the verb the loop's plan-status pass uses, `apps/supervisor/src/planstatus.ts`), records a `plan-status` service event with the actor `owner`, and answers the new frontmatter; any other transition is refused by name (`StoryStatusNotOwnerWritable`) with the column that owns it; a story whose plan lease is held (`plan-lease` events) is refused with the holder named; `api.test.ts` covers the accepted transition, both refusals and the lease case.

AC4. **Given** the story page (`apps/studio-web/src/story/*`, new)
**When** `/app/story/<id>` is opened
**Then** it shows the plan text, the Stage Log table with a total line, the runs with links to `/app/run/<id>`, the PR and findings, the Jira key as a link, and the "Needs you" strip with the inbox item when one exists; pending reads say "Loading the story…"; `src/story/model.test.ts` pins the model.

## Settled shape

Each settled shape below cites the document that constrains it. None is a Block If.

1. **`GET /stories/{id}?project=<id>` (CAP-12; addendum §3.3 `/app/story/<ST-id>`, §3.2 F-D; epics.md §Story 39.4).**
   - Auth: the bearer, or a cookie session. Add `/^\/stories\/[^/]+$/` to the cookie `readRoute`.
   - `{id}` must match `STORY_ID_RE = /^ST-\d{3,}$/` after `decodeId`, else `400 {ok:false, error:"BadStory", story}`.
   - No `project` is `400 ProjectRequired`. An unregistered project is `404 UnknownProject {project}`.
   - A registered project with no plan directory, or no `ST-*.md` whose frontmatter `id` is `{id}`: `404 {ok:false, error:"UnknownStory", project, story}`.
   - Any other method: `405` `Allow: GET`.
   - `200`:
   ```
   {ok: true, project, built_at,
    story: {id, key, title, status, parent, epic: {id, number, title} | null, band: "S"|"M"|"L"|null,
            jira_key: string|null, jira_url: string|null, updated: string|null},
    plan_text: string,
    stage_log: {specs: [<root-relative POSIX path>], rows: [StageLogRow], total: {rows, priced, tokens_in, tokens_out, cost_usd, seconds}},
    runs: [{run_id, studio_run_id, job_id, state, pr, host_verify, created, ended_at, cost_usd}],
    pr: string|null, findings: [{id, title, severity}],
    needs_you: {run_ids: string[], inbox: <the inbox item as written> | null} | null}
   ```
   - The `story` fields:
     - `key` is `N.M` from `source`, else null.
     - `epic` is the parent `EP-` entity (`number` from its `source` `epics.md#epic-N`).
     - `jira_key` is `external.jira.key`.
     - `jira_url` is `https://<planning.jira.site>/browse/<KEY>` from the project's `.tk-studio/config.yaml` (`readProjectConfig`). It is null without a site or a key; a site already carrying a scheme is kept.
     - `updated` is the frontmatter's.
   - `plan_text` is the entity's body after the frontmatter (CRLF to LF, BOM dropped): the plan store's text, never the planner's `plans/<N>-<M>.md`.
   - `runs` are every run of the project naming the story by `board.ts`'s rule (strong names; a weak-only run when no run names it strongly), in queue creation order. `cost_usd` is `runCost(ledgerPath(env), studio_run_id)` (null unmetered).
   - `pr` is the latest named run's PR (`runPr ?? priorPr`).
   - `findings` are `readFindings(root)` for the story's `N.M`.
   - `needs_you` is null when neither of these holds:
     - `run_ids` is the story's runs in the board's `triage.needs_you`;
     - `inbox` is the first `state: "open"` item of `readInbox(root)` whose `entity` is the id or whose `issue` is the Jira key.
   - Machine paths never appear (AD-15): the specs are root-relative.
2. **The Stage Log rows (CAP-12; `stagelog.py` §stage log, AC1).**
   - `StageLogRow` is `{spec, stage, pass, started, ended, session_id, model, effort, tokens_in, tokens_out, cost_usd, outcome, buffered, posted}`.
   - `spec` is the story key of the file the row came from (the spec stem less `-spec`, or the buffer's stem).
   - Every text cell is the table's string, `—` → `null`. `tokens_in`, `tokens_out` and `cost_usd` are numbers or null.
   - `buffered: true` marks a row read from `stages/<key>.jsonl`. A buffered row whose row key a table already holds is dropped.
   - `posted`:
     - `true` when `stage-posts.json` holds `start`, and, for a closed row, `stop` and `worklog` (a string worklog counts);
     - `false` otherwise;
     - `null` when the file is absent.
   - Rows are sorted by `started`, stable on file order.
   - `total`:
     - `rows` is the row count;
     - `priced` is the count with a cost;
     - `cost_usd` is the sum rounded to 4 places, or `null` when `priced` is 0;
     - `tokens_in`/`tokens_out` are sums, or null when none;
     - `seconds` is the sum of the closed rows' `ended − started`.
3. **The story's files (CAP-12; `worktree.ts:1156-1183` the split/remediation naming, task-planning.md §3).** The specs and buffers come from one readdir per folder of `_bmad-output/specs/*`:
   - **specs:** every `stories/<N>-<M>-*.md` and `stories/<N>-<M>.md`. The first half, a `-s<n>` split and a `-r<n>` remediation are all the story's cost. `39-4-` never matches `39-40-`.
   - **buffers:** every `stages/<N>-<M>-*.jsonl`.
   - **plan:** the band is the first sorted `plans/<N>-<M>.md` whose frontmatter `band` is `S`, `M` or `L`.
   - Each file's parse is cached on `(size, mtimeMs)` through `board.ts cachedFile`, and so are `stage-posts.json` and the entity's body. The queue is read per request (AC1: "cached on file mtimes as `GET /board` is").
4. **`POST /stories/{id}/status?project=<id>` `{status}` (CAP-14; D9, addendum §3.1.1, §4 choice 3).**
   - Auth: the bearer, or a cookie session with `X-CSRF-Token`, else `403 CsrfRefused`. Add `/^\/stories\/[^/]+\/status$/` to the cookie POST allowlist.
   - The body is exactly `{status: <string>}`. Not JSON is `400 MalformedJson`. Another key, or a status outside the canonical seven, is `400 SchemaError`.
   - `BadStory`, `ProjectRequired`, `UnknownProject` and `UnknownStory` are as in 1. Any other method: `405` `Allow: POST`.
   - The order, each step under a per-`(project, id)` chain (the `replyChains` precedent), so two presses never both call:
     1. Re-read the story's status.
     2. The transition: anything but `from: "draft", to: "ready"` is `409 {ok:false, error:"StoryStatusNotOwnerWritable", project, story, from, to, column, owner}`. `column` is `to` when `to` is not `ready`, else `from`. `owner` is `COLUMN_OWNERS[column]` (Settled shape 7).
     3. The lease: a live plan lease on the story is `409 {ok:false, error:"StoryLeaseHeld", project, story, run_id, phase, holder: {pid, host}, since}` (Settled shape 6).
     4. The verb: `callStatus(root, id, "ready", "the owner moved <id> draft → ready (<cookie|bearer>)", {env})`, i.e. `uv run <plugin>/lib/plansync.py status --directory <root> --id <id> --status ready --note … --caller tk-studio-supervisor` on the host.
     5. The `plan-status` service event (Settled shape 5).
     6. Re-read the entity.
   - The answers:
     - re-read status `ready`: `200 {ok: true, project, story: <the story view of 1>, previous_status, sync: "ok"|"partial"|"blocked", reason?}`. `partial` is a held AD-5 conflict; `blocked` means the write landed and the re-sync failed, with its reason.
     - not `ready` (a refusal: pinned by `sprint-status.yaml`, or reverted by the pull-back): `409 {ok:false, error:"StoryStatusRefused", project, story, status: <re-read>, reason}`.
     - a transient failure (the runner threw, no JSON): `500 {ok:false, error:"StoryStatusFailed", project, story, detail}`.
   - The refusals in steps 2 and 3 call nothing and record nothing.
5. **The `plan-status` service event (CAP-14; `planstatus.ts` header :9-28, the shape the loop's events use).**
   - `queue.serviceEvent("plan-status", {phase: "ready", project, story_key: "<N.M>", id, owner: <project>, directory: <root>, actor: "owner", source: "cookie"|"bearer", ok, previous_status?, error?, blocked?, reason?, status?: "partial", conflict?})`, once per verb call, including a refused or transient call (`ok: false` with its `error`).
   - `owner` keeps its meaning: the project whose plan it is. `actor: "owner"` is the new field: the owner, not the loop, asked.
   - The loop's run-scoped `plan-status` events are unchanged and carry no `actor`.
6. **The story's lease (CAP-14; `queue.ts:2120-2149`).**

   - A story `N.M` is held when a run of the project has a live lease that either:
     - is a per-story phase `in-progress:<k>` or `draft:<k>` with `storyNumber(k) === N.M`; or
     - is a run-wide phase `review`, `done` or `stage` on a run whose `board.ts` facts name `N.M` strongly.
   - `holder` is `{pid, host}` (never the nonce), `since` the lease event's `at`.
   - The owner's own call takes no lease (it has no run). The chain (shape 4) serialises owner presses. The remaining window against a loop pass is accepted (Risks).

   - `in-progress`: "in-progress is written by the loop's launched pass when a run starts the story (Story 36.6)"

   - `review`: "review is written by the loop's review pass when the run's PR opens (Story 27.5)"
   - `done`: "done is written by the loop's merge pass when the PR merges (Story 27.5)"
   - `dropped`: "dropped is written by the Jira pull-back (a DNI issue) or a plan change"
