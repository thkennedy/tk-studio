# Atlassian free tier, verified (Story 31.1, 2026-10-24)

The design spec's §6.8 says "verify before building", and decisions Appendix C leaves two questions to this story. This record answers them. The findings come from a chartered `tk-studio-research` run whose graded digest is on disk (§5). Grades follow `plugins/tk-studio/lib/research.py`: **A** primary source verified directly, **B** several independent sources agree, **C** one credible source, **D** inference.

**How it was read.** The engine sandbox could not reach Atlassian on 2026-10-24. Every request to `api.atlassian.com:443` and to the site answered `HTTP 403` from the sandbox proxy (`Approval required for api.atlassian.com:443`). The sandbox's page fetcher was refused by every `*.atlassian.com` host too. So every finding below comes from documentation, read through web-search excerpts of the cited pages on 2026-10-24, and is graded B or C (D where it is inference; the one A is a repository fact, not a site fact). A second documentation pass on 2026-10-24 added the token-scope list, the one-app-per-token finding, the absence of published rate-limit numbers, the per-file attachment limit and the inactivity rule. Each live probe is listed with its exact command as **attended check not yet done**. None of the findings halts the epic: no finding graded A or B says "does not fit" on the statuses or the API.

## 1. Attended steps (for the owner)

1. Create an Atlassian Cloud site with Jira and Confluence on the **Free** plans (`https://www.atlassian.com/software/jira/free`). Note the site host `<site>.atlassian.net`.
2. **The owner seat** is the account that created the site. On an always-Free site it is a site and product admin.
3. **The agent user seat**: a second Atlassian account with its own email address. Invite it to the site with Jira and Confluence access. The two seats use two of the ten free seats. On an always-Free site the agent seat is a Jira admin too (§2 Q2); nothing can restrict it.
4. **The org-admin API-token toggle** (AD-7): in Atlassian Administration > Security, confirm that API-token access is allowed for the site's users. The adapter's `GET /myself` preflight proves both the token and this toggle in one call. Leave the Rovo MCP server's API-token authentication **off**; this story found it is not needed (§2 Q5).
5. **Scoped API tokens: two for the agent seat (one per app), one for the owner seat**. Sign in as that seat at `https://id.atlassian.com/manage-profile/security/api-tokens` and choose *Create API token with scopes*. The flow lets one token carry scopes of both apps (seen 2026-10-26: the agent's Jira token also lists classic Confluence scopes; the grade-C "one app per token" reading was wrong), but Confluence's v2 API, which the studio's client uses, needs the *granular* Confluence scopes, so the agent seat still needs a token that carries them (`TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN`). Set an expiry (1 to 365 days) and calendar the rotation. Treat the scopes as fixed after creation (grade D, unconfirmed; §2 Q3), so tick every scope below at creation; a missing scope means a new token.
   - Agent seat, app **Jira** (`TK_ATLASSIAN_AGENT_TOKEN`). Classic scopes: `read:jira-work`, `write:jira-work`, `read:jira-user` (issues, JQL search, comments, transitions, attachments, changelog, users: 31.4, 31.5, 31.7), **plus** `manage:jira-project` (create the project and edit its settings: 31.2) and `manage:jira-configuration` (create the two statuses with `POST /rest/api/3/statuses` and update the workflow: 31.2). If the page shows only granular scopes, tick their equivalents (for example `write:status:jira`, `write:workflow:jira`, `write:project:jira` beside the read/write issue and comment scopes). Grade C for the scope meanings, D for the exact endpoint-to-scope mapping (§2 Q3); the attended check is the token page itself plus the 31.2 dry run.
   - Agent seat, app **Confluence** (`TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN`). Granular scopes: `read:space:confluence`, `read:page:confluence`, `write:page:confluence`, `read:attachment:confluence`, `write:attachment:confluence` (31.3 publishes pages with images, 31.4 mirrors them); if classic scopes are offered instead, `read:confluence-content.all`, `write:confluence-content`, `read:confluence-space.summary`, `write:confluence-file`. Grade C names; confirm them on the token page.
   - Owner seat, app **Jira** (`TK_STUDIO_ATLASSIAN_OWNER_TOKEN`): `read:jira-work`, `write:jira-work` (31.6 posts the owner's reply and transitions with it).
   - Copy each value once; it is never shown again.
6. **The cloud id**: open `https://<site>.atlassian.net/_edge/tenant_info` in a browser and copy `cloudId`.
   - **The owner seat's `accountId`** is recorded at setup too: 31.5 and 31.7 identify the owner by it, and refuse by name when none is recorded. It is an identifier, not a credential. Either the owner, signed in, reads it from their own Atlassian profile in the browser, or 31.2's setup reads it with the agent's Jira token through a user lookup covered by `read:jira-user` (for example `GET /rest/api/3/user/search?query=<owner email>`; the endpoint is ungraded). Where it is stored is 31.2's design.
7. **The environment variables, by name only** (User environment on the box, `setx NAME …`, never a file in a checkout; `apps/supervisor/README.md:198`, `kb/agent-pc-setup-runbook.md:920`):
   - Agent seat: `TK_ATLASSIAN_SITE`, `TK_ATLASSIAN_AGENT_EMAIL`, `TK_ATLASSIAN_AGENT_TOKEN` (the Jira token), `TK_ATLASSIAN_CLOUD_ID`, and `TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN` (the Confluence token; same email, same cloud id). The supervisor passes every `TK_ATLASSIAN_*` into the engine sandbox by name (`SBX_ENV_PASSTHROUGH_PREFIXES`, `apps/supervisor/src/server.ts:534`), so the fifth name rides the same channel with no supervisor change.
   - Owner seat: `TK_STUDIO_ATLASSIAN_OWNER_TOKEN` (and its account email `TK_STUDIO_ATLASSIAN_OWNER_EMAIL`). The names do **not** start with `TK_ATLASSIAN_`, so the by-prefix pass-through never carries them into the sandbox. The supervisor reads them on the host alone (31.6). ### Q1. Can a Free Jira project carry `Blocked - Awaiting User` and `Block Resolved` with a transition between them?

- **Finding (grade B, read 2026-10-24).** Yes, in both project types. Free includes customisable workflows and standard Jira admin functions.
  - **Team-managed:** statuses are created in the browser at Project settings > Issue types > Edit workflow, or from the board's columns. Sources: [What is the Free Jira Cloud plan?](https://support.atlassian.com/jira-cloud-administration/docs/what-is-the-free-jira-cloud-plan/); [Create, edit and delete statuses in team-managed spaces](https://support.atlassian.com/jira-software-cloud/docs/create-edit-and-delete-statuses-in-team-managed-projects/).
  - **Company-managed:** Settings > Work items > Workflows > *Edit* > *Add status*, then add the transition. Source: [Add statuses to a Jira workflow](https://support.atlassian.com/jira-cloud-administration/docs/add-statuses-to-a-jira-workflow/).
  - Corroborated by a community answer that the Free plan has no limit on adding columns or workflows ([community](https://community.atlassian.com/forums/Jira-questions/JIRA-workflow-on-free-version/qaq-p/2194907)).
- **Through REST (grade C, read 2026-10-24).** `POST /rest/api/3/statuses` takes `scope.type` `GLOBAL` (company-managed) or `PROJECT` (team-managed) and needs *Administer Jira* or *Administer projects*. Only a third-party mirror of the reference could be read ([withone.ai](https://withone.ai/knowledge/jira/conn_mod_def%3A%3AGJ4qo9s2I4g%3A%3A2HZqcrpVS0a0q2MTkny7qg)). [JRASERVER-69428](https://jira.atlassian.com/browse/JRASERVER-69428) records the older gap, when statuses could not be created over REST. The transition then needs the workflow update API (company-managed). A team-managed project's transitions are set most reliably in the browser editor.
- **Attended check not yet done:**
  - `curl -sS -u "$TK_ATLASSIAN_AGENT_EMAIL:$TK_ATLASSIAN_AGENT_TOKEN" "https://api.atlassian.com/ex/jira/$TK_ATLASSIAN_CLOUD_ID/rest/api/3/project/search"`: the project types, `style`, and the `simplified` flag.
  - `…/rest/api/3/statuses/search` and `…/rest/api/3/workflow/search?expand=statuses,transitions`.
  - `…/rest/api/3/project/<KEY>/statuses`.
  - The create endpoints are documented only, never called from a research run.
- Verdict: fits with a workaround (31.2 creates the statuses and the transition over REST on a company-managed project; on a team-managed project or on any refusal it emits the exact numbered browser steps for the project's own type, team-managed or company-managed as above, and checks the result with `GET statuses/search`)

### Q2. The project-permission model on Free: who can transition, comment and attach?

- **Finding (grade B, read 2026-10-24).** On Free, project permissions, project roles and work-level (issue) security cannot be customised. On a site that has always been on Free, everyone with Jira access is an admin for all Jira projects. So the owner seat and the agent seat can both transition, comment and attach on every project. Nothing can stop the agent from doing what only the owner should do. Free has no audit log. Sources: [What is the Free Jira Cloud plan?](https://support.atlassian.com/jira-cloud-administration/docs/what-is-the-free-jira-cloud-plan/); [community: Jira for free](https://community.atlassian.com/forums/Jira-questions/Jira-for-free/qaq-p/2581916).
- **Inactivity deactivation (grade B, read 2026-10-24).** If every Jira product on a site is Free, Jira is deactivated after 120 days of inactivity; Confluence Free sites likewise. Admins get warning emails first, and there is a short reactivation window (14 or 15 days; sources differ). The documented activity is a person signing in and viewing any page (an issue, a board, a dashboard, an admin screen). The 120-day rule for Jira is stated on Atlassian's [What is the Free Jira Cloud plan?](https://support.atlassian.com/jira-cloud-administration/docs/what-is-the-free-jira-cloud-plan/). Atlassian's [Track storage and move data across products](https://confluence.atlassian.com/x/CDgWN) says only that Confluence Free sites are deactivated after "a period of inactivity" and that viewing any Confluence page counts; the 120-day figure for Confluence comes from the community threads alone (grade C for that number). Sources: [community: free Confluence site deactivated](https://community.atlassian.com/forums/Confluence-questions/Why-was-my-free-Confluence-site-deactivated-and-when-reactivated/qaq-p/2737084); [community: are projects deleted when inactive](https://community.atlassian.com/forums/Jira-questions/Are-Jira-Projects-Spaces-deleted-after-some-time-of-not-being/qaa-p/3140993).
- **Does API-token traffic count as activity? (unknown, read 2026-10-24).** No source read says whether REST calls with an API token reset the 120-day clock. It is not graded; the loop must not rely on its own sync-back traffic to keep the site alive. Attended: the owner signs in periodically (§1 step 10).
- **Attended check not yet done:** `curl -sS -u "$TK_ATLASSIAN_AGENT_EMAIL:$TK_ATLASSIAN_AGENT_TOKEN" "https://api.atlassian.com/ex/jira/$TK_ATLASSIAN_CLOUD_ID/rest/api/3/mypermissions?permissions=TRANSITION_ISSUES,ADD_COMMENTS,CREATE_ATTACHMENTS,ADMINISTER_PROJECTS&projectKey=<KEY>"`; `…/rest/api/3/permissionscheme`; `…/rest/api/3/filter/search`.
- Verdict: fits with a workaround (permissions cannot tell the owner from the agent: 31.5, 31.6 and 31.7 identify the owner by the `accountId` recorded at setup (§1 step 6), on a comment's `author` and `updateAuthor` and on the `Block Resolved` transition in the changelog, refuse by name when no owner `accountId` is recorded, never match an absent or empty `accountId`, and never rely on a role or a permission scheme; inactivity deactivation: the owner signs in at least monthly (§1 step 10) and 31.4's drift `tracking` plane surfaces an unreachable or deactivated site)

### Q3. The REST API's rate limits and the token's scope

The box's agent token is a scoped token by the studio's own setup (`kb/agent-pc-setup-runbook.md:920`, a repository fact), so this record covers scoped tokens; classic unscoped tokens were not graded here and are not the path the studio uses.

- **Rate limits (grade B, read 2026-10-24).** Points-based and tiered quotas, enforced from 2 March 2026, apply to Forge, Connect and OAuth 2.0 (3LO) apps. **API-token traffic is not affected.** It stays under the burst limits (per second, per tenant, per endpoint, per HTTP method), plus a per-issue write limit. A `429` carries `Retry-After`. The `RateLimit` / `RateLimit-Policy` and older `X-RateLimit-*` headers do not appear on every response. Sources: [Jira rate limiting](https://developer.atlassian.com/cloud/jira/platform/rate-limiting/); [Confluence rate limiting](https://developer.atlassian.com/cloud/confluence/rate-limiting/); [Build an app that respects rate limits](https://developer.atlassian.com/cloud/jira/platform/build-an-app-that-respects-rate-limits/); [developer community: missing headers](https://community.developer.atlassian.com/t/jira-cloud-api-rate-limits-and-missing-headers/94358).
- **The numbers (grade C, read 2026-10-24: an absence in the pages read).** Atlassian publishes **no numeric threshold** for API-token traffic: neither the burst limit per endpoint and method nor the per-issue write limit (`RateLimit-Reason: jira-per-issue-on-write`) has a published number. The burst limit is a token bucket (a steady rate plus a burst capacity, per tenant and endpoint); a `429` names the limit in `RateLimit-Reason` (`jira-burst-based`, `jira-per-issue-on-write`), and the advice is exponential backoff (double the delay per retry). The only figures found are an illustrative "10 requests/second" steady rate on the official page (grade C: an example, not a limit) and a third-party probe that saw `X-RateLimit-Limit: 350` on one endpoint and `200` on search for one API token ([sky-ai-eng/triage-factory#1257](https://github.com/sky-ai-eng/triage-factory/pull/1257), grade C). The source of the real numbers is the attended header probe below: it records `RateLimit-Policy` / `X-RateLimit-Limit` for the search and issue endpoints the sync-back uses.
- **What this supports for 31.4.** A sync-back that makes one paged JQL search per tick plus a few writes per changed issue is a light, bounded load, and a 10-minute tick leaves the bucket long idle between bursts. Without published numbers this is an expectation (grade D), not a measured fit; the header probe and 31.4's first real ticks confirm it.
- **Token expiry (grade B, read 2026-10-24).** A scoped API token has an expiry of 1 to 365 days. Sources: [Manage API tokens](https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account/); [Scoped API tokens in Confluence Cloud](https://support.atlassian.com/confluence/kb/scoped-api-tokens-in-confluence-cloud/).
- **Fixed scopes (grade D, unconfirmed, read 2026-10-24).** No source read says whether a token's scopes can be edited after creation. The creation flow picks the scopes before the token exists, so they are taken as fixed. That is inference. It is why §1 step 5 ticks every scope at creation: if scopes turn out to be editable, nothing is lost. Attended: the token page itself shows whether an existing token's scopes can be edited.
- **One app per scoped token (grade C, read 2026-10-24).** The creation flow has the user choose the app the token will access before choosing scopes ([Manage API tokens](https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account/), step list in the Japanese edition), and a July 2026 community thread reports that since about May 2026 a scoped token can pick only Jira *or* Confluence ([community: create multi-project API tokens](https://community.atlassian.com/forums/Jira-questions/Create-multi-project-api-tokens/qaq-p/3266241)). So the agent seat takes a second, Confluence token: `TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN` (§1 steps 5 and 7). Attended: the token page shows whether more than one app can be ticked; if it can, one token may carry both and the second variable can hold the same value.
- **The scopes 31.2 to 31.7 need (grade C for the scope meanings, D for the endpoint mapping, read 2026-10-24).** `read:jira-work` / `write:jira-work` cover issues, search, comments, transitions and attachments; `read:jira-user` covers user lookups; `manage:jira-project` covers creating and editing project settings; `manage:jira-configuration` covers Jira administration actions, which include creating statuses and changing workflows ([Amazon Quick: Jira integration scopes](https://docs.aws.amazon.com/quick/latest/userguide/jira-integration.md); [Google Gemini Enterprise: Jira Cloud](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/jira-cloud)). The Atlassian reference pages that list each endpoint's scopes refused the sandbox's fetcher, so which scope `POST /rest/api/3/statuses`, the workflow update and `POST /rest/api/3/project` each demand is inferred from those meanings (D). Because scopes are taken as fixed after creation (D above), the agent's Jira token takes all five (§1 step 5). Confluence: the page, space and attachment read/write scopes (C, [sphinxcontrib-confluencebuilder: scoped token](https://sphinxcontrib-confluencebuilder.readthedocs.io/en/latest/guide-scope-token/); [Google Gemini Enterprise: Confluence Cloud](https://docs.cloud.google.com/gemini/enterprise/docs/confluence-cloud)). A `403` naming a scope on 31.2's first create means a new token with the missing scope, never a different auth path; a `401` follows the 31.2 rule (§4) and is never reported as a missing scope.
- **Gateway only (grade B, read 2026-10-24).** A scoped token authenticates (Basic `email:token`) only through `https://api.atlassian.com/ex/jira/<cloud id>/…` and `…/ex/confluence/<cloud id>/…`. Against `<site>.atlassian.net` it answers 401. Sources: [Scoped API tokens in Confluence Cloud](https://support.atlassian.com/confluence/kb/scoped-api-tokens-in-confluence-cloud/); [JRACLOUD-94545](https://jira.atlassian.com/browse/JRACLOUD-94545); [sooperset/mcp-atlassian#968](https://github.com/sooperset/mcp-atlassian/issues/968); `kb/agent-pc-setup-runbook.md:920`.
- **Repository fact (grade A, read 2026-10-24).** `plugins/tk-studio/lib/jirabackend.py:53-55,138-146` builds `https://<site>/rest/api/2` and reads `JIRA_API_TOKEN` / `JIRA_EMAIL`. The box provides `TK_ATLASSIAN_*`, and the token works only through the gateway. So the adapter's transport must change in 31.2. This was SPEC open question 1.
- **Attended check not yet done:** `curl -sS -D - -o /dev/null -u "$TK_ATLASSIAN_AGENT_EMAIL:$TK_ATLASSIAN_AGENT_TOKEN" "https://api.atlassian.com/ex/jira/$TK_ATLASSIAN_CLOUD_ID/rest/api/3/myself" | grep -i -E 'ratelimit|retry-after'`; the same `myself` call against `https://$TK_ATLASSIAN_SITE/rest/api/3/myself` (expected 401 for a scoped token); the rate-limit numbers, read from the headers of the two endpoints the sync-back uses: `curl -sS -D - -o /dev/null -u "$TK_ATLASSIAN_AGENT_EMAIL:$TK_ATLASSIAN_AGENT_TOKEN" "https://api.atlassian.com/ex/jira/$TK_ATLASSIAN_CLOUD_ID/rest/api/3/search/jql?jql=updated%3E%3D-1d&maxResults=1" | grep -i -E 'ratelimit|retry-after'` and the same on `…/rest/api/3/issue/<KEY-1>`; and the Confluence token: `curl -sS -o /dev/null -w '%{http_code}' -u "$TK_ATLASSIAN_AGENT_EMAIL:$TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN" "https://api.atlassian.com/ex/confluence/$TK_ATLASSIAN_CLOUD_ID/wiki/api/v2/spaces?limit=1"` (expected 200).
- Verdict: fits with a workaround (31.2 moves the adapter to the gateway base URL built from `TK_ATLASSIAN_CLOUD_ID` with the `TK_ATLASSIAN_*` names, refuses by name when either agent token is set without the cloud id, and reads Confluence with `TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN`, never through the site URL; the agent's Jira token is created with all five scopes including `manage:jira-project` and `manage:jira-configuration`; 31.4 makes one paged JQL search on `updated` per tick, honours `Retry-After` and backs off exponentially, treats absent rate-limit headers as normal, and records the observed limits since Atlassian publishes no number)

### Q4. Confluence Free's space, page, storage and attachment limits

- **Finding (grade B, read 2026-10-24).** Confluence Free has up to 10 users, **2 GB** of file storage, and **unlimited spaces and pages**. Permissions cannot be customised and there is no anonymous access. Going past 10 users starts a 7-day Standard trial. Confluence Free sites are deactivated after a period of inactivity (120 days per community threads only, grade C; §2 Q2); a person signing in and viewing content resets the clock, and whether API-token traffic does is unknown (§2 Q2). REST attachment uploads **over 100 MB fail** (502) whatever the site limit; the UI respects the site limit. Sources: [Confluence Cloud plans](https://support.atlassian.com/confluence-cloud/docs/learn-about-confluence-cloud-plans/); [Confluence pricing](https://www.atlassian.com/software/confluence/pricing); [CONFCLOUD-85173](https://jira.atlassian.com/browse/CONFCLOUD-85173).
- **Per-file attachment limit (grade B for the default and the setting, C for its application to Free; read 2026-10-24).** Confluence Cloud's default *Attachment maximum size* is **100 MB** (104,857,600 bytes), and a Confluence admin can change it in bytes at Confluence administration > General configuration > Attachment settings ([Configure attachment size](https://support.atlassian.com/confluence-cloud/docs/configure-attachment-size/); [Configuring attachment size](https://confluence.atlassian.com/display/ConfCloud/Configuring+attachment+size); third-party walk-throughs agree). No source read says the Free plan sets a different value or locks the setting, so its applying to Free unchanged is grade C. Reconciled with CONFCLOUD-85173: the effective per-file ceiling for 31.3 is the smaller of the site's setting and 100 MB, and at the default both are 100 MB. On Free the owner seat is an admin, so the setting could be lowered below 100 MB; 31.3 uses the site's setting only when the operator supplies it or it can be read (no endpoint for reading it is graded here); otherwise it uses 100 MB and says so. Attended: open Confluence administration > General configuration > Attachment settings in the browser and note *Attachment maximum size*.
- **Attended check not yet done:** `curl -sS -u "$TK_ATLASSIAN_AGENT_EMAIL:$TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN" "https://api.atlassian.com/ex/confluence/$TK_ATLASSIAN_CLOUD_ID/wiki/api/v2/spaces"`; `…/wiki/api/v2/pages?limit=1`; the storage used, read in the browser at Confluence Settings > Storage; the *Attachment maximum size* in Confluence administration > General configuration > Attachment settings.
- Verdict: fits with a workaround (31.3 downscales or compresses design images, refuses by name any file over the per-file ceiling, the smaller of the site's *Attachment maximum size* and the 100 MB REST ceiling, 100 MB at the default or when the setting is unknown, saying so in its output, and reports the bytes it has uploaded against the 2 GB, site-wide use being read in the browser at Confluence Settings > Storage; 31.4's page mirror reads bodies and attachment metadata and never re-uploads an unchanged file; inactivity deactivation: the owner signs in at least monthly, §1 step 10, and 31.4's drift `tracking` plane surfaces an unreachable or deactivated site)

### Q5. Does the Rovo MCP server add anything the REST API with an API token does not?

- **Finding (grade C, read 2026-10-24).** Every Atlassian Cloud customer has the Rovo MCP server, Free included. Its site rate limit depends on plan: **Free 500 calls/hour**, Standard 1,000. It authenticates with OAuth 2.1, or with an API token over Basic auth at `https://mcp.atlassian.com/v1/mcp` once an org admin enables that (off by default). Its tools wrap the same Jira and Confluence read, write and search operations the REST API exposes. On Free its hourly cap is tighter than the burst-only limits REST tokens face, and it would add a second admin toggle. Nothing in 31.2 to 31.7 needs a capability only MCP has. AD-7 as amended by AD-22 (REST unless MCP is shown necessary) stands. ## 4. What the stories carry

Each line is mirrored by an open entry in `_bmad-output/implementation-artifacts/replan-queue.md` (Settled shape 2).

- **31.2** (`31-2-project-setup-from-a-template`): the adapter's transport moves to `https://api.atlassian.com/ex/jira/$TK_ATLASSIAN_CLOUD_ID/rest/api/3` (Confluence `…/ex/confluence/…/wiki/api/v2`) and reads the `TK_ATLASSIAN_*` names, with `JIRA_*` and the site URL kept as the legacy fallback only when no `TK_ATLASSIAN_AGENT_TOKEN` is set. When `TK_ATLASSIAN_AGENT_TOKEN` or `TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN` is set without `TK_ATLASSIAN_CLOUD_ID`, it refuses by name (a scoped token fails against the site URL). Confluence calls use `TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN` and never fall back to the site URL. The agent's Jira token carries `read:jira-work`, `write:jira-work`, `read:jira-user`, `manage:jira-project` and `manage:jira-configuration` (§1 step 5). A `401` is reported by name as the token, its email (`TK_ATLASSIAN_AGENT_EMAIL`), its expiry or the org toggle (§1 step 4), never as a missing scope. Inside the engine sandbox, a `403` whose body is the proxy's `Approval required for <host>:443` is the network approval step (§1 step 8); any other `403` refusal is a missing scope, named, with a request for a new token. Setup records the owner seat's `accountId` (§1 step 6); where it is stored is 31.2's design. The two statuses and their transition are created over REST on a company-managed project; on a team-managed project or on any refusal, the story gives the exact numbered browser steps for the project's own type (team-managed or company-managed, §2 Q1) and checks them with `GET statuses/search`.
- **31.3** (`31-3-publish-design-pages-to-confluence`): Confluence calls authenticate with `TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN` through the gateway. Downscale or compress design images, refuse by name any attachment over the per-file ceiling (the smaller of the site's *Attachment maximum size* and 100 MB; 100 MB at the default; the setting is used only when the operator supplies it or it can be read, no endpoint being graded here; otherwise 100 MB, and the output says the ceiling was assumed), and report the bytes it has uploaded against the 2 GB Free storage. Site-wide use is read in the browser at Confluence Settings > Storage (attended, §2 Q4).
- **31.4** (`31-4-sync-back-on-a-timer`): one paged JQL search per tick, never one GET per issue. JQL reads `updated` to the minute in the agent seat's Jira time zone, so the search overlaps a few minutes (`updated >= <cursor − a few minutes>`, the time written in that time zone or in a form JQL reads unambiguously), orders by `updated ASC`, de-duplicates by issue key and `updated`, and advances the cursor from the largest `updated` seen, not the host clock, only after every page of the tick has been read; an interrupted tick (a `429` or an error mid-pages) leaves the cursor where it was. On `429`, wait `Retry-After` (exponential backoff when it is absent). Absent rate-limit headers are normal; Atlassian publishes no number for API-token limits, so the sync-back records the `RateLimit-*` / `X-RateLimit-*` values it sees and any `429` with its `RateLimit-Reason`, and the 10-minute budget is confirmed from those, not assumed. The page mirror never re-uploads an unchanged attachment. When `TK_ATLASSIAN_AGENT_CONFLUENCE_TOKEN` is absent, the mirror refuses by name (as 31.3 does) and the `tracking` plane reports that as its own state, not as "no changes". The drift check's `tracking` plane reports an unreachable or deactivated site (Free products deactivate after 120 days of inactivity, and API traffic may not count) as its own state, naming the owner's sign-in as the fix.
- **31.5** (`31-5-the-two-statuses-and-the-inbox-items`): roles and permission schemes cannot separate the seats, so the inbox treats a block as answered only by a comment whose `author.accountId` **and** `updateAuthor.accountId` are both the owner seat's (recorded at setup, §1 step 6). When no owner `accountId` is recorded, the inbox refuses by name; an absent or empty `author` or `updateAuthor` `accountId` never matches. The agent seat is an admin and could edit an owner comment, which changes `updateAuthor`; such a comment is not the owner's reply. Agent-authored comments are never the owner's reply.
- **31.6** (`31-6-the-inbox-and-issue-screens`): the owner's reply and Done are posted with the owner's token (`TK_STUDIO_ATLASSIAN_OWNER_TOKEN`, host-only) through the gateway, so the author `accountId` is the owner's. The agent's token never posts as the owner. When `TK_STUDIO_ATLASSIAN_OWNER_TOKEN` or `TK_STUDIO_ATLASSIAN_OWNER_EMAIL` is absent on the host, the supervisor refuses by name and never posts the reply or the Done transition with another identity.
- **31.7** (`31-7-validation-of-a-resolution`): any seat can transition on Free, so validation accepts `Block Resolved` only when the changelog shows the owner seat's `accountId` made the most recent transition into `Block Resolved`; an older owner transition never validates a later one by another seat. When no owner `accountId` is recorded (§1 step 6), validation refuses by name; an absent or empty changelog `accountId` never matches. Otherwise the issue returns to the inbox with a follow-up.
